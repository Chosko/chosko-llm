# Task 231 — Decide the editorial question when the evidence is clear, ask only when it isn't

Target: claude

## Goal
`/architect amend` and `/pipeline-revise` ask whether a change is "Editorial"
or "Not editorial" on every run, even when their own evidence already settles
it — they mark a recommended letter and then still wait for the user to name
it. Make the classification automatic when the evidence is unambiguous: the
agent applies it, states it with one evidence line, and continues without a
reply. The question is asked only when the call genuinely rests on judgement.
`/pipeline-patch` inherits the behaviour through the `/architect amend` arm it
runs.

## Acceptance criteria
- `skills/architect/amend.md` § 4 splits the recommendation rule into clear and
  ambiguous cases:
  - clear editorial — touched set empty, no scope added, and no contract or
    interface text in the edited sections changes;
  - clear not editorial — a task is touched on its summary block (title or
    `Files:`), or the added scope is a nameable component/contract/promise;
  - ambiguous — a task's touched status needed its body read, or the scope
    call is borderline, or the two findings point different ways.
- On a clear case the arm renders the change, touched set and outcome plus one
  line `Classified: <editorial | not editorial> — <evidence>` and proceeds to
  write without a reply. On an ambiguous case it asks the existing A/B/C
  question, unchanged, including Stop on silence/EOF.
- The `[IN PROGRESS]` touched-task refusal (step 3) is unchanged and still
  fires before anything is written.
- The carried-answer exception from `/pipeline-revise`: when the arm's own
  findings agree with the carried answer, it applies it with no confirmation
  prompt; when they disagree, it asks (the confirmation form, with the
  "This edit's own findings would mark …" line).
- `skills/pipeline-revise/SKILL.md` step 7: insert, delete and reorder are

  signal (edge added/dropped, `Files:` change, scope change → not editorial;
  all three editorial conditions in `amend.md` § Tier hold → editorial) is

## Decisions
- **Reverses a recorded decision.** `owner-amend-arms.md` lists "applying an
  editorial-versus-semantic classification without an answer" as a non-goal,
  because the user then chose to be asked every time. The user now wants the
  opposite for clear cases (2026-09-16).
- **A clear case needs no reply at all** (user decision). Replacing the
  question with a "Proceed / switch / stop?" prompt is the same friction
  under another name. The user's description of the change is authorisation
  enough when the evidence settles the tier.
- **"Clear" means a mechanical signal, not confidence.** Auto-classify only on
  findings the gate already renders (touched on a summary block, a named
  scope item, an edge, a `Files:` change, or the full editorial triple).
  Anything that needed a body read or a borderline scope call asks. This keeps
  the rule checkable instead of "the agent felt sure".
- **Owner gates other than the editorial question are untouched.** Task-engine
  and runbook step amend arms keep their own gates. `/pipeline-revise`'s
  runbook-vs-here choice (arm C) is still asked when offered, since it is not
  a classification.
- **`/pipeline-patch` needs no body edit.** It runs `/architect amend` by path,
  so it inherits the rule. Only the docs mention it.
- **Editing `.claude/domain/features/owner-amend-arms.md` is explicitly
  authorised for this task (user decision, 2026-09-16), for the 3
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document
  is normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- **Editing `.claude/domain/features/pipeline-revision.md` is explicitly
  authorised for this task (user decision, 2026-09-16), for the 2
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document
  is normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
