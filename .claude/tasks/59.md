# Task 59 — Teach /task-add to author and reconcile tasks from a feature doc via feature=<slug>

Target: claude

## Goal
Close the pipeline: `/architect` produces a low-level feature doc, and `/task-add` should
turn it into implementation tasks without the user re-describing the work in prose — and,
on a re-planning run, reconcile the tasks that already exist instead of duplicating them.
Add a `feature=<slug>` argument resolving through `.claude/FEATURES.md`.

## Acceptance criteria
- The ARGUMENT NOTE before PHASE 1 scans `$ARGUMENTS` for `feature=<slug>` alongside
  `--enrich` / `--no-split` / `--no-commit`, strips it, sets FEATURE. Composes with all
  three.
- `feature=<slug>` plus free-form text is valid: the text narrows or annotates scope
  (`feature=user-profile just the avatar upload`); the feature doc remains primary.
- Resolution: read `.claude/FEATURES.md`, match the slug, read the path in its `Doc:` line.
  Missing `FEATURES.md` stops with a message pointing at `/domain-setup` and `/architect`.
  Unknown slug stops and lists the available slugs.
- PHASE 1 (READ) treats the feature doc as the primary context source — as
  `/task-implement` treats a task body — fanning out to CLAUDE.md, the context layer, and
  other domain docs only where it doesn't cover what's needed. It also reads the entry's
  `Tasks:` IDs and, when non-empty, those tasks' summary blocks and bodies.
- PHASE 1.5 (SPLIT CHECK) weighs the feature doc's own structure; a feature decomposing
  into distinct deliverables normally becomes several tasks. `--no-split` still forces one.
- PHASE 3 (DRAFT) names the source feature above the drafts. On a feature with existing
  tasks it presents a RECONCILIATION section before the new drafts, classifying every
  existing task with a one-line reason:
  - still valid under the new design → left untouched, no edit
  - needs minor change and is `[STALE]` or `[MISSING]` → body updated in place; a `[STALE]`
    task flips back to `[MISSING]`
  - substantially invalidated → marked `[SKIP]` with a reason, and a replacement task
    drafted
  The choice between update-in-place and skip-and-replace is a judgment call on how much
  of the task survives; the command states the criteria rather than a mechanical rule.
  One approval covers the reconciliation and the new tasks together.
- A `[DONE]` task is NEVER modified, skipped, or reopened — completed work stands, and any
  follow-up is a new task.
- PHASE 4 (WRITE) writes `.claude/TASKS.md` and the task bodies, and — when FEATURE is
  set — updates the feature's entry: appends the new IDs to `Tasks:` (dropping IDs of tasks
  it just marked `[SKIP]`) and sets `Status:` to `[PLANNED]` from either `[NEW]` or
  `[ITERATED]`. Every new task's summary block carries `Feature: <slug>`.
- Each generated body's `## Goal` names the originating feature and its doc path appears in
  `## Hints`.
- PHASE 5 (COMMIT) stages `.claude/FEATURES.md` alongside `.claude/TASKS.md` and the body
  files when FEATURE is set. Explicit paths only.
- The feature doc itself is read-only to `/task-add` — it never edits
  `.claude/domain/features/<slug>.md`.
- The free-form path is completely unchanged when `feature=` is absent: same phases, same
  output, no new prompts, no `Feature:` line.
- Frontmatter `description`, the `# Usage:` block, and `version` updated;
  `.claude/domain/task-workflow.md`, `.claude/context/features.md`, `README.md` updated;
  root `VERSION` bumped (minor).

## Decisions
- `feature=<slug>` rather than inference from free-form text. Confirmed by the user: matches
  the existing `scope=` / `focus=` / `files=` / `threshold=` style in `/refactor-codebase`,
  `/refactor-tests`, and `/context-update`, and is greppable in shell history.
- Reconciliation is presented in PHASE 3 under the existing single-approval gate rather
  than as a new phase — the user approves the whole plan (edits, skips, new tasks) at once,
  and PHASE 4 remains the only writer.
- Update-in-place is preferred over skip-and-replace for `[MISSING]` and `[STALE]` tasks,
  per the user's guidance: nothing has been implemented, so rewriting the body is cheaper
  and keeps the backlog free of dead `[SKIP]` entries. Skip-and-replace is reserved for
  tasks whose goal no longer survives the design change.
- `/task-add` writes only two fields of a feature entry — `Tasks:` and `Status:` — never
  `Doc:` or `Source:`, which are `/architect`'s.
