# Task 125 — Add the `requires:` frontmatter field and its install-time resolution

Target: claude

## Goal

Step 1 of the `shared-phase-engine` migration order
(`.claude/domain/features/shared-phase-engine.md`). A feature that reads a file
inside another installed feature breaks if that feature is not installed, and
nothing today prevents `chosko-llm add command:task-add` without
`skill:task-engine` — the failure would surface as an agent following a dangling
path mid-run. Add an optional `requires:` frontmatter key, teach `cmd-add` to
install what a feature names before installing the feature, and teach `cmd-rm` to
refuse to remove a feature something installed still requires. Land it with no
feature declaring it, so this task is inert on its own and independently
verifiable before anything depends on it.

## Acceptance criteria

- `parse_frontmatter` in `scripts/lib.sh` recognises `requires` as a sixth key.
  Its awk block already splits on the first colon generically — so the value
  `skill:task-engine` survives that split intact — but it only emits keys in an
  explicit allowlist (`name`, `version`, `type`, `description`, `replaces`,
  `event`, `matcher`). `requires` is added to that allowlist and to the
  function's header comment. Without it `read_frontmatter_field <file> requires`
  returns empty. See Decisions — the feature document is wrong on this point.
- A comma-separated `requires:` value yields one `<kind>:<name>` spec per entry,
  each split with the existing `parse_replaces_spec` helper rather than a second
  parser. Whitespace around commas is tolerated. An entry with no recognised
  kind prefix is a hard error naming the offending spec, not a silent skip.
- `cmd-add`, single-feature path: inside `add_one`, after `resolve_feature`,
  `scope_supports_kind` and `require_versioned_source` have passed and **before
  any file is copied**, the source's `requires:` is read and each named feature
  that is not already installed is installed first, each logged as a dependency
  install distinguishable from the requested feature's own success line.
- Resolution is **one level deep**: a dependency's own `requires:` is not
  followed. This is stated in a comment at the call site so it is not "fixed"
  later.
- A dependency already installed is skipped with one info line, not an error.
- A dependency that does not exist in the managed clone aborts that feature and
  installs nothing for it — the check runs before the first copy, so a feature
  can never half-install. Consistent with existing best-effort multi-name
  semantics: other specs in the same invocation still run and the exit code is 1.
- A dependency installs into the same scope as its dependent and is subject to
  the same `scope_supports_kind` rule; a scope-invalid dependency aborts the
  dependent with the existing `scope_violation_message` wording.
- `cmd-add --all` is unchanged, and a comment says why: it installs every
  feature, so every dependency is satisfied incidentally, and the reference is
  resolved when an agent runs — not at install time — so the copy order within
  the run is irrelevant. This settles the feature document's first open question.
- `cmd-rm` gains `--force`, stripped from the argument list the same way
  `--local` / `--global` are, and documented in its `-h` heredoc.
- Before removing, `cmd-rm` scans **installed** features for any whose
  `requires:` names the resolved `<kind>:<name>`. On a hit it refuses, naming
  every dependent and pointing at `--force`. With `--force` it removes and warns
  naming the dependents it just broke.
- The dependents scan reads installed frontmatter directly for `command`,
  `skill`, `statusline` and `hook`. For `claude-md` it reads the managed-clone
  source of each installed claude-md name instead, because `inject_section`
  strips frontmatter — an installed claude-md section carries no `requires:` to
  read. This asymmetry is commented at the scan.
- `uninstall.sh` is untouched and keeps working: it deletes artifacts directly
  and never calls `cmd-rm`, so the new guard cannot block a bulk uninstall. The
  guard is not duplicated into it.
- `cmd-update` and `cmd-ls` are untouched. The field is visible through
  `cmd-show`, which prints frontmatter already.
- `docs/authoring-guide.md` gains a `requires:` subsection beside the existing
  `replaces:` one, in the same register: what the key is for, the
  comma-separated kind-prefixed syntax, a row in the optional-field table, what
  `add` and `rm` do with it, and the three explicit limits — one level deep,
  unversioned, non-transitive. The frontmatter-schema preamble is updated to
  mention it alongside `replaces:`.
- `docs/cli-help.txt`: the `add` entry notes that a feature's declared
  requirements are installed first; the `rm` entry notes the refusal and
  `--force`.
- **No feature under `commands/`, `skills/`, `claude-md/`, `statusline/` or
  `hooks/` declares `requires:` in this task.** It lands inert; task 127 is the
  first consumer.
- Root `VERSION` takes a minor bump (new CLI capability), relative to whatever
  is in place when this lands.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  131 owns both knowledge layers.
- No test suite by design: verify against a clone where `install.sh` has run —
  `chosko-llm add` on a feature with a hand-added `requires:` installs the
  dependency first; `chosko-llm rm` on that dependency refuses and names the
  dependent; `--force` overrides; `chosko-llm add --all` still succeeds.

## Decisions

- **`scripts/lib.sh` does need a change, contrary to the feature document.**
  The document (lines 116-120) claims `parse_frontmatter` "needs no change at
  all". Verified false on 2026-08-24: the generic first-colon split is real, but
  the emit is gated on a key allowlist at `scripts/lib.sh:182`, and
  `.claude/context/shared-lib.md` already records that adding a sixth field
  costs that edit. The change is one token in an existing condition, so the
  design is unaffected and no parser rewrite is needed. Task 131 reconciles the
  document.
- **The dependency check runs before the first copy**, so an unresolvable
  requirement cannot leave a half-installed feature. This is why it sits after
  validation rather than beside `apply_replaces`, which is deliberately a
  post-install step.
- **`--force` on `rm`, not `--no-deps` on `add`.** Removing an engine out from
  under five consumers silently is the failure being guarded; installing an
  extra small skill the user did not ask for is not a failure worth a flag.
- **`add_one` already runs in a subshell**, so a dependency install that `die`s
  aborts only the dependent it was requested for. Reuse `add_one` recursively
  rather than writing a second install path.
- **`--all` is left alone deliberately**, answering the document's open
  question, rather than left undecided.
- **claude-md dependents are resolved through the managed clone.** The
  alternative — recording `requires:` inside the injected section markers —
  would put state in a user-edited file, which this repo's rules forbid.
