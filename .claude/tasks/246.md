# Task 246 — Defer the feature-flip proposal to the outermost run

Target: claude

## Goal
When the last task of a feature lands `[DONE]`, `/task-implement` proposes
flipping the feature's `FEATURES.md` status. In an in-context run that
proposal is already batched to the very end. Nested, it is not: a delegated
agent under `--agents` treats its one task as the whole run and reaches the
proposal itself, and a runbook step's subagent cannot talk to the user, so the
proposal comes back as a relayed `QUESTIONS FOR USER` that blocks the runbook
mid-run. Move the proposal to the outermost run in both cases — the launcher
under `--agents`, the orchestrator under `/runbook-run` — as rules, not
explanation.

## Decisions
- **Nesting is detected by the invocation, not a flag.** A delegated agent
  is told in its prompt; a runbook step's agent carries `OPERATING RULES`. No
  new flag on either runner.
- **The orchestrator proposes but never writes `FEATURES.md`.** Acting on the
  reply is post-run conversation, the same handle `/follow-ups`' numbering
  uses; the runbook and the index stay its only writes.
- **Rules, not explanation.** The shipped bodies state obligations; reasons
  go in the maintainer section, one line.
- **Preconditions: 245** because tasks 244 and 245 edit the same
  `runbook-run` files.
- **Editing `.claude/domain/features/task-implement-launcher.md` and
  `.claude/domain/features/runbook-suite.md` is explicitly authorised for
  this task (user decision, 2026-09-21), for the 1 + 1 reconciliations listed
  above and for nothing else. Do not ask for permission at implementation
  time — the permission is already granted.** Those documents are normally
  `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
