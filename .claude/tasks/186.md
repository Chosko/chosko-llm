# Task 186 — Update documentation for feature `owner-amend-arms`

Target: claude

## Goal
Feature `owner-amend-arms` adds an `amend` form to `/architect` and two new
reference files to the `task-engine` and `runbook-run` folders. The
documentation describing those areas — the user-facing reference, the domain
layer's iterate-guard and one-authority-per-rule sections, and the context
layer's per-file notes — still describes the world before those arms existed.
Bring it up to date with what task 182 shipped.

## Acceptance criteria
- `README.md` describes the amend path where it describes the iterate loop: a
  targeted change is `/architect amend feature=<slug> "<change>"` and stales only
  the tasks the change touches.
- `docs/reference.md` § `/architect` documents the `amend` argument form, its
  single gate, the editorial question, and the precision guard's difference from
  the blanket one. § `task-engine` lists the eighth reference file. § The
  `runbook-*` commands notes the third reference file and the strike/insert
  rules. § `pipeline-engine` (added by task 181) notes that the routing table
  records where each owner's amend entry is, and which owners have none.
- `.claude/domain/product-workflow.md` § The iterate guard gains the precision
  variant beside the blanket one, stating which flips each produces.
- `.claude/domain/task-workflow.md` § One authority per rule adds
  `references/amend.md` to its table and updates the file-count and consumer
  sentences around it.
- `.claude/context/features.md` reflects: `skills/architect/`'s supporting-file
  count, `task-engine`'s eighth reference file, and `runbook-run/references/`'s
  third file.
- `.claude/context/INDEX.md`'s `Last updated:` anchor is refreshed.
- `.claude/domain/features/runbook-suite.md` is reconciled on exactly these 3
  points — editing it is authorised for this task, see Decisions:
  1. Its account of `skills/runbook-run/references/` names two files; a third,
     `step-amend.md`, now exists and owns the single-step amend rules.
  2. Its step-marker material records that a struck step is written `[x]` with a
     `Done:` line opening `struck — <reason>` and no commit sha, and is never
     deleted or renumbered.
  3. Its statement that a step's prompt block is immutable gains the named
     consequence — a wrong prompt is struck and a corrected step inserted.
  Nothing else in the document changes.
- `.claude/domain/features/owner-amend-arms.md` is reconciled on exactly these 3
  points — editing it is authorised for this task, see Decisions:
  1. § *Open questions*, bullet 2 — "Should `/architect amend` accept a
     free-form change with no section names?" is settled by what shipped
     (refuse) and reads as decided rather than open.
  2. § *Architecture* — the two new reference files are named abstractly; the
     shipped paths (`skills/architect/amend.md`,
     `skills/task-engine/references/amend.md`,
     `skills/runbook-run/references/step-amend.md`) replace the abstract naming.
  3. § *Dependencies* — "the precision gate may run the scoped lint" is settled
     by what shipped: the arm does not invoke `/pipeline-check`; the reviser
     does. The routing-table half of that dependency stands.
  Nothing else in the document changes. In particular the first open question,
  about how coarse `Files:` is as evidence, is left open — real use answers it.
- No `VERSION` bump and no `CHANGELOG.md` entry — every path above is
  documentation or the navigation/domain layer, which `CLAUDE.md` § Versioning
  exempts. `./scripts/check-changelog.sh` must still exit zero.

## Decisions
- **Editing `.claude/domain/features/runbook-suite.md` and
  `.claude/domain/features/owner-amend-arms.md` is explicitly authorised for
  this task (user decision, 2026-09-09), for the 3 + 3 reconciliations listed
  above and for nothing else. Do not ask for permission at implementation time —
  the permission is already granted.** Those documents are normally
  `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- **No `VERSION` bump.** `CLAUDE.md` § Versioning exempts `README.md`, `docs/`,
  `.claude/domain/` and `.claude/context/`. The shipped feature bodies changed
  in task 182, which bumped for itself; bumping again for a change
  no user receives would corrupt the version `install.sh` reports.
- **`docs/authoring-guide.md` and `CLAUDE.md` are deliberately untouched.** This
  feature adds supporting files to existing skills — an established pattern with
  no new frontmatter, no new asset kind and no new hard rule — so neither
  document has anything to reconcile.
- **`.claude/domain/features/pipeline-engine.md` and
  `.claude/domain/features/backlog-ordering.md` are deliberately untouched.**
  This feature consumes their routing table and positional append; it changes
  nothing about either, so there is nothing to reconcile, and both belong to
  `/architect` and to their own features' planning runs.
