# Task 126 — Create the task-engine skill by verbatim extraction

Target: claude

## Goal

Step 2 of the `shared-phase-engine` migration order
(`.claude/domain/features/shared-phase-engine.md`). Create `skills/task-engine/`
— a non-invocable reference library holding one authority per shared rule of the
`task-*` suite. The engine lives in a skill folder because `cmd-add` installs a
skill with `cp -R` of the whole folder, so supporting files ship with it, while
a command is a single `.md` that can carry nothing. Every reference file is
extracted **verbatim** from the current bodies: no rewording during extraction,
so any behaviour change shows up as a visible diff rather than hiding in a
paraphrase. No consumer is migrated in this task — the engine lands unused.

## Acceptance criteria

- `skills/task-engine/SKILL.md` exists with full frontmatter: `name:
  task-engine`, `version: 0.1.0`, `type: skill`, and a `description` that says
  plainly it is a reference library read by the `task-*` features and **not a
  skill the user invokes**, so it does not surface as a skill suggestion.
- `SKILL.md` carries the map of which reference file owns which rule, its own
  install path in `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/` form, and
  **no rule text of its own** — every rule lives in a reference file.
- Six files under `skills/task-engine/references/`, each the single authority
  for its rule:
  - `resolution.md` — `TASKS.md` parsing and the `all` / `next` / explicit-list
    selectors, from the three `LOCATING THE BACKLOG` sections
    (`commands/task-list.md`, `commands/task-clean.md`,
    `skills/task-implement/SKILL.md`) and `/task-add`'s PHASE 0 setup check.
  - `status.md` — the status vocabulary and its transitions, from
    `commands/task-add.md`'s `STATUS TAGS`, `commands/task-list.md`'s
    `STATUS TAGS`, `commands/task-clean.md`'s terminal/non-terminal split, and
    `skills/task-implement/SKILL.md`'s implementable-status list.
  - `targets.md` — the `Target:` values (`claude`, `claude+human`, `human`) and
    the delegation guard.
  - `stale.md` — `[STALE]` detection against `FEATURES.md` and what it means.
  - `tree.md` — the dirty-tree protocol.
  - `commit.md` — commit/push gating and `--no-commit` / `--no-push`, deferring
    to `docs/authoring-guide.md`'s push protocol by name exactly as the current
    bodies do.
- **Extraction is verbatim, and where the copies differ the divergence is
  recorded rather than silently merged.** Where two consumers state the same
  rule in different words, the reference file carries the fuller of the existing
  statements unchanged, and every material divergence in the other copies is
  written down as an explicit per-consumer note in the same file. A merged
  paraphrase that matches none of the four originals is the failure this
  criterion exists to prevent.
- Extraction is from the **post-118** shape of every source. No `Target: local`,
  no `/task-enrich`, no enriched body schema, no `chosko-llm task-impl`, no
  aider/Ollama material reaches the engine. `targets.md` lists exactly three
  target values.
- Every path the engine names uses the `${CLAUDE_HOME:-$HOME/.claude}` form,
  never `~/.claude`, and no reference file points at a `docs/` path — `docs/` is
  authoring-time-only and is never installed.
- The engine is prose only: no scripts, no state file, no data.
- `skills/task-engine/` declares no `requires:` of its own — it depends on
  nothing.
- **No file under `commands/` or `skills/task-implement/` is edited in this
  task.** The extraction sources are read, not changed; tasks 127-130 remove the
  originals one consumer at a time, so a failed migration never leaves a rule
  with no home.
- Root `VERSION` takes a minor bump (new shipped skill), relative to whatever
  task 125 leaves in place.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  131 owns both knowledge layers.
- No test suite by design: verify by reading the diff and confirming
  `./bin/chosko-llm ls --available` lists `task-engine  skill  —  0.1.0` against
  a clone where `install.sh` has run.

## Decisions

- **Precondition 118, so no dead material is extracted.** The feature document
  is explicit: the dual-LLM deletion touches the same file and goes first, "so
  the extraction does not carry dead material into the engine". Extracting
  first would bake `Target: local` and the enriched-body schema into the one
  place the whole suite then points at.
- **Precondition 125 even though the engine declares no `requires:`.** The
  document's migration order puts the field first, and keeping the chain linear
  means each task is verifiable against a codebase where everything before it
  has landed. The two genuinely converge at task 127, the first consumer.
- **Not preconditioned on 119 or 123**, although both change
  `skills/task-implement/SKILL.md`. What they change — the fixed-size launcher
  hand-off prompt and the `--review` / `--rounds` loop — is not among the six
  rules extracted here. The one point of contact is `commit.md`: task 123 adds a
  one-commit-per-task-under-`--review` rule. Task 130 preconditions on 123 and
  reconciles `commit.md` against the final shape, which is the right place for
  it — blocking the whole extraction on the peer-review feature would serialise
  work that does not need to be serialised.
- **Six files, exactly as the document specifies.** The document's own open
  question — whether `task-engine` is the right granularity — stays open on
  purpose. Splitting later is cheap; starting split is speculative.
- **`SKILL.md` holds no rules.** It exists because `cmd-add` requires a
  versioned `SKILL.md` to install a folder at all. Letting it accumulate rule
  text would recreate the problem this feature exists to solve.
- **Verbatim extraction is the mechanism, not a style preference.** The whole
  claim of this feature is that it changes no behaviour. That claim is only
  checkable if the diff shows text moving rather than text being rewritten.
