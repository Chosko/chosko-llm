# Task 53 — Author the product-workflow domain doc — the design→architecture→task pipeline contract

Target: claude

## Goal
This repo documents each workflow as a domain doc (`task-workflow.md`,
`context-workflow.md`, `refactor-workflow.md`), and every participating command is authored
against it. The new product pipeline — `/product-design` → `/architect` → `/task-add` —
has none, yet eight downstream tasks must agree on the same file layout, two status
vocabularies, a state machine, and a reconciliation protocol. Write the spec FIRST so tasks
54–61 implement a contract instead of each inventing one.

## Acceptance criteria
- `.claude/domain/product-workflow.md` exists, following the prose style of its siblings
  (why it exists → artifacts → per-stage responsibilities → cross-references).
- Defines the pipeline and each stage's inputs/outputs: `/product-design` (high-level
  design + optional business model) → `/architect` (low-level feature docs) → `/task-add`
  (implementation tasks) → `/task-implement`.
- Specifies the file layout verbatim:
  - `.claude/domain/INDEX.md`, `design-process.md`, `product-design.md`,
    `business-model.md`, `features/<slug>.md`
  - `.claude/FEATURES.md` — the feature index, sibling to `.claude/TASKS.md`
- Specifies the FEATURES.md entry schema exactly: `## <slug> — <title>` plus `Status:`,
  `Doc:`, `Source:`, `Tasks:` and nothing else. `Source:` is `prompt` when architected
  without design docs. `Tasks:` is a comma-separated ID list or `none`. No
  `Last feature number` counter — slugs are the identifiers.
- Specifies the feature state machine as the normative table:
  - `[NEW]` — architected, never planned. Written by `/architect` on first write.
  - `[ITERATED]` — planned, and the design has since changed. Written by `/architect`
    when it re-architects a feature that is `[PLANNED]`.
  - `[PLANNED]` — tasks exist and match the current design. Written by `/task-add`.
  - Legal: `[NEW]→[PLANNED]`, `[ITERATED]→[PLANNED]`, `[PLANNED]→[ITERATED]`, plus the
    self-transitions `[NEW]→[NEW]` and `[ITERATED]→[ITERATED]` (re-architecting when no
    new tasks have been generated since — the common case, not an error).
  - Illegal, with the reason stated: `[PLANNED]→[NEW]` (tasks exist; the past can't be
    un-planned) and `[NEW]→[ITERATED]` (nothing downstream to drift from).
- States that `[ITERATED]` means DRIFT — design moved, backlog not yet re-planned — and is
  the one actionable state, so commands that report on features surface it.
- Specifies the `[STALE]` task status and its role: set on a task by `/architect` when the
  feature it came from is re-architected, meaning the design this task was generated from
  has changed. Not terminal, not implementable unattended.
- Specifies the `Feature:` line in a TASKS.md summary block: the originating feature slug,
  present ONLY on tasks created from a feature, absent on free-form tasks. This is what
  makes reconciliation possible.
- Specifies the `/architect` iterate guard: `[IN PROGRESS]` among the feature's tasks is a
  hard refusal; otherwise the user chooses stop or proceed, and proceeding marks every
  non-`[DONE]` task `[STALE]`.
- Specifies the `/task-add` reconciliation protocol for a feature with existing tasks: a
  task still valid under the new design is left untouched; one needing minor change is
  updated in place (a `[STALE]` task flips back to `[MISSING]`); one substantially
  invalidated is marked `[SKIP]` and replaced by a new task. Judgment is the author's —
  the doc gives the criteria, not a mechanical rule.
- Specifies that `/task-implement` warns on a `[STALE]` task and lets the user implement or
  stop, and that the unattended orchestrator (`chosko-llm task-impl`) never implements one.
- States the domain/context separation and reconciles it with `context-workflow.md`: the
  context layer describes code STRUCTURE and is owned by `/context-build`; the domain layer
  describes PRODUCT and RULES, owned by humans, `/domain-setup`, `/product-design`, and
  `/architect`. The context commands still never write to `.claude/domain/`.
- Records the writer table — exactly one writer per artifact, with `FEATURES.md` the sole
  exception (`/architect` owns entries and `Status`; `/task-add` owns `Tasks:` and the flip
  to `[PLANNED]`; `/task-clean` prunes IDs).
- Records the session-resumability contract: `design-process.md` is the state file and
  every phase transition rewrites its stage marker.
- `CLAUDE.md`'s "Authoritative references" gains a bullet; `.claude/context/INDEX.md`'s
  `## Domain` table gains a row and its `Last updated` is refreshed.
- Root `VERSION` bumped (patch — doc-only).

## Decisions
- Spec before implementation: eight tasks write to this layout and would otherwise drift.
- Two separate status vocabularies, deliberately. Feature status tracks the design/backlog
  relationship; task status tracks implementation. Conflating them would make FEATURES.md a
  second, stale backlog.
- `[ITERATED]` is named for the event, not the state (`[STALE]` would name the state) —
  the user's choice, kept because it is non-pejorative and the transition table removes the
  ambiguity. The task-level tag IS named `[STALE]`, since there it describes the state.
- `[STALE]` is not terminal, so `/task-clean` does not prune it — a stale task is live work
  awaiting reconciliation, not abandoned work.
- `Tasks:` is retained (reversing an earlier decision to drop it) because it stopped being
  bookkeeping and became the input to the `/architect` guard.
- `Feature:` appears only on feature-derived tasks; free-form tasks stay exactly as they
  are today, so the change is invisible to existing backlogs.
