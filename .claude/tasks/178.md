# Task 178 — Write the lint finding catalogue

Target: claude

> Merged into task 175 on 2026-09-11; that body is the authority. This task is `[SKIP]` and awaits `/task-clean`.

## Goal
Add `skills/pipeline-engine/references/lint.md`, the finding catalogue: for each
finding, the detection rule stated over index lines only, its severity, its
one-line output template, and the single command that resolves it.
`/pipeline-check` and both revision surfaces read this file, so a finding is
defined exactly once and three features cannot drift apart on what counts as
drift. Feature `task-archive` removes one finding from the design's list before
it is ever written — an id a feature still names but `TASKS.md` no longer
carries is archived, not dangling — so this task also reconciles the feature
document on that point.

## Acceptance criteria
- The catalogue covers exactly these eleven findings and no others: a task's
  `Feature:` slug absent from `FEATURES.md`; a task with no `Feature:` line on a
  project whose `FEATURES.md` exists; a `Preconditions:` id that resolves to no
  task; a `Preconditions:` id naming a `[SKIP]` task; a precondition cycle; an
  `[ITERATED]` feature; a `[STALE]` task; a `FEATURES.md` slug absent from
  `PLAN.md`; a plan edge naming an unknown slug; a `[PENDING]` runbook whose
  `Steps:` shows every step done; a `[PLANNED]` feature whose every task has
  resolved and which has not been flipped.
- **"A feature's `Tasks:` id absent from `TASKS.md`" is not a finding**, and the
  file says so in a short note rather than by silent omission: under feature
  `task-archive`, `/task-clean` moves the body to `.claude/tasks/archive/<N>.md`
  and leaves the `Tasks:` line intact, so that absence is the normal state of a
  cleaned feature and means **archived, terminal**.
- That rule is cited, never restated:
  `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/references/resolution.md` is
  named as its authority.
- No detection rule probes `.claude/tasks/archive/`, opens an archived file, or
  reports on its contents, and the file states that prohibition once, for the
  whole catalogue.
- The `[PLANNED]`-feature finding is defined so an archived id counts as
  resolved: a `[PLANNED]` feature fires when every id on its `Tasks:` line is
  `[DONE]`, `[SKIP]`, or absent from `TASKS.md`. Without that clause a cleaned
  feature would never be reported as ready to flip, which is the exact ambiguity
  `task-archive` exists to remove.
- Each remaining finding's detection rule names the `graph.md` edge it walks and
  reads only index lines. No rule opens a file under `.claude/tasks/`,
  `.claude/runbooks/` or `.claude/domain/`.
- The runbook `[PENDING]` finding is derived from `RUNBOOKS.md` alone —
  `Steps: <n>/<n>` together with `Status: [PENDING]` — and the file states that
  derivation, since it is the one finding whose index-only form is not obvious.
- The catalogue records that "a pending runbook step naming a task already
  `[DONE]` or `[SKIP]`" is **deliberately absent**, and why: detecting it would
  mean opening a runbook body, which the read-only register forbids, and
  `/runbook-run` surfaces the same problem when it prints the step before
  spawning it. `RUNBOOKS.md` carrying per-step targets is what would unblock a
  cheap index-only version. A reader must not conclude it was forgotten.
- Severity is **two levels, `ERROR` and `WARNING`**, and the file states the
  discriminator once rather than leaving it per finding: `ERROR` is a reference
  that cannot be resolved or a state that will misdirect a run — an unknown
  slug, an unknown or `[SKIP]` precondition id, a cycle, a plan edge naming a
  slug that does not exist. `WARNING` is a legal state that needs its owner's
  attention — an `[ITERATED]` feature, a `[STALE]` task, a slug missing from
  `PLAN.md`, a finished-but-`[PENDING]` runbook, a fully resolved `[PLANNED]`
  feature, a task with no `Feature:` line. Every finding carries exactly one.
- Each finding names exactly one fixing command, and every command named has a
  row in `routing.md`: `/task-add feature=<slug>` for an `[ITERATED]` feature,
  `/production-plan` for a slug missing from the plan, a plain `flip to [DONE]`
  for a fully resolved `[PLANNED]` feature, `/pipeline-patch` or
  `/pipeline-revise` for the rest.
- Each finding carries a one-line output template so `/pipeline-check` and the
  revision surfaces render it identically, with the severity, the artifact and
  the offending identifier in a fixed position.
- The file states the two failure rules: a finding whose index is absent is
  dropped from the run rather than reported as an error, and a malformed block
  is a finding of its own — `ERROR`, with its own fix — rather than an abort.
- The file states that it detects **structural** inconsistency only. Whether a
  feature document still describes what its tasks build is `/architect amend`'s
  precision guard, and the catalogue says so rather than leaving the boundary to
  a reader's judgement.
- `.claude/domain/features/pipeline-engine.md` is reconciled with what ships
  here on exactly these 2 points — editing it is authorised for this task, see
  Decisions:
  1. § *The findings* — remove the bullet "a feature's `Tasks:` id absent from
     `TASKS.md`". Under `task-archive` that absence means archived and terminal,
     which is the normal state of a cleaned feature, not drift.
  2. § *The reference files*, the **Graph** bullet — add one sentence stating
     that a `Tasks:` id with no `TASKS.md` block resolves as archived and
     terminal, per `task-archive`.
  Nothing else in the document changes; in particular the four points task 181
  reconciles are not touched here.
- `skills/pipeline-engine/SKILL.md` takes a **minor** `version:` bump; its map
  table is not edited.
- Root `VERSION` takes a **patch** bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` exits zero.

## Decisions
- **Editing `.claude/domain/features/pipeline-engine.md` is explicitly
  authorised for this task (user decision, 2026-09-09), for the 2
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document is
  normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- The `Tasks:`-id finding is dropped at authoring time rather than shipped and
  retracted later. Shipping it would make `/pipeline-check` report every cleaned
  feature as drift on its first run against an archived backlog — the loudest
  possible false positive, on exactly the projects the lint is most useful for.
- Two severity levels, not three (user decision at planning time), and
  deliberately **not** `/task-review`'s `BLOCKING` / `IMPORTANT` / `ADVISORY`.
  Those were defined for judging code against acceptance criteria; a drift
  finding is either a broken reference or a state someone should look at, and a
  middle tier would only invite argument about which findings belong in it.
  `ERROR` / `WARNING` also stays clear of all three status vocabularies, so a
  grep for a status never returns a severity.
- The archived-and-terminal rule is cited from `resolution.md`, never restated
  here, per `shared-phase-engine`'s one-authority-per-rule discipline. Feature
  `task-archive` is what puts the rule in that file, and it may not be there yet
  when this task is implemented. Cite it regardless; if the file has not gained
  it, note that in the commit rather than writing a second copy. Runbook
  `pipeline-revision-planning` wires the ordering: a later step adds the id of
  the `task-archive` task that writes the rule onto this task's
  `Preconditions:` line, so this body deliberately does not name one.
- No archive probe anywhere in the catalogue. `task-archive` states that a
  hand-deleted body and an archived one are indistinguishable to every reader by
  design; a rule that checked would be claiming a distinction the product has
  deliberately declined to make.
- The catalogue is closed, not extensible-by-default: adding a finding is an
  edit to this file, so `/pipeline-check` and both revision surfaces gain it at
  once and cannot disagree about whether it exists.
