# Task 250 — Two-group closing report for `/task-implement` and `/task-review`; consequential edits are in scope, untraceable doc edits are a finding

Target: claude

## Goal
Two defects in how an implementation run ends. Its closing report mixes items
that need a decision with items that merely record a deviation, and the latter
run to a paragraph each, so the reader cannot tell at a glance whether anything
is being asked. And an implementer that notices a passage its own approved
change made stale leaves it untouched when another command owns the file,
knowingly shipping a code-versus-design mismatch. Fix both: a fixed two-group
report, and the rule that ownership guards decisions, never consistency.

## Acceptance criteria
- The closing report of `/task-implement` (single task, batch and `--review`
  runs alike) has two groups, in this order. **Needs you**: items awaiting a
  decision, as long as they need to be. **For the record**: one line per item
  in the fixed shape `<what deviated> — <why> — <resolved by whom>`; no item in
  this group runs longer than one line. An empty group prints its heading and
  `none`. Example of the second group's shape: `Task 245 asked ~25 net lines
  across two files — mandated block needed 19 — +31, reviewer approved.`
- `/task-review`'s report adopts the same two groups for its closing section;
  its findings list is unchanged.
- `skills/task-implement/SKILL.md` defines a *consequential edit*: an edit that
  only makes a passage agree with a change already approved (by the task body,
  a user reply or a gate) and changes no meaning beyond it. Consequential edits
  are in scope for the implementer, made in the same commit, whatever file owns
  the passage, and reported one line each under **For the record**. They are
  never asked about and never left as a follow-up.
- A passage whose update would introduce new meaning in an owned document
  stays untouched and is named under **Needs you** as a precise follow-up: the
  exact command, anchor and passages (`/architect amend feature=<slug> "…"`),
  never a vague pointer at the owner.
- `skills/task-review/SKILL.md` gains one finding: a documentation edit in the
  diff that is not traceable to the approved change. A consequential edit is
  traceable by definition; a new decision presented as one is the finding.
- `.claude/domain/features/task-peer-review.md` is reconciled with what ships
  on exactly these points — editing it is authorised for this task, see
  Decisions: (1) the closing report's two-group shape; (2) the traceability
  finding as part of `/task-review`'s finding set. Nothing else in the
  document changes.
- `.claude/domain/task-workflow.md`, `.claude/context/features.md` and
  `docs/reference.md` describe the report shape and the consequential-edit
  rule.
- `skills/task-implement` and `skills/task-review` `version:` minor bumps;
  root `VERSION` minor bump; `CHANGELOG.md` entry; `./scripts/check-changelog.sh`
  and `./scripts/check-home-paths.sh` silent.

## Decisions
- The safety net moves from ask-before to check-after: the review already
  runs, so a smuggled decision is caught there at no extra gate.
- **Editing `.claude/domain/features/task-peer-review.md` is explicitly
  authorised for this task (user decision, 2026-09-21), for the two
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time.** The document is normally `/architect`'s; a change
  beyond those points is a design decision and stops the run to say so.
- Aligned with task 244's `/runbook-run` closing report: same two groups, so a
  runbook's report and a task's report read the same way.
