# Task 153 — Order `ls` output by feature name instead of by kind

Target: claude

## Goal
`chosko-llm ls` prints its rows in five sequential passes — commands, then
skills, then claude-md artifacts, then statusline scripts, then hooks — so a
feature's position depends on its kind rather than its name. Finding one
feature in a ~50-row listing means knowing its kind first, and the KIND column
already carries that information. Buffer the rows and emit them in a single
name-ordered sequence instead.

## Acceptance criteria
- `chosko-llm ls` prints every row in one sequence ordered ascending by
  feature name. No kind grouping survives in the output.
- Two rows sharing a name are ordered by kind rank — command, skill,
  claude-md, statusline, hook — so a `superseded` / `migration pending` pair
  stays adjacent and in that order.
- Ordering is byte-deterministic regardless of the caller's locale.
- The header, every column width, the KIND values and their per-kind colours,
  and the `Home:` line are unchanged.
- Scope gating is unchanged: the statusline pass is still skipped when
  `scope_is_local`, the hook pass still runs only when `scope_is_local`, so
  `ls --global` still omits hooks and `ls --local` still omits statusline.
- `--installed`, `--available`, `--all`, `--local`, `--global` all produce the
  name-ordered listing; per-row filtering still happens before a row is
  buffered, so the displayed set is identical to today's.
- Colours survive buffering: a row's padding is still computed from its
  visible length, not its escape-laden length.
- `No features found.` and the TTY-gated suggestions footer are unchanged in
  wording and in the counts they report.
- `docs/cli-help.txt` states in the `chosko-llm ls` block that the listing is
  ordered by feature name.
- `VERSION` bumped minor (1.14.1 → 1.15.0) with a matching top `CHANGELOG.md`
  section; `./scripts/check-changelog.sh` exits silent.

## Decisions
- **Kind rank as the tie-break, not alphabetical kind** (user decision).
  Keeps a mid-migration pair adjacent in the order the migration reads.
- **The repo's word is "kind", not "type".** The user's "type" is the KIND
  column; use `kind` throughout, matching `compute_status`, `collect_names`
  and the context layer.
- **Buffer-then-sort, five passes left in place.** Each pass appends one
  record — name, kind rank, and the fully rendered line — to a single array;
  one loop at the end sorts and prints. This keeps each pass's own filter
  logic and scope gate untouched, and is a much smaller change than
  collapsing the five near-identical passes into one generic function.
- **Task 152 is repointed to depend on this task** (user decision,
  2026-08-25). Reordering is the structural change and touches all five
  passes; landing it first means 152's implementer writes the REQUIRES cell
  into one render point instead of five. This run edited task 152's
  `Preconditions:` line to `153`, and its VERSION acceptance criterion to the
  next minor after this task's bump.
