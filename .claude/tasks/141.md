# Task 141 — Add the /runbook-create command

Target: claude

## Goal

Second artifact of the `runbook-suite` feature
(`.claude/domain/features/runbook-suite.md`): the authoring side, and the half
the feature's second argument rests on. A prompt written inside a rich
conversation reads as complete and is not — it leans on decisions made an hour
ago and written down nowhere, on a document everyone present had already read,
and on knowledge of which options were already rejected. `/runbook-create`
harvests that material while the conversation is still open and enforces the
checklist that makes each prompt survive a fresh agent, writing
`.claude/runbooks/<name>.md` and its `.claude/RUNBOOKS.md` index block — or
appending steps to a runbook that already exists, including one that is running.

## Acceptance criteria

- `commands/runbook-create.md` exists with full frontmatter: `name:
  runbook-create`, `version: 0.1.0`, `type: command`, a `description`, and
  `requires: skill:runbook-run`.
- The body cites the schema by installed path —
  `${CLAUDE_HOME:-$HOME/.claude}/skills/runbook-run/references/runbook-schema.md`
  — and does **not** restate the body schema, the step markers, the status
  vocabulary or the index block. One authority, cited.
- **Target axis**, four forms:
  - `/runbook-create <name>` — a new runbook under that name. A single
    kebab-case token is read as a name; anything longer is read as a
    description.
  - `/runbook-create --append <name>` — appends steps after the last existing
    step of that runbook.
  - `/runbook-create --append` with no name — targets the runbook the session is
    currently running (the orchestrator session knows which; a step's subagent
    knows because the spawned prompt names its runbook). With no current runbook
    it is an error naming `--append <name>`.
  - `/runbook-create` with no arguments — asks which: a new runbook, with the
    name given free-form, or an append to an existing one, listed from
    `.claude/RUNBOOKS.md` with non-`[DONE]` runbooks first and the currently
    running one first of all. **This is the only place new-versus-append is
    asked**, and the body says so, because it is the command the user chose to
    run.
- **Source axis**, two modes:
  - *Conversation mode* is the default when no description is given, and the
    mode the feature exists for. The source is the **most recent** enumerated
    follow-up list in the conversation; earlier lists are superseded and
    ignored, except for items still outstanding, which are carried forward.
  - *From-scratch mode* takes a free-form description and gathers the material
    through a short interview, asked as **one batch** with a recommended answer
    for each so it can be settled in a sentence: (1) what must be true when this
    runbook is finished — the end state, which is what makes the last step
    recognizable as the last step; (2) the steps, in order, titles being enough
    at this stage; (3) which steps must precede which **and why**, the reason
    being what goes on the `Sequencing:` line; (4) for each step, which document
    the agent should read first — a step with no such document needs its
    evidence inline instead, which is worth knowing now rather than at write
    time; (5) what has already been decided, tried or rejected, which becomes
    prompt material and the optional `## Do not re-propose` section. A sixth
    question, the model, is asked only when the default `opus` is not wanted.
- **The nine prompt-quality rules are stated in the body in full**, not
  summarised, and enforced against every step before the file is written:
  self-contained — meaning complete given what the invoked command reads, not
  exhaustive (the rule the other eight serve); names the document to read
  first, or carries the evidence inline where there is none, and does not
  repeat a document the invoked command names itself; carries every decision
  that exists nowhere on disk **and nothing that already does** — restating a
  task body, a feature document or `CLAUDE.md` duplicates it and the duplicate
  drifts, so the correct prompt for an authored task is the one-line
  `/task-implement <n>` and one-line prompts are the expected case, not a
  shortcut; states its sequencing and why; states
  what must not be re-proposed, step-specific ones in the prompt and
  runbook-wide ones in `## Do not re-propose`; uses an existing slash command
  where one fits, in its real argument form; references no path that will not
  exist at run time, and in particular nothing under `docs/`; produces one
  deliverable, because a step that lands two unrelated artifacts has no honest
  marker for half of it succeeding; and never invokes `/runbook-run`.
- A step failing a rule is **fixed before the file is written, and the fix is
  named in the confirmation report rather than applied silently** — the user is
  the only one who knows whether a missing decision was an omission or a
  deliberate delegation.
- Rule 9 is enforced here as well as at spawn time: a step whose prompt would
  invoke `/runbook-run` is rejected at authoring time, with the depth-budget
  reason.
- `Context:` is written as `none` at authoring time in the common case, and the
  body says why: the decisions a prompt needs belong **inside** the prompt,
  which keeps the fenced block pasteable into a fresh session on its own — the
  property that keeps a runbook executable by hand if `/runbook-run` is
  unavailable or the user simply prefers to drive it. `Context:` is the run's
  field: corrections, failure notes, and facts learned by earlier steps.
- **Append rules**, all stated: numbering continues from the last existing step;
  `Depends on:` may reference existing steps including completed ones; the
  `Sequencing:` header line is extended, never replaced; existing steps are
  never edited, so an append touches nothing above the append point; appending
  to a `[DONE]` runbook flips it back to `[PENDING]`; appending to a `[FAILED]`
  one leaves it `[FAILED]`, because the halt still needs a decision and adding
  steps does not resolve it; appending to a `[RUNNING]` one is allowed **only
  from the running session itself** — one session, one tree, no race — and the
  run picks the new steps up at its next step re-read; the index
  `Steps: <done>/<total>` is updated.
- **First use is silent and idempotent**: `.claude/runbooks/` and
  `.claude/RUNBOOKS.md` are created on demand, the index with its title and
  nothing else — no counter, because names are the identifiers. A project needs
  no setup step, and `/task-setup` and `/project-setup` are not touched by this
  task and gain no runbook step.
- A name already present is **refused with a suggested alternative** rather than
  disambiguated automatically, since a runbook is referred to by name for the
  length of its execution and two similar names are a real hazard. Names of
  removed runbooks are not reserved.
- **The confirmation gate** reports the proposed shape only — target runbook,
  step titles, the sequencing line, dependencies, and any one-deliverable splits
  it made — and stops for approval. Full prompts are deliberately not shown
  back: they are a wall of text that gets skimmed, and they are in the file a
  moment later, uncommitted and open to review.
- Authoring-command commit convention: output is left uncommitted for one review
  pass by default; `--commit` opts in, `--commit --no-push` commits without
  pushing, per `docs/authoring-guide.md`'s commit-and-push protocol. The body
  notes the review pass matters more here than usual — the prompts are the whole
  product and are cheapest to fix before the first step runs.
- It writes exactly the runbook body and the index block — never a task, never a
  feature document, and never a line that belongs to a run: no `Done:` line, no
  step marker other than `[ ]`, and no index `Status:` other than `[PENDING]`,
  the sole exception being the `[DONE]` → `[PENDING]` flip an append forces.
- Every path in the shipped body uses `${CLAUDE_HOME:-$HOME/.claude}` where it
  names an install location, and no path under `docs/` appears.
- Root `VERSION` takes a minor bump (new shipped command), relative to whatever
  is in place when this lands.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  145 owns both knowledge layers.
- No test suite by design: verify by reading the diff and confirming
  `./bin/chosko-llm ls --available` lists `runbook-create  command  —  0.1.0`
  against a clone where `install.sh` has run.

## Decisions

- **Preconditioned on 140 as well as 125.** The body cites a file inside
  `skills/runbook-run/references/` by installed path and declares `requires:
  skill:runbook-run`; both the citation and the declaration are dangling until
  140 and 125 have landed.
- **Appending is a flag, not a `/runbook-append` command.** The interview, the
  prompt-quality rules and the confirmation gate are identical in both
  directions; only the write target differs, and a second command would
  duplicate the entire authoring apparatus to change one path.
- **The prompt-quality rules stay in this body** rather than becoming a third
  reference file: exactly one consumer, and a shared file with one consumer is
  indirection without benefit.
- **The gate shows shape, not prompts.** Its job is catching a wrong order or a
  missing step — both expensive after the first step has run and cheap now.
- **Most-recent-list selection in conversation mode** is deliberate and settled;
  earlier lists are superseded, with still-outstanding items carried forward.
- **`.claude/runbooks/implement-ecc-import.md` is the reference shape for what
  a rule-compliant prompt block looks like.** It is hand-written (2026-08-24,
  before any runbook artifact shipped), is not generated output, must not be
  edited by this task, and nothing in the shipped body may read it at run time.
