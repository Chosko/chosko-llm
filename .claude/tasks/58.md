# Task 58 — Add the /architect skill — turn high-level features into low-level feature docs

Target: claude

## Goal
Add an `/architect` skill that takes one or more high-level features and designs an
implementation architecture grounded in the project's existing code or, for greenfield, a
chosen tech stack. Output is technical documentation of LOW-LEVEL features under
`.claude/domain/features/`, indexed in `.claude/FEATURES.md` — the bridge between
`/product-design` and `/task-add`. One high-level feature may produce several low-level
ones.

## Acceptance criteria
- `skills/architect/SKILL.md` with complete frontmatter (`name: architect`,
  `version: 0.1.0`, `type: skill`).
- Three supporting files, each read only when its branch fires, triggers named in SKILL.md:
  - `tech-stack-selection.md` — evaluation axes, pros/cons framing, tying the choice back
    to the product design. Read ONLY when the project has no existing stack.
  - `feature-doc-template.md` — the `.claude/domain/features/<slug>.md` section schema and
    the `.claude/FEATURES.md` entry format.
  - `iterating.md` — the full iterate guard and `[STALE]` marking protocol. Read ONLY when
    PHASE 0 finds the target feature already exists in `FEATURES.md`.
- Input resolved in PHASE 0: a section of the `/product-design` output, one or more named
  features, or a bare free-form prompt. With no argument it reads `product-design.md` and
  asks which feature(s) to architect. Works with no design documents at all, architecting
  from the prompt plus the existing codebase.
- PHASE 0 — GATE + INPUT. Verifies the domain layer exists (stops, pointing at
  `/domain-setup`). Reads `.claude/domain/INDEX.md`, `product-design.md` if present,
  `.claude/FEATURES.md`, and the `.claude/context/` layer if present.
- PHASE 0b — ITERATE GUARD, entered only when the target feature already has an entry:
  - Reads the entry's `Tasks:` IDs and looks up each status in `.claude/TASKS.md`.
  - If ANY is `[IN PROGRESS]`: REFUSE. Report the task ID and title and stop — no
    override. Work is actively underway against the current design.
  - Otherwise, if any is not `[DONE]`: list them with statuses and titles, state that
    re-architecting may invalidate them, and offer stop or proceed.
  - On proceed: flip every non-`[DONE]` task to `[STALE]` in `.claude/TASKS.md`, and set
    the feature `[PLANNED]` → `[ITERATED]`.
  - When the feature is `[NEW]` (never planned), no tasks exist: skip the guard entirely
    and leave the status `[NEW]`. Same for a feature already `[ITERATED]`.
  - IDs in `Tasks:` that resolve to no task are ignored, not an error.
- PHASE 1 — CLARIFY (skippable). Questions when the feature is ambiguous; answers written
  back into `product-design.md` when the feature came from there. Skipped outright when
  everything is clear, saying so in one line.
- PHASE 2 — ARCHITECT. With no stack yet, first proposes candidate stacks with pros and
  cons for the user to choose (reading `tech-stack-selection.md`); skipped when a stack
  exists. Then proposes one or more architectures, starting high-level and descending,
  conversationally, weighing trade-offs and asking questions. Stops at a mid-to-high
  technical level — no real code, no file-by-file plan; that is `/task-add`'s job.
- PHASE 3 — WRITE. Writes one `.claude/domain/features/<slug>.md` per low-level feature,
  and appends or updates its `FEATURES.md` entry carrying exactly `Status:`, `Doc:`,
  `Source:`, `Tasks:`. New features get `[NEW]` and `Tasks: none`. Iterated features keep
  their `Tasks:` line untouched — `/task-add` owns it — and carry `[ITERATED]`. Registers
  new docs in `.claude/domain/INDEX.md` and updates `product-design.md` where the
  architecture changed a high-level decision.
- Re-running on an existing feature updates the doc and entry in place; slugs are stable
  identifiers and are never renamed.
- The closing report names each feature written, its status transition, and every task
  flipped to `[STALE]`, with the `/task-add feature=<slug>` command to reconcile them.
- Nothing committed by default; `--commit` stages exactly the written paths — including
  `.claude/TASKS.md` when the guard flipped statuses — in one commit. Non-git VCS honours
  the `## VCS` mapping.
- A `DO NOT` section forbids: implementation-level or file-by-file plans, creating tasks,
  writing the `Tasks:` line, editing source code, renaming slugs, overriding the
  `[IN PROGRESS]` refusal, committing without `--commit`.
- `.claude/context/features.md` and `README.md` updated. Root `VERSION` bumped (minor).

## Decisions
- Skill rather than command, confirmed by the user — the tech-stack material is dead weight
  on the common brownfield path, so it belongs in an on-demand file. The iterate guard gets
  the same treatment: it only fires on re-architecture.
- `[IN PROGRESS]` is a hard refusal with no override, per the user's instruction. Every
  other non-`[DONE]` status is negotiable because nothing is mid-flight.
- `/architect` writes `Status:` but never `Tasks:`; `/task-add` writes `Tasks:` and the
  flip to `[PLANNED]`. FEATURES.md is the one shared-writer artifact, and the split is by
  line so the two can never race on the same field.
- `/architect` writes to `.claude/TASKS.md` — narrowly, only to flip statuses to `[STALE]`.
  It never creates, deletes, or reorders task entries.
- Runs from a bare prompt with no design documents, so it is useful on existing projects
  before `/product-design` is ever run.
