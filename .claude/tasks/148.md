# Task 148 — Print what changed on upgrade, from CHANGELOG.md

Target: claude

## Goal

`chosko-llm upgrade` currently dumps `git log --oneline` — commit subjects written
for the repo's author, not for someone who wants to know whether the CLI they use
every day behaves differently this morning. This is the third part of the
`version-changelog` feature (`.claude/domain/features/version-changelog.md` §§ 4–6):
put the curated record in front of the user at the one moment they are demonstrably
interested. Three helpers in `scripts/lib.sh`, and a coloured range readout in
`scripts/cmd-upgrade.sh` covering exactly the versions just pulled.

## Acceptance criteria

- `scripts/lib.sh` gains **three** additions, with no signature change to anything
  existing:
  1. A **raw version reader** — the trimmed contents of `$CHOSKO_LLM_HOME/VERSION`,
     empty when the file is absent. `resolve_version` is refactored to call it, so
     the trim and the path exist in exactly one place. `resolve_version`'s output
     format is unchanged byte-for-byte, and its two callers (`install.sh`,
     `scripts/cmd-version.sh`) are untouched.
  2. A **changelog path helper** resolving `CHANGELOG.md` under
     `$CHOSKO_LLM_HOME`, alongside the existing `src_*_path` family. No path is
     assembled inline in `cmd-upgrade.sh`.
  3. A **changelog range printer**, owning both the awk extraction and the
     formatting.
- `scripts/cmd-upgrade.sh` reads the raw `VERSION` **before** `git pull --ff-only`
  and again **after** it, and prints the range between them.
- **Neither read goes through `resolve_version`** — it appends ` (<git describe>)`,
  and with no tags in this repo that is a bare sha which changes on every commit,
  making it useless as a version comparison.
- The range is **two-sided**: from the new version's header inclusive, down to but
  excluding the old version's header. Because the file is descending semver this is
  a single forward scan with awk, matching `^## ` and comparing the first token —
  no sorting, no second pass, no temporary file.
- Placement: after the pull and the existing pulled-commits reporting, before the
  proxy refresh, so the news arrives before the mechanical follow-up hints.
- **The raw `git log --oneline` dump is suppressed exactly when a changelog range
  was printed.** Exactly one of the two appears on any non-empty pull. It still
  prints in every case where no range was printed.
- The block is written to **stderr**, like every other line `cmd-upgrade.sh` emits.
- Colour is gated by the **same `_use_color` predicate `log_info` and friends use**
  (`NO_COLOR` unset *and* fd 2 is a TTY), applied with the same
  `printf '\033[...m'` handling. The `C_*` variables are deliberately **not** used
  — they are gated on *stdout* being a TTY and this block goes to stderr.
- Layout, for a pull from `0.61.0` to `0.62.1`:
  - the framing line goes through `log_info`, so it carries the standard `[info]`
    prefix and needs no colour of its own: `What changed since 0.61.0 → 0.62.1`;
  - one blank line, then per section a two-space-indented `<version> — <date>` and
    four-space-indented bullets, a blank line between sections and one after the
    block;
  - one accent colour for the whole block: the version **bold**, the ` — <date>`
    **dim**, the bullet's leading `- ` marker in the accent colour, the bullet text
    default. No per-version highlighting, no distinction between newest and older
    sections.
- **The marker stays ASCII `-`.** The CLI runs under git-bash on Windows, where a
  non-ASCII bullet glyph can mangle in a legacy codepage console. The printer
  colours the two characters the source bullet already begins with rather than
  substituting a glyph, which also leaves any inline backticks or punctuation in the
  bullet untouched.
- **No wrapping and no pager.** No terminal-width detection, no `tput` probe.
- No new flag, no new subcommand, no new exit code. `--enable-auto` /
  `--disable-auto` still exit before any of this runs.
- Every row of the situation table holds:

  | Situation | Behaviour |
  | --- | --- |
  | `CHANGELOG.md` absent from the clone | Silent. No warning, no error — clones predating this feature are the normal case. |
  | Old and new version identical | Print nothing; the `git log --oneline` list prints as it does today. |
  | Both headers present | Print the range, new inclusive / old exclusive; suppress the commit list. |
  | New version's header missing | One line saying `CHANGELOG.md` has no section for that version; print no sections; commit list still prints. |
  | Old version's header missing | Print only the new version's section, plus one line saying the earlier range could not be resolved. |
  | Old version newer than new (a `channel` switch, a downgrade) | Empty range, so nothing prints — falls out of the ordering rule with no special case. |
  | `VERSION` unreadable before or after the pull | Treated as a missing header on that side, per the two rows above. |
  | Range spans many versions | Print all of them. No cap. |
  | `NO_COLOR` set, or stderr not a TTY | Same text, same layout, no escapes. |

- **Failure contract: degrade, never fail.** Nothing in the readout may change
  `upgrade`'s exit code or abort the run. A malformed, truncated or unreadable
  `CHANGELOG.md` costs the user their release notes, never their upgrade. A line
  inside a section that is neither a header nor a bullet is passed through indented
  and uncoloured rather than dropped — losing content is worse than printing
  something unexpected.
- Two verified non-changes, confirmed rather than implemented: `cmd-upgrade.sh`
  already resolves everything through `$CHOSKO_LLM_HOME` and never hardcodes a path,
  so the override is already honoured; and `scripts/auto-upgrade.sh` invokes
  `cmd-upgrade.sh` directly (line 29) without swallowing its output, so the readout
  fires during daily auto-upgrade as intended.
- `scripts/cmd-channel.sh` is **not** modified — `chosko-llm channel <branch>`
  prints nothing. A channel switch can move `VERSION` in either direction and is a
  developer action, not an upgrade.
- `CHANGELOG.md` gains a section for this task's own bump.
- Root `VERSION` takes a minor bump.

## Decisions

- **The printer lives in `lib.sh`, not in `cmd-upgrade.sh`.** That is where the
  colour helpers already are, and `.claude/context/shared-lib.md` records the
  standing convention that `cmd-*.sh` scripts never inline `\033[` escapes.
- **`_use_color`, not the `C_*` variables.** The `C_*` set is computed once at
  source time from `[ -t 1 ]`; this block goes to stderr, so it must be gated on
  `[ -t 2 ]` like `log_info`. When colour is off every escape resolves to an empty
  string and the layout, indentation and markers are unchanged.
- **The commit list is suppressed when the range prints.** A forty-line subject dump
  alongside a curated summary is strictly worse for this audience, and the commits
  stay one `git -C ~/.chosko-llm log` away.
- **No cap on range length.** Bullets are short by schema, this is the one moment
  the information is wanted, and daily auto-upgrade keeps real ranges to one or two
  sections.
- **`resolve_version` is refactored, not changed.** It keeps its current output
  format exactly; the refactor only moves the trim and the path into the new raw
  reader so they exist in one place.
- **Minor bump.** This is a new capability in the CLI's `upgrade` surface, visible
  to every user, with no flag removed and no behaviour broken.
