# Task 54 — Extend the backlog schema — the [STALE] status and the Feature: slug line

Target: claude

## Goal
The product pipeline needs two additions to the task backlog before `/architect` can exist:
a `[STALE]` status meaning "the design this task came from has changed", and a `Feature:`
line recording which feature a task was generated from. Land both across every reader and
writer in one task — the status vocabulary is duplicated in a shell parity guard and an
allowlist, so a partial rollout breaks the guard.

## Acceptance criteria
- `commands/task-add.md`'s STATUS TAGS section documents `[STALE]`: set by `/architect`
  when the originating feature is re-architected; means the task may no longer match the
  design; resolved by `/task-add feature=<slug>` reconciliation. Explicitly NOT set by
  `/task-add` when creating a task.
- The INDEX FILE FORMAT blocks in `commands/task-add.md` and `commands/task-setup.md` gain
  the optional `Feature:` line, documented as present only on feature-derived tasks.
- `scripts/check-task-parity.sh`: `[STALE]` added to `CANONICAL_TAGS`, and deliberately
  NOT added to `BASH_REQUIRED_TAGS` — with the comment explaining why, matching the
  existing `[SKIP]` precedent.
- `scripts/cmd-task-impl.sh`: `[STALE]` is excluded from the implementable-status allowlist
  (both the awk selection and the per-task guard). A `[STALE]` ID passed explicitly is
  refused with a message naming the feature and pointing at `/task-add feature=<slug>`.
  The unattended orchestrator never silently implements against a changed design.
- `skills/task-implement/SKILL.md`: on a `[STALE]` task, warn before starting — name the
  feature, say the design changed since the task was written, and offer implement-anyway or
  stop. Interactive `/task-implement` may proceed on the user's say-so; this is the
  deliberate asymmetry with the unattended orchestrator.
- `commands/task-list.md`: `[STALE]` is listed among the filterable statuses and marked in
  the output so it's visible at a glance, alongside the existing `⚠` human-in-the-loop
  marker. The `Feature:` slug is shown when present.
- `commands/task-clean.md`: `[STALE]` is explicitly NOT terminal and is never pruned;
  terminal remains `[DONE]` / `[SKIP]`. Say so in the command so a future reader doesn't
  add it.
- `.claude/domain/task-workflow.md` documents both additions and the body↔TASKS.md split
  they imply (`Feature:` is tracking metadata, so it lives in TASKS.md, not the body —
  consistent with how `Status:` and `Preconditions:` are handled).
- `.claude/context/cmd-task-impl.md` reflects the allowlist change.
- `scripts/check-task-parity.sh` passes after the change.
- Existing backlogs are unaffected: no `Feature:` line is added to any existing task, and
  no existing status changes meaning.
- `.claude/context/features.md` and `README.md` updated; each touched command's frontmatter
  `version` bumped; root `VERSION` bumped (minor).

## Decisions
- One task, not six. The status vocabulary is mirrored in a shell parity guard that fails
  when the prompt and the script disagree, so the markdown and the shell must land together.
- `[STALE]` is implementable interactively but not unattended. A human can look at a stale
  task and judge; an external LLM driven by `chosko-llm task-impl` cannot, and implementing
  against a superseded design is worse than stopping.
- `Feature:` lives in the TASKS.md summary block rather than the body, matching `Status:`
  and `Preconditions:` — it is backlog metadata, not part of the implementation contract.
- Landed before `/architect` (task 58) because `/architect` writes `[STALE]`; building the
  writer before the vocabulary exists would break the parity guard mid-batch.
