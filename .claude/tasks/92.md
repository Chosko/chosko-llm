# Task 92 — Offer per-task subagent delegation on multi-task /task-implement runs

Target: claude

## Goal
A multi-task `/task-implement` run (`/task-implement 20 21 22`, `all`, or any
selector resolving to 2+ tasks) currently implements every task in one
conversation, so context accumulated by task 1 is still loaded when task 3
starts — the later tasks get progressively less headroom and more noise. Give
the run the option to implement each task in a fresh subagent instead: after
the task list resolves, ask the user whether to delegate, and if so spawn one
agent per task **sequentially** — never in parallel, since the tasks share a
working tree and a git branch. Interactive tasks (`claude+human` / `human`)
cannot be delegated because a subagent cannot pause for the user, so a mixed
run keeps those in the parent conversation and delegates only the `claude`
ones.

## Acceptance criteria
- `skills/task-implement/SKILL.md` gains an `--agents` / `--no-agents` flag,
  parsed alongside `--no-commit` / `--no-push` / `-y` in ARGUMENT PARSING. The
  two are mutually exclusive; passing both stops with
  `--agents and --no-agents cannot be combined. Pick one.`
- When the resolved task list has 2 or more tasks and neither flag was passed,
  PRE-FLIGHT asks the user whether to run each task in a fresh subagent,
  stating that agents run one after another, not in parallel. Silence is not
  approval — the default on an unclear answer is in-context.
- The question is never asked when the resolved list has fewer than 2 tasks; a
  single-task run is unchanged in every respect.
- `--agents` pre-answers yes and `--no-agents` pre-answers no, so neither
  prompts. `--agents` on a single-task run is accepted and ignored (the run
  stays in-context) rather than being an error.
- When delegation is active and the resolved list contains `claude+human` /
  `human` tasks, the skill says so explicitly before starting — naming the
  task IDs and that they will run in the parent conversation because they need
  the user present — then runs `claude` tasks via agents and the interactive
  ones in-context, each in its original list order.
- An explicitly-requested `[STALE]` task is likewise never delegated: its
  STALE TASKS approval question is asked by the parent, and if the user
  chooses to implement it, that task runs in-context.
- A new supporting file `skills/task-implement/delegated-runs.md` holds the
  delegation protocol, and the SKILL.md read-on-demand table gains a row for
  it whose condition is that delegation is active for a multi-task run. It is
  not read on single-task runs, nor when the user declines.
- `delegated-runs.md` specifies: agents are spawned one at a time and the
  parent waits for each to finish before spawning the next; what the agent
  prompt must carry (the task ID, the repo path, the resolved flags, the
  already-resolved test-runner/testing-policy decision, and the dirty-tree
  decision so the agent does not re-ask); that the agent performs that task's
  full per-task workflow including its own status flips and its own commit and
  push; and that the parent re-reads `.claude/TASKS.md` between tasks to pick
  up the status the agent wrote.
- Failure semantics are preserved: if a delegated task fails, the parent stops
  the whole run and does not spawn the next agent, reporting which tasks
  completed and which never started — the same halt behavior as an in-context
  failure.
- The per-task "Proceed?" confirmation of skip-tests mode is asked by the
  parent before spawning each agent (suppressed when AUTO_CONFIRM is true),
  not by the agent.
- `.claude/domain/task-workflow.md` documents delegated runs under the
  `/task-implement` discipline section: the multi-task-only trigger,
  sequential-not-parallel, the fresh-context rationale, and why interactive
  and stale tasks stay in the parent.
- The skill's frontmatter `description` mentions the capability, its `version`
  is bumped (minor — new behavior), and the root `VERSION` is bumped minor.
- `.claude/context/features.md` reflects the new supporting file and the new
  flags in whatever form it already describes the skill's files.

## Decisions
- Flag pair `--agents` / `--no-agents` rather than prompt-only, so an
  unattended run (`all -y --agents`) never blocks on the question —
  consistent with how `--no-commit`, `--no-push`, and `-y` already pre-answer
  interactive branches.
- Mixed execution rather than refusing delegation outright when the list
  contains interactive tasks: the user gets fresh contexts for the autonomous
  majority without losing the ability to batch, and the skill states which
  tasks run where so the split is never silent.
- Sequential only, with no parallel option offered. The tasks share one
  working tree, one branch, and one `.claude/TASKS.md`; concurrent agents
  would race on status flips, staging, and pushes.
- Each agent owns its own commit and push, keeping "each task gets exactly one
  commit / one push" intact rather than deferring commits to the parent.
- Protocol lives in a supporting file, gated on a multi-task delegated run, so
  single-task runs — the common path — load none of it.
