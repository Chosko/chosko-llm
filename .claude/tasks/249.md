# Task 249 — Reframe `/task-add`'s ownership question as a design-change check and drop the read-only marker

Target: claude

## Goal
The Grant / Reference / Drop question asks about file permissions, and the
answer is always Grant: a Reference lets the document drift, a Drop blinds the
implementer. The question worth asking is whether the user agrees with the
design change the drafted task implies. Replace the question with that, scope
agreement to the design change rather than to enumerated passages, and remove
the read-only marker everywhere it is defined or keyed on.

## Acceptance criteria
- `commands/task-add.md` OWNERSHIP PRE-AUTHORISATION becomes a design-change
  check. Detection (the owner table) and enumeration of points stay. Points
  split in two: a point that *settles* something the document leaves open is
  listed for the record and covered without a question; a point that
  *diverges* from what the document states is a design change and asks, inside
  PHASE 3's single gate: "Task <N> as drafted changes the design at these
  points: <before → after, one line of context each>. Agree?" Zero points
  asks nothing.
- Agreement covers the design change as a whole: the implementer updates every
  passage of the document that states the old design, not only the enumerated
  ones. The body records the agreed change and its date under `## Decisions`
  and the document under `## Hints` as an edit target.
- Disagreement returns to PHASE 2 drafting questions about the task's
  direction; it never produces a documentation setting.
- The literal marker `— read-only reference, do not edit`, the Reference and
  Drop outcomes, the carried-over Reference rule and every hard rule that
  distinguishes a Reference from a grant are removed from `commands/task-add.md`,
  and PHASE 4 feature-case step 2 states only that the feature document is
  named under `## Hints`.
- `skills/task-implement/SKILL.md` no longer keys on the marker; the passage
  that handles an owned document at implementation time reads the task's
  recorded design-change agreement instead.
- `skills/task-engine/references/amend.md` no longer mentions the marker or
  the three answers; an amendment that adds an owned path asks the
  design-change question.
- `skills/pipeline-engine/references/routing.md`: the "Agreement with
  `/task-add`" paragraph and the `/task-add` row describe the design-change
  check.
- `.claude/domain/task-workflow.md`, `.claude/domain/product-workflow.md`,
  `.claude/context/features.md` and `docs/reference.md` describe the check and
  no longer mention the marker.
- `commands/task-add.md` `version:` minor bump; `skills/task-implement` and
  `skills/task-engine` patch bumps; root `VERSION` minor bump; `CHANGELOG.md`
  entry; `./scripts/check-changelog.sh`, `./scripts/check-routing.sh` and
  `./scripts/check-home-paths.sh` silent.

## Decisions
- Ownership guards decisions, not files. The question is reframed rather than
  removed because a divergence the user has not seen is a wrong task, and the
  gate is where that surfaces.
