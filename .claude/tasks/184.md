# Task 184 — Add the single-step amend reference to `runbook-run`

Target: claude

## Goal
Feature `owner-amend-arms` gives each artifact owner a standalone amend file.
The runbook suite's amendable unit is one step of an unfinished runbook, and
there is no rule today for changing one. This task adds
`skills/runbook-run/references/step-amend.md` beside `runbook-schema.md` as the
single authority for striking a step, inserting one, and adding facts to a
step's `Context:` — without inventing a marker, a status or a second insertion
mechanism.

## Acceptance criteria
- `skills/runbook-run/references/step-amend.md` exists beside
  `runbook-schema.md` and `subagent-contract.md`, and is complete on its own: it
  names its inputs, its single gate, exactly what it writes and its closing
  report line.
- **Strike.** A struck step is marked `[x]` and carries a `Done:` line opening
  `struck — <reason>`, with no commit sha. It keeps its number and its prompt
  block, and is never deleted; steps are never renumbered, because a
  `Depends on:` line elsewhere may point at the struck step's number.
- **Insert.** Inserting a step is the positional append that task 173 adds to
  `/runbook-create --append` (`--before N` / `--after N`). This file cites that
  command and describes no second insertion mechanism of its own.
- **Context.** A step's `Context:` may gain dated fact bullets. It is the only
  field an amendment adds to.
- **Immutable prompt.** The prompt block is never edited — the existing rule in
  `runbook-schema.md`, cited and not restated. The named consequence is stated:
  a step whose prompt is wrong is struck and a corrected step inserted.
- A `[RUNNING]` runbook accepts inserts after the current step and nothing
  before it. A step already `[x]` or `[!]` is never edited, and an existing
  `Done:` line is never rewritten.
- No new step marker and no new status value is introduced;
  `runbook-schema.md`'s four markers and four statuses stand unchanged.
- `skills/runbook-run/SKILL.md`'s `description:` is updated — it currently says
  the folder carries "the two files the rest of the runbook suite reads by path"
  — and the install-path assumption note names the third file.
- `skills/runbook-run/SKILL.md`'s `version:` is bumped (minor), root `VERSION`
  is bumped, `CHANGELOG.md` gains a matching top section, and
  `./scripts/check-changelog.sh` is silent.

## Decisions
- **A struck step is `[x]` with `Done: struck — <reason>` and no commit sha**
  (user decision, 2026-09-09). `owner-amend-arms.md` § Data and state requires
  the existing marker vocabulary, and `[x]` is the only one of the four that
  works: `/runbook-run`'s selection already skips ticked steps, so a struck step
  is passed over with no special case, and the runbook can still reach `[DONE]`
  when every step is `[x]`. `[!]` was rejected — it means *failed*, halts the
  run and drives `.claude/RUNBOOKS.md` to `[FAILED]`, and a strike is a decision,
  not a failure. A fifth marker was rejected by the feature document itself.
  The `Done:` line is already the schema's place for what happened and why, so
  the reason needs no new field.
- **Insert is delegated, never reimplemented.** `/runbook-create --append` is
  the runbook suite's only step writer; a second insertion path in this file
  would be exactly the drifting copy the reference layer exists to prevent.
  That is why `Preconditions:` is 173.
- **The file lives in `runbook-run/references/`, not in `/runbook-create`'s
  body.** `runbook-create`'s body is authoring rules with one consumer; this is
  a rule several features read by path, which is what the references folder is
  for.
