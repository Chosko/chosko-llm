# Task 56 — Wire /domain-setup into the /project-setup wizard

Target: claude

## Goal
`/project-setup` is the single entry point for initializing a project and already gathers a
choice then delegates to `/task-setup` and `/context-build`. Now that the domain knowledge
layer is structural, the wizard must offer it too — otherwise every new project still
starts without one and the product pipeline has nowhere to write.

## Acceptance criteria
- PHASE 1 (GATHER) gains a domain-layer step beside `### 1d. Task backlog` and
  `### 1e. Context layer`, asking whether to initialize it and explaining in one line what
  it is and which commands depend on it. Defaults to yes.
- The step detects an existing `.claude/domain/` and offers "index the docs you already
  have" rather than a blank initialization.
- PHASE 2 (CONFIRM) includes the choice in the single approval plan.
- PHASE 3 (EXECUTE) invokes `/domain-setup` after the task-backlog step and BEFORE
  `/context-build`.
- Commit delegation matches the existing pattern exactly: `/domain-setup` invoked without
  `--commit` by default (output left for the user's single review pass), and with
  `--commit` under `/project-setup --commit`.
- The wizard holds no domain-layer logic of its own — it asks and delegates, the same
  contract it has with `/unity-mcp-setup`.
- The Final report mentions the domain layer when initialized.
- `.claude/context/features.md`'s project-setup entry reflects the new step and its
  position in the execution order.
- Root `VERSION` bumped (minor).

## Decisions
- `/domain-setup` runs BEFORE `/context-build`, unlike `/unity-mcp-setup` which runs after.
  `/context-build` emits DOMAIN DEPENDENCIES sections linking to domain files, so the
  domain index should exist when it runs; `/unity-mcp-setup` is last precisely because it
  needs a freshly-built context layer. Opposite ordering, opposite reason.
- No new flag — the domain layer is a gathered yes/no like the backlog and context layer.
