# Task 128 — Migrate /task-clean onto the task-engine

Target: claude

## Goal

Step 4 of the `shared-phase-engine` migration order, first of the three
remaining consumers. `/task-clean` (295 lines) is the first migration of a
feature that **writes** — it prunes summary blocks and body files, and commits
and pushes — so it is the first consumer to cite `commit.md`, and the first
chance to confirm the extracted commit-gating rule reads correctly from the
consuming side. Replace its restated rules with engine references and change
nothing a user can observe.

## Acceptance criteria

- `commands/task-clean.md`'s frontmatter carries `requires: skill:task-engine`.
- Its restatements are replaced by references of the form
  `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/references/<file>.md`,
  each followed only by what `/task-clean` does differently:
  `resolution.md` for backlog location and parsing, `status.md` for the status
  vocabulary, `stale.md` for what `[STALE]` means, and `commit.md` for the
  `--no-commit` / `--no-push` gating and the push protocol.
- Everything unique to `/task-clean` stays: which statuses are **terminal**
  (`[DONE]` and `[SKIP]` only) and the standing rule that `[STALE]` is live work
  awaiting reconciliation and is never pruned by default; that survivors are
  never renumbered and `Last task number` is never decremented; the plan-and-
  confirm gate before any write; and the `.claude/FEATURES.md` `Tasks:` line
  pruning that keeps `/architect`'s iterate guard off dead IDs.
- **Observable behaviour is unchanged**: same usage lines and examples, same
  confirmation prompt and plan output, same commit message, same `--no-commit` /
  `--no-push` semantics, same FEATURES.md side effect.
- Verification is a before/after comparison of a dry run: invoke `/task-clean`
  with no argument against this repo's backlog before and after, and confirm the
  proposed plan it prints for confirmation is identical. Do not confirm the
  prune.
- The body is under 150 lines, with the same caveat as task 127: the criterion
  is that no rule the engine owns is restated here.
- `commands/task-clean.md` takes a minor frontmatter `version:` bump (expected
  `0.7.0` → `0.8.0`); root `VERSION` takes a patch bump, relative to whatever
  task 127 leaves in place.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  131 owns both knowledge layers.

## Decisions

- **First writing consumer, so `commit.md` gets its first real reader here.**
  If the extracted commit-gating text turns out to be unusable by reference —
  because it was written as one command's prose rather than as a shared rule —
  that is a bug in task 126's extraction, and the fix belongs in
  `commit.md`, not in a `/task-clean`-local restatement. Say so if it happens
  rather than working around it.
- **`tree.md` is not cited.** `/task-clean` has no dirty-tree protocol of its
  own; it plans, confirms, writes and commits. Citing an engine file a command
  does not use would be as wrong as restating one it does.
- **Same bump reasoning as task 127** — minor on the feature for the new
  install-time dependency, patch on root `VERSION` for a behaviour-preserving
  restructure.
