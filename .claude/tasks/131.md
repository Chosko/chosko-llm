# Task 131 — Update documentation for feature shared-phase-engine

Target: claude

## Goal

Tasks 125-130 ship the `shared-phase-engine` feature: a new `requires:`
frontmatter field with install-time resolution, a new `task-engine` skill, and
four `task-*` features restructured onto it. Every layer that describes this
area still describes the world before it — the README's install section, the
authoring guide's standing prohibition on extracting shared files between
skills, both context files for `cmd-add` and `cmd-rm`, the shared-library
context file's five-key frontmatter list, the shipped-artifact inventory, and
the domain layer's task workflow — and the feature document itself carries three
statements that turned out to be wrong plus open questions the implementation
settled. Bring the documentation in line with what shipped.

## Acceptance criteria

- `README.md`'s "Installing and removing" section states that `add` installs a
  feature's declared requirements first, and that `rm` refuses to remove a
  feature something installed still requires unless `--force` is passed. Its
  "Feature names" / authoring material mentions `requires:` alongside the other
  optional frontmatter keys, and its "Work through a backlog — the `task-*`
  commands" section notes that installing any `task-*` feature also installs
  `skill:task-engine`.
- `docs/authoring-guide.md`'s "Keeping the two `council-gate.md` copies in step"
  section is **qualified, not deleted**. Its blanket rule — that a shared file
  outside a skill folder is always wrong because it would be absent on installed
  machines — is now conditional: with `requires:`, a shared file that lives in
  its own installable skill is safe, because the dependency is installed with
  its dependent. The council-gate case still stands and the section says why it
  is different: that gate must keep working when `claude-council` is **absent**,
  which is an optional dependency, and `requires:` expresses only mandatory ones.
  `skills/task-engine/` is named as the worked example of the new pattern.
- The authoring guide's "Authoring a skill" section notes that a skill may be a
  non-invocable reference library consumed through `requires:`, with
  `task-engine` as the example, including the `description`-says-so convention
  that keeps it out of skill suggestions.
- `.claude/context/shared-lib.md` is corrected: `parse_frontmatter`'s recognised
  keys are six, not five, and its "Internal patterns" note about the cost of
  adding a field is updated to reflect that `requires` has now been added. Its
  "When to read the source" rows cover the new field.
- `.claude/context/cmd-add.md` describes the dependency-install step: where it
  sits relative to validation and copy, the one-level-deep limit, the
  already-installed and missing-from-clone cases, scope inheritance, and why
  `--all` needs nothing.
- `.claude/context/cmd-rm.md` describes the dependents guard, `--force`, the
  claude-md scan asymmetry (an injected section carries no frontmatter, so the
  managed-clone source is read instead), and the fact that `uninstall.sh` is
  unaffected because it never calls `cmd-rm`.
- `.claude/context/features.md` gains an entry for `skills/task-engine/` in the
  same register as the surrounding entries — the six reference files and what
  each owns, that `SKILL.md` is a map and not a rule holder, and that it is not
  user-invocable. The `task-list`, `task-clean`, `task-add` and `task-implement`
  entries note that they now reference the engine and declare `requires:`, and
  the frontmatter-contract paragraph lists `requires:` among the optional keys
  beside `replaces:` and the hook-only `event:` / `matcher:`.
- `.claude/context/INDEX.md`'s `Last updated` anchor is current. No new context
  file is created: `task-engine` is a shipped artifact and `features.md` is
  where shipped artifacts are covered.
- `.claude/domain/task-workflow.md` records the one-authority-per-rule model in
  its own compressed register: which rules the engine owns, that a consumer
  states only its own deviations, why the engine had to be a skill rather than a
  command (`cp -R` of a folder versus a single file), and that `requires:` is
  flat, one level deep and non-transitive by design.
- `.claude/domain/features/shared-phase-engine.md` is reconciled with what
  shipped on exactly these five points — editing it is authorised for this task,
  see Decisions:
  1. The `### The requires: field` claim that `parse_frontmatter` "needs no
     change at all" is corrected: the parser splits on the first colon
     generically so the **value** survives intact, but its recognised-key
     allowlist had to gain `requires` — one condition, no parser rewrite.
  2. The "Scope and non-goals" paragraph says "the `cmd-add` / `cmd-update`
     change"; the Architecture section, the CLI contract and the feature's own
     title all say `cmd-add` / `cmd-rm`. Corrected to `cmd-add` / `cmd-rm`.
  3. The "Purpose" paragraph still counts `task-enrich` among the bodies and
     says the material is "stated five times". Corrected to the four surviving
     consumers, with real line counts.
  4. The open questions the implementation settled are recorded as resolved
     rather than left open: `cmd-add --all` needs no dependency handling, and
     why; and what was actually observed about a non-invocable skill surfacing
     in skill selection. The granularity question and the authoring-time
     validation question stay open — nothing decided them.
  5. The "Rough targets, to be confirmed as the extraction proceeds" line-count
     figures are replaced with what the migration actually achieved.
  Nothing else in the document changes.
- Root `VERSION` takes a patch bump.
- `docs/cli-help.txt` is not edited here: task 125 already updated its `add` and
  `rm` entries as part of the CLI change, and it never enumerates individual
  skills.
- No shipped feature body under `commands/` or `skills/` is edited here — tasks
  125-130 own those, and any needed change there is a bug in one of them, not
  this task.

## Decisions

- **Editing `.claude/domain/features/shared-phase-engine.md` is explicitly
  authorised for this task (user decision, 2026-08-24), for the five
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document is
  normally `/architect`'s, and anything beyond those five points still belongs
  to `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- **The council-gate prohibition is qualified rather than removed.** It is the
  single most load-bearing "don't do this" in the authoring guide, and this
  feature does the thing it forbids — safely, because `requires:` did not exist
  when it was written. Leaving it unqualified teaches the opposite of what
  shipped; deleting it would license the genuinely broken version of the same
  idea for optional dependencies like the council gate.
- **The `requires:` field's own reference documentation is not here.** Task 125
  lands it in `docs/authoring-guide.md` beside `replaces:` and in
  `docs/cli-help.txt`, because tasks 126-130 all author against that contract
  and would otherwise be writing an undocumented field. This task covers
  everything downstream of it.
- **Patch bump, not minor.** Documentation-only; no shipped feature's behaviour
  changes in this task.
