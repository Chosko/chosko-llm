# Task 114 — Add milestone grouping to /task-list

Target: claude

## Goal
Extend the shipped `/task-list` command so the backlog can be read through
the plan, from feature `plan-readout`. When `.claude/PLAN.md` exists, tasks
group by milestone — resolving each task's `Feature:` line through the plan —
and tasks whose feature is blocked carry a flag naming the blocker. With no
`PLAN.md`, output is byte-for-byte what it is today: a silent no-op, not a
warning.

## Acceptance criteria
- With no `.claude/PLAN.md`, output is unchanged in every respect — same
  lines, same order, same summary, and no message about a missing plan.
- With a `PLAN.md`, tasks group under milestone headings in plan order. Each
  task's `Feature:` slug is resolved through the plan's `Features:` lists to
  find its milestone.
- Tasks with no `Feature:` line — every free-form task — group under a
  trailing unplanned heading. A `Feature:` line naming a slug absent from the
  plan groups there too.
- A task whose feature is blocked carries a flag naming the blocker,
  alongside the existing `⚠ <target>`, `[<slug>]` and `⚠ stale` markers.
  Marker order is defined explicitly in the command body so lines stay
  scannable.
- Blocked-ness uses the same rule as `/production-status`: a feature is
  blocked when some dependency edge pointing at it originates from a feature
  that is not `[PLANNED]` with all tasks `[DONE]` or `[SKIP]`.
- The existing status filter keeps working, and works within groups.
- The command stays read-only and still opens no file under `.claude/tasks/`.
  It now reads `.claude/PLAN.md` and `.claude/FEATURES.md` in addition to
  `.claude/TASKS.md`, all read-only.
- `commands/task-list.md` frontmatter `version` bumped `0.4.0` → `0.5.0`
  (new behavior), and its `description` updated to mention milestone
  grouping.
- Root `VERSION` bumped minor.

## Decisions
- **Grouping is silent without a plan.** Explicit in the feature's non-goals:
  no behaviour change whatsoever on projects with no plan, including no
  warning — most projects using `/task-list` have no roadmap.
- **The blocker flag duplicates `/production-status` rather than defers to
  it.** The two commands share the readiness rule but not an implementation;
  these are markdown prompts, and a shared file for one paragraph of logic
  costs more than it saves.
- **`/task-list` stays a separate command.** The feature document leaves
  merging it with `/production-status` open; keeping them separate is the
  recorded default — one reports features, the other reports tasks.
- **Minor bump, not major.** The default no-plan path is byte-identical, so
  nothing existing breaks.

## Hints
- `commands/task-list.md` — the file to change.
- `VERSION` — minor bump.
- `.claude/domain/features/plan-readout.md` — the originating feature

- `.claude/domain/features/production-plan.md` — the `PLAN.md` schema being
  read.
- `.claude/domain/task-workflow.md` — the `Feature:` line's meaning and the
  `[STALE]` marker this sits beside.
- `.claude/context/features.md` — the entry describing `commands/task-list.md`
  and its current marker set.
