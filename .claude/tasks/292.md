# Task 292 — Add --parallel <N|max> to /task-implement with the scheduler, barriers and landing

Target: claude

## Goal
Give `/task-implement` the `--parallel <N|max>` flag of feature
`parallel-task-runs`: a delegated run that keeps up to N tasks in flight at
once — every eligible task under `max` — each in its own worktree per
`task-engine`'s `worktree.md`, scheduled by `Preconditions:` and landed one
at a time as the agents return. The launcher stays a launcher: it reads no
body, hands each agent the same fixed-size prompt with two more values, and
does its between-tasks bookkeeping on the base after every landing. Without
the flag nothing changes.

## Acceptance criteria
- ARGUMENT PARSING accepts `--parallel <N>` with N ≥ 2 and `--parallel max`
  (case-insensitive), sets PARALLEL in the run's resolved flags and implies
  `--agents` so the delegation question is not asked. It refuses, each with
  one line: `--no-agents` beside it; `--no-commit` beside it; a project whose
  `CLAUDE.md` maps git to another VCS; and N below 2. A run resolving to a
  single task takes the flag as a silent no-op. Every other flag composes
  and rides through the agent prompt unchanged.
- `delegated-runs.md` gains the scheduling loop under PARALLEL: `all` is
  still resolved once up front and its report and delegation count printed
  from that list; the list is then the admissible set, its order the
  priority. At every scheduling point — run start and each landing — the
  launcher re-reads the base `TASKS.md`, re-derives eligibility with
  `resolution.md`'s clause, and starts tasks in list order while fewer than
  N are in flight (no bound under `max`), skipping a task that is not
  eligible on this read, is in flight, or whose worktree already exists
  (the skip-while-present line of `worktree.md`); a skipped task is
  re-examined at the next scheduling point. The run ends when nothing is in
  flight and nothing in the list can start. An explicit-list task whose
  precondition is in flight waits for it to land.
- `resolution.md` § *Eligibility* states, as one added clause cited by
  `/task-implement` and later by `/runbook-run`, that under a parallelism
  above one a unit in flight is neither done nor eligible: its `Preconditions:`
  dependents wait for it to land, since landing is what writes the status
  the next read sees. The between-tasks precondition re-check is stated as
  subsumed by the per-read derivation under PARALLEL.
- Each delegated task is spawned in a worktree per `worktree.md`: the
  launcher creates it immediately before the spawn, and the agent prompt
  carries PARALLEL and the worktree path as the repository root — two
  run-level values, the prompt still O(1) in the batch. The agent's own
  flow is unchanged apart from what `worktree.md` says about its Step 7.
- Each return is landed per `worktree.md` § *The orchestrator lands* —
  fast-forward only, one rebase-again message to the same agent when the
  base moved, push unless NO_PUSH, worktree removed and `wt/task-<N>`
  safely deleted — and then the existing between-tasks steps run on the
  base unchanged: `TASKS.md` re-read, status confirmed, feature-completion
  check, chat replies by `P<n>` handle, progress line. Returns are handled
  one at a time in arrival order; a relayed question from one agent does
  not stop another agent's landing. After each relay the launcher prints one
  line naming the agents still waiting on the user.
- Parent-kept tasks (`human`, `claude+human`, explicitly requested
  `[STALE]`) are barriers: when the next task in list order is parent-kept
  the launcher starts nothing more, waits for every task in flight to land,
  runs it in the base tree as an in-context run does, then resumes
  spawning.
- A delegated failure spawns nothing more; tasks already in flight land;
  the closing report names completed, failed and never-started tasks as
  today, a failed task's row naming its worktree path.
- The progress line names what is in flight: `Task 20 landed (abc1234). In
  flight: 22, 23. Starting task 24.` The six-field return contract, the
  batched feature-completion proposal and the two-group closing report are
  unchanged.
- The `/task-implement` routing row in `pipeline-engine`'s `routing.md`
  lists the flag, the worktrees it writes and the new refusals;
  `./scripts/check-routing.sh` and `./scripts/check-home-paths.sh` pass.
- `task-implement`'s `version:` is bumped (minor); root `VERSION` is bumped
  (minor) with a matching `CHANGELOG.md` section; `./scripts/check-changelog.sh`
  passes.

## Decisions
- The `Files:` overlap rule and its `CLAUDE.md` marker are task 293: the
  scheduler must be correct without them, since they are a safety net under
  the backlog's own declaration of independence, and the marker is a separate
  project contract worth its own diff.
- `resolution.md` gains the in-flight reading as one clause in
  § *Eligibility* rather than a new section: it is the same clause with one
  more condition, and `parallel-runbooks` will cite the same sentence for
  steps.
- Settled here, without conflict with the feature document: under
  `attended`, two agents may ask at once; each relay block already carries
  its task heading and the answer goes back by agent id, and the launcher
  prints one line naming the agents still waiting after each relay — the
  readability call the document leaves to implementation.
