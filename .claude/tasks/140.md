# Task 140 — Add the /runbook-run skill with the schema and subagent-contract references

Target: claude

## Goal

First artifact of the `runbook-suite` feature
(`.claude/domain/features/runbook-suite.md`), and the one the whole suite hangs
off. Ship `skills/runbook-run/` — the orchestrator that walks a runbook top to
bottom, spawning one subagent per step, relaying that subagent's questions to
the user and the answers back to the same subagent, recording what each step
actually did, and committing after every step — together with the two reference
files the rest of the suite cites by installed path. It ships first because
three of the other four artifacts read files inside this folder and the fourth
proposes a command that does.

## Acceptance criteria

- `skills/runbook-run/SKILL.md` exists with full frontmatter: `name:
  runbook-run`, `version: 0.1.0`, `type: skill`, and a `description` naming the
  orchestration job and its arguments. It declares **no** `requires:` — it is
  the dependency.
- Exactly two files under `skills/runbook-run/references/`:
  `runbook-schema.md` and `subagent-contract.md`. No third reference file — the
  prompt-quality rules have one consumer and stay in `/runbook-create`'s body
  (task 141).
- `references/runbook-schema.md` is the single authority for the asset kind and
  covers, and only covers:
  - **The store** — `.claude/runbooks/<name>.md` plus the `.claude/RUNBOOKS.md`
    index, both committed; `<name>` kebab-case and the identifier; created on
    first use.
  - **The body schema** — the header (`Created:` / `Source:` / `Model:` /
    `Sequencing:`, plus optional `Companion:`), `## [ ] <n>. <title>` steps each
    carrying `Depends on:`, `Context:` and one fenced ```prompt``` block, and the
    optional trailing `## Do not re-propose` section that is global to the
    runbook and appended to every spawned prompt.
  - **The four step markers** — `[ ]` pending, `[~]` in progress, `[x]` done,
    `[!]` failed — and the `Done:` line, which does not exist until a run writes
    it and records the commit sha, the decisions taken while executing, and any
    premise in the step that proved wrong.
  - **The four-status vocabulary** — `[PENDING]`, `[RUNNING]`, `[FAILED]`,
    `[DONE]` — with who writes each, and the note that it is deliberately
    distinct from `TASKS.md`'s and `FEATURES.md`'s vocabularies so a grep never
    confuses them.
  - **The index block** — `Status:` / `File:` / `Created:` / `Source:` /
    `Steps:`, where `Steps:` is `<done>/<total>` and done counts `[x]` only,
    plus the fifth line `Failed at: step <n> — <reason>` present only while the
    status is `[FAILED]` and removed when a re-run clears it. The index is a
    summary and holds nothing that is not derivable from the body.
- The schema file records the two deliberate absences with their reasons, so a
  later reader does not re-add them: there is no `[SKIP]` status (a runbook is
  authored complete; an unwanted step is deleted before the run, not carried as
  a tombstone), and no per-step `Produces:` field (the result classification is
  already unambiguous without it, and a field the author must predict correctly
  is a field that will be wrong).
- `references/subagent-contract.md` holds the OPERATING RULES block as fixed
  text, written to be pasted verbatim into a spawned prompt. It tells the
  subagent: that it cannot talk to the user; that at any clarifying question or
  approval gate it must stop and end its turn with `QUESTIONS FOR USER`
  followed by the questions, the options, and a recommendation for each — and,
  at an approval gate, the full draft; that it must follow the default commit
  behaviour of whatever skill it invokes and add no flag the user did not type;
  that it must never edit the runbook or the index; which runbook and step it is
  executing; and that it must end with `DONE` and a concise report naming the
  commit sha, the decisions taken, and any premise in the prompt that proved
  wrong.
- `SKILL.md` carries the execution loop as eight numbered steps — resolve,
  re-read the body, select, mark, spawn, wait, handle the result, commit and
  loop — with these behaviours stated:
  - **Resolve.** An unknown name reports the available ones. A `[DONE]` runbook
    with no `--only` / `--from` says so and stops rather than doing nothing
    quietly.
  - **Re-read the body at the start of every step**, not once per run, and the
    body says why: it reconciles a body edited by hand between steps, and it is
    what makes steps appended mid-run by `/runbook-create --append` visible to
    the run already in progress. There is no separate reconciliation mechanism
    because this one is free.
  - **Select** the first step whose marker is `[ ]`, `[~]` or `[!]` and whose
    every `Depends on:` step is `[x]`. A `[~]` step is reported as one a
    previous run was interrupted in and re-run; a `[!]` step is re-run with its
    failure already recorded in `Context:` by the run that failed. Steps
    remaining with none selectable is a dependency deadlock: report the blocked
    steps and their unmet dependencies, and stop.
  - **Mark** the step `[~]` and the index `[RUNNING]`.
  - **Spawn** one subagent with fresh context, the assembled prompt, and the
    model from the header (`--model` overrides for the whole run).
  - **Wait.** The body calls this out as the single most dangerous point in the
    feature: a spawn returns an id and the result arrives later as a separate
    notification, so a body that treats the spawn's return value as the result
    ticks a step that never ran and commits the lie. No step is ticked before
    its subagent's result has actually arrived.
  - **Commit** the runbook and the index, then loop back to the re-read. When no
    `[ ]` steps remain, set the index `[DONE]` and report.
- The spawned prompt is assembled in this fixed order, stated in the body:
  preamble (orient in a fresh session — read the project's `CLAUDE.md` and
  follow its navigation instructions, including both navigation layers where
  they exist — and name the runbook and step this agent is executing, which is
  what lets a step's subagent use `/runbook-create --append` with no name), then
  the `Companion:` document if the header names one, then `## Do not
  re-propose` if present, then the step's `Context:` bullets, then the fenced
  prompt block **verbatim** — never paraphrased, trimmed, or merged with the
  surrounding material — then the OPERATING RULES from
  `references/subagent-contract.md`, last, so they are the final thing the agent
  reads.
- The three result cases are handled exactly as the design specifies:
  `QUESTIONS FOR USER` → relay, collect the answer, send it to the same
  subagent, repeat; `DONE` + report → mark `[x]`, write `Done:`, propagate
  facts, update `Steps:`, commit, continue; anything else or a report of failure
  → mark `[!]`, write `Done:` opening with the reason, set the index `[FAILED]`
  with `Failed at:`, halt and report. **An ambiguous report is a failure, not a
  success**, and the body says why: the alternative is ticking a step on a
  guess, and the whole value of the `Done:` line is that it is true.
- The question relay is rendered as one fixed block — step `n` of `N`, the step
  title, the round number, the question in one or two lines, lettered options
  each with what it costs, and a one-line recommendation. At an approval gate
  the full draft follows the block verbatim and unabridged, and the body names
  this as the one place the orchestrator must not compress, since a summarized
  draft cannot be approved. The answer is relayed to the **same** subagent,
  whose context is intact, for as many rounds as it takes.
- The orchestrator compresses, it does not answer. It may add facts it already
  holds — a `Done:` line from an earlier step that answers the question — and
  must say that it is doing so; it may never invent a decision on the user's
  behalf, and it never asks the user to re-state something an earlier step
  already settled.
- **Fact propagation**: when a step's report changes a fact a later step relies
  on, a dated bullet naming the correction is appended to that step's
  `Context:`. The prompt block itself is never edited — a reader must always be
  able to see what was originally asked and what was learned since, separately.
- **One run per runbook.** `[RUNNING]` in the index blocks a second
  `/runbook-run` of that name, which reports it as already running and stops.
  The single exception is a `[~]` marker present in the working tree, which
  means this tree is the one that was interrupted. `[RUNNING]` in the index plus
  `[~]` in the tree is the whole resume signal: no staleness heuristic, no
  timestamp, no lock file.
- **Nested runbooks are refused at spawn time**: a step whose prompt invokes
  `/runbook-run` is refused, with the depth-budget reason given, so a
  hand-written runbook cannot smuggle one in.
- **The depth budget is stated plainly**: the orchestrator occupies one level
  and the step's agent a second, leaving one confirmed level (nesting to depth 3
  verified 2026-08-24). A step whose prompt itself spawns subagents — e.g.
  `/task-implement --review`, which wants an implementor and then a reviewer —
  would need depth 4, which has not been probed. Nothing refuses it; the body
  warns so an author who writes such a step knows they are past verified ground.
- Arguments: `<name>`, `--from N`, `--only N`, `--model <model>`,
  `--no-commit`, `--no-push`. `--from` and `--only` **do not weaken
  dependencies**: a selected step whose `Depends on:` are not all `[x]` stops
  the run with the unmet dependency named, and the body says the remedy is
  marking that step `[x]` by hand — a visible, committed act rather than a
  silent flag.
- **The orchestrator writes exactly two files**, the runbook and the index, and
  the body says so as a hard contract: every other change in the tree is made by
  a subagent. It reads `QUESTIONS FOR USER` and `DONE` and does not review,
  re-test, or second-guess a subagent's commit — review is `/task-review`'s job
  and is invoked, when wanted, from inside a step's prompt.
- Commit cadence: one commit per completed step, staging exactly the runbook and
  the index and never a catch-all, then a push, following
  `docs/authoring-guide.md`'s commit-and-push protocol by name.
  `--no-commit` / `--no-push` carry their usual meaning. The `[~]` marker is
  never committed — it is in-run working state and the resume signal.
- Every path the skill names uses the `${CLAUDE_HOME:-$HOME/.claude}` form,
  never `~/.claude`, and no path under `docs/` appears anywhere in the shipped
  bodies — `docs/` is authoring-time-only and is never installed.
- **This task creates no `.claude/runbooks/` directory and no
  `.claude/RUNBOOKS.md` in this repo.** The store is created on first use by
  `/runbook-create` (task 141).
- No `chosko-llm` subcommand is taught about runbooks, and nothing under
  `scripts/` or `bin/` changes: runbooks are input to agents, never to tooling,
  and the rule that the filesystem plus frontmatter is the CLI's only state is
  unchanged.
- Root `VERSION` takes a minor bump (new shipped skill), relative to whatever is
  in place when this lands.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  145 owns both knowledge layers.
- No test suite by design: verify by reading the diff and confirming
  `./bin/chosko-llm ls --available` lists `runbook-run  skill  —  0.1.0`
  against a clone where `install.sh` has run.

## Decisions

- **Preconditioned on 125.** The feature document's Dependencies section is
  explicit that every task derived from this feature preconditions on the
  `requires:` field, and this task is the target four other artifacts point at.
  Landing the suite before the field exists means a command can be installed
  citing a schema file that is not there.
- **The skill and both reference files are one task.** `cmd-add` installs a
  skill by `cp -R` of the whole folder and refuses a folder with no versioned
  `SKILL.md`, so a half-populated folder is not installable and therefore not
  independently verifiable. The reference files also have no consumer until task
  141.
- **Two reference files, not three.** The prompt-quality rules have exactly one
  consumer, and a shared file with one consumer is indirection without benefit.
- **The shared files live in a skill because a command can carry nothing.** A
  command is a single `.md` file; a skill folder ships every file beside
  `SKILL.md`. `runbook-run` is the natural host because it is also the artifact
  everything else depends on.
- **The orchestrator's relay when it is itself a subagent.** The design permits
  `/runbook-run` to run as a subagent (that is what allows a runbook to be
  driven from a batch parent) but does not say how the relay works when there is
  no user to ask. Resolution: it emits the same fixed relay block as its own
  final turn, under a `QUESTIONS FOR USER` heading, for its parent to carry, and
  resumes when the answer comes back. It never answers on the user's behalf in
  either position. Task 145 reconciles the feature document on this point.
- **`.claude/runbooks/implement-ecc-import.md` (with its `.claude/RUNBOOKS.md`
  block) is a shape to imitate, not a dependency.** It is the hand-written
  runbook this feature generalises, authored 2026-08-24 to the schema in the
  feature document before any runbook artifact shipped. Read it while authoring
  the schema and the contract; do not edit it, do not treat it as generated
  output, and make nothing in the shipped bodies read it at run time.
- **Nothing in this suite couples to `/architect`, `/product-design` or
  `/product-roadmap`,** and none of them learn about runbooks. Where a runbook's
  prompts came from is provenance, not structure.
