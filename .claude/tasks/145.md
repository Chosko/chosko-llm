# Task 145 — Update documentation for feature runbook-suite

Target: claude

## Goal

Tasks 140-144 ship the five artifacts of the `runbook-suite` feature — the
`/runbook-run` orchestrator with its two reference files, `/runbook-create`,
`/runbook-list`, `/runbook-clean` and `/runbook-suggest` — and add a whole new
asset kind, `.claude/runbooks/` plus `.claude/RUNBOOKS.md`, that none of the
documentation layers mention. Bring the layers back in line with what actually
shipped, and reconcile the feature document on the two points where
implementation departed from its design.

## Acceptance criteria

- `README.md` gains a subsection under "Claude Code Workflows" covering the
  suite: what a runbook is (an ordered list of self-contained prompts, each
  written for a fresh agent that has none of the conversation the prompts came
  out of), the committed store, the five artifacts and what each is for, the
  execution loop in brief (one subagent per step, sequential always, the
  question relay, one commit per step), and the authoring rules that make a
  prompt survive a fresh session. Placed alongside the other workflow families
  and matching their depth and voice.
- `.claude/context/features.md` gains a "Currently shipped" entry for each of
  the five artifacts, in the terse register that file uses, each covering: kind
  (command vs. skill) and why; its `requires:` edge and the reason for it; its
  commit convention (`/runbook-create` authoring-style, `/runbook-clean`
  cleanup-style, `/runbook-run` one commit per completed step, `/runbook-list`
  and `/runbook-suggest` writing nothing); and the hard contracts — the
  orchestrator writes exactly two files, steps are always sequential, no step is
  ticked before its subagent's result arrives, no step invokes `/runbook-run`,
  and no `chosko-llm` subcommand reads `.claude/runbooks/`.
- `docs/authoring-guide.md` § "State that outlives a session belongs in a
  project document" gains a cross-reference noting that
  `.claude/runbooks/<name>.md` plus `.claude/RUNBOOKS.md` are exactly such a
  store, with the body as source of truth and the index derived from it.
- `.claude/domain/features/runbook-suite.md` is reconciled on the points listed
  under Decisions, and only those.
- `.claude/context/INDEX.md` is deliberately NOT changed — no new context file is
  created, and shipped features are covered by `features.md`.
- `docs/cli-help.txt` is deliberately NOT changed — it documents the
  `chosko-llm` CLI and carries no slash commands, and no subcommand learned
  about runbooks.
- `.claude/domain/task-workflow.md` and `.claude/domain/product-workflow.md` are
  deliberately NOT changed — a runbook is not a task and not a pipeline stage,
  and nothing in this suite couples to `/architect`, `/product-design` or
  `/product-roadmap`.
- `.claude/domain/INDEX.md` is deliberately NOT changed — its
  `features/runbook-suite.md` row already exists and stays accurate.
- `CLAUDE.md` is deliberately NOT changed — its "Authoritative references" list
  points at `.claude/domain/*.md` workflow documents, and this feature has none:
  its authority is the feature document, already indexed in the domain index.
- Root `VERSION` takes a patch bump (documentation only), relative to whatever
  is in place when this lands.

## Decisions

- **Editing `.claude/domain/features/runbook-suite.md` is explicitly authorised
  for this task, user decision 2026-08-24, for the listed reconciliations only;
  do not ask at implementation time.** The file is normally owned by
  `/architect` and read-only to `/task-add`. The reconciliations are:
  1. **`/runbook-suggest`'s suggestion is generic.** The document's
     `### /runbook-suggest — the trigger` section says the skill emits its line
     "mentioning `--append <name>` when `RUNBOOKS.md` lists non-`[DONE]`
     runbooks, and naming the current runbook if one is running". Correct that
     to what shipped (task 144): the skill reads no file, looks at no index,
     names no runbook, and says nothing about whether one is running — it
     suggests `/runbook-create` to turn the follow-ups into a new runbook or
     append them to an existing one, and stops. New-versus-append is asked
     entirely by `/runbook-create`'s no-argument gate. The section's closing
     "It reads no file, writes no file, proposes once, and never creates a
     runbook itself" is correct as written and stays.
  2. **The question relay when the orchestrator is itself a subagent.** The
     Dependencies section permits depth 3 explicitly — "the orchestrator may
     itself be a subagent, which is what allows a runbook to be driven from a
     batch parent" — but the relay is specified only for an orchestrator that
     can address the user. Record that in the subagent position it emits the
     same fixed relay block as its own final turn, under a `QUESTIONS FOR USER`
     heading, for its parent to carry, and resumes when the answer comes back;
     it never answers on the user's behalf in either position.
  3. **The `VERSION` line.** The closing line of `## Interfaces and contracts`
     says "Root `VERSION` takes a minor bump". The suite lands over five
     shipped-feature tasks, each taking its own minor bump relative to whatever
     is in place when it lands, plus a patch bump for this documentation task.
     Record the per-task rule.
  None of these re-opens a settled question: `## Open questions` stays "None
  outstanding" and keeps its existing text.
- **The deliberately-unchanged files are named rather than silently omitted**,
  so a later reader does not treat their absence as an oversight.
- **No new domain document and no new context file.** The feature document is
  the authority for the asset kind and is already indexed; `features.md` is
  where shipped artifacts are described. A third home for the same material is
  the copy that drifts.
