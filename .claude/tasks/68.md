# Task 68 — Author the shared commit-then-push protocol and update the authoring guide's commit-control convention

Target: claude

## Goal
Every command/skill that currently ends its workflow with a `git commit`
should also push, but the algorithm (pull-first, re-sync-before-push,
abort-on-conflict, --no-push semantics) is identical everywhere it applies.
Author it once in docs/authoring-guide.md, replacing the "Commit-control
convention" section (renamed "Commit-and-push convention"), so the 7
dependent tasks (69-75) reference this section instead of each re-deriving
the algorithm. This task is doc-only — it does not touch any command file.

## Acceptance criteria
- `docs/authoring-guide.md`'s "Commit-control convention" section is
  renamed "Commit-and-push convention" and rewritten to cover, in addition
  to the existing commit rules (unchanged): the full protocol below.
- Protocol, git projects only (see exemption below):
  1. **Pull at start.** Before the command's own work begins (right after
     its precondition/setup checks), run `git pull` on the current branch.
     If it fails with a conflict, stop immediately before doing any of the
     command's normal work; report the conflict output and tell the user
     to resolve manually and re-run. "Already up to date" / clean
     fast-forward: proceed normally.
  2. Do the command's own work and commit exactly as already specified
     (unchanged: explicit paths only, no empty commits, no
     `--no-verify`/`--amend`, report-and-stop on commit failure).
  3. **Pre-push re-sync.** Immediately before pushing, run `git pull` again
     (other commits may have landed upstream during the run). A clean
     fast-forward/merge: continue to push. A conflict: abort the merge,
     leave the local commit intact, do NOT push, and report that the
     commit exists locally but could not be synced — the user must
     resolve and push manually.
  4. **Push.** `git push`. On failure (rejected, no upstream, no remote):
     report the exact output and stop. Never retry, never force-push.
- **`--no-push` flag.** Every command that pushes accepts `--no-push` to
  skip steps 1, 3, and 4 above while still committing as it does today.
  For auto-committing commands (task-add, task-clean, task-implement,
  context-update), `--no-commit` implies `--no-push` (nothing to push).
  For authoring commands (context-build, task-enrich, refactor-codebase,
  refactor-tests, task-setup, domain-setup, unity-mcp-setup,
  product-design, architect, project-setup), which only commit under
  `--commit`, `--commit --no-push` is a valid combination: commit locally,
  skip the sync/push cycle.
- **Non-git VCS exemption.** When the project's CLAUDE.md defines a
  `## VCS` section overriding git (e.g. Plastic SCM), skip the entire
  pull → re-sync → push sequence unconditionally — only the commit
  (checkin) step runs. This is a project-level fact recorded once in that
  project's CLAUDE.md by `/project-setup` (task 73), not something each
  command re-decides.
- The existing line "Never push, branch, or tag" is corrected to "Never
  branch or tag. Push only via the commit-and-push protocol above" — it
  was accurate before this change and must not keep telling authors the
  opposite of the new behavior.
- Root `VERSION` bumped (minor — behavior-affecting doc convention).

## Decisions
- Protocol lives in docs/authoring-guide.md (single-sourced), not
  duplicated per command — mirrors how task 47 single-sourced the non-git
  VCS rule. Dependent tasks reference this section by name.
- Push granularity for multi-commit runs (e.g. task-implement's
  one-commit-per-task) is decided per dependent task, not here.
