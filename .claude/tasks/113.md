# Task 113 — Add the /production-status command

Target: claude

## Goal
Ship `commands/production-status.md`, the read-only reporter that answers the
question the planning layer exists to answer — what should I build next. From
feature `plan-readout`: `PLAN.md` holds milestones, order and dependency
edges, `FEATURES.md` holds each feature's design/backlog state, `TASKS.md`
holds the work, and the useful answer lives in the join of all three and in
none of them alone. The command computes readiness on every read, reports the
recommended next feature, names what blocks the rest, and writes nothing.

## Acceptance criteria
- `commands/production-status.md` exists with complete frontmatter:
  `name: production-status`, `version: 0.1.0`, `type: command`, one-line
  `description`. A command, not a skill — a thin read-only reporter with no
  conversation and no supporting files, the register `/task-list` occupies.
- Output sections, in this order: (1) active milestone — slug, title, `Goal:`
  and `Exit criteria:` echoed from the roadmap; (2) its features in plan
  order, each with its `FEATURES.md` status, task rollup and readiness;
  (3) the ready set; (4) the single recommended next feature, the first ready
  one in plan order; (5) blocked features, each named with what blocks it;
  (6) coverage gaps — roadmap slices with no architected features, and
  `product-design.md` sections no milestone covers; (7) unplanned features —
  `FEATURES.md` slugs absent from `PLAN.md`; (8) remaining milestones, one
  line each.
- Readiness: a feature is ready when every dependency edge pointing at it
  originates from a feature that is `[PLANNED]` in `FEATURES.md` with all of
  its tasks `[DONE]` or `[SKIP]`. A feature with no dependencies is ready.
  Everything else is blocked and is named with its blocker. Derived on every
  read, never stored.
- Task rollup defaults to counts per status; `--task-ids` switches it to
  naming each task ID.
- `milestone=<slug>` scopes the report to that milestone instead of the
  active one. An unknown slug stops with the available slugs listed, matching
  `/task-add feature=<slug>`'s unknown-slug behavior.
- The staleness signal is structural, not temporal: the report names every
  `FEATURES.md` slug missing from `PLAN.md` and points at `/production-plan`.
  Nothing compares `Last reconciled:` against modification times.
- Reads `.claude/PLAN.md`, `.claude/FEATURES.md`, `.claude/TASKS.md` and
  `.claude/domain/product-roadmap.md`, all read-only. Never opens a file
  under `.claude/tasks/` — `TASKS.md` carries everything needed.
- Writes nothing: no status flips, no reordering, no commit, no cached
  answer, no shell command of any kind.
- Failure contract is degradation, never refusal — no `PLAN.md` → say the
  project has no plan and point at `/production-plan`; no roadmap → omit
  milestone goals and exit criteria, report everything else; no `TASKS.md` →
  features report with no rollup and every feature with satisfied
  dependencies is ready; no active milestone → report the first `[PLANNED]`
  one and say none is active; a dependency edge naming an unknown slug →
  report a plan inconsistency and treat the feature as ready, failing open.
- The command does not select or start work — it reports the next ready
  feature and stops there.
- Root `VERSION` bumped minor (new command).
- `./bin/chosko-llm ls --available` lists `production-status` at `0.1.0`.

## Decisions
- **Counts by default, `--task-ids` to expand.** The feature document leaves
  rollup granularity to implementation. Counts keep a milestone's feature
  list scannable, which is the command's whole register; the flag recovers
  precision without a second command.
- **`milestone=<slug>` for scoping, not a flag.** Matches
  `/task-add feature=<slug>` and `/context-update unit=<names>` — a
  `key=value` argument for a named target, `--flags` for booleans.
- **Failing open on an unresolvable dependency edge.** Explicit in the
  feature's failure contract: a hand-edited plan must not make the report
  claim there is nothing to do.
- **Separate from task 114.** `/production-status` reports features and
  `/task-list` reports tasks; different files, different version bumps, no
  ordering between them.
