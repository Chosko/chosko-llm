# Task 143 — Add the /runbook-clean command

Target: claude

## Goal

The pruning side of the `runbook-suite` feature
(`.claude/domain/features/runbook-suite.md`). Finishing a runbook flips a status
and deletes nothing — the `Done:` lines are the record of what was decided while
the work was being done, and they are re-read more often than anyone expects.
But the store is committed and grows without bound, and a directory holding a
year of finished runbooks makes `/runbook-list` useless for the one question it
exists to answer. `/runbook-clean` is the explicit, confirmed removal, behaving
exactly like `/task-clean`.

## Acceptance criteria

- `commands/runbook-clean.md` exists with full frontmatter: `name:
  runbook-clean`, `version: 0.1.0`, `type: command`, a `description`, and
  `requires: skill:runbook-run`.
- The body cites
  `${CLAUDE_HOME:-$HOME/.claude}/skills/runbook-run/references/runbook-schema.md`
  for the status vocabulary and the index block shape, and restates neither.
- Three stages, in order:
  1. **Resolve.** With no argument, every `[DONE]` runbook. With names, exactly
     those.
  2. **Plan and confirm.** Print each runbook to be deleted with its name,
     created date and steps done/total, plus **both** paths — the body file and
     the index block — and ask. Nothing is written before an explicit answer.
  3. **Remove and commit.** Delete each body file, remove each index block
     **including its surrounding `---` rules**, then stage exactly the deleted
     paths and `.claude/RUNBOOKS.md` and commit. Never a catch-all stage.
- **Only `[DONE]` is eligible**, and the body gives the reason for each of the
  other three: `[PENDING]` is unstarted work, `[RUNNING]` is a run someone is in
  the middle of, and `[FAILED]` is the status most likely to be misread as
  finished — it is the record of a halt that still needs a decision.
- **There is no `--force` and no status argument widening the set.** A user who
  genuinely wants a `[FAILED]` runbook gone flips its status by hand first — one
  visible, committed edit. The body states this is narrower than `/task-clean`,
  which prunes `[DONE]` and `[SKIP]`, because runbooks have no second terminal
  status.
- A **named runbook that is not `[DONE]` is refused by name with its actual
  status**, never silently skipped: the user asked for it explicitly, and a
  silent skip reads as a successful removal.
- An **unknown name aborts the whole run before anything is deleted**, rather
  than removing the names it did recognise — a partial deletion from a mistyped
  list is the worst outcome available here.
- An **empty plan says so and stops** without asking anything.
- Commit convention is the **cleanup** one, not the authoring one: it commits
  and pushes by default, with `--no-commit` and `--no-push` to opt out, and the
  body records the reason — a deletion left uncommitted is the change most
  likely to be lost, and the confirmation gate has already served as the review
  pass. The push follows `docs/authoring-guide.md`'s commit-and-push protocol.
- It touches no runbook it is not deleting, and never edits a body file.
- Every install path named uses `${CLAUDE_HOME:-$HOME/.claude}`; no path under
  `docs/` appears.
- Root `VERSION` takes a minor bump (new shipped command), relative to whatever
  is in place when this lands.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  145 owns both knowledge layers.
- No test suite by design: verify by reading the diff and confirming
  `./bin/chosko-llm ls --available` lists `runbook-clean  command  —  0.1.0`
  against a clone where `install.sh` has run.

## Decisions

- **Preconditioned on 140 and 125**, like every other consumer: the cited schema
  path and the `requires:` declaration are dangling before those land.
- **Parity with `/task-clean` is deliberate and near-total** — same three
  stages, same explicit-paths staging, same commit-by-default convention — with
  exactly one narrowing: one terminal status instead of two.
- **Removal is an explicit act, never a consequence of completion.** `[DONE]`
  deletes nothing on its own; that is what makes the `Done:` record durable.
