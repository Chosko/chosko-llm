# Task 182 — Add the three owner amend arms and record them in the pipeline routing table

Target: claude

## Goal
Feature `owner-amend-arms` gives each pipeline artifact's owner a small,
standalone file describing how to make a targeted change to one artifact, so a
surgical edit costs one small file instead of a whole skill body. Three arms
ship, one per owner folder:

1. **`/architect amend`** — a new argument form dispatching to
   `skills/architect/amend.md`, which applies a described change to a named
   feature document and runs a *precision* iterate guard: each of the
   feature's tasks is classified touched or untouched instead of all of them
   being staled.
2. **Single-task amend** — `skills/task-engine/references/amend.md`, the eighth
   reference file and the single authority for changing one existing task.
3. **Single-step amend** — `skills/runbook-run/references/step-amend.md`, the
   single authority for striking a step, inserting one, and adding facts to a
   step's `Context:`.

Every arm follows one schema — it names its inputs, its single gate, exactly
what it writes and its closing report line — and the three are written together
so that schema is one author's, not three approximations of it. Once they
exist, this task records where each owner's amend entry is in
`pipeline-engine`'s routing table (task 175), which is how a revision surface
finds an owner's cheap path without loading the owner.

## Acceptance criteria

### `skills/architect/amend.md` and `skills/architect/SKILL.md`
- `skills/architect/amend.md` exists and is complete on its own: a consumer that
  has read only this file can execute the arm end to end. It names its inputs,
  its single gate, exactly what it writes, and its closing report line.
- `skills/architect/SKILL.md`'s ARGUMENT PARSING recognises
  `amend feature=<slug> "<change>"` and dispatches to `./amend.md` after
  PHASE 0's domain-layer gate and before ordinary input resolution. The clarify
  and architecture phases do not run on this path. `--commit` and `--no-push`
  compose with it unchanged.
- The SUPPORTING FILES table gains a row for `./amend.md` with its "exactly
  when", and the do-not-read-speculatively note still reads correctly.
- The precision guard in `amend.md` specifies: every task on the feature's
  `Tasks:` line that is not `[DONE]` or `[SKIP]` is classified touched or
  untouched from its summary block's title and `Files:` alone; a body is opened
  only when the summary block cannot decide.
- A *touched* `[IN PROGRESS]` task refuses the amendment, naming the task, with
  no override. An *untouched* `[IN PROGRESS]` task does not refuse.
- Exactly one gate presents the change, the touched set and the proposed status
  outcome, and asks whether the change is editorial. That question is asked on
  every amendment and is never inferred or classified.
- On proceed, `[STALE]` is written on touched tasks only. The feature flips to
  `[ITERATED]` when any task was staled or when the change adds scope no
  existing task covers; an editorial change leaves the status as it was.
- The arm's write set is stated and closed: the feature document,
  `FEATURES.md`'s `Status:`, `TASKS.md`'s `Status:` lines, and
  `product-design.md` when the change belongs upstream. No progress marker is
  written — an amendment is one gate long and has nothing to resume.
- Failure contract stated: a change that cannot be scoped to named sections is
  refused with a pointer to the full skill; an unknown slug stops by listing the
  slugs that exist; a `[NEW]` feature is amended with no guard at all; `Tasks:`
  ids that resolve to nothing are tolerated exactly as `./iterating.md`
  tolerates them.
- `amend.md` cites `./iterating.md` and `./feature-doc-template.md` by path
  where a rule already lives there, and restates nothing they own.
- `skills/architect/SKILL.md`'s `description:` mentions the `amend` form.

### `skills/task-engine/references/amend.md` and `skills/task-engine/SKILL.md`
- `skills/task-engine/references/amend.md` exists as a peer of the other seven
  reference files, and is complete on its own: it names its inputs, its single
  gate, exactly what it writes and its closing report line.
- It states which body sections may be rewritten and which summary-block fields
  may change.
- It states that `Preconditions:` may be rewritten to add or drop an edge, and
  that a dropped edge is named in the task's `## Decisions` so the removal has a
  written reason.
- It states that deleting a live task means `[SKIP]` with a reason, never
  physical removal — removal is `/task-clean`'s act over terminal statuses. It
  cites `./status.md` for the vocabulary rather than restating it.
- It states that `Feature:` may be added to an orphan task but never changed on
  a feature-derived one, because the feature's `Tasks:` line is the other half
  of that link and would have to move with it.
- It states the two checks a consumer makes before writing: the task is not
  `[IN PROGRESS]`, and the change does not alter what the task's feature
  document promises — the second case routes to `/architect amend` instead.
- It never touches `[DONE]` or `[SKIP]` work; follow-up work is a new task.
- It cites `./resolution.md`, `./status.md` and `./stale.md` by path and
  restates nothing they own, per the engine's one-authority discipline; any
  per-consumer divergence is recorded as a note, not as new shared rule text.
- `skills/task-engine/SKILL.md`'s map table gains a row for the new file, its
  `description:` says eight files rather than seven, and the sentence naming who
  may open the skill is widened to admit the pipeline revision surfaces —
  generically ("the pipeline revision surfaces read `references/amend.md` by
  path"), since `/pipeline-patch` and `/pipeline-revise` are not shipped yet
  and shipped content never names an unshipped command. Task 187 adds the names.

### `skills/runbook-run/references/step-amend.md` and `skills/runbook-run/SKILL.md`
- `skills/runbook-run/references/step-amend.md` exists beside
  `runbook-schema.md` and `subagent-contract.md`, and is complete on its own: it
  names its inputs, its single gate, exactly what it writes and its closing
  report line.
- **Strike.** A struck step is marked `[x]` and carries a `Done:` line opening
  `struck — <reason>`, with no commit sha. It keeps its number and its prompt
  block, and is never deleted; steps are never renumbered, because a
  `Depends on:` line elsewhere may point at the struck step's number.
- **Insert.** Inserting a step is the positional append that task 173 adds to
  `/runbook-create --append` (`--before N` / `--after N`). This file cites that
  command and describes no second insertion mechanism of its own.
- **Context.** A step's `Context:` may gain dated fact bullets. It is the only
  field an amendment adds to.
- **Immutable prompt.** The prompt block is never edited — the existing rule in
  `runbook-schema.md`, cited and not restated. The named consequence is stated:
  a step whose prompt is wrong is struck and a corrected step inserted.
- A `[RUNNING]` runbook accepts inserts after the current step and nothing
  before it. A step already `[x]` or `[!]` is never edited, and an existing
  `Done:` line is never rewritten.
- No new step marker and no new status value is introduced;
  `runbook-schema.md`'s four markers and four statuses stand unchanged.
- `skills/runbook-run/SKILL.md`'s `description:` is updated — it currently says
  the folder carries "the two files the rest of the runbook suite reads by path"
  — and the install-path assumption note names the third file.

### `skills/pipeline-engine/references/routing.md` — amend entries
- Records, for every owner that has an amend entry, the path to it, in the
  place task 175 left for it:
  - `/architect` → `skills/architect/amend.md`
  - the task suite → `skills/task-engine/references/amend.md`
  - the runbook suite → `skills/runbook-run/references/step-amend.md`
  - `/product-design` → its existing arm in `skills/product-design/resuming.md`
    § 6, which shipped long before this feature.
- Owners with no amend arm — `/production-plan` and `/product-roadmap` — are
  recorded as having none, with the one-clause reason (both are
  diff-and-propose on every run), so a reader does not go looking for a file
  that was never meant to exist.
- The entries are added in the shape task 175 shipped. No new column is
  invented beyond that and no new file is created; if the shape turns out to
  have no place for an entry, add the smallest field that fits its existing
  convention and say so in the commit.
- Only shipped features are named. Nothing here names `/pipeline-patch`,
  `/pipeline-revise` or `/pipeline-suggest`; those add their own rows when they
  land.
- `scripts/check-routing.sh` still exits clean.

## Decisions
- **One task for the three arms and their routing entries.** Planned as four
  tasks (182–185) and merged on 2026-09-11 (user decision). The three arms
  share one schema and are best kept parallel by one author; the routing
  bookkeeping (formerly task 185) folds in because this task now preconditions
  on the engine (task 175) anyway, so the table exists when the arms do. The
  documentation task (186) stays separate.
- **The arms are supporting files, not new skills or commands.**
  `owner-amend-arms.md` § Scope and non-goals rules out new writers: each
  artifact stays its owner's, so each arm lives in its owner's folder, is
  reached by the folder's existing relationships, and no new install unit
  appears.
- **`/architect amend` does not invoke `/pipeline-check`.** The feature document
  says the precision gate "may" run the scoped lint. Running the lint before and
  after an action belongs to the reviser in `pipeline-revision`; wiring it in
  here would gain nothing.
- **Writing `product-design.md` is not a breach of "an arm never writes a line
  another owner owns".** The full `/architect` skill already writes clarify
  answers back into that document; the arm inherits exactly its write set and
  nothing beyond it.
- **A free-form change naming no sections is refused.** The feature document's
  open question is settled the way it recommends — refusing keeps the arm
  surgical, and the full skill is one prompt away.
- **The task amend reference is a new peer file, not a section inside
  `status.md` or `resolution.md`.** The amend protocol spans several of those
  files; putting it inside one of them would give it two homes and break the
  one-authority discipline the engine exists to hold.
- **Rewriting a `Preconditions:` edge does not depend on `backlog-ordering`'s
  task side (task 169 — neither its selection change nor its `--before` /
  `--after` placement).** It is an operation on a field that already exists.
  The step insert does depend on task 173, which is why 173 is a precondition.
- **A struck step is `[x]` with `Done: struck — <reason>` and no commit sha**
  (user decision, 2026-09-09). `owner-amend-arms.md` § Data and state requires
  the existing marker vocabulary, and `[x]` is the only one of the four that
  works: `/runbook-run`'s selection already skips ticked steps, so a struck step
  is passed over with no special case, and the runbook can still reach `[DONE]`
  when every step is `[x]`. `[!]` was rejected — it means *failed*, halts the
  run and drives `.claude/RUNBOOKS.md` to `[FAILED]`, and a strike is a decision,
  not a failure. A fifth marker was rejected by the feature document itself.
  The `Done:` line is already the schema's place for what happened and why, so
  the reason needs no new field.
- **Insert is delegated, never reimplemented.** `/runbook-create --append` is
  the runbook suite's only step writer; a second insertion path in
  `step-amend.md` would be exactly the drifting copy the reference layer exists
  to prevent.
- **`step-amend.md` lives in `runbook-run/references/`, not in
  `/runbook-create`'s body.** `runbook-create`'s body is authoring rules with
  one consumer; this is a rule several features read by path, which is what the
  references folder is for.
- **The routing entries point only at files that exist.** An amend entry
  pointing at a file that does not exist yet is precisely the drift
  `/pipeline-check` exists to catch, which is why the entries are written in
  the same task as the arms rather than before them.
