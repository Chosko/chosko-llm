# Task 182 — Add the `/architect amend` arm

Target: claude

## Goal
Feature `owner-amend-arms` gives each pipeline artifact's owner a small,
standalone file describing how to make a targeted change to one artifact, so a
surgical edit costs one small file instead of a whole skill body. This task
builds the first of the three arms: a new `amend` argument form on `/architect`
that dispatches to a new on-demand supporting file, `skills/architect/amend.md`,
which applies a described change to a named feature document and then runs a
*precision* iterate guard — classifying each of the feature's tasks as touched
or untouched instead of staling all of them.

## Acceptance criteria
- `skills/architect/amend.md` exists and is complete on its own: a consumer that
  has read only this file can execute the arm end to end. It names its inputs,
  its single gate, exactly what it writes, and its closing report line.
- `skills/architect/SKILL.md`'s ARGUMENT PARSING recognises
  `amend feature=<slug> "<change>"` and dispatches to `./amend.md` after
  PHASE 0's domain-layer gate and before ordinary input resolution. The clarify
  and architecture phases do not run on this path. `--commit` and `--no-push`
  compose with it unchanged.
- The SUPPORTING FILES table gains a row for `./amend.md` with its "exactly
  when", and the do-not-read-speculatively note still reads correctly.
- The precision guard in `amend.md` specifies: every task on the feature's
  `Tasks:` line that is not `[DONE]` or `[SKIP]` is classified touched or
  untouched from its summary block's title and `Files:` alone; a body is opened
  only when the summary block cannot decide.
- A *touched* `[IN PROGRESS]` task refuses the amendment, naming the task, with
  no override. An *untouched* `[IN PROGRESS]` task does not refuse.
- Exactly one gate presents the change, the touched set and the proposed status
  outcome, and asks whether the change is editorial. That question is asked on
  every amendment and is never inferred or classified.
- On proceed, `[STALE]` is written on touched tasks only. The feature flips to
  `[ITERATED]` when any task was staled or when the change adds scope no
  existing task covers; an editorial change leaves the status as it was.
- The arm's write set is stated and closed: the feature document,
  `FEATURES.md`'s `Status:`, `TASKS.md`'s `Status:` lines, and
  `product-design.md` when the change belongs upstream. No progress marker is
  written — an amendment is one gate long and has nothing to resume.
- Failure contract stated: a change that cannot be scoped to named sections is
  refused with a pointer to the full skill; an unknown slug stops by listing the
  slugs that exist; a `[NEW]` feature is amended with no guard at all; `Tasks:`
  ids that resolve to nothing are tolerated exactly as `./iterating.md`
  tolerates them.
- `amend.md` cites `./iterating.md` and `./feature-doc-template.md` by path
  where a rule already lives there, and restates nothing they own.
- `skills/architect/SKILL.md`'s `version:` is bumped (minor) and its
  `description:` mentions the `amend` form; root `VERSION` is bumped and
  `CHANGELOG.md` gains a matching top section; `./scripts/check-changelog.sh`
  is silent.

## Decisions
- **The arm is a supporting file, not a new skill or command.**
  `owner-amend-arms.md` § Scope and non-goals rules out new writers: the feature
  document stays `/architect`'s, so the arm lives in `/architect`'s folder, is
  reached by the folder's existing relationships, and no new install unit
  appears.
- **The arm does not invoke `/pipeline-check`.** The feature document says the
  precision gate "may" run the scoped lint. Running the lint before and after an
  action belongs to the reviser in `pipeline-revision`; wiring it in here would
  block this task on task 179 for no gain. `Preconditions:` is `none` as a
  result.
- **Writing `product-design.md` is not a breach of "an arm never writes a line
  another owner owns".** The full `/architect` skill already writes clarify
  answers back into that document; the arm inherits exactly its write set and
  nothing beyond it.
- **A free-form change naming no sections is refused.** The feature document's
  open question is settled the way it recommends — refusing keeps the arm
  surgical, and the full skill is one prompt away.
