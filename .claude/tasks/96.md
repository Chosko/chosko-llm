# Task 96 — Document the claude-council gate and bump the repo version

Target: claude

## Goal
Bring the documentation layers up to date with the council gate that tasks 94
and 95 shipped, and record the one maintenance obligation the change creates:
`council-gate.md` now exists in two skill folders and the copies must be kept in
step. Also make the integration discoverable to users who don't have
claude-council installed, since the gate itself is deliberately silent about it.

## Acceptance criteria
- `docs/authoring-guide.md` gains a "Keeping the two `council-gate.md` copies in
  step" note, placed and worded alongside the existing "Keeping `/task-implement`
  and `task-impl` in step" and "The status vocabulary lives in three places"
  conventions. It states why duplication is forced (skills install as
  self-contained folders; no cross-skill shared-file mechanism) so a future
  reader doesn't try to "fix" it.
- `.claude/domain/product-workflow.md` documents the gate in the pipeline: where
  it fires, that it is optional delegation, that it never decides, and how
  dissent folds into each skill's documents. The "Who writes what" section
  reflects that council artifacts are owned by neither skill.
- `.claude/context/features.md` describes both new supporting files in the
  `skills/architect/` and `skills/product-design/` entries, matching the
  existing "read only when their branch fires" phrasing.
- `README.md`'s `/architect` and `/product-design` sections each mention the
  optional integration and how to install it
  (`npx skills add TorpedoD/claude-council`).
- Both skills' frontmatter `description:` mention the optional council
  integration in one clause, staying within the authoring guide's length spec
  (see task 89, which trimmed oversized descriptions).
- Root `VERSION` bumped 0.44.1 → 0.45.0 — minor, per CLAUDE.md's semver rule for
  a new capability.
- No shipped body (command or skill) references a `docs/` path. The authoring
  guide note is authoring-time material and lives in `docs/` correctly; the
  runtime protocol stays in the skill folders.

## Decisions
- Discoverability lives in README and frontmatter, not mid-run. The gate stays
  silent when claude-council is absent, so browsing and `chosko-llm ls` are the
  only places a user can learn the capability exists without being nagged.
- The in-step note goes in `docs/authoring-guide.md` rather than a domain file
  because it's an authoring rule about how features are written, matching where
  the two sibling in-step conventions already live.
- Minor, not patch, on the root `VERSION`: this ships a new user-visible
  capability in two skills, which CLAUDE.md's versioning rule puts at minor.
- Runs last. The documentation describes behaviour tasks 94 and 95 define, so
  writing it earlier would document a design rather than an implementation.
