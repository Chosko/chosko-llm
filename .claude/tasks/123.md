# Task 123 — Add the --review / --rounds loop to /task-implement

Target: claude

## Goal

Wires `/task-review` and `/task-iterate` into `/task-implement` so a task can be
implemented, reviewed by a genuinely fresh context, and corrected without
leaving the run — completing the `task-peer-review` feature. New flag
`--review`, optionally `--rounds N` (default 1); default off, and a run without
it must behave exactly as it does today. The review runs as a **subagent**
because fresh context is the mechanism and not a detail — a reviewer that
watched the code being written will rationalise it — while the iterate runs in
the **main session** because its edits must land in the tree Step 7 commits.

## Acceptance criteria

- ARGUMENT PARSING gains two flags, stripped before the selector is resolved:
  - `--review` — sets REVIEW = true. Default false.
  - `--rounds N` — sets ROUNDS = N, a positive integer, default 1. `--rounds`
    without `--review` stops with a clear message
    (`--rounds requires --review.`); a non-positive or non-integer N stops too.
- A run without `--review` is byte-for-byte the run it is today: no new prompt,
  no new file read, no behaviour change on any path, and no mention of the loop
  in its output.
- A new supporting file `skills/task-implement/review-rounds.md` holds the loop
  protocol, and the SUPPORTING FILES table gains a row for it whose condition
  is "REVIEW is true". It is never read on a run without `--review`.
- **Placement.** The loop runs after Step 5 (full test suite) and **before**
  Step 6 (terminal status flip), on the uncommitted tree. Step 6 and Step 7 are
  otherwise unchanged, and Step 7's single commit therefore includes the
  review's fixes.
- **Each round spawns `/task-review` as a subagent** — the Agent tool with
  `subagent_type: "general-purpose"` — whose prompt carries the repo path, the
  task number, the diff scope for this round, the round number, and (from round
  2 on) the previous rounds' rejection ledger plus the hunks the last iterate
  changed. The body states that fresh context is the reason, so a later editor
  does not "optimise" the spawn away.
- **The spawned reviewer returns ASYNCHRONOUSLY, and the body must say so.**
  The Agent call yields an agent id immediately; the reviewer's findings arrive
  later as a separate notification, **not** as the tool call's return value.
  The body must therefore instruct the round to wait for that notification
  before invoking `/task-iterate`, and must forbid reaching Step 6 or Step 7
  until the final round's reviewer result has actually arrived. It must also
  say why: a body written as though the spawn returned findings inline will
  commit unreviewed work. (Verified by direct probe, 2026-08-24 — see
  Decisions.)
- **Iterate runs in the current session**, never as a subagent, invoked via the
  `/task-iterate` skill, and is told explicitly that it is running inside a
  `/task-implement --review` round and must not commit or push. Its edits land
  in the tree Step 7 commits.
- **Loop control.**
  - `N = 1` (the default) — one review, one iterate, stop. No re-review, no
    gating.
  - `N ≥ 2` — after iterate, re-review and repeat, bounded by two rules: the
    loop continues **only while `BLOCKING` findings remain**, and it stops at N
    rounds regardless. `IMPORTANT` and `ADVISORY` findings are reported in the
    round that found them and are never re-raised.
  - Rounds after the first review **only the hunks the previous iterate
    changed**, not the whole diff.
- **Sticky rejections travel between rounds as binding context**: a finding
  rejected in round *k* may not be re-raised in round *k+1*, only escalated,
  and only with evidence the earlier round did not have. The body states that
  no round counter substitutes for this rule.
- **Nothing in the loop blocks on advisory findings.** Unresolved `BLOCKING`
  findings after the last round stop the run: report them, leave the tree as it
  is (uncommitted), leave the task `[IN PROGRESS]` per FAILURE HANDLING, and
  hand back to the user. Do not flip to `[DONE]` and do not commit.
- `--no-commit` and `--review` compose: the loop runs, Step 7 is skipped, the
  corrected tree is left uncommitted.
- **Exactly one commit per task under `--review`.** The DO NOT list gains a
  bullet forbidding a separate commit for review fixes, and forbidding letting
  `/task-iterate` commit inside a run.
- **Availability gate.** If either the `task-review` or the `task-iterate`
  skill is unavailable in this session, a `--review` run stops before the first
  task with a clear error naming both and the
  `chosko-llm add skill:task-review skill:task-iterate` remedy. It never
  silently skips the review.
- **Batch propagation.** `--review` and `--rounds N` ride through
  `skills/task-implement/delegated-runs.md`'s hand-off prompt as two more
  entries in "the run's resolved flags" that task 119 left open-ended. The
  prompt's fixed-size property is preserved, and the flag list is **not**
  converted into a closed enumeration. The parent launcher passes them through
  and never sees a finding.
- `delegated-runs.md` additionally states that each implementor spawns its own
  reviewer (launcher → implementor → reviewer, a depth confirmed to work on
  2026-08-24), that the implementor's reviewer also returns asynchronously, and
  that an implementor must not reach its own Step 7 before its reviewer's
  result has arrived. The parent's four-field return contract from task 119 is
  unchanged — no finding travels to the parent.
- The parent's between-agent protocol, the sequential-never-parallel rule,
  FEATURE COMPLETION, the partial-delegation rule and failure handling are all
  unchanged.
- The usage header and the frontmatter `description` of
  `skills/task-implement/SKILL.md` document `--review` and `--rounds N`, with a
  usage line and an example.
- `skills/task-implement/SKILL.md` takes a minor frontmatter `version:` bump
  and root `VERSION` a minor bump, both relative to what tasks 118, 119, 121
  and 122 leave in place (expected `1.1.0` → `1.2.0` on the skill and
  `1.3.0` → `1.4.0` on root `VERSION`).
- No file under `.claude/context/` or `.claude/domain/` is edited here — task
  124 owns the documentation.

## Decisions

- **A spawned subagent returns asynchronously, and this is binding on the
  body.** Probed directly on 2026-08-24: the Agent call yields an id
  immediately and the result arrives later as a separate notification. The
  obvious way to write this loop — treat the spawn call's return value as the
  findings — produces a run that commits unreviewed work while reporting that
  it reviewed it. This is the single most load-bearing sentence in the task and
  belongs in `review-rounds.md` in plain language, with the failure it
  prevents named.
- **The loop sits before Step 6, not between 6 and 7.** The feature document's
  diagram shows it before Step 7 and is silent about Step 6. Running it first
  means a cap-hit with unresolved blocking findings leaves the task
  `[IN PROGRESS]`, which is exactly what FAILURE HANDLING already specifies for
  a halted run — whereas flipping to `[DONE]` and then halting would leave the
  backlog claiming work that was never accepted.
- **Subagent nesting to depth 3 was verified, so batch `--review` is in
  scope.** A general-purpose subagent has the `Agent` tool and successfully
  spawned a child that ran and returned (2026-08-24). No fallback to
  "review only in single-task runs" is needed or wanted.
- **Ride task 119's flag list; do not redesign the hand-off.** 119 deliberately
  describes the prompt's flag list as "the run's resolved flags" rather than a
  closed set, precisely so `--review` / `--rounds` could ride through it once
  they existed. Adding two named entries and keeping the list open-ended is the
  whole of the batch work here.
- **`--rounds` without `--review` is an error, not a silent no-op.** A user who
  typed `--rounds 3` expected a review loop; accepting and ignoring it would
  run a plain implementation while looking like it reviewed.
- **A new supporting file, not more of SKILL.md.** `--review` is off by
  default, so the loop protocol is exactly the kind of branch this skill's
  read-on-demand table exists for; inlining it would tax every ordinary run.
- **The availability gate is a body-level check, not frontmatter.** The
  `requires:` field that would express a cross-feature dependency properly
  belongs to the unimplemented `shared-phase-engine` feature; until it ships,
  the skill checks and errors at runtime rather than shipping a dangling
  reference.
- **Preconditions.** 118 leaves this file without the `Target: local` block,
  the `chosko-llm task-impl` asides and the external-LLM material — this task
  must not reintroduce or reference any of it. 119 leaves `delegated-runs.md`
  with the fixed-size launcher prompt this task extends. 121 and 122 provide
  the two skills the loop invokes.
