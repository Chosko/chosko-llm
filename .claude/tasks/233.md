# Task 233 — Add `/runbook-prune` — remove done steps, keep their ids in an `Archive:` line

Target: claude

## Goal
A long-running runbook accumulates finished steps whose prompt blocks are dead
weight: the steps are `[x]`, the work is committed, and the body they sit in is
re-read at every step of every subsequent run. `/runbook-prune <id|name|id-name>`
removes them. The pruned ids go on a new `Archive:` header line, which is what
keeps a surviving `Depends on:` naming a pruned step resolvable — an id in
`Archive:` counts as `[x]` — so the prune itself needs no dependency check and
reads no file beyond the index block and the one body.

## Acceptance criteria
- `commands/runbook-prune.md` exists with full frontmatter: `name:
  runbook-prune`, `version: 0.1.0`, `type: command`, `requires: skill:runbook-run`,
  and a `description:` in the suite's register.
- Takes one runbook as `<id>`, `<name>` or `<id>-<name>`, resolved by
  `runbook-schema.md`'s four ordered checks; an unknown argument lists the
  runbooks that exist.
- Removes every `[x]` step, heading through prompt block. `[ ]`, `[~]` and `[!]`
  are never touched. A struck step is `[x]` and is pruned like any other.
- Each removed id is appended to the body header's `Archive:` line, in ascending
  order, comma-separated, placed after `Companion:`. The line is created on
  first prune and absent on a runbook never pruned.
- On a body with no `Last step number:` line, the backfill is the prune's FIRST
  write: the highest step id present — counting the `[x]` steps about to be
  removed — is written to the header before any step is deleted. Pruning a legacy
  body that way can never lower the next append's id.
- `Last step number:` is otherwise never touched by a prune — that is what task
  232 exists for, and it is why pruning the highest-numbered step is legal.
- The index block's `Steps: <done>/<total>` counts archived ids toward **both**
  halves, so a runbook pruned to nothing still reads `7/7` rather than `0/0`.
  Derivable from the body, so the index-as-summary rule holds.
- Refuses a `[RUNNING]` runbook by name with its status, and refuses when `[~]`
  is present in the tree. Nothing else gates: any status may otherwise be pruned.
- A runbook with no `[x]` steps says so and stops without asking anything.
- Plan-and-confirm before any write: the steps to be removed by id and title, the
  resulting `Archive:` line, the resulting `Steps:` count, and both paths. Nothing
  is written before an explicit answer.
- Commits and pushes by default, staging exactly the body's `File:` path and
  `.claude/RUNBOOKS.md`, never a catch-all; `--no-commit` and `--no-push` opt out.
- `runbook-schema.md` documents `Archive:` in § The header, states the
  archived-counts-as-`[x]` rule where the markers are defined, and records the
  prune's `Steps:` accounting in § The index block.
- `skills/runbook-run/SKILL.md`'s *Select* step resolves a `Depends on:` id
  found in `Archive:` as satisfied.
- A `/runbook-prune` row is added to
  `skills/pipeline-engine/references/routing.md`, and `./scripts/check-routing.sh`
  runs silent.
- Root `VERSION` minor-bumped with a matching top `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` silent.

## Decisions
- **No dependency check at prune time (user decision, 2026-09-17).** The
  `Archive:` list makes a reference to a pruned step resolve rather than dangle,
  so the check the prune would have run is replaced by one rule in the schema and
  one sentence in `/runbook-run`. Prune stays a two-file operation.
- **`Archive:` is a bare id list (user decision, 2026-09-17).** No `## Pruned`
  digest section, no retained `Done:` lines. The commit shas and the decisions
  recorded while executing are left to git history; the runbook stops carrying
  them. The ids exist for dependency resolution and the `Steps:` count, not as a
  record.
- **Comma-separated, matching `Depends on:`.** The request said space-separated
  and showed commas; the suite's existing id lists use commas.
- **Prune backfills the counter, `/runbook-run` does not.** Prune is one of only
  two commands that can change what max() would return, so it carries the
  backfill; a run cannot, so it doesn't, and the header stays `/runbook-create`'s
  line everywhere else. Routing.md's `/runbook-prune` and `/runbook-create` rows
  record the backfill the way the existing rows record id assignment on an
  id-less index.
- **Prune never migrates a legacy body path.** It reads and writes at `File:`,
  the way `step-amend.md` does, leaving `body-migration.md`'s reader set at
  `/runbook-run` and `/runbook-create --append`.
- **Commit-by-default, `/runbook-clean`'s convention rather than the authoring
  one.** The confirmation gate is the review pass, and a deletion left
  uncommitted is the change most likely to be lost.
