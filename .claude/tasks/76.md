# Task 76 — Add a technical-direction phase and write-back to /product-design

Target: claude

## Goal
`/product-design` stops at the high-level feature set, and `/architect` then
works feature-by-feature — so nothing in the pipeline ever decides the
product's technical foundations as a whole: tech stack, overall
architecture, topology (monolith vs. services), data store, queue, hosting,
worker/transport protocols. Add two phases to the skill: PHASE 6, a
conversational round in the same register as PHASE 4 that establishes the
technical direction for the whole product, aware of everything phases 2–5
produced (especially the high-level features, which are what force specific
technical choices); and PHASE 7, the write-back that fills the dedicated
document `.claude/domain/technical-direction.md`, stubbed alongside the
other design documents in PHASE 1. The document becomes the standing
constraint every later `/architect` run designs within (wired up by the
follow-up task).

## Acceptance criteria

  PHASE 7 — TECHNICAL WRITE-BACK, after PHASE 5, following the existing
  phase conventions: conversational, user-confirms-completion, stage marker
  rewritten before each phase ends, `WRITTEN` list appended for each path.
- PHASE 1 step 3 stubs `.claude/domain/technical-direction.md` alongside
  `design-process.md` and `product-design.md` — unconditionally, since
  PHASE 6 always runs, unlike the opt-in `business-model.md`. Step 4's
  "register every created document in `.claude/domain/INDEX.md`" then covers
  it without further change, and PHASE 1's existing never-overwrite rule
  applies to it as to the others.
- The skill's SUPPORTING FILES read trigger for `./document-templates.md`
  becomes PHASE 1, 3, 5, and 7; `document-templates.md`'s own opening line
  is updated to match.
- PHASE 6 always runs and explicitly reads back the PHASE 4/5 feature set,
  naming which features drive which technical choices.
- PHASE 6 branches on the greenfield/brownfield judgement PHASE 1 already
  made: brownfield starts from the stack that exists ("here's what I see
  you're built on — is this still the intent?") and only decides what is
  genuinely open; greenfield proposes candidates with trade-offs and a
  recommendation.

  `skills/product-design/technical-direction.md` carries the question bank /

- `document-templates.md` gains a `technical-direction.md` template section

- The `product-design.md` template gains a one-line pointer to

- `document-templates.md`'s `design-process.md` phase table gains rows for

- `skills/product-design/SKILL.md` frontmatter `version:` bumps 0.1.0 →

## Decisions
- **Stubbed in PHASE 1 with the other design documents, not created in
  PHASE 7.** PHASE 6 always runs, so the document is never conditional —
  creating it up front matches `product-design.md`, gets it into
  `INDEX.md` through the existing step-4 registration, and makes the full
  document set visible from the first phase. `business-model.md` stays the
  one conditional document.
- **PHASE 6 always runs, unlike business modelling.** Every product has
  technical foundations, and the document's whole purpose is to constrain
  later `/architect` runs; an opt-in would leave the common case unguided.
  Brownfield doesn't skip it — it changes register to confirm-and-record.
- **Phases appended as 6 and 7 rather than inserted.** Existing phase
  numbers are load-bearing: they appear in every written stage marker, so
  renumbering would corrupt in-flight `design-process.md` files.
- **A dedicated `technical-direction.md`, not a section of
  `product-design.md`.** `product-design.md` is deliberately user-facing and
  free of technical detail; keeping the direction separate preserves that
  contract and gives `/architect` one unambiguous file to read. The pointer
  line is what keeps the separation navigable rather than hidden.
- **A supporting question-bank file rather than inline prose.** Matches
  `./business-model.md` and keeps SKILL.md's on-demand read discipline
  intact.
- **`.claude/context/` needs no change.** `commands/context-build.md`
  enumerates domain files generically, so the new document is picked up
  without naming it there.
- **This task does not touch `/architect`.** Consuming the document is task
  77 — separable, and this task is complete without it.
