# Task 261 — `/task-implement --unattended`: park at a question, unpark when reached, pre-ask at launch

Target: claude

## Goal
Part of feature `unattended-parking`. Wire `/task-implement` to the protocol
task 260 wrote: a `--unattended` flag, UNATTENDED resolved as *the flag was
passed or the conversation declares this run unattended*, the refusals, the
load rule for `parking.md`, parking at a question about the work, unparking a
`[PARKED]` task when it is reached and an answerer exists, the launch-time
pre-ask with `--skip-parked`, and mid-run answers by number handle. Under
`attended` nothing changes.

## Acceptance criteria
- ARGUMENT PARSING strips `--unattended` and `--skip-parked`; `--skip-parked`
  without `--unattended` stops with `--skip-parked requires --unattended.`;
  `--unattended` beside `--no-commit` stops with a one-line error; on a
  project whose `CLAUDE.md` carries a `## VCS` override `--unattended` stops
  with a one-line error naming the parking branch as the reason. The usage
  header and examples list both flags.
- UNATTENDED is true when the flag was passed **or** the conversation
  declares the run unattended (the sentence a runbook preamble or a
  delegated-agent prompt carries); the body says so in one sentence and says
  that *non-interactive* alone is not that declaration.
- SUPPORTING FILES gains the row: read
  `../task-engine/references/parking.md` when UNATTENDED is true or any
  resolved task is `[PARKED]`; never otherwise.
- Under UNATTENDED, every prompt the run can raise resolves per
  `parking.md` § prompts with a default; the ambiguous-test-runner abort is
  stated where RESOLVING THE TEST RUNNER step 2 asks.
- PER-TASK WORKFLOW: at a question about the work under UNATTENDED the task
  is parked per `parking.md` — the step reached is the one the handoff
  names — and the run continues with the next task; under attended the
  question is asked as today.
- PRE-FLIGHT, under UNATTENDED and unless `--skip-parked`: after the
  resolution report, one numbered block lists every `[PARKED]` task in the
  resolved list with its `Question:` verbatim; the user answers by number or
  replies `skip` per item or for all; `approval gate` items are listed as
  skip-only; answers are held for the run.
- Step 1 on a `[PARKED]` task: with an answerer (attended session, or a held
  answer) run the unpark transaction from `parking.md`, then continue the
  workflow at the resumed step; with none, skip with one line and continue.
  A `[PARKED]` task named by number is unparked under either policy.
- BETWEEN TASKS: a chat reply by number handle (or naming the task) to a
  question printed this run is recorded and its task moved to the front of
  the remaining list; any other message is ordinary conversation; an answer
  to a question never printed this run, or a second answer to one already
  answered, is rejected with one line and records nothing.
- Explicit-by-number handling in `status.md`'s implementable list is cited,
  not restated; the STALE TASKS section's register is matched by a PARKED
  TASKS section of the same length that points at `parking.md`.
- The frontmatter description and the usage header say what `--unattended`
  does in one clause each.
- `task-implement`'s frontmatter `version:` bumped (minor); root `VERSION`
  bumped (minor) with a matching `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` and `./scripts/check-home-paths.sh` pass.

## Decisions
- UNATTENDED from a declaration as well as the flag: a runbook prompt block
  is verbatim and the contract forbids adding flags, so the signal must be
  readable from context.
- Pre-flight prompts never park (no current task yet); they take their
  silence value, per `parking.md`.
- Answers for tasks live in run memory only; a run that dies loses them and
  the next pre-ask asks again.
