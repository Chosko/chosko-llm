# Task 154 — Fix zero-task rollup and replace `/production-status`'s Ready column with a Next column

Target: claude

## Goal
Section 2 of `/production-status` lies twice on a finished feature. Its task
rollup prints `no tasks yet` for any feature whose `Tasks:` is `none`, which
reads as "never planned" when the real cause is that `/task-clean` pruned
completed tasks. And its trailing readiness field prints `ready` on features
where nothing is actually startable, which tells the reader a fact about the
dependency graph instead of the one thing they came for — what to do next.
Fix both: render `-` for a zero-task rollup on a `[DONE]` or `[PLANNED]`
feature, and turn the readiness field into a Next field that names the
concrete next action.

## Acceptance criteria
- The task rollup rule in `commands/production-status.md` renders `-` when a
  feature has zero tasks and its `FEATURES.md` status is `[DONE]` or
  `[PLANNED]`, and keeps `no tasks yet` for every other status. The
  "signal that `/task-add feature=<slug>` has not run" gloss stays attached
  to `no tasks yet` only, since it is false for the `-` case.
- The same rule applies under `--task-ids`: zero tasks on a `[DONE]` or
  `[PLANNED]` feature renders `-` there too, not an empty ID list.
- Section 2's last field is a **Next** field, not a readiness field, and
  prints exactly one of:
  - `-` — feature is `[DONE]`.
  - `/task-add feature=<slug>` — feature is `[NEW]` or `[ITERATED]`.
    Printed even when the feature is blocked; planning is never blocked by a
    dependency.
  - `flip to [DONE]` (worded as a suggestion to update `FEATURES.md`
    manually) — feature is `[PLANNED]` and has no task that is not `[DONE]`
    or `[SKIP]`, including the zero-task case. Printed even when blocked;
    there is no work left to block.
  - `/task-implement <N>` — feature is `[PLANNED]` with at least one task
    not `[DONE]`/`[SKIP]` and the feature is **not** blocked. `<N>` is the
    lowest-numbered such task.
  - `blocked by <slug>[, <slug>]` — the case above, but the feature **is**
    blocked. This is the only status where blockedness suppresses the
    action, because `/task-implement` is the only suggested action a
    dependency can actually block.
- Section 2's example block is updated to show the new column, and the
  prose that described the field as readiness ("Each carries … and its
  readiness", the `[DONE]` row exception) is rewritten to describe the Next
  field. A `[DONE]` row still ends with `-` rather than nothing computed.
- Readiness itself is unchanged: still derived every read, still never
  stored, still what sections 3, 4 and 5 are built from, and still never
  computed for a `[DONE]` feature. Only section 2's presentation of it
  changes.
- Sections 3, 4, 5 and the FAILURE CONTRACT table are not reworded beyond
  what the Next field forces. The command stays read-only and shell-free.
- The `description:` frontmatter, which currently says "Readiness and
  coverage are derived on every read", reflects the Next column.
- `version:` in `commands/production-status.md` is bumped (minor — output
  surface changes), root `VERSION` is bumped, and `CHANGELOG.md` gets a
  matching top section. `./scripts/check-changelog.sh` is silent.
- `.claude/context/features.md`'s `commands/production-status.md` entry
  describes both the zero-task rollup rule and the Next column, and
  `.claude/context/INDEX.md`'s `Last updated:` anchor is moved.

## Decisions
- **`-` is scoped to `[DONE]` and `[PLANNED]`.** Those are the two states a
  feature reaches only after `/task-add feature=<slug>` has run, so zero
  tasks there means pruned, not unplanned. `[NEW]` and `[ITERATED]` keep
  `no tasks yet`, where it is true.
- **The Next field replaces readiness rather than joining it.** A separate
  Ready and Next column would repeat the same fact in two shapes; the
  blocked case already carries readiness into the Next field where it
  matters.
- **Blockedness gates only `/task-implement`** (user decision). `/task-add`
  against a blocked feature is legitimate — planning ahead of a dependency
  is fine — and a flip-to-`[DONE]` suggestion is bookkeeping, not work.
- **`[ITERATED]` is treated as `[NEW]`** (user decision): the next step is
  re-planning through `/task-add feature=<slug>`, which is what that
  command's reconciliation pass exists for.
- **`.claude/domain/features/plan-readout.md` is deliberately left to
  `/architect`.** Its section-2 description ("its readiness") is written at
  a level general enough that this change does not contradict it, so there
  is no concrete reconciliation to make and it is not a Hint here.
