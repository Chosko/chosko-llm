# Task 146 — Backfill CHANGELOG.md and make a VERSION bump require an entry

Target: claude

## Goal

The `version-changelog` feature (`.claude/domain/features/version-changelog.md`)
closes the gap between the ~104 releases this repo has shipped and the nothing it
tells its users about any of them. This task lands the first two of its three
parts together, because neither holds alone: the record itself — a curated
`CHANGELOG.md` at the repo root, backfilled from `git log` for every version ever
recorded — and the rule that makes writing an entry part of what a `VERSION` bump
*is*. The rule and the file must land in the same bump; a rule that is live before
the file exists is violated by the very change that introduces it.

## Acceptance criteria

- `CHANGELOG.md` exists at the repo root, beside `VERSION` and `README.md`. It
  opens with a short preamble stating the rule it lives under and its converse, so
  the file explains itself to a first-time reader. Everything above the first
  `## ` is preamble and is never printed by anything.
- Every section has the shape `## <version> — <YYYY-MM-DD>`, followed by a blank
  line and one or more `- ` bullets. The version is the **first
  whitespace-delimited token after `## `** — that token is the only thing any
  parser reads; the em dash and the date are for human readers.
- The date is the commit date of the commit that set that `VERSION` value.
- **Every distinct `VERSION` value ever recorded gets a section, branch-only
  values included** — 104 as of authoring, `0.1.0` through `0.62.1` — plus one for
  the value this task bumps `VERSION` to. Branch-only values are in scope because
  `chosko-llm channel <branch>` exists precisely so a clone can sit on unmerged
  work, so a clone can genuinely be at `0.55.0`.
- **Ordering is strictly descending semver, newest first, with no duplicates** —
  not chronological.
- Bullets are short and user-facing. Each names the feature, command or script
  touched and the change a user would notice. No prose paragraphs, no commit shas,
  no nested lists, and **no `Added` / `Changed` / `Fixed` sub-headings**.
- **Attribution rule.** Walk the `VERSION`-setting commits in topological order;
  each version's bullets come from the commits between the previous such commit
  (exclusive) and its own (inclusive). Bullets are written from the *effect* of
  each commit, not by paraphrasing its subject line.
- **The `bd2a1cf` merge.** Commit `13e01c3` reset `VERSION` to `0.53.0` on a side
  branch that then ran up to `0.59.0`, while master independently ran `0.53.1` …
  `0.58.2`; the two merged at `bd2a1cf`, so master's first-parent sequence jumps
  `0.53.0` → `0.59.0`. The branch's own sections keep their bullets — its bumps
  already claimed those commits — and the `0.59.0` section records only that the
  branch merged.
- `CLAUDE.md` § Versioning gains the rule: **a `VERSION` bump without a matching
  `CHANGELOG.md` section is an incomplete change**, plus its converse stated
  generically: **a change that does not bump `VERSION` gets no `CHANGELOG` entry.**
- `docs/authoring-guide.md` § Versioning gains the same rule at length: the section
  schema, the descending-semver ordering rule and why the history forces it, and
  the parser contract (`^## ` introduces a section; the first token after it is the
  version; everything until the next `^## ` is that section's body; everything else
  on the line is presentational).
- `CHANGELOG.md` is **not a shipped feature**: no YAML frontmatter, it does not
  live under `commands/`, `skills/`, `claude-md/`, `statusline/` or `hooks/`, it is
  never copied into `$CLAUDE_HOME`, it is never listed by `chosko-llm ls`, and it
  is **not** added to `scripts/cmd-export.sh`'s selection.
- No backfill script is written or committed. This is authoring work done once;
  nothing in the repo replays it.
- The four invariants the guard in task 147 will check hold on the file this task
  writes, and are checked by hand here: (1) the file exists and has at least one
  section; (2) the **top** section's version token equals the trimmed contents of
  `VERSION`; (3) headers are strictly descending semver with no duplicates; (4) the
  top section has at least one bullet.
- Root `VERSION` takes a patch bump, and the resulting value is the top section of
  `CHANGELOG.md`.

## Decisions

- **Descending semver, not chronological — forced by the history, not a taste
  call.** The repo's history is a DAG, not a line (the `bd2a1cf` merge above).
  Chronological order would interleave the two lines and make "everything above the
  old version's header" wrong for the upgrade readout in task 148; descending semver
  makes it exactly right, and coincides with chronology everywhere outside that
  merge.
- **Branch-only versions are included**, because omitting them would send exactly
  the users who used `chosko-llm channel` down the degraded path of the readout.
- **No `Added` / `Changed` / `Fixed` sub-headings.** With ~104 sections of two-to-
  five bullets, sub-headings would roughly triple the file's line count and force a
  taxonomy judgement on every bullet, for a signal the bullet already carries by
  naming its artifact. Keep-a-Changelog's header shape, without its groupings.
- **The rule and the file land in one bump**, per the feature document's first
  internal ordering constraint.
- **The converse is stated generically, not as a named special case.** The known
  instance is `.claude/skills/` — this repo's own unshipped, unversioned audit
  skills, which by their feature's contract never bump `VERSION`. Phrasing it as a
  consequence of the general rule means it holds whether or not that feature has
  landed, and covers any future repo-local artifact on the same footing.
- **Verification is the guard's four invariants.** They are checked by hand in this
  task because the guard does not exist yet — it lands in task 147, which runs it
  against this file as its own acceptance criterion. The feature document requires
  the guard to land with or after the file, so it cannot come first.
- **Patch bump.** `CHANGELOG.md` is documentation, not a shipped feature or a CLI
  surface change, and `CLAUDE.md` § Versioning maps doc-only changes to patch.
- **No automation that writes entries from commit messages**, now or later. A
  generated changelog is a second, worse `git log`. Entries are curated prose.

## Hints

- `.claude/domain/features/version-changelog.md` — the feature document; §§ 1, 2
  and 7 govern this task.
- `CHANGELOG.md` (new, repo root)
- `CLAUDE.md` — § Versioning
- `docs/authoring-guide.md` — § Versioning
- `VERSION`
- Enumerating the versions and their dates:
  - `git log --all --format=%H -- VERSION` — every commit that touched the file
    (105 as of authoring, yielding 104 distinct values).
  - `git show <sha>:VERSION` — the value that commit set.
  - `git show -s --format=%cs <sha>` — its commit date as `YYYY-MM-DD`.
  - `git log --oneline <prev-sha>..<sha>` — the commits a section's bullets come
    from.
- Deliberately NOT touched: `scripts/cmd-export.sh`, `docs/cli-help.txt`,
  `bin/chosko-llm`, `install.sh`.
- No test suite by design: verify by reading the diff and by checking the four
  invariants by hand.
