# Task 193 — Update documentation for feature `pipeline-revision`

Target: claude

## Goal
Feature `pipeline-revision` adds a command and a skill for changing planned
work after it has been planned — a path the documentation does not describe at
all today, since until now an amendment meant re-running whichever owner
happened to hold the artifact. Bring the user-facing reference, the domain
layer's workflow documents and the context layer's per-file notes up to date
with what task 187 shipped.

## Acceptance criteria
- `README.md` describes the revision path where it describes planning: a change
  touching exactly one owner is `/pipeline-patch`, anything structural is
  `/pipeline-revise`, and both write only through the artifact's owner.
- `docs/reference.md` gains `### /pipeline-patch` and `### /pipeline-revise`
  sections in § 4: the three anchor forms, the patcher's single-owner rule and
  its five refuse signals, the reviser's four branches, the three tiers, the
  single gate, the editorial question, the lint-before/lint-after bracket, and
  the four-or-more-steps runbook offer.
- `.claude/domain/product-workflow.md` gains a revision section covering both
  surfaces, and its who-writes-what material records that neither surface owns
  a line in any index.
- `.claude/domain/task-workflow.md` records that a live task is changed through
  `task-engine`'s amend reference driven by these two surfaces, and that
  removing one is `[SKIP]` with a reason, never deletion.
- `.claude/context/features.md` reflects the new `commands/pipeline-patch.md`
  and the new `skills/pipeline-revise/` folder with its four branch files.
- `.claude/context/INDEX.md`'s `Last updated:` anchor is refreshed.
- `.claude/domain/features/pipeline-revision.md` is reconciled on exactly these
  3 points — editing it is authorised for this task, see Decisions:
  1. § *Architecture* — both surfaces and the branch files are named
     abstractly; the shipped paths (`commands/pipeline-patch.md`,
     `skills/pipeline-revise/SKILL.md`, and the flat `amend.md`, `insert.md`,
     `delete.md`, `reorder.md`) replace the abstract naming.
  2. § *Interfaces and contracts* — `/pipeline-patch`'s argument shape gains
     the `[--commit] [--no-push]` it ships with, forwarded to the amend arm it
     executes (recorded as a decision in task 187).
  3. § *Open questions*, bullet 2 — "Is a reorder branch worth shipping first?"
     is settled by what shipped and reads as decided rather than open.
  Nothing else in the document changes. In particular open questions 1
  (subagents for in-session actuation) and 3 (where a roadmap-milestone
  revision goes) are left open — real use answers them.
- No `VERSION` bump and no `CHANGELOG.md` entry — every path above is
  documentation or the navigation/domain layer, which `CLAUDE.md` § Versioning
  exempts. `./scripts/check-changelog.sh` must still exit zero.

## Decisions
- **Editing `.claude/domain/features/pipeline-revision.md` is explicitly
  authorised for this task (user decision, 2026-09-09), for the 3
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document
  is normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- **No `VERSION` bump.** `CLAUDE.md` § Versioning exempts `README.md`,
  `docs/`, `.claude/domain/` and `.claude/context/`. The shipped bodies changed
  in task 187, which bumped for itself; bumping again for a change no user
  receives would corrupt the version `install.sh` reports.
- **`docs/authoring-guide.md` and `CLAUDE.md` are deliberately untouched.**
  This feature adds one command and one skill — both established kinds, with no
  new frontmatter field, no new asset kind and no new hard rule — so neither
  document has anything to reconcile.
- **`.claude/domain/features/pipeline-engine.md` and
  `owner-amend-arms.md` are deliberately untouched.** This feature consumes
  their routing table and their arms exactly as those documents already
  anticipate; there is nothing to reconcile, and both belong to `/architect`
  and to their own features' planning runs.
