# Task 253 — `/pipeline-revise` takes a change set behind one numbered plan gate; `/pipeline-patch` retired

Target: claude

## Goal
A revision of planned work is usually several changes at once, and the skill
takes one: a request of two kinds is two runs, a change across four features
is four runs, and `/pipeline-patch` refuses anything structural instead of
escalating. Make `/pipeline-revise` take the whole change set, plan it as one
numbered owner sequence behind one gate the user edits by number, run every
pre-answerable owner headless, announce every gate that remains, and retire
`/pipeline-patch`, whose single-owner case is the trivial change set.

## Acceptance criteria
- **Input.** `/pipeline-revise "<change set>" [--no-commit] [--no-push]`: the
  change set is free-form text describing several changes, or a pasted
  numbered list in the shape `/follow-ups` prints. Anchors are named inline
  and several are allowed; the anchor argument form still works for a
  single-item set.
- **Per item.** Each item is classified into amend, insert, delete or reorder
  with the existing test order, and its impact walked as today. A run reads
  every branch file its items need; the four branch files keep their schema.
- **Merge and order.** Items become one owner sequence: two edits to the same
  feature document are one `/architect amend` with several sections; several
  feature documents are one multi-slug run; two roadmap or plan edits are one
  arm run; deletes precede plan reconciliation, which precedes runbook strikes;
  `/architect amend` precedes `/task-add` reconciliation.
- **Decisions at plan time.** Every owner decision that is a closed rule over
  reads is made while planning and shown on its step: the editorial
  classification per feature, task-amend drafts, runbook strikes and
  `Context:` facts, the roadmap, plan and design arms' drafted edits. Such a
  step is tagged `headless`. A `/task-add` create or reconcile step is tagged
  `GATED` with one `Will ask:` line naming what the owner will ask; gated steps
  sort last when dependency order allows. A reconcile step is conditional on
  plan-time evidence and shows it (`because step 1 stales 12, 14`). An id
  unknown until a step runs is a placeholder (`<id from step 5>`).
- **The gate.** One plan gate, always waiting for a reply: numbered steps,
  each with owner, tag, invocation or arm path, what it writes and the lint
  findings it clears or creates. Reply grammar: `go`; `all but N`; `N as
  runbook step`; `N after M`; `stop`. An edit re-renders the plan at the same
  gate. A step deferred to a runbook is appended to a named runbook, or a new
  one is created, through `/runbook-create`, with a self-contained prompt.
- **Execution.** Steps run sequentially in the session, arms headless with
  their carried decisions, never in a subagent, never in parallel. Nothing is
  written before the gate, and no step is added after it.
- **Closing follow-up gate.** When execution surfaces something the plan did
  not hold — a task created with no runbook step, a successor that no longer
  reads as a sequence — one closing gate renders those items in the same
  numbered shape with the same reply grammar; nothing is written on them
  without it. A run that surfaces nothing ends with the report alone.
- Lint before and after, one commit, the report line and the failure contract
  are unchanged in meaning.
- **Retire `/pipeline-patch`.** `commands/pipeline-patch.md` is deleted. Its
  routing row, every `lint.md` fix-command reference, `pipeline-suggest`'s
  routing, `/pipeline-check`'s pointers, `/task-add`'s write-back line,
  `/runbook-create`'s and `architect/amend.md`'s mentions, `pipeline-engine`'s
  and `task-engine`'s body text, `docs/reference.md`, `docs/authoring-guide.md`
  and `README.md` name `/pipeline-revise` instead. `./scripts/check-routing.sh`
  and `./scripts/check-home-paths.sh` are silent.
- `.claude/domain/features/pipeline-revision.md` and `pipeline-suggest.md` are
  reconciled with what ships on exactly these points — editing them is
  authorised for this task, see Decisions: (1) one revision surface, the
  patch/revise split gone; (2) a change set as input and one numbered plan
  gate; (3) headless and gated steps, decisions at plan time; (4) the closing
  follow-up gate; (5) `pipeline-suggest` routes every revision request to
  `/pipeline-revise`. Passages in other feature documents that mention
  `/pipeline-patch` only in passing are updated as consequential edits.
  Nothing else in those documents changes.
- `.claude/domain/product-workflow.md`, `.claude/domain/task-workflow.md` and
  `.claude/context/features.md` describe one revision surface.
- `skills/pipeline-revise` `version:` major bump; `pipeline-engine`,
  `pipeline-suggest`, `task-add`, `runbook-create`, `pipeline-check`,
  `architect`, `task-engine` patch bumps; root `VERSION` minor bump;
  `CHANGELOG.md` entry naming the removal; `./scripts/check-changelog.sh`
  silent.

## Decisions
- Retiring `/pipeline-patch` in the same task as the fusion: a separate task
  would leave a window in which two surfaces exist and their documents
  contradict each other.
- Root `VERSION` bumps minor, not major: major is reserved for the `chosko-llm`
  CLI surface, and a removed command is a feature change.
- No subagents and no parallel steps: every owner step writes `TASKS.md` or
  `FEATURES.md`, and sequential headless steps are already fast once the gates
  are gone.
- **Editing `.claude/domain/features/pipeline-revision.md` and
  `.claude/domain/features/pipeline-suggest.md` is explicitly authorised for
  this task (user decision, 2026-09-21), for the five reconciliations listed
  above and for nothing else; the same decision covers the passing mentions
  of `/pipeline-patch` in the other feature documents. Do not ask for
  permission at implementation time.** The documents are normally
  `/architect`'s; a change beyond those points is a design decision and stops
  the run to say so.
