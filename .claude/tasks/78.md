# Task 78 — Sweep the conversation for uncaptured design detail at the end of /product-design PHASE 3

Target: claude

## Goal
`/product-design` PHASE 3 fills `product-design.md` (and `business-model.md`
when it exists) from the PHASE 2 interview, then reports and stops for the
user. Everything the interview surfaced but the write-back didn't capture
dies with the context window — and PHASE 3 is exactly where a session
typically ends. Add a final step to PHASE 3, after the write-back and before
the existing report-and-stop, that re-reads the documents just written
against the conversation transcript, identifies material the documents do
not cover, and integrates it. The phase then concludes with the report and
stop it already has.

## Acceptance criteria
- `skills/product-design/SKILL.md` PHASE 3 gains a final step, placed after
  the write-back and before the stage-marker rewrite / report / stop, that
  compares the documents just written against the conversation so far and
  integrates what is missing.
- The step names what it is looking for: decisions, constraints, user or
  flow detail, rejected alternatives, and terminology raised in conversation
  that no section of the written documents reflects.
- The step states where each kind of finding goes — WHAT/HOW into
  `product-design.md`'s existing sections, business material into
  `business-model.md` when it exists, WHY/rationale/rejected alternatives
  into `design-process.md` — consistent with PHASE 3's documentational
  register.
- The step respects PHASE 3's existing guards: it does not write technical
  or implementation-level detail (a hard technical constraint stated by the
  user is captured in one line, as elsewhere in the skill), does not write
  the high-level feature set (PHASE 4/5's output), and does not touch
  `.claude/FEATURES.md`, `.claude/domain/features/`, or `.claude/TASKS.md`.
- The step is automatic — it does not open a new approval gate or a new
  question round — and integrates the findings directly.
- Every path the step writes is added to `WRITTEN`, so the existing
  `--commit` path and the "nothing was committed" reminder stay correct.
  `design-process.md` in particular must land in `WRITTEN` if the step
  writes rationale into it.
- The existing PHASE 3 report is extended to name what the sweep integrated
  (or to state that the documents already covered everything), and the phase
  still ends by rewriting the stage marker and stopping for the user.
- The sweep is a no-op when nothing is missing: it reports that and writes
  nothing, rather than manufacturing content or restating what is already
  written.
- `.claude/domain/product-workflow.md` records the sweep — as the mechanism
  that keeps `design-process.md` and `product-design.md` from losing what
  the conversation held, under or beside the "Session resumability" section.
- `.claude/context/features.md`'s `skills/product-design/` bullet describes
  PHASE 3 as write-back plus transcript sweep.
- `README.md`'s `/product-design` section mentions in one sentence that
  PHASE 3 sweeps the conversation before it stops.
- `skills/product-design/SKILL.md` frontmatter `version:` gets a minor bump
  from whatever it is when this task is implemented, and root `VERSION` gets
  a minor bump from its then-current value. Do not assume the values this
  task was written against — tasks 76 and 77 bump both files first if they
  land first.

## Decisions
- Scoped to PHASE 3 only, as asked. PHASE 5 is the other write-back and the
  other natural session boundary, so the same sweep arguably belongs there
  too — but PHASE 5's material is the feature set the user explicitly
  confirms in PHASE 4, which is a weaker case for an automatic sweep. Left
  out; a follow-up task if wanted.
- Automatic, not gated. The instruction says the information is integrated,
  and PHASE 3 already ends with a report the user reviews before PHASE 4 —
  that report is the review surface, so a second approval prompt would only
  add friction.
- Findings are routed to three documents rather than all funnelled into
  `product-design.md`. The register split (documentational vs. rationale) is
  already the skill's rule; a sweep that ignored it would push WHY-material
  into the wrong document.
- Minor version bump on both the skill and root `VERSION`: this is new
  behaviour in a shipped skill, not a fix or a doc-only change. Stated
  relatively rather than as fixed numbers because tasks 76 and 77 touch the
  same two files.
- Not sequenced behind task 76 despite the file overlap. Task 76 appends
  phases 6 and 7 and edits PHASE 1, the SUPPORTING FILES table, and the DO
  NOT list; PHASE 3 keeps its number either way, so the two are independent.
  Whichever lands second reconciles the shared DO NOT list and the version
  lines.
