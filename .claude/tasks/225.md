# Task 225 — Let an owned document stay in a task's Hints as a read-only Reference

Target: claude

## Goal
`/task-add`'s OWNERSHIP PRE-AUTHORISATION treats every owned path in `## Hints` or `Files:` as something to edit, and drops any path with no nameable reconciliation. A pointer the implementer only needs to *read* therefore disappears exactly when the design document is already correct, the healthy state. It also contradicts PHASE 4 feature case step 2, which requires the feature's document under `## Hints`. Observed on job-hunter-cli, 2026-09-15: three of five detected paths (tasks 206, 199, 188) were read-only pointers and were deleted, and hand-restoring them doesn't last because the next reconciliation strips them again. Add a third outcome, Reference, keeping the rule's core property: every detected file gets a decision, silence is never a grant, and PHASE 4 never writes a file nobody decided on.

## Acceptance criteria
- The ownership question in `commands/task-add.md` offers three answers: **Grant**, **Reference**, **Drop**. A Reference keeps the path in `## Hints` with a fixed read-only marker (one literal text, defined once in that section). It never keeps the path in `Files:` and authorises no edit.
- The Enumeration step decides each detected file by what can be named:
  - Reconciliation points can be named: ask Grant / Reference / Drop. Reference and Drop both record the points left undone in `## Decisions`, as Decline does today.
  - No points, the path is the feature-derived task's own `Doc:` document, and the task is not the documentation task: write it as a Reference without asking. The rule itself decides this, because PHASE 4 feature case step 2 requires that pointer.
  - No points, some other owned path, and a concrete reason to read it (the section the task implements): ask Reference / Drop.
  - No points and no read reason: drop, ask nothing (today's behaviour).
  - The documentation task, with no points: drop, as today. It exists to edit, so a read-only pointer adds nothing there.
- A marked Reference carried unchanged into a rewritten body (reconciliation, or `task-engine/references/amend.md`) counts as already decided and is not asked again. Turning it into something to edit, or adding a new owned path, is a new question.
- The hard rules and the DO NOT bullet cover all three outcomes: PHASE 4 refuses a task where a detected file is not granted, referenced or removed, and a Reference is never a grant.
- The `## Hints` description in the body schema mentions read-only references.
- `skills/task-engine/references/amend.md` § *Owned documents* cites three answers instead of "grant-or-drop" and "its two answers", and states the marker-carryover rule.
- `skills/task-implement/SKILL.md` § USING THE TASK BODY says a Hint with the marker is read-only. If the implementation turns out to need that document edited, stop and say so; don't edit it.
- `.claude/domain/product-workflow.md` § Documentation task, `.claude/domain/task-workflow.md` (the "Feature document itself read-only" paragraph) and `.claude/context/features.md` (the `/task-add` owned-documents passage) describe three outcomes.
- Frontmatter versions are bumped (`task-add`, `task-engine`, `task-implement`), root `VERSION` gets a minor bump with a matching `CHANGELOG.md` section, and `./scripts/check-changelog.sh` passes.

## Decisions
- **Reference is a third answer, not lighter detection on Hints.** The body schema defines Hints as "file paths the implementer should touch: edit targets…", so Hints are part of what gets edited, and splitting by field would make an ungated edit target possible.
- **A feature-derived task's own document becomes a Reference without asking** (user decision, 2026-09-15). This isn't a grant: PHASE 4 step 2 already requires that pointer, so the rule decides it. The documentation task is excluded, and so is any path where edit points can be named. Those are still asked.
- **An unchanged marker counts as a decision on re-runs** (user decision, 2026-09-15). This is the same shape as amend.md's "an existing grant is never widened", and it's what makes restored pointers survive the next reconciliation.
