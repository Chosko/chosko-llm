# Task 80 — Make /task-add append a final documentation-update task in feature mode

Target: claude

## Goal
When `/task-add feature=<slug>` plans (or reconciles) a batch of tasks, the
resulting implementation work routinely leaves shipped documentation
(README.md, docs/authoring-guide.md, domain docs, context-layer docs)
describing the pre-feature state. Nothing in the current flow captures that
follow-up, so it gets forgotten or done ad hoc. Make PHASE 3/4's feature
case append one additional task at the end of the batch whose job is to
update the documentation layers affected by the feature, once its other
tasks are implemented. This only applies to feature mode — the free-form
path is unchanged.

## Acceptance criteria
- In `commands/task-add.md`'s feature case (PHASE 3 draft + PHASE 4 write),
  after the normal new-task drafts (and any reconciliation), exactly one
  more task is drafted and — on approval — written: title along the lines
  of "Update documentation for feature `<slug>`", `Target: claude`,
  `Feature: <slug>`, and `Preconditions:` listing every other new task ID
  created in this run (signals it should land last; not enforced
  mechanically, same as any other `Preconditions:` line).
- Skipped when the run creates zero new tasks (a reconciliation-only run
  where every existing task is left untouched) — there is nothing new to
  document.
- The doc task's `## Hints` are populated from the same collateral
  identified in PHASE 1 (README.md, docs/authoring-guide.md, relevant
  `.claude/domain/*.md`, `.claude/context/features.md`,
  `.claude/context/INDEX.md`) — whichever of these actually describe the
  behavior the feature changed. Not a fixed list; judgment per feature,
  same as any other task's Hints.
- **Ownership gate:** if any of the identified documentation lives in a
  file `/task-add` does not itself own — `.claude/domain/features/<slug>.md`
  (owned by `/architect`) or `product-design.md` / `technical-direction.md`
  / `business-model.md` (owned by `/product-design`) — do NOT add it to the
  doc task's Hints silently. Instead, surface it explicitly during PHASE 3
  and ask the user for confirmation before including it (default suggestion:
  leave it out, since these stay read-only elsewhere in the pipeline).
  Include it in the drafted task only on explicit yes.
- This is additive to the feature case only; a plain `/task-add
  <description>` run (no `feature=`) is unaffected and indistinguishable
  from before.
- `commands/task-add.md` frontmatter `version:` bumped (minor); root
  `VERSION` bumped (minor) per CLAUDE.md's versioning rule.
- `README.md`, `docs/authoring-guide.md`, `.claude/domain/product-workflow.md`,
  `.claude/context/features.md`, and `.claude/context/INDEX.md` (if its
  `Last updated` anchor scheme requires it) reflect the new behavior.

## Decisions
- Treated as one task rather than split into "append the doc task" +
  "add the ownership-confirmation gate" — the confirmation gate is a
  constraint on the same behavior, not an independently deliverable unit.
- The doc-update task's `Preconditions:` names the other new tasks from the
  same run, even though `Preconditions:` is informational only (not
  enforced by `/task-implement`) — consistent with how the field is used
  elsewhere in this backlog.
- A reconciliation-only run (no new tasks) does not get a doc task, since
  the trigger is "new work exists to document."
