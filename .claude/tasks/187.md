# Task 187 — Add the `pipeline-revise` skill body and its branch classifier

Target: claude

## Goal
Feature `pipeline-revision` ships two surfaces for changing already-planned
work. This task builds the heavier one's spine: a new skill folder,
`skills/pipeline-revise/`, whose `SKILL.md` holds everything common to all four
branches — the probe and its verdict line, anchor resolution and the graph
walk, the classification that picks exactly one branch file, the three tiers
and the single gate, the lint-before/lint-after verification bracket, and the
two actuation modes. The branch files themselves land in tasks 188–191.

## Acceptance criteria
- `skills/pipeline-revise/SKILL.md` exists with `name: pipeline-revise`,
  `version: 0.1.0`, `type: skill`, a description naming the impact walk, the
  single gate and the four-or-more-steps runbook offer, and
  `requires: skill:pipeline-engine, skill:architect, skill:task-engine,
  skill:runbook-run`.
- Argument shape: `/pipeline-revise [<anchor>] "<change>" [--commit]
  [--no-push]`. The anchor is optional when the description resolves one; its
  forms are `feature=<slug>`, `task=<N>` and `runbook=<name|id> step=<n>`.
- Probing cites
  `${CLAUDE_HOME:-$HOME/.claude}/skills/pipeline-engine/references/probes.md`
  by path, prints or reuses the verdict line per that file's own reuse rule,
  and states no probe rule of its own.
- The graph walk cites `.../references/graph.md` as its only traversal input
  and restates none of it.
- Classification picks exactly one of amend / insert / delete / reorder and
  then reads only that branch's file (`./amend.md`, `./insert.md`,
  `./delete.md`, `./reorder.md`). A SUPPORTING FILES table with an "exactly
  when" column and a do-not-read-speculatively note carries the dispatch, in
  the register `skills/architect/SKILL.md` uses.
- Body reading is scoped and the scope is stated: the target artifact, the
  tasks whose `Preconditions:` name it or whose `Files:` overlap, and the
  runbook steps that name it. A bulk read of the backlog is forbidden as a
  DO NOT.
- The proposal names the tier — editorial, local or structural — the artifacts
  touched, the owner steps in order, and the lint findings the change will
  create or clear.
- The editorial question is asked on every run and is never inferred,
  classified or skipped, whatever the tier.
- Exactly one gate. Nothing is written before it, by this skill or by any arm
  it drives.
- Verification bracket: `/pipeline-check` scoped to the anchor runs before the
  proposal and again after actuation, and the report shows the difference.
  Where an insertion or deletion changed a precondition, the successor tasks'
  bodies are read afterwards to confirm the sequence still reads as a
  sequence.
- Actuation: three or fewer owner steps run in the session, sequentially, each
  through the owner's amend arm or command with that owner's own gate intact.
  Four or more offer a choice — run them in the session anyway, or hand them to
  `/runbook-create` and stop. `/runbook-create` is detected at run time and the
  offer is omitted silently when it is absent, the same optional delegation
  `skills/architect/council-gate.md` uses. The skill never writes a runbook
  itself.
- Write set closed and stated: this skill writes no line any owner owns; every
  write goes through an arm or an owner command. `--commit` / `--no-push` are
  forwarded to each owner step and acted on nowhere here.
- Failure contract stated: an anchor that resolves to nothing stops by listing
  what exists; an owner arm that refuses — a touched `[IN PROGRESS]` task, for
  instance — stops the sequence at that step with earlier steps' writes intact
  and reported, never rolled back.
- `skills/pipeline-engine/references/routing.md` gains a row for
  `pipeline-revise` — consumes, produces, owner-of `none`, preconditions,
  argument shape — so `scripts/check-routing.sh` stays silent once this ships.
- Root `VERSION` is bumped (minor) and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` is silent.

## Decisions
- **The branch files sit flat beside `SKILL.md`, not under `references/`.**
  They are on-demand files read only by their own skill — the
  `skills/architect/` and `skills/product-design/` pattern. `references/` in
  `task-engine` and `pipeline-engine` holds rules read by *other* features,
  which is not what these are; no `requires:` relationship is involved.
- **The reviser ships before the patcher.** `/pipeline-patch`'s refuse line
  names `/pipeline-revise`, and shipped content never names an unshipped
  command. Task 192 preconditions on this one for that reason alone.
- **The routing row lands with the skill.** `scripts/check-routing.sh` flags a
  shipped pipeline skill that has no row, so deferring the row to a later
  consolidating task would leave the repo failing its own check in between.
- **`requires:` names the owner skills, not only the engine.** A reviser with
  no owner to delegate to has nothing to do — the reasoning the feature
  document gives for the patcher applies here unchanged.
- **The skill commits nothing by default.** It is a skill, and every skill in
  this repo takes `--commit`; the arms it drives default the same way.
