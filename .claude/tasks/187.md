# Task 187 — Ship the `pipeline-revise` skill with its four branches and the `/pipeline-patch` command

Target: claude

## Goal
Feature `pipeline-revision` ships two surfaces for changing already-planned
work, at proportional cost, through the artifacts' owners:

- **`pipeline-revise`**, the heavier one: a skill folder whose `SKILL.md` holds
  everything common to a revision — the probe and its verdict line, anchor
  resolution and the graph walk, the classification that picks exactly one
  branch file, the three tiers and the single gate, the lint-before/lint-after
  verification bracket, and the two actuation modes — plus four branch files
  read on demand: `amend.md` (something that exists changes), `insert.md` (the
  feature's motivating example: attach, place, write back, insert the runbook
  step, confirm the lint is clean), `delete.md` (removal mapped onto `[SKIP]`
  and struck steps, never physical deletion) and `reorder.md` (a
  skip-and-insert, the shortest file).
- **`/pipeline-patch`**, the cheap one: a command that probes, walks the graph
  reading only the indexes, counts the owners the change would touch, and
  either executes that one owner's amend arm and runs the scoped lint, or
  refuses in one line naming `/pipeline-revise` and the signal that triggered
  it.

The two surfaces are two halves of one boundary — the patcher's five refuse
signals are exactly the cases the reviser's classifier receives, and their
anchor forms must be identical — and the four branch files share one schema
and one dispatch table. One author writes all of it in one pass, and the skill
ships complete at `0.1.0` instead of gaining a branch per release. Both
surfaces write nothing themselves; every write goes through an owner's amend
arm (task 182) or an owner command, and the insertion primitives come from
`backlog-ordering` (tasks 169 and 173).

## Acceptance criteria

### `skills/pipeline-revise/SKILL.md`
- Exists with `name: pipeline-revise`, `version: 0.1.0`, `type: skill`, a
  description naming the impact walk, the single gate and the
  four-or-more-steps runbook offer, and
  `requires: skill:pipeline-engine, skill:architect, skill:task-engine,
  skill:runbook-run`.
- Argument shape: `/pipeline-revise [<anchor>] "<change>" [--commit]
  [--no-push]`. The anchor is optional when the description resolves one; its
  forms are `feature=<slug>`, `task=<N>` and `runbook=<name|id> step=<n>`.
- Probing cites
  `${CLAUDE_HOME:-$HOME/.claude}/skills/pipeline-engine/references/probes.md`
  by path, prints or reuses the verdict line per that file's own reuse rule,
  and states no probe rule of its own.
- The graph walk cites `.../references/graph.md` as its only traversal input
  and restates none of it.
- Classification picks exactly one of amend / insert / delete / reorder and
  then reads only that branch's file (`./amend.md`, `./insert.md`,
  `./delete.md`, `./reorder.md`). A SUPPORTING FILES table with an "exactly
  when" column and a do-not-read-speculatively note carries the dispatch, in
  the register `skills/architect/SKILL.md` uses. All four rows are written
  here, complete, since all four files ship in this task.
- Body reading is scoped and the scope is stated: the target artifact, the
  tasks whose `Preconditions:` name it or whose `Files:` overlap, and the
  runbook steps that name it. A bulk read of the backlog is forbidden as a
  DO NOT.
- The proposal names the tier — editorial, local or structural — the artifacts
  touched, the owner steps in order, and the lint findings the change will
  create or clear.
- The editorial question is asked on every run and is never inferred,
  classified or skipped, whatever the tier.
- Exactly one gate. Nothing is written before it, by this skill or by any arm
  it drives.
- Verification bracket: `/pipeline-check` scoped to the anchor runs before the
  proposal and again after actuation, and the report shows the difference.
  Where an insertion or deletion changed a precondition, the successor tasks'
  bodies are read afterwards to confirm the sequence still reads as a
  sequence.
- Actuation: three or fewer owner steps run in the session, sequentially, each
  through the owner's amend arm or command with that owner's own gate intact.
  Four or more offer a choice — run them in the session anyway, or hand them to
  `/runbook-create` and stop. `/runbook-create` is detected at run time and the
  offer is omitted silently when it is absent, the same optional delegation
  `skills/architect/council-gate.md` uses. The skill never writes a runbook
  itself.
- Write set closed and stated: this skill writes no line any owner owns; every
  write goes through an arm or an owner command. `--commit` / `--no-push` are
  forwarded to each owner step and acted on nowhere here.
- Failure contract stated: an anchor that resolves to nothing stops by listing
  what exists; an owner arm that refuses — a touched `[IN PROGRESS]` task, for
  instance — stops the sequence at that step with earlier steps' writes intact
  and reported, never rolled back.

### `skills/pipeline-revise/amend.md`
- Exists and is complete on its own: a consumer that has read `./SKILL.md` and
  this file can execute the branch end to end.
- Top-down rules stated: from a design section or a feature document to the
  tasks carrying that `Feature:`, the `PLAN.md` edges naming the slug, and the
  runbook steps naming the slug or one of its task ids.
- Bottom-up rules stated: from a task to the feature document that promised it,
  when its `Feature:` slug resolves in `FEATURES.md`. A `Feature:` slug that
  resolves to nothing, or an absent one, stops the upward walk and the task is
  treated as free-form — not an error.
- The owner sequence is fixed and stated, upstream first: `/product-design`'s
  amend arm, then `/architect amend`, then task bodies through
  `task-engine`'s amend reference, then runbook steps through `runbook-run`'s
  step-amend reference. No downstream step is written against a state a later
  step changes.
- Tier logic stated: *editorial* — wording only, nothing downstream changes
  meaning; *local* — one artifact plus the entries that merely name it;
  *structural* — scope changes, or a downstream entry's contract changes. The
  tier drives how long the owner sequence is; it never decides whether the gate
  is asked.
- Adds no read of its own beyond the anchor scope `./SKILL.md` already fixes.
- Writes nothing itself. Every step names, by path, the arm it delegates to.
- No new status value: the outcomes are `[STALE]`, `[ITERATED]` and the
  owners' existing flips, and the file says so.

### `skills/pipeline-revise/insert.md`
- Exists and is complete on its own: a consumer that has read `./SKILL.md` and
  this file can execute the branch end to end.
- The composition is named explicitly, by primitive:
  `/task-add feature=<slug> --single` attaches exactly one task to a planned
  feature; `--before <N>` / `--after <N>` place it; the orphan-task prompt
  covers a task belonging to no feature;
  `/runbook-create --append --before <n>` / `--after <n>` inserts a step.
- Direction rules stated: an insertion walks *forward* to the successor tasks
  whose `Preconditions:` must gain the new id, and *upward* to the feature
  document that must promise the new scope.
- The owner sequence for the worked example is given in order: `/architect
  amend` for the scope, then `/task-add feature=<slug> --single --after <N>`,
  then each successor's `Preconditions:` through `task-engine`'s amend
  reference, then the runbook step insert, then the scoped lint.
- Tier logic stated: an insert adding scope no existing task covers is
  *structural* and flips the feature `[ITERATED]` through `/architect amend`;
  an insert of something the feature document already promises is *local* and
  leaves the feature status alone.
- The branch-specific half of the verification bracket is stated: after
  actuation the successor tasks' bodies are read to confirm the sequence still
  reads as a sequence.
- A `[RUNNING]` runbook accepts an insert after the current step and nothing
  before it — cited from `runbook-run`'s step-amend reference, not restated as
  a rule of this file's own.
- Writes nothing itself; every step names the primitive or arm it delegates
  to, by path or by command name.

### `skills/pipeline-revise/delete.md`
- Exists and is complete on its own: a consumer that has read `./SKILL.md` and
  this file can execute the branch end to end.
- Task removal is `[SKIP]` with a reason recorded in the task body, through
  `task-engine`'s amend reference. Physical removal is never performed here;
  it stays `/task-clean`'s explicit act over terminal statuses, and the file
  says so.
- Runbook-step removal is a strike — `[x]` with a `Done:` line opening
  `struck — <reason>` and no commit sha — through `runbook-run`'s step-amend
  reference. A step is never deleted and never renumbered.
- Feature removal is `[SKIP]` on every one of its live tasks followed by a
  `/production-plan` run, whose reconciliation drops the edges. The feature's
  `FEATURES.md` entry stays, with its ids intact.
- `[DONE]` work is never reopened, re-statused or removed, in any of the three
  shapes.
- Direction rules stated: a deletion walks *forward* to the successors whose
  `Preconditions:` name the removed id — each such edge is dropped through the
  task amend reference, and the drop is named in that task's `## Decisions` —
  and *upward* to the feature document that promised the deleted scope.
- Tier logic stated: deleting a task no other entry names is *local*; a
  deletion that crosses artifacts, or that drops an edge, is *structural*.
- The branch-specific half of the verification bracket is stated: after
  actuation the successor tasks' bodies are read to confirm the sequence still
  reads as a sequence.
- Writes nothing itself; every step names the arm it delegates to, by path.
- No new status value and no change ledger: `[SKIP]`, struck steps and the
  owners' commits are the provenance, and the file says so explicitly.

### `skills/pipeline-revise/reorder.md`
- Exists and is complete on its own: a consumer that has read `./SKILL.md` and
  this file can execute the branch end to end, following the two cited files
  for the mechanics. Deliberately the shortest of the four.
- Reordering a task is stated as: `[SKIP]` the entry in place, with a reason
  naming the reorder, then insert a replacement at the new position — per
  `./delete.md` and `./insert.md`, cited by path. Ids are never renumbered and
  the file cites `task-engine`'s resolution rule for why.
- Reordering a runbook step is the same shape: strike, then positional insert.
- The classifier boundary is stated: a change to `Preconditions:` that does not
  move an entry is an *amend*, not a reorder, and routes to `./amend.md`. This
  is what keeps `./SKILL.md`'s classification unambiguous.
- The tier is fixed, not judged: every reorder is *structural*, because it
  changes an order or an edge by definition.
- Restates no rule that `./delete.md` or `./insert.md` owns; it composes them
  and adds only its own boundary, tier and reason wording.
- Writes nothing itself.

### `commands/pipeline-patch.md`
- Exists with `name: pipeline-patch`, `version: 0.1.0`, `type: command`, a
  description naming the single-owner rule and the refuse, and
  `requires: skill:pipeline-engine, skill:architect, skill:task-engine,
  skill:runbook-run`.
- Argument shape: `/pipeline-patch <anchor> "<change>" [--commit] [--no-push]`.
  The anchor is required here, unlike on the reviser; its forms are
  `feature=<slug>`, `task=<N>` and `runbook=<name|id> step=<n>` — identical to
  the reviser's, word for word.
- Probing cites `pipeline-engine`'s `probes.md` by path and reuses a verdict
  line already in the conversation per that file's rule.
- The graph walk reads ONLY the indexes — `.claude/FEATURES.md`,
  `.claude/TASKS.md`, `.claude/PLAN.md`, `.claude/RUNBOOKS.md`. Never a task
  body, never a feature document, never a runbook body. This appears as an
  explicit DO NOT, and it is the line separating this command from the reviser.
- The proceed condition is a count plus a checklist, never a judgement: exactly
  one owner among feature document, task and runbook step, AND none of the five
  structural signals present.
- The five signals are listed verbatim and closed: more than one owner; a
  dependency edge changing; scope added that no task covers; a deletion that
  crosses artifacts; a reorder of existing entries. Each signal corresponds to
  a case the reviser's classifier handles; check the correspondence before
  finishing.
- Proceed path: load that owner's amend arm by path, execute it including its
  own gate, then run `/pipeline-check` scoped to the anchor, then report.
- Refuse path: one line naming `/pipeline-revise` and the signal that triggered
  it, then stop. No escalation, no second question, nothing written, no partial
  work.
- Failure contract: an anchor resolving to nothing stops by listing what
  exists.
- `--commit` / `--no-push` are parsed and forwarded to the arm; the command
  makes no commit of its own.
- The command writes no line any owner owns and does not appear in the
  who-writes-what table.

## Decisions
- **One task for both surfaces.** Planned as six tasks (187–192) and merged on
  2026-09-11 (user decision). Four branch files sharing one schema, each
  editing one SUPPORTING FILES table in turn, were four sequential edits by four
  agents to one small table; the patcher's refuse checklist and the reviser's
  classifier are the same boundary seen from two sides. Task 58 (`/architect`,
  four files) and task 140 (`runbook-run`, three files) are the precedent for a
  whole skill folder in one task. The documentation task (193) stays separate.
- **The branch files sit flat beside `SKILL.md`, not under `references/`.**
  They are on-demand files read only by their own skill — the
  `skills/architect/` and `skills/product-design/` pattern. `references/` in
  `task-engine` and `pipeline-engine` holds rules read by *other* features,
  which is not what these are; no `requires:` relationship is involved.
- **The routing rows land with the surfaces.** `scripts/check-routing.sh`
  flags a shipped consumer of the engine that has no row, so deferring the
  rows to a later consolidating task would leave the repo failing its own
  check in between.
- **`requires:` names the owner skills, not only the engine**, on both
  surfaces. A reviser or patcher with no owner to delegate to has nothing to
  do — the reasoning the feature document gives for the patcher applies to
  both.
- **Neither surface commits by default.** The skill takes `--commit` like every
  skill in this repo; the command takes `[--commit] [--no-push]` and forwards
  them, because the arms it executes take exactly this pair and default to
  committing nothing, and a patcher that could not express the arm's own
  default would be the only writer in the suite unable to. The feature
  document's interface line lists no flags; recorded as reconciliation point 2
  for task 193.
- **The owner sequence runs upstream first.** The feature document fixes the
  set of owners but not their order. Writing a task body before the feature
  document that governs it would have the task amended against a promise about
  to change, which is the drift this feature exists to prevent.
- **A feature document change routes through `/architect amend`, never
  through the full skill.** The precision iterate guard is the whole point of
  that arm; the blanket guard would stale tasks the change does not touch.
- **An orphan task is walked, not refused.** A task with no resolvable
  `Feature:` is common on projects that never ran `/architect`; the amend
  branch amends it and stops the upward walk rather than treating it as drift.
- **`--single` is the attachment primitive, not a full `/task-add
  feature=<slug>` run.** A whole-feature re-plan reconciles every existing task
  — a far larger revision than the user proposed, and one the gate never
  showed them.
- **A successor's `Preconditions:` is never written directly.** It changes
  through `task-engine`'s single-task amend reference, which owns that field's
  rules, including naming a dropped edge in the task's `## Decisions`.
- **Scope first, task second.** `/architect amend` runs before `/task-add` so
  the new task is drafted against a feature document that already promises it;
  the reverse order produces a task whose `Feature:` points at a document that
  does not mention it, which is a lint finding on its own.
- **Feature removal keeps the entry.** The feature document's non-goals rule
  out physical deletion; an entry whose tasks are all `[SKIP]` and whose edges
  `/production-plan` has dropped is inert without erasing what was planned or
  why.
- **`/production-plan` is invoked, not imitated.** Dropping an edge by hand
  would make the reviser a writer of `PLAN.md`, which the feature's hard
  contract forbids; the reconciliation the plan already performs on every run
  is the sanctioned path.
- **A dropped edge is always narrated.** `task-engine`'s amend reference
  requires the drop to appear in the successor's `## Decisions`; the delete
  branch states that the reason names the deletion, so a later reader can see
  why the precondition vanished.
- **The reorder branch ships with the feature rather than as a later
  increment.** The feature document leaves this open, but `/pipeline-patch`'s
  fixed refuse checklist names a reorder and points at `/pipeline-revise`;
  shipping that refuse path into a surface with no branch for it would be a
  documented dead end. The file is small precisely because it composes.
- **A reorder is skip-and-insert, never a renumber or a move.** Task ids are
  stable by `resolution.md`, and runbook steps are never renumbered by
  `runbook-run`'s schema; a move would break both.
- **Preconditions-only changes are excluded from reorder by name.** Without
  that sentence the classifier has two plausible branches for the same
  request, which is the one failure a four-way classification can actually
  produce.
- **No escalation on the patcher.** A patch that discovers it is structural
  stops rather than silently becoming a revise; the user chose the cheap tool
  and gets to choose again.
