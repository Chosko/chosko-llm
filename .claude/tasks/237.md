# Task 237 — Call `/follow-ups` at the end of every `/runbook-run` and `/task-implement` run

Target: claude

## Goal
Wire the closing `/follow-ups` call into both runners, so a run never ends
leaving unrecorded work visible only in the transcript. It fires exactly
once per run, after the run's own closing report, at every point a run
stops — and in the spawned modes the orchestrator collects the follow-ups
the step agents and task agents named in their result reports.

## Acceptance criteria
- Both `skills/runbook-run/SKILL.md` and `skills/task-implement/SKILL.md`
  declare `requires: command:follow-ups` in frontmatter, and both bump their
  own `version:`.
- The call fires **once per run, never per step and never per task**, after
  the run's own closing report is printed.
- It fires at every stopping point, not only completion:
  - `/runbook-run` — when no `[ ]` steps remain; at a `--to`, `--only` or
    `--steps` bound; at a failure halt (`[!]` / index `[FAILED]`); and when
    the user asks to stop after a step mid-run, **even when the run carried
    no bound to that step**.
  - `/task-implement` — after the last task in the run, whatever the run
    resolved to (`<N>...`, `all`, `next`), and after the FEATURE COMPLETION
    proposal rather than before it; at a failure halt; and at a
    user-requested stop between tasks.
  - A single-step or single-task run is not a special case: the end of the
    one step or task is the end of the run.
- Under `/runbook-run`'s default spawned mode, the orchestrator's
  `/follow-ups` reading covers the step subagents' result reports as well as
  its own conversation — agents routinely name their own follow-ups there,
  and that report is the orchestrator's only window onto the step. Under
  `--inline` nothing changes.
- Under `/task-implement --agents` the same holds for the parent: it reads
  the per-agent result reports it already collects. The closing call is not
  skipped in this mode.
- Where the user then asks to execute or plan a listed follow-up that came
  from a spawned agent, the runner **may** forward it to that original agent
  where doing so is convenient. Written as judgement, not as a rule, and not
  as a new relay protocol.
- The call changes no bookkeeping: it is outside the commit cadence, adds no
  commit, and runs after the index `Status:` (`[DONE]` / `[FAILED]` /
  `[PENDING]`) and the final commit are already written, so it never dirties
  a tree the runners just cleaned.
- Both skills skip the call silently when `/follow-ups` is not installed —
  an absent optional closing step is not a run failure and produces no
  message.
- Both `DO NOT` lists gain the two failure modes this wiring invites: firing
  per step / per task, and skipping the call because the run stopped early
  or failed.
- Root `VERSION` takes a minor bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` passes.

## Decisions
- **A failure halt still calls it.** The user named completion, a bound and
  a user-requested stop. A halted run is a run that ended, and it is the
  case most likely to strand unrecorded work, so it is included — a
  deliberate extension of the user's list, not a reading of it.
- **After the FEATURE COMPLETION proposal, not before.** That proposal can
  itself leave something unresolved — a slug the user declined stays
  `[PLANNED]` — and a follow-up list drawn before it would miss exactly that.
- **No new commit, no bookkeeping.** Putting the call after the last commit
  keeps `/runbook-run`'s "the `[~]` marker is never committed" discipline and
  its Stop-hook reply untouched, and keeps `/task-implement`'s
  one-commit-per-task rule intact.
- **`requires:` rather than a probe.** The dependency helpers in
  `scripts/lib.sh` already install a declared dependency with its dependent,
  so the silent skip only covers a user who removed the command by hand.
