# Task 252 — Direct, headless-capable amend arms for `/product-roadmap`, `/production-plan` and `/product-design`

Target: claude

## Goal
A revision that touches the roadmap or the plan has to run the whole owner
command with its diff-and-propose gate, and one that touches the product design
has to re-run `/product-design` and pick an arm from a resume menu. Give each
of the three owners a direct `amend "<change>"` entry that is a standalone file,
so a revision surface can draft the edit at plan time and run the arm with the
decision carried in, the way `/architect amend` already works.

## Acceptance criteria
- `skills/product-roadmap/amend.md` carries `/product-roadmap amend "<change>"
  [--commit] [--no-push]`: the change is pinned to named milestone lines
  (`Goal:`, `Exit criteria:`, `Rationale:`, `Covers:` slices), the edit is
  drafted to those lines only, one gate shows before/after, and the write set
  is `product-roadmap.md` alone. A change that cannot be pinned to named lines
  is refused with a pointer to the full command.
- `skills/production-plan/amend.md` carries `/production-plan amend
  "<change>"`: `PLAN.md` is reconciled against `FEATURES.md` with the change as
  context, the proposal is limited to the milestones and edges the change
  names, one gate shows the diff, and the write set is `PLAN.md` alone. The
  existing cycle and later-milestone refusals hold.
- `skills/product-design/amend.md` carries `/product-design amend "<change>"`:
  the edit `resuming.md` § 6 makes today, reached directly, without reading
  `design-process.md`'s resume state or rendering the resume menu. `resuming.md`
  § 6 cites the file rather than restating it.
- Each arm is complete on its own (a consumer that has read only that file can
  execute it end to end), and its one decision is a closed rule over its reads,
  so a caller may draft the edit before the arm runs and pass the drafted edit
  in; the arm then writes without a gate of its own when the draft matches
  what it would have drafted, and shows the difference otherwise.
- `SKILL.md` of each owner dispatches the `amend` form to its file from
  ARGUMENT PARSING, after its existing preconditions.
- `skills/pipeline-engine/references/routing.md`: the Amend column of the
  three rows names the new files by relative path; argument shapes carry the
  `amend` form. `skills/pipeline-revise/amend.md` and `delete.md` route the
  design-decision, roadmap and plan steps of their owner sequences through the
  arms.
- `.claude/domain/features/owner-amend-arms.md` is reconciled with what ships
  on exactly these points — editing it is authorised for this task, see
  Decisions: (1) the three owners have arms; (2) an arm is headless-capable, its
  decision a closed rule over its reads. Nothing else in the document changes.
- `docs/reference.md` and `.claude/context/features.md` describe the three
  forms.
- `version:` minor bump on the three owner skills, patch on `pipeline-revise`;
  root `VERSION` minor bump; `CHANGELOG.md` entry; `./scripts/check-changelog.sh`,
  `./scripts/check-routing.sh` and `./scripts/check-home-paths.sh` silent.

## Decisions
- One task for three arms: the routing table, `pipeline-revise`'s branch files
  and the feature document change once, and the arms share one shape.
- **Editing `.claude/domain/features/owner-amend-arms.md` is explicitly
  authorised for this task (user decision, 2026-09-21), for the two
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time.** The document is normally `/architect`'s; a change
  beyond those points is a design decision and stops the run to say so.
