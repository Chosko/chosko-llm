# Task 288 — Move `/task-implement`'s checkpoint automation out of Unity MCP into a tool-agnostic human-in-the-loop passage

Target: claude

## Goal
First slice of feature `unity-mcp-removal`. `/task-implement` stops
reading the `Unity MCP for /task-implement:` marker and
`unity-mcp-checkpoints.md`; what was generic in that file moves into
`human-in-loop.md` as one tool-agnostic passage, so a project whose session
has any connected tool able to perform a manual step (Unity's official MCP
included) keeps the "agent does the step, user verifies" behaviour without
the repo naming a server.

## Acceptance criteria
- `skills/task-implement/unity-mcp-checkpoints.md` is deleted, with its row
  in `SKILL.md`'s supporting-files table.
- `human-in-loop.md`'s *Unity MCP gate* section is gone and replaced by one
  passage stating, for any checkpoint whose manual step a tool connected
  this session can perform, the four rules of the feature document
  § *What moves into the human-in-the-loop protocol*: automatic-or-manual
  asked once per task (a real decision under the interaction policy, never
  auto-picked — cited from `interaction-engine`, not restated); after a
  compile, read the tool's console and fix this task's errors before moving
  on, stopping on errors it cannot resolve; wait for the tool to report
  ready after a reload/re-import/restart; verify the outcome by re-query
  through the tool or the filesystem, with a step the tool cannot perform
  falling back to the standard protocol for that step alone.
- The passage names no server, package or tool prefix; tool discovery is
  from the live tool set. The standard protocol's explain-first,
  end-the-turn-with-no-tool-call and independent-verification rules are
  unchanged. The "(e.g. the Unity editor)" example in the file's opening
  stays.
- `SKILL.md` Step 1 no longer mentions Unity MCP or the checkpoint file; it
  defers to `human-in-loop.md` for whether a connected tool drives a
  checkpoint.
- `task-engine`'s `targets.md` `/task-implement` consumer note names the
  tool-agnostic passage instead of the Unity MCP gate; its Unity worked
  example for `claude+human` stays.
- No shipped body under `skills/task-implement/` or `skills/task-engine/`
  names `Unity MCP for /task-implement:`, `mcp__UnityMCP__`,
  `unity-mcp-checkpoints.md` or `/unity-mcp-setup`.
- `version:` bumped on `task-implement` and `task-engine`; root `VERSION`
  bumped with a `CHANGELOG.md` section; `check-changelog.sh` and
  `check-home-paths.sh` pass.

## Decisions
- Precondition 282: the automatic/manual question cites `interaction-engine`
  as a real decision, and 282 is what makes `/task-implement` require that
  skill; both tasks also edit `skills/task-implement/SKILL.md`.
- The question is asked once per task, as the feature document states —
  the checkpoint file's per-run opt-out does not survive.
- The tracked `--local` install copies under `.claude/skills/` are
  refreshed by task 289, once both slices have shipped.
