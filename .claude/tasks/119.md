# Task 119 — Turn /task-implement's batch parent into a launcher

Target: claude

## Goal

Implements the `task-implement-launcher` feature. On a delegated run,
`/task-implement`'s parent session today reads each task body so it can compose
an accurate hand-off prompt per agent — which costs exactly the context the
delegation exists to save, since a ten-task batch ends with the parent holding
ten bodies it will never use again, and each agent re-reads most of the same
material anyway. Make the parent a launcher instead: it resolves the task list,
evaluates the delegation guard from data it already has, and hands every agent
the same fixed-size prompt. The agent gathers its own context exactly as it
would if the user had typed `/task-implement <n>` by hand — which is what the
`.claude/context/` layer is for, and handing an agent a pre-chewed summary
instead pays for that layer twice. Observable behaviour of the command does not
change; its token profile does.

## Acceptance criteria

- `skills/task-implement/delegated-runs.md`'s "The agent prompt" section is
  replaced by a hand-off prompt whose size is independent of the task: the task
  number, the run's resolved flag list, an instruction to read the task body,
  CLAUDE.md and `.claude/context/` itself, and the return contract. A fifty-task
  batch composes the same prompt fifty times with a different number in it.
- The prompt's flag list carries only run-level decisions already resolved in
  PRE-FLIGHT: NO_COMMIT, NO_PUSH, AUTO_CONFIRM, the resolved testing mode (with
  the concrete test command in full test mode), DIRTY_FOLD /
  DIRTY_FOLD_UNTRACKED, and the non-interactivity notice. Any flag
  `/task-implement` gains later rides in this list without changing the prompt's
  size — the list is described as "the run's resolved flags", not enumerated as
  a closed set.
- `delegated-runs.md` states plainly that on a delegated run the parent opens no
  `.claude/tasks/<N>.md`, on any path — for a delegated task, ever.
- The agent's return contract is exactly four things: task number, terminal
  status, commit hash (or that nothing was committed under NO_COMMIT), and a
  one-line failure reason when it failed. The parent accumulates that and
  nothing else, so its context after a fifty-task run is fifty short rows.
- `skills/task-implement/SKILL.md`'s PRE-FLIGHT step 2 states that `Target:`,
  `Status:` and `Feature:` — the three fields the delegation guard needs — all
  come from the `TASKS.md` summary block already read there, so no per-task body
  read is required to evaluate the guard.
- Tasks the parent keeps — `claude+human`, `human`, and `[STALE]` tasks
  requested explicitly by number — still have their bodies read, and still only
  in Step 1 when each becomes the current task. That path is unchanged.
- The between-agent protocol is unchanged in substance: re-read
  `.claude/TASKS.md`, confirm the agent's claim against the file and against
  `git status --porcelain`, one progress line, and the skip-tests "Proceed?"
  gate unless AUTO_CONFIRM. FEATURE COMPLETION still runs in the parent off that
  re-read, batched to the end of the run.
- Failure handling is unchanged: a failed or ambiguous agent halts the run
  before the next spawn, and the parent reports which tasks completed with
  hashes, which failed and what the agent said, and which were never started.
- The sequential-never-parallel rule and the mixed-run announcement ("Delegating
  tasks 20, 22 … tasks 21, 23 run here") are unchanged.
- No usage-surface change: no new flag, no altered usage line, no altered
  example, `--agents` / `--no-agents` behave exactly as before, and single-task
  runs are untouched.
- `skills/task-implement/SKILL.md` takes a minor frontmatter `version:` bump and
  root `VERSION` takes a minor bump, both relative to the values task 118 leaves
  in place (expected `1.0.0` → `1.1.0` on each).
- `.claude/context/features.md` and `.claude/domain/task-workflow.md` are NOT
  edited by this task — task 120 owns them.

## Decisions

- **The parent reads the three guard fields from `TASKS.md`, not from the task
  body.** The feature document's table says the parent "greps exactly three
  fields out of the task body", but `Target:`, `Status:` and `Feature:` all
  appear in each task's `TASKS.md` summary block, which PRE-FLIGHT step 2
  already reads once for the whole run. Greping bodies would open the files the
  design forbids opening and add per-task cost for data already in hand. The
  design's intent — the parent reads no task body — is met more cheaply, and the
  document's "grep reliability on the three fields" open question is moot.
  (Confirmed with the user, 2026-08-24.)
- **No `FEATURES.md` join for staleness.** The document says `Feature:` alone is
  not enough and the parent must read `FEATURES.md` to learn whether the feature
  was re-architected. In the shipped design `[STALE]` is already a `Status:`
  value in `TASKS.md`, written there by `/architect`, so the guard reads it
  directly. `FEATURES.md` is still read once per run — for FEATURE COMPLETION,
  which this task does not change. (Confirmed with the user, 2026-08-24.)
- **The dirty-tree decision travels in the flag list**, settling the document's
  first open question: DIRTY_FOLD and DIRTY_FOLD_UNTRACKED are run-level values
  resolved once in PRE-FLIGHT and are already in today's agent prompt. They are
  O(1) in batch size, so they stay.
- **`--review` / `--rounds` are not named.** They belong to the
  `task-peer-review` feature, which is not implemented. Because the prompt
  passes the run's resolved flags rather than a closed list, those flags ride
  through automatically once they exist; naming a flag that does not yet exist
  would ship a dangling reference.
- **The between-agent `TASKS.md` re-read is kept.** It is not a task body, it is
  one small file re-read once per returning agent, and both the
  agent-verification step and FEATURE COMPLETION depend on it.
- **Written against the post-118 shape of `SKILL.md`.** Task 118 removes the
  `Target: local` block, the `chosko-llm task-impl` asides and the external-LLM
  material from the same file; this task must not reintroduce or reference any
  of it. Hence the precondition.
- **Minor bump, not patch, despite no interface moving** — per the feature
  document: the delegation contract is materially different even though its
  surface is not.
