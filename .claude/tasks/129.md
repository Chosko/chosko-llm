# Task 129 — Migrate /task-add onto the task-engine

Target: claude

## Goal

Step 4 of the `shared-phase-engine` migration order, second of three.
`commands/task-add.md` is the largest command in the repo — 879 lines before
task 118 trims the `--enrich` apparatus out of it — and most of the bulk it does
not need is the same material the other four `task-*` features also state:
backlog resolution, the status vocabulary, the `Target:` values, what `[STALE]`
means, and the commit/push gating. Replace all of it with engine references. The
design's rough target is under 400 lines, but the measure of success is that
each rule appears once.

## Acceptance criteria

- `commands/task-add.md`'s frontmatter carries `requires: skill:task-engine`.
- Its restated rules are replaced by references of the form
  `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/references/<file>.md`,
  each followed only by `/task-add`'s own deviations: `resolution.md` for the
  PHASE 0 setup check and index-file location, `status.md` for the `STATUS TAGS`
  block, `targets.md` for the `TARGET VALUES` half of
  `TARGET VALUES & MANUAL INTERVENTIONS`, `stale.md` for the `[STALE]`
  paragraph, and `commit.md` for PHASE 5.
- Everything genuinely unique to `/task-add` stays and is not compressed as a
  side effect: the eight-phase flow (SETUP-CHECK → READ → SPLIT-CHECK → ASK →
  DRAFT → CONFIRM → WRITE → COMMIT), the `INDEX FILE FORMAT` and body schemas,
  the `## Manual interventions` authoring rules and worked example, PHASE 1.5's
  split check, `FEATURE RESOLUTION`, `RECONCILIATION` with its four-way
  classification table and the untouchable-`[DONE]` rule, `DOCUMENTATION TASK`
  with its ownership notice, the `--short` / `--no-split` / `--no-commit` /
  `--no-push` argument note, and the `DO NOT` list.
- The `DO NOT` list keeps every bullet whose rule still exists after the
  references land. A bullet that now restates an engine rule is rewritten to
  point at the engine, never dropped.
- Written against the **post-118** shape: no `--enrich`, no `Target: local`, no
  enriched-body schema, no `commands/task-enrich.md` existence gate, and a
  `Target:` value list of exactly `claude`, `claude+human`, `human`.
- **Observable behaviour is unchanged**: same usage header and examples, same
  flags and their mutual exclusions, same prompts and phase gates, same written
  artifacts, same commit message forms, same `.claude/FEATURES.md` two-field
  write.
- Verification is a real run: author one throwaway task with
  `/task-add --no-commit --short` before and after the migration and confirm the
  prompts, the draft shape and the written files are the same. Discard the
  throwaway task afterwards.
- The body is under 400 lines, with the same caveat as tasks 127 and 128.
- `commands/task-add.md` takes a minor frontmatter `version:` bump, relative to
  what task 118 leaves in place (expected `2.0.0` → `2.1.0`); root `VERSION`
  takes a patch bump, relative to what task 128 leaves in place.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  131 owns both knowledge layers.

## Decisions

- **Its own task, not bundled with `/task-clean`.** At 879 lines pre-118 this is
  the single largest restructure in the feature, and the document's design
  intent is that each migration step be independently verifiable with its own
  version bump. Bundling it would put the riskiest migration behind the same
  approval as a routine one.
- **The phase structure is not touched.** The temptation in a body this size is
  to reorganise while extracting. That would break the feature's only hard
  contract — no observable behaviour change — and make the diff unreviewable.
  Text moves out; nothing else moves.
- **`tree.md` is not cited.** `/task-add` writes two files and commits them; it
  has no dirty-tree protocol.
- **Precondition 128, not just 126.** `/task-clean` proves the reference form
  works for a writing, committing consumer before that form is applied to the
  most complex body in the repo.
