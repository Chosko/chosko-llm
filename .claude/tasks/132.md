# Task 132 — Add the /session-save command

Target: claude

## Goal
Ship `commands/session-save.md`, the write half of the `session-continuity`
feature: a single-pass command that captures what a conversation knows before
it ends — what was tried, what failed, what was deliberately not tried, which
files are half-finished, and the exact next step — into a per-project file
under `.claude/sessions/`. Today that knowledge dies with the session and is
re-derived from scratch at full token cost, with no guarantee the
re-derivation matches. The command writes one file per invocation, links it to
the task, feature or document the work belongs to, and shrinks to a pointer
when the work already has a real resume artifact.

## Acceptance criteria
- `commands/session-save.md` exists with complete frontmatter: `name:
  session-save`, `version: 0.1.0`, `type: command`, one-line `description`.
- Writes `.claude/sessions/YYYY-MM-DD-HHMM-<slug>.md`, creating the directory
  on first save. `<slug>` is a two-or-three-word kebab-case summary of the
  work, not a random id — the directory listing is the only way the user finds
  an old session. `/session-save <slug>` overrides it.
- Never updates a file in place. A second save in the same session writes a
  second file — a handoff is a snapshot, and rewriting history in it defeats
  the purpose.
- Both file forms open with the same header block: `# Session: YYYY-MM-DD
  HH:MM`, then a `Work:` line and a `Running:` line.
- `Work:` takes exactly one of `task <n>`, `feature <slug>`, `document <path>`,
  or `none`. `none` is a first-class value, not a failure, and may carry a
  short trailing explanation after an em dash (`none — cross-feature
  architecture session`), as the reference file does. Inventing a link for an
  anchorless session would make the link untrustworthy everywhere else.
- **Full form** (the generic case) writes all nine sections, in the order given
  in the feature document, after an optional one-paragraph preamble: what we
  are building; what worked (with evidence); what did not work (and why); what
  has not been tried yet; current state of files (a `File | Status | Notes`
  table, status one of Complete / In progress / Broken / Not started);
  decisions made (each with its reason); blockers and open questions; exact
  next step (one concrete action); environment and setup notes.
- **Every section is written, always** — `N/A` or `nothing yet` where a section
  is genuinely empty. The command body states why: a skipped section is
  indistinguishable from an overlooked one, and an honest empty section is
  information. Claims under "what worked" carry the command output, test name
  or file that proves them; an unevidenced claim is written as a guess.
- **Pointer form** is the header block plus a `Resume from: <path>` line and one
  sentence telling the reader that file holds the state. Nothing else — no
  narrative, no file table, no decisions. Two accounts of the same state that
  can disagree is worse than one.
- Artifact detection runs in two steps, in order:
  1. The **known-artifact table** carried in the command body. An entry is a
     *project-scoped state document carrying a resume marker* — the class
     `docs/authoring-guide.md` § "State that outlives a session belongs in a
     project document" already defines. One row today: `/product-design` →
     `.claude/domain/design-process.md`. The table grows only when a skill
     actually ships such a document.
  2. A **recency check** — a file written this session carrying a resume marker
     (a current-stage, phase, or next-step line). Offer the pointer form; write
     the full form if the user declines.
  No artifact found, or no skill running: full form. `/task-implement` has no
  entry and its sessions take the full form.
- The command detects; skills declare nothing. A skill that gains a resume
  artifact later needs no change here, and one that loses its artifact degrades
  to the full form on its own.
- **Supersession delete.** When the current session itself resumed from a
  session file, `/session-save` writes its new snapshot and then deletes the
  file it resumed from — that file is superseded, its state now lives in the
  newer one, and two snapshots of the same work must never coexist. The command
  therefore has to know which file, if any, this session resumed from; it takes
  that from the conversation (`/session-resume` says so explicitly in its
  briefing), and deletes nothing when it cannot tell. The deletion is reported
  on its own line beside the path written.
- The command does not commit, does not push, and offers no `--commit`. It
  reports the path it wrote and notes in one line that the file is untracked.
- It does not touch `.gitignore`.
- It writes nothing outside `.claude/sessions/`, and no `chosko-llm`
  subcommand reads what it writes — session files are context for an agent,
  never input to the tooling.
- Root `VERSION` takes a minor bump (new feature).

## Decisions
- **Command, not skill.** Single-pass reporter, no conversation, no supporting
  files — the register `/task-list` and `/production-status` occupy. Straight
  from the feature document.
- **The known-artifact table drops the `/task-implement` row** (user decision,
  2026-08-24). `skills/task-implement/delegated-runs.md` is a static shipped
  instruction file: it holds no session state, and its path is relative to the
  installed skill folder rather than the project. A pointer form built on it
  would have discarded the entire handoff — exactly the failure this feature
  exists to prevent. `/task-implement` is treated as a feature that writes no
  resume marker, so its sessions take the full form, which is correct: its
  state is a half-finished tree plus what was tried, not a file. A table entry
  is now defined by the authoring guide's existing class, which makes the
  growth rule precise instead of a judgment call.
- **Gitignore open question resolved to the document's own leaning:** do not
  touch `.gitignore`; print the untracked note and leave the decision to the
  user. Supported by this repo, where `.claude/sessions/` is tracked and both
  files in it are exactly what you would hand a colleague.
- **"Does the command know what skill is running?" resolved to the document's
  own fallback:** infer from the conversation, and ask the user once when the
  inference is not clear. Cheap and honest; no state is read to find out.
- **Pruning resolved** (user decision, 2026-08-24). A session file is deleted
  automatically once it has been resumed and the work it describes is finished.
  This task owns the second half of that mechanism — the supersession delete
  above, for a session that resumed but did not finish. The first half (telling
  the resumed session to delete the file when the work completes) is task 133's,
  and stays there so `/session-resume` remains read-only. Files that were never
  resumed are never auto-deleted, and there is no `--prune` flag.
- **Optional preamble paragraph** between the header block and section 1 —
  present in the reference file, absent from the design document. Adopted as
  optional.
- **`VERSION` is bumped by this task and again by task 133**, rather than once
  across the feature. The repo rule is one bump per shipped change and each
  task commits separately. No target number is named here, because task 118 may
  move the base first.
