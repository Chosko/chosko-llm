# Task 86 — Extend check-task-parity.sh to guard Target-field gating

Target: claude

## Goal
scripts/check-task-parity.sh currently only diffs the status-tag vocabulary
and the 7-step workflow between skills/task-implement/ (prompt side) and
scripts/cmd-task-impl.sh + scripts/lib-task-external.sh (bash side). It has
no coverage of Target-field gating, so task 85's hard-refuse behavior for
non-`claude` targets on the unattended orchestrator could silently regress
(e.g. someone drops the refusal case while touching implement_one for an
unrelated reason) with no guard catching it — the same failure mode the
guard already prevents for status tags. Extend the guard to check that both
sides still agree on which Target values the unattended path refuses vs.
the interactive path handles via checkpoints.

## Acceptance criteria
- check-task-parity.sh gains a check verifying scripts/cmd-task-impl.sh
  still contains the hard-refuse logic for `claude+human`, `human`, and
  `local` Target values added in task 85 (grep-based cheap-invariant check,
  consistent with the existing tag/step checks — not a behavioral test).
- The guard verifies skills/task-implement/ still documents all four Target
  values (`claude`, `local`, `claude+human`, `human`) and their handling
  (human-in-loop.md's checkpoint protocol for claude+human/human), so the
  prompt side can't silently drop target-gating documentation either.
- A failure produces a clear message naming which side is missing which
  target-value handling, matching the existing fail()/log_error style.
- Running `./scripts/check-task-parity.sh` after task 85 lands passes; a
  git-reverted task 85 change makes it fail (manually verify by checking
  out the pre-85 commit and confirming the new check catches the gap,
  then restore).
- Existing tag/step checks are unchanged and still pass.
