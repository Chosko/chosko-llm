# Task 181 — Update documentation for feature `pipeline-engine`

Target: claude

## Goal
Tasks 175–180 ship feature `pipeline-engine`: a second non-invocable reference
skill with four reference files, the read-only `/pipeline-check` command, and a
repo-local routing guard. The documentation describing this area still knows
only one engine, lists no lint, and — in the feature document itself — describes
findings and a routing check that shipped in a narrower form than designed. It
is now out of date and needs to reflect the shipped behaviour.

## Acceptance criteria
- `README.md` § 4 (Plan the work) covers `/pipeline-check`: what drift it
  reports, that it fixes nothing, and the `feature=<slug>` form.
- `docs/reference.md` gains a `/pipeline-check` entry in § 4 and a
  `pipeline-engine` entry beside the existing `task-engine` one, naming the four
  reference files and stating that the skill is not invocable.
- `docs/authoring-guide.md` names `scripts/check-routing.sh` alongside
  `check-changelog.sh` as an authoring-time guard, and says what it checks.
- `CLAUDE.md` § Versioning (or § Testing, whichever the existing
  `check-changelog.sh` mention sits in) names `./scripts/check-routing.sh` and
  when to run it. No `VERSION` bump follows from this edit.
- `.claude/domain/product-workflow.md` gains `/pipeline-check` as a **fourth
  read-side entry** in the stage table and in § *The read stage*, stated as
  read-only and as spanning the whole pipeline the way `/production-status`
  does.
- `.claude/context/features.md` gains rows for `commands/pipeline-check.md` and
  `skills/pipeline-engine/`, and its existing `requires:` discussion names the
  second engine.
- `.claude/context/INDEX.md`'s `Last updated:` anchor is refreshed.
- `.claude/domain/features/pipeline-engine.md` is reconciled on exactly these 4
  points — editing it is authorised for this task, see Decisions:
  1. § *The findings* — the bullet "a pending runbook step naming a task already
     `[DONE]` or `[SKIP]`" is not in the shipped catalogue and why; its sibling
     "a runbook `[PENDING]` with no unticked step" does ship, derived from
     `Steps: <n>/<n>` and `Status:` in `RUNBOOKS.md` alone.
  2. § *Open questions*, bullet 2 — the runbook-index question blocks one named
     finding, not "two lint findings".
  3. § *The routing check* — "every shipped pipeline command or skill has a row"
     narrowed to the two invariants the script implements: every row names a
     feature that exists as a command or a skill, and every feature declaring
     `requires: skill:pipeline-engine` has a row.
  4. § *The reference files → Lint* — the catalogue's severity vocabulary is two
     levels, `ERROR` and `WARNING`.
  Nothing else in the document changes. In particular the third open question,
  about a second non-invocable skill and harness behaviour, is left open — a
  real install answers it — and the two `task-archive` points are already
  reconciled by task 178 and are not revisited here.
- Root `VERSION` is **not** bumped and `CHANGELOG.md` gets **no** entry; the
  change is confined to `README.md`, `docs/`, `CLAUDE.md`, `.claude/domain/` and
  `.claude/context/`, which `CLAUDE.md` § Versioning exempts.
  `./scripts/check-changelog.sh` still exits zero.

## Decisions
- **Editing `.claude/domain/features/pipeline-engine.md` is explicitly
  authorised for this task (user decision, 2026-09-09), for the 4
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document is
  normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
- Two tasks in this run hold grants on the same document, on disjoint points:
  task 178's two `task-archive` reconciliations and this task's four. This task
  runs after 178 via `Preconditions:`, so it reads a document those two points
  have already been applied to. If either of 178's points is still outstanding
  when this task runs, report it rather than applying it — it is not in this
  grant.
- No `VERSION` bump and no `CHANGELOG` entry — the boundary in `CLAUDE.md`
  § Versioning puts this task entirely on the documentation side, and a bump for
  a change no user receives corrupts the version `install.sh` reports.
- `.claude/domain/technical-direction.md` is deliberately untouched: its
  `check-changelog.sh` mention is an example of the repo's guard register, not a
  list that has to enumerate every guard.
- `.claude/domain/features/task-archive.md` is deliberately untouched. This run
  consumes its resolution rule; it changes nothing about it, so there is nothing
  to reconcile, and the document belongs to `/architect` and to that feature's
  own planning run.
- No new `.claude/context/` file is created for `scripts/check-routing.sh`.
  `check-changelog.sh` has no context file either — repo-local guards are
  covered by `features.md` and `CLAUDE.md`, and a per-script context file for a
  40-line guard is cost without navigation value.
