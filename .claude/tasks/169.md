# Task 169 — Make `next` and `all` honour `Preconditions:`

Target: claude

## Goal
Feature `backlog-ordering` makes recorded order the order selection follows.
Today `Preconditions:` is written on every task and read by nothing that picks
one: `next` takes the first implementable task in appearance order, and `all`
takes every implementable task, so a task inserted late is picked last however
many preconditions name it. This task adds the one eligibility clause to the
selectors in `task-engine`'s `resolution.md` — the single home for them — and
makes `/task-implement` re-check it between tasks. It is the prerequisite of
every other task in this feature: nothing downstream can insert into a sequence
the selectors ignore.

## Acceptance criteria
- `resolution.md` § *Selectors* states the eligibility clause once: a task is
  eligible only when its status is implementable **and** every id on its
  `Preconditions:` line resolves to a task whose status is `[DONE]` or
  `[SKIP]`. An id resolving to no task is ignored, never a blocker — the same
  tolerance the stale rule extends to a hand-edited backlog.
- `next` is defined against that clause and keeps its existing one-line
  resolution report and its no-eligible-task stop; when the only reason nothing
  is eligible is unmet preconditions, the stop names the blocked tasks by id
  instead of claiming everything is DONE/SKIP/IN PROGRESS/STALE.
- `all` is defined as `next` applied repeatedly until no task is eligible, and
  the file states how it is resolved: one pass up front that walks the backlog
  repeatedly, treating each already-selected task as satisfied, so the run
  still gets a fixed ordered list, one resolution report and one delegation
  count.
- The `all` resolution report names, by id, every implementable task left
  unselected because its preconditions are unmet — an unsatisfiable edge is
  visible rather than silently skipped.
- A precondition cycle is stated: every task on it is ineligible, the
  resolution terminates rather than looping, and the cycle's tasks are reported
  as blocked.
- Explicit-list selection is unchanged and the file says so: a task requested
  by number is never blocked by a precondition.
- `/task-implement`'s BETWEEN TASKS step 2 (and the matching step in
  `skills/task-implement/delegated-runs.md`, if it restates it) re-checks the
  upcoming task's preconditions against the `TASKS.md` it already re-reads. A
  task whose preconditions are no longer satisfied is skipped with a one-line
  report. No new read is introduced anywhere.
- `skills/task-implement/SKILL.md`'s ARGUMENT PARSING still cites
  `resolution.md` § *Selectors* as the authority and states only the
  re-check as its own departure; the rule is not restated there.
- `skills/task-engine/SKILL.md` and `skills/task-implement/SKILL.md` each take
  a minor `version:` bump.
- Root `VERSION` takes a minor bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` exits zero.

## Decisions
- `all` resolves once up front by simulating the repeated `next` rather than
  re-resolving after every task. It yields the same list the repeated rule
  would, and it preserves the single resolution report, the fixed list and the
  `k`-task delegation count that `/task-implement`'s PRE-FLIGHT step 2b already
  depends on.
- The feature document's second open question is answered here rather than
  deferred: `/task-implement` already re-reads `TASKS.md` between tasks, so
  per-spawn re-evaluation costs nothing and needs no new read point.
- `/task-list` gains no `(waits on N)` marker. The feature document leaves that
  out until the rule has been used, and it is a rendering change, cheap to add
  later.
- No topological sort and no scheduler. One eligibility clause, stated once, in
  the file that already owns the selectors.
