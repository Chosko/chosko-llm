# Task 169 — Backlog ordering on the task side: selectors honour `Preconditions:`, `/production-status` agrees, `/task-add` can insert and attach

Target: claude

## Goal
Feature `backlog-ordering` makes recorded order the order selection follows,
and gives the backlog an insertion operation. Today `Preconditions:` is written
on every task and read by nothing that picks one: `next` takes the first
implementable task in appearance order, `all` takes every implementable task,
`/production-status`'s Next column names the lowest-numbered open task, and
`/task-add` only ever appends — so a task written late carries the highest id,
sorts last, and is picked last however many preconditions name it.

This task ships the whole task-side half of the feature in one pass, because
its four pieces are one rule and its consequences:

1. **The eligibility clause**, stated once in `task-engine`'s `resolution.md`
   and honoured by `next`, `all` and `/task-implement`'s between-tasks re-check.
2. **`/production-status`'s Next derivation**, changed to the same clause so
   the read side and the run side agree.
3. **`/task-add --before <N>` / `--after <N>`**, which place the summary block
   *and* write the `Preconditions:` edge the selectors follow.
4. **`/task-add feature=<slug> --single`** and the orphan-task question, so a
   single task can be attached to a planned feature without re-planning it.

Pieces 3 and 4 both edit `commands/task-add.md`; pieces 1 and 2 are the same
rule in two files. Written together they get one `VERSION` bump, one
`CHANGELOG` section and one coherent read of each body. The runbook store's
insertion operation is task 173, which is independent of everything here.

## Acceptance criteria

### `skills/task-engine/references/resolution.md` — the eligibility clause
- § *Selectors* states the eligibility clause once: a task is eligible only when
  its status is implementable **and** every id on its `Preconditions:` line
  resolves to a task whose status is `[DONE]` or `[SKIP]`. An id resolving to
  no task is ignored, never a blocker — the same tolerance the stale rule
  extends to a hand-edited backlog.
- `next` is defined against that clause and keeps its existing one-line
  resolution report and its no-eligible-task stop; when the only reason nothing
  is eligible is unmet preconditions, the stop names the blocked tasks by id
  instead of claiming everything is DONE/SKIP/IN PROGRESS/STALE.
- `all` is defined as `next` applied repeatedly until no task is eligible, and
  the file states how it is resolved: one pass up front that walks the backlog
  repeatedly, treating each already-selected task as satisfied, so the run
  still gets a fixed ordered list, one resolution report and one delegation
  count.
- The `all` resolution report names, by id, every implementable task left
  unselected because its preconditions are unmet — an unsatisfiable edge is
  visible rather than silently skipped.
- A precondition cycle is stated: every task on it is ineligible, the
  resolution terminates rather than looping, and the cycle's tasks are reported
  as blocked.
- Explicit-list selection is unchanged and the file says so: a task requested
  by number is never blocked by a precondition.

### `skills/task-implement/SKILL.md` (and `delegated-runs.md` if it restates the step)
- BETWEEN TASKS step 2 (and the matching step in
  `skills/task-implement/delegated-runs.md`, if it restates it) re-checks the
  upcoming task's preconditions against the `TASKS.md` it already re-reads. A
  task whose preconditions are no longer satisfied is skipped with a one-line
  report. No new read is introduced anywhere.
- ARGUMENT PARSING still cites `resolution.md` § *Selectors* as the authority
  and states only the re-check as its own departure; the rule is not restated
  there.

### `commands/production-status.md` — the Next field
- In § READINESS, **The Next field**'s `/task-implement <N>` bullet no longer
  says "the lowest-numbered such task". `<N>` is the first task in appearance
  order that is not `[DONE]`/`[SKIP]` and whose `Preconditions:` are all
  `[DONE]` or `[SKIP]`, with an id resolving to no task ignored.
- The bullet names `task-engine`'s `resolution.md` § *Selectors* as the
  authority for the eligibility clause rather than restating it in full — the
  one-authority-per-rule discipline the `task-*` suite already follows.
- A `[PLANNED]`, unblocked feature whose every open task has unmet
  preconditions gets a stated value rather than an undefined one; whichever
  value is chosen is written into the field's enumerated list, so the field
  still has a closed set of values.
- No new read is introduced: `Preconditions:` already comes from the summary
  blocks the command opens, and the never-open-a-file-under-`.claude/tasks/`
  contract in the frontmatter and the DO NOT list still holds.
- Section 4 still echoes section 2's value rather than re-deriving it, and the
  DO NOT list's "Store or cache readiness, the Next field…" line is unchanged.

### `commands/task-add.md` — `--before` / `--after`
- The ARGUMENT NOTE parses `--before <N>` and `--after <N>`, strips them, and
  states they are mutually exclusive; naming both stops the run. An `N` matching
  no task stops with the command's usual unknown-task message.
- `--before <N>` writes the new summary block immediately above task N's and
  appends the new id to task N's `Preconditions:` line. `--after <N>` writes it
  immediately below task N's and puts N on the new task's `Preconditions:`.
- The body states why both halves are written together: the position is for the
  human reading top to bottom, the edge is for the selectors, and either alone
  leaves the two disagreeing.
- PHASE 4's write steps say "insert at the resolved position" rather than
  "append the new summary block", for both the single-task and the split case.
- The DO NOT list's "Update any other task's `Preconditions:` line" entry is
  narrowed so it no longer forbids the one edit `--before` requires — the
  exception is stated explicitly and bounded to task N's `Preconditions:` line.
- PHASE 2's "Position questions are unnecessary — new tasks are appended at the
  end by default" is corrected to reflect that position is now expressible.
- `--before` / `--after` each compose with any of `--short`, `--no-split`,
  `--no-commit`, `--no-push`, `feature=<slug>` and `--single` (the
  `--short` / `--single` exclusion below is between those two, not with the
  placement flags); on a split they apply to the first part and the remaining
  parts follow it in order.
- Renumbering is explicitly still forbidden: an insertion consumes the next id
  from `Last task number:` exactly as an append does, and no existing id moves.
- A task carrying a `Feature:` line placed among another feature's tasks is
  stated to be legal — reconciliation keys on the `Feature:` line, never on
  position.

### `commands/task-add.md` — `feature=<slug> --single` and the orphan question
- `/task-add feature=<slug> --single "<description>"` plans exactly one task
  against the named feature's document, writes its `Feature: <slug>` line, and
  appends its id to that feature's `FEATURES.md` `Tasks:` line.
- `--single` runs no reconciliation over the feature's other tasks, and the body
  says so explicitly.
- The feature's `FEATURES.md` `Status:` is untouched under `--single` — a
  `[PLANNED]` feature with one more planned task has not changed its
  design-to-backlog relationship. `Doc:` and `Source:` are still never written.
- The closing report carries one fixed line saying the feature document was not
  updated and naming `/pipeline-patch feature=<slug>` as the write-back, so the
  drift is announced when it is created rather than discovered later.
- `--single` is mutually exclusive with `--short`, for the same reason
  `feature=<slug>` already is; naming both stops the run with the existing
  message shape.
- On a project where `.claude/FEATURES.md` exists, a free-form `/task-add` run
  asks — inside PHASE 3's existing single approval gate, never as a second gate
  — whether the task belongs to a feature, listing the available slugs and
  offering "none". A slug takes the `--single` path; "none" writes the task
  exactly as today.
- A project with no `.claude/FEATURES.md` sees no change at all — the question
  is not asked and nothing is said about it.
- The DOCUMENTATION TASK section is stated not to fire on a `--single` run: one
  attached task is not a planning pass.

### Versions
- `skills/task-engine/SKILL.md`, `skills/task-implement/SKILL.md`,
  `commands/production-status.md` and `commands/task-add.md` each take a
  **minor** `version:` bump — once each, whatever the number of edits above.
- Root `VERSION` takes **one minor** bump and `CHANGELOG.md` gains **one**
  matching top section whose bullets cover the selection rule, the Next-column
  change, the placement flags and `--single`; `./scripts/check-changelog.sh`
  exits zero.

## Decisions
- **One task for the task-side half.** The four pieces were planned as four
  tasks (169–172) and merged on 2026-09-11 (user decision): two of them edited
  `commands/task-add.md` back to back, two of them were the same rule in two
  files, and the split cost four `VERSION` bumps and four `CHANGELOG` sections
  for one feature. The runbook store (task 173) stays separate: nothing there
  reads `Preconditions:`, and it has no product file in common with this task
  (only `VERSION` and `CHANGELOG.md`).
- `all` resolves once up front by simulating the repeated `next` rather than
  re-resolving after every task. It yields the same list the repeated rule
  would, and it preserves the single resolution report, the fixed list and the
  `k`-task delegation count that `/task-implement`'s PRE-FLIGHT step 2b already
  depends on.
- The feature document's second open question is answered here rather than
  deferred: `/task-implement` already re-reads `TASKS.md` between tasks, so
  per-spawn re-evaluation costs nothing and needs no new read point.
- `/task-list` gains no `(waits on N)` marker. The feature document leaves that
  out until the rule has been used, and it is a rendering change, cheap to add
  later.
- No topological sort and no scheduler. One eligibility clause, stated once, in
  the file that already owns the selectors.
- This repository has no `.claude/PLAN.md` and no
  `.claude/domain/product-roadmap.md` by design, so the `/production-status`
  change is specified and verified against the command body alone. Neither
  document is created here to exercise it.
- Placement and edge are one flag, not two. The feature document rejects a
  position-only flag because it would leave `TASKS.md` reading one order and the
  selectors following another.
- Inserting never moves an existing task. Moving one is a revision and belongs
  to `/pipeline-revise` through the owner amend files, not here.
- No automatic feature write-back. `--single` announces that the feature
  document was not updated and names the patcher; updating it is
  `/pipeline-patch`'s job, and `/task-add` stays a non-writer of every owned
  document.
- The orphan question rides the existing PHASE 3 gate rather than adding one.
  A second gate on the common path is the cost this feature is explicitly
  trying not to pay.
- `.claude/domain/features/plan-readout.md` — which owns the read side's design
  — is deliberately untouched: it predates the Next column and states nothing
  about how `<N>` is picked, so there is no drift to reconcile.
- Root `VERSION` is minor, not patch: two new `/task-add` surfaces reach the
  user. The per-feature `version:` bumps are minor because each body's visible
  behaviour changes.
