# Task 199 — State the archive deviation in every id reader, including `/production-status`'s rollup

Target: claude

## Goal
Feature `task-archive` (.claude/domain/features/task-archive.md) puts the
archived-and-terminal rule in `resolution.md` (task 196) and requires every
consumer that meets an absent id to cite that path and state only its own
deviation. Most readers already tolerate an id that resolves to nothing; what
changes is what the id *means* and, for two of them, what happens next:
`/task-implement` stops on an explicitly requested archived id, and
`/production-status` — which today would render a fully archived `[PLANNED]`
feature as having no tasks at all — reports the absent ids as `archived: N`.
Seven files, one task: each edit is a clause or two, all of them the same
deviation from the same rule, and none of them gains a probe of the archive
folder.

## Acceptance criteria

### `commands/task-add.md`
- PHASE 1b: the sentence "IDs that resolve to no task are ignored, not an error
  — `/task-clean` normally prunes them" is replaced by a citation of
  `resolution.md`'s rule plus this command's deviation — an absent id is
  archived and terminal, is left unclassified by reconciliation, and is not an
  error.
- PHASE 4 step 4 says the rewritten `Tasks:` line keeps absent ids alongside
  the survivors and the new ones (`[SKIP]` ids still dropped, `[DONE]` ids
  still kept).

### `skills/task-implement/SKILL.md`
- PRE-FLIGHT step 2: an id requested explicitly by number with no summary block
  in `TASKS.md` stops the run and names `.claude/tasks/archive/<N>.md` as where
  its body would be, without opening it; the body is read only if the user then
  asks, and the task is never re-implemented. `all` and `next` are unaffected —
  they resolve from blocks that exist.

### `skills/task-review/SKILL.md` and `skills/task-iterate/SKILL.md`
- The fourth resolution fallback (the most recently modified
  `.claude/tasks/*.md`) excludes `.claude/tasks/archive/` from the search, in
  one clause each. `/task-review` cites `resolution.md` for the reason;
  `/task-iterate` states the exclusion without a citation and gains no
  `requires:` line.

### `skills/architect/iterating.md` and `skills/architect/SKILL.md`
- `iterating.md` step 1 and its step-4 aside: the rationale is rewritten — an id
  absent from `TASKS.md` is archived and terminal, not "pruned by `/task-clean`
  from the `Tasks:` line" — and the `Status:`-keyed special case is explicitly
  kept for backlogs cleaned before this feature. The status table, the flip
  rules, the `[IN PROGRESS]` refusal and the report wording are untouched:
  behaviour does not change here.
- `skills/architect/SKILL.md` items 5 and 6 carry the same corrected rationale,
  in the same words as `iterating.md`'s, so the two do not disagree.

### `commands/production-status.md`
- The default rollup counts absent ids as `archived: N` alongside the per-status
  counts, e.g. `6 tasks — DONE: 2, MISSING: 1, archived: 3`. It is a new value
  inside the existing line, not a new column or section.
- Under `--task-ids` each absent id is named with `[archived]`, e.g.
  `tasks: 41 [archived], 42 [DONE], 43 [MISSING]`.
- "A task ID that resolves to no entry in `TASKS.md` is ignored, not an error"
  is replaced by a citation of `resolution.md`'s rule and this command's
  deviation: an absent id is archived and terminal and is *reported*, not
  ignored. Nothing probes or opens the archive; the command's no-shell and
  never-open-`.claude/tasks/` rules are unchanged, in the frontmatter
  description, the header comment, READING THE INPUTS and the DO-NOT list.
- The zero-task case narrows to a literal `Tasks: none`. A `Tasks:` line whose
  every id is absent is no longer a zero-task case — it renders `archived: N`.
- The `Status:`-keyed split on that narrowed zero-task case stays, with its
  rationale rewritten: it survives for backlogs cleaned before this feature,
  where the ids were dropped from the line rather than archived.
- Readiness and the `Next` field are unchanged in behaviour, and their wording
  says why: an archived id is terminal, so it counts as resolved — it never
  blocks `flip to [DONE] in FEATURES.md` and is never the `<N>` in
  `/task-implement <N>`, which after task 169 names the first task in
  appearance order that is not `[DONE]`, `[SKIP]` or archived and whose
  preconditions are satisfied. The archived clause is added to that wording.
- The milestone table's `Tasks` column and every other section are otherwise
  untouched.

### Across all seven files
- Every edited file states only its deviation; none restates the rule, and no
  new copy of the archive path's meaning appears outside `resolution.md`.
- No file gains a probe of `.claude/tasks/archive/`.

### Versions
- Each edited feature's own `version:` frontmatter is bumped (`task-add`,
  `task-implement`, `task-review`, `task-iterate`, `architect`,
  `production-status`).
- Root `VERSION` takes **one patch** bump and `CHANGELOG.md` gains **one**
  matching top section; `./scripts/check-changelog.sh` is silent afterwards.

## Decisions
- **Seven files, one task.** Planned as two tasks (199 and 200) and merged on
  2026-09-11 (user decision): `/production-status` is one more id reader
  stating the same deviation, and the original task 199 already argued that
  splitting such edits "would produce five commits that each say cite the
  archive rule in X".
- `/task-iterate` gains no `requires: skill:task-engine` (user decision at
  planning time). Its fallback resolves a task from a filename, not from a
  `Tasks:` or `Preconditions:` id, so excluding one folder from a search needs
  no authority cited — and an install-time dependency for a single clause costs
  more than it explains. `/task-review` cites the file because it already reads
  the engine for `review-budget.md`.
- `/architect`'s special case is kept rather than removed. Under this feature a
  cleaned `[PLANNED]` feature keeps its ids, so `Tasks:` could discriminate
  again — but only on backlogs cleaned after it lands. The guard must stay
  correct on backlogs cleaned before, and `Status:` is still the field that is
  right in both worlds.
- `/task-implement` stops rather than skipping. The user named that id
  explicitly; silently continuing would leave them thinking work was queued.
- `archived: N` sits in the counts line rather than becoming a status. It is
  not one of `status.md`'s eight tags and must not read as one — the count is
  derived from absence, and no `Status:` field anywhere ever holds it.
- The zero-task rule narrows instead of being deleted. Deleting it would
  mis-report every backlog cleaned before this feature, which is exactly the
  population the rule was written for.
- Task 169 is a precondition so the `Next` field's wording is settled before
  this task adds the archived clause to it; otherwise the outcome would depend
  on which of the two ran first.
- The `Next` and readiness wording is made explicit even though behaviour does
  not change. Both already assumed an unresolvable id was terminal; leaving
  that implicit next to a new `archived:` count is how the two drift apart.
- Patch on root `VERSION`: no new command or flag reaches the user; readers
  gain a clause and a read-only report gains a value in an existing line.
