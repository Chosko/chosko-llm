# Task 199 — State the archive deviation in every id reader

Target: claude

## Goal
Feature `task-archive` (.claude/domain/features/task-archive.md) puts the
archived-and-terminal rule in `resolution.md` (task 196) and requires every
consumer that meets an absent id to cite that path and state only its own
deviation. Most readers already tolerate an id that resolves to nothing; what
changes is what the id *means* and, for `/task-implement`, what happens next.
None of these five files gains a probe of the archive folder.

## Acceptance criteria
- `/task-add` PHASE 1b: the sentence "IDs that resolve to no task are ignored,
  not an error — `/task-clean` normally prunes them" is replaced by a citation
  of `resolution.md`'s rule plus this command's deviation — an absent id is
  archived and terminal, is left unclassified by reconciliation, and is not an
  error. PHASE 4 step 4 says the rewritten `Tasks:` line keeps absent ids
  alongside the survivors and the new ones (`[SKIP]` ids still dropped,
  `[DONE]` ids still kept).
- `/task-implement` PRE-FLIGHT step 2: an id requested explicitly by number
  with no summary block in `TASKS.md` stops the run and names
  `.claude/tasks/archive/<N>.md` as where its body would be, without opening
  it; the body is read only if the user then asks, and the task is never
  re-implemented. `all` and `next` are unaffected — they resolve from blocks
  that exist.
- `/task-review` and `/task-iterate`: the fourth resolution fallback (the most
  recently modified `.claude/tasks/*.md`) excludes `.claude/tasks/archive/`
  from the search, in one clause each. `/task-review` cites `resolution.md` for
  the reason; `/task-iterate` states the exclusion without a citation and gains
  no `requires:` line.
- `/architect` `iterating.md` step 1 and its step-4 aside: the rationale is
  rewritten — an id absent from `TASKS.md` is archived and terminal, not
  "pruned by `/task-clean` from the `Tasks:` line" — and the `Status:`-keyed
  special case is explicitly kept for backlogs cleaned before this feature. The
  status table, the flip rules, the `[IN PROGRESS]` refusal and the report
  wording are untouched: behaviour does not change here.
- `skills/architect/SKILL.md` items 5 and 6 carry the same corrected rationale,
  in the same words as `iterating.md`'s, so the two do not disagree.
- Every edited file states only its deviation; none restates the rule, and no
  new copy of the archive path's meaning appears outside `resolution.md`.
- Each edited feature's own `version:` frontmatter is bumped.
- Root `VERSION` takes a patch bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` is silent afterwards.

## Decisions
- `/task-iterate` gains no `requires: skill:task-engine` (user decision at
  planning time). Its fallback resolves a task from a filename, not from a
  `Tasks:` or `Preconditions:` id, so excluding one folder from a search needs
  no authority cited — and an install-time dependency for a single clause costs
  more than it explains. `/task-review` cites the file because it already reads
  the engine for `review-budget.md`.
- `/architect`'s special case is kept rather than removed. Under this feature a
  cleaned `[PLANNED]` feature keeps its ids, so `Tasks:` could discriminate
  again — but only on backlogs cleaned after it lands. The guard must stay
  correct on backlogs cleaned before, and `Status:` is still the field that is
  right in both worlds.
- `/task-implement` stops rather than skipping. The user named that id
  explicitly; silently continuing would leave them thinking work was queued.
- Five files, one task: each edit is a clause or two, all of them are the same
  deviation from the same rule, and splitting them would produce five commits
  that each say "cite the archive rule in X".
