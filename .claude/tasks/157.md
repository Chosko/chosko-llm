# Task 157 — Key the iterate guard's status flip on the feature's status, not its `Tasks:` line

Target: claude

## Goal
`/architect`'s iterate guard decides whether to act by reading the
`FEATURES.md` entry's `Tasks:` line: `Tasks: none` means "skip the guard
entirely, status stays as it is". That test is ambiguous. `/task-clean`
prunes `[DONE]`/`[SKIP]` IDs out of `Tasks:` lines and deliberately leaves
`Status:` alone, so a cleaned `[PLANNED]` or `[DONE]` feature looks exactly
like a never-planned `[NEW]` one. Re-architecting such a feature therefore
leaves it `[DONE]`, which contradicts the state machine (`[DONE]` →
`[ITERATED]` is the documented transition), contradicts product-workflow.md's
own rule that pruning does not un-plan a feature, and strands it:
`/task-add feature=<slug>` never targets a `[DONE]` feature, so the
re-architected design has no path back into the backlog. Make `Status:` the
discriminator, and amend the guard's prose everywhere it is restated.

## Acceptance criteria
- `skills/architect/iterating.md` step 1 no longer treats `Tasks: none` as a
  blanket skip. The guard's task half (list, refuse, ask, flip to `[STALE]`)
  is skipped when there are no resolvable tasks; the status half is decided
  by the entry's `Status:`.
- With no resolvable tasks: `[NEW]` stays `[NEW]`, `[ITERATED]` stays
  `[ITERATED]`, and `[PLANNED]` or `[DONE]` flips to `[ITERATED]` — no ask,
  no `TASKS.md` write, and the flip named in PHASE 3's closing report.
- An entry whose `Tasks:` IDs all resolve to nothing behaves identically to
  `Tasks: none` — same status rule, still not an error.
- `iterating.md` step 4's note that a `[DONE]` feature "reaches this guard
  with every one of its tasks already `[DONE]` or `[SKIP]`" is corrected: a
  cleaned entry reaches it with no tasks at all.
- `skills/architect/SKILL.md` PHASE 0b item 5 restates the new rule and no
  longer says "the status stays as it is"; its frontmatter `description`
  still describes the guard accurately.
- `.claude/domain/product-workflow.md` § The iterate guard item 4 matches,
  and the `[DONE]` → `[ITERATED]` / illegal-transition sections stay
  consistent with it.
- `.claude/context/features.md`'s `/architect` bullet reflects the amended
  guard.
- `skills/architect/SKILL.md` frontmatter `version:` 0.7.2 → 0.7.3, root
  `VERSION` 1.19.0 → 1.19.1, matching top `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` exits silent.

## Decisions
- **The discriminator becomes `Status:`, not `Tasks:`.** `Tasks: none` is
  ambiguous by design after `/task-clean`; the status is the only field that
  records whether tasks ever existed.
- **`[PLANNED]` gets the same treatment as `[DONE]`.** Identical bug, and
  product-workflow.md:132 already states that pruning leaves a feature
  `[PLANNED]`.
- **No new prompt.** The guard's ask exists to warn about tasks about to be
  marked `[STALE]`. With none, there is nothing to warn about — flip and
  report.
- **`/task-clean` is not changed.** Leaving `Status:` alone is correct; the
  reader was making the wrong inference, not the writer the wrong write.
- **README.md is not touched.** Its guard walkthrough covers the has-tasks
  path and never states what happens with none, so it does not drift.
- **Patch bump on both versions** — behaviour fix, no new surface.
