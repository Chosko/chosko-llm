# Task 163 — Find and fix what made `ls` slow

Target: claude

## Goal
`chosko-llm ls` (plain, global scope, Git Bash on Windows) now takes several
seconds on a clone of ~34 features. Measure where the time actually goes, then
remove it. Task 155 already paid down one such regression by parsing each
file's frontmatter once per row; this is the next one, and it must be diagnosed
before it is fixed — the profile decides the fix, not the suspicion below.

Two suspects are visible from reading the code, and the profile confirms or
kills each:

1. `compute_status` calls `lib.sh::find_replacement` on every `local only` row.
   That function rescans every source file in the clone, calling
   `read_frontmatter_field` (two awk processes) per file, until it hits. Only 2
   files in the whole clone declare `replaces:`, so the scan is ~68 processes
   per local-only row and almost always finds nothing — quadratic in the
   feature count for a lookup that could be one pass. `check_migration_pending`
   is the same probe from the other side.
2. Per-row fork count. Each row spawns command substitutions for both path
   helpers, two `read_frontmatter_fields` process substitutions (a subshell
   plus two awk each), one for `compute_status`, one for the row render, and
   one more inside `_requires_cell`. Forking is expensive under Git Bash on
   Windows, and this cost is paid ~34 times even when nothing is superseded.

## Acceptance criteria
- The run is profiled before any edit, and the profile is reported: where the
  time went, and which of the two suspects above (or a third cause the profile
  found) actually dominated. A fix landed without that measurement does not
  satisfy this task.
- `chosko-llm ls` is measurably faster on the repro — plain `ls`, global scope,
  Git Bash on Windows — with before and after wall-clock numbers reported. No
  absolute target is set; the win is whatever removing the measured cost buys.
- Output is **byte-identical** to the pre-change output for: `ls`,
  `ls --installed`, `ls --available`, `--global` and `--local` scope, and both
  piped and TTY stdout (the footer block differs between the two). Verified by
  diffing captured output from before and after, not by eye.
- `superseded` and `migration pending` still appear on exactly the rows that
  earned them — a `replaces:` index or memoization must not silently drop a
  status. Exercise both, including the malformed-`replaces:` warning path.
- A malformed `requires:` entry still renders raw and dimmed and the listing
  still completes: `ls` stays non-fatal, `cmd-add` / `cmd-rm` stay fatal.
- `.claude/context/cmd-ls.md` and, if `lib.sh` changed,
  `.claude/context/shared-lib.md` describe the new shape — the same way task
  155's parse-once note is recorded there today.
- Root `VERSION` bumped (patch) and a matching `CHANGELOG.md` section added;
  `./scripts/check-changelog.sh` silent.

## Decisions
- **Diagnose before fixing.** The user asked for the cause, not just a faster
  script. The two suspects are starting points from a code read, not a
  conclusion — the profile is what picks the fix.
- **Behaviour is frozen; only cost changes.** No new columns, no dropped
  statuses, no reordering, no changed colors. Byte-identical output is the
  guard, and it is what makes an aggressive rewrite of the passes safe.
- **No on-disk cache or state file.** CLAUDE.md forbids lockfiles and state
  files — filesystem plus frontmatter is the state. Any index or memo built
  here lives in the process and dies with it.
- **No new dependencies.** POSIX-ish bash with awk/sed/grep, per CLAUDE.md. A
  single awk pass over many files is in bounds; jq/python is not.
- **Verification is the repro, not a test suite.** This repo has none by
  design; the change is verified by running the CLI against the real clone and
  diffing output.
