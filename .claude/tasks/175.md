# Task 175 — Ship the `pipeline-engine` skill, the `/pipeline-check` command and the repo-local routing check

Target: claude

## Goal
Feature `pipeline-engine` gives the revision suite one home for what every
pipeline feature needs to know about the pipeline as a whole. A shared file can
only ship inside a skill folder, so the engine is a skill — non-invocable in
exactly the way `task-engine` is — carrying four reference files: `probes.md`
(how a consumer describes a project's pipeline setup and the one verdict line
every consumer prints), `graph.md` (how the pipeline's indexes point at each
other), `routing.md` (one row per pipeline feature: consumes, produces, owns,
preconditions, argument shape) and `lint.md` (the finding catalogue). On top of
the engine sit two thin consumers: `commands/pipeline-check.md`, the read-only
drift report that evaluates `lint.md` over `graph.md`'s edges and prints each
finding with the one command that fixes it, and `scripts/check-routing.sh`, an
authoring-time guard that the routing table stays honest in both directions.

This task ships all of it at once. The four reference files constrain each
other — every `graph.md` edge must be consumed by a `lint.md` finding, every
`lint.md` fix must have a `routing.md` row, `probes.md` names the writers whose
runs invalidate a verdict — and the command is a thin reader of all four. One
author writing them together is what keeps them consistent; the skill ships
complete at `0.1.0` rather than at `0.4.0` with three intermediate states no
one can use. Precedent: `task-engine` (task 126) and `runbook-run` (task 140)
each landed as one task with every reference file.

Feature `task-archive` puts the archived-and-terminal rule in `task-engine`'s
`resolution.md` (task 196); `graph.md` and `lint.md` cite that rule, so this
task lands after 196.

## Acceptance criteria

- Exists with complete frontmatter: `name: pipeline-engine`, `version: 0.1.0`,
  `type: skill`, and a `description:` that states plainly that it is not
  invocable, takes no arguments, produces no output, and must never be
  suggested — the wording `task-engine`'s description already uses for the same
  property.
- Carries **no rule text**. It holds only: the not-directly-invocable notice,
  the install-path assumption naming
  `${CLAUDE_HOME:-$HOME/.claude}/skills/pipeline-engine/references/<file>.md`
  and never a hardcoded home path, the map table, and a short note on how a
  reference file is read. Adding rule text here recreates the duplication the
  engine exists to remove, and the file says so.
- The map table carries all four rows — `references/probes.md`,
  `references/graph.md`, `references/routing.md`, `references/lint.md` — each
  stating what that file owns. All four files exist when this task lands.
- `./bin/chosko-llm ls --available` lists `skill:pipeline-engine` at `0.1.0`.

### `skills/pipeline-engine/references/graph.md`
- Names each edge by the artifact and the exact line it lives on: `FEATURES.md`
  `Source:` → a `product-design.md` section plus the optional milestone
  parenthetical; `FEATURES.md` `Doc:` → the feature document path;
  `FEATURES.md` `Tasks:` ↔ `TASKS.md` `Feature:`; `TASKS.md` `Preconditions:` →
  task ids; `PLAN.md` milestone `Features:` lists and its flat `## Dependencies`
  edge list → `FEATURES.md` slugs; `RUNBOOKS.md` `File:` → the body path;
  runbook steps naming task ids or feature slugs.
- Each edge states its direction, which side is authoritative when the two
  disagree, and which command writes each side.
- The `FEATURES.md` `Tasks:` → `TASKS.md` direction states the resolution rule
  explicitly: **an id on a `Tasks:` line with no summary block in `TASKS.md` is
  archived and terminal, not dangling.** Feature `task-archive` makes that the
  normal state of a cleaned feature — `/task-clean` moves the body to
  `.claude/tasks/archive/<N>.md` and leaves `Tasks:` alone — so the absence
  carries meaning rather than indicating drift.
- That rule is **cited, never restated**:
  `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/references/resolution.md` is
  named as its authority, and `graph.md` adds only what the edge does with it.
- Adds **no probe of `.claude/tasks/archive/`** and states that traversing the
  graph never requires one: an absent id resolves to "archived, terminal" from
  the absence itself, and no reader checks whether the archived file is there.
- The reverse direction is unchanged and stated separately: a `TASKS.md`
  `Feature:` slug with no entry in `FEATURES.md` is a real inconsistency, since
  nothing archives a feature slug.
- States explicitly that no edge requires opening a task body, an archived
  body, a feature document, a runbook body or a design document, and that a
  consumer that opens one is doing so for its own reasons, not to traverse the
  graph.
- Restates no schema owned elsewhere. `TASKS.md`'s block shape cites
  `task-engine/references/resolution.md`; the runbook body, index block and
  `Steps:` counter cite
  `${CLAUDE_HOME:-$HOME/.claude}/skills/runbook-run/references/runbook-schema.md`;
  `PLAN.md`'s schema cites `/production-status`. Each citation adds the edge and
  nothing else.
- Every edge in the file is consumed by at least one `lint.md` finding or one
  impact-walk step; an edge used by neither is cut, per the design's
  every-line-is-consumed rule. Check this in both directions before finishing —
  it is the reason the two files ship together.
- Notes which edges simply do not exist on a project missing that index, so a
  consumer degrades rather than failing — the same contract `/production-status`
  already keeps.

### `skills/pipeline-engine/references/routing.md`
- One row for every pipeline command or skill shipped today: `/domain-setup`,
  `/product-design`, `/product-roadmap`, `/architect`, `/production-plan`,
  `/task-add`, `/task-implement`, `/task-review`, `/task-iterate`, `/task-list`,
  `/task-clean`, `/production-status`, `/runbook-create`, `/runbook-run`,
  `/runbook-list`, `/runbook-describe`, `/runbook-clean`, `runbook-suggest`, and
  `/pipeline-check` (which ships in this same task).
- Five columns: Consumes, Produces, Owns, Preconditions, Argument shape.
- The Owns column is **by line, not by file**, wherever a file has more than one
  writer — `FEATURES.md` `Doc:` and `Source:` are `/architect`'s while `Tasks:`
  and `Status:` are `/task-add`'s; `TASKS.md`'s summary blocks are `/task-add`'s
  to create and `/task-implement`'s to flip. No two rows claim the same line.
- Every row's Owns entry is verified against the shipped body it describes, not
  against the domain layer, and a row that cannot be verified from a shipped
  body is not written.
- Where a path also appears in `/task-add`'s OWNERSHIP PRE-AUTHORISATION owner
  table, this table agrees with it. A disagreement is resolved by fixing this
  table, never `/task-add`'s — that table is the sole source of ownership for
  the pre-authorisation check and is not this feature's to change.
- Each row identifies its feature by name only. The kind — command or skill — is
  not a column, so a later kind migration changes no row.
- The table has a place for an owner's amend entry — a column, or a documented
  per-row field — even though task 182 is what fills it in. Deciding the shape
  here, with the table, is cheaper than retrofitting it.
- States the table's contract in one line: it is the ownership authority the
  revision suite reads, and a consumer states only its deviations from a row.
- Rows for the three not-yet-shipped revision surfaces (`/pipeline-patch`,
  `pipeline-revise`, `pipeline-suggest`) are **not** written: this task's own
  `check-routing.sh` requires every row to name a feature that exists in the
  repo, so a row for an unwritten feature would fail its own guard. Those
  features add their own rows when they land (tasks 187 and 194).

### `skills/pipeline-engine/references/lint.md`
- Covers exactly these eleven findings and no others: a task's `Feature:` slug
  absent from `FEATURES.md`; a task with no `Feature:` line on a project whose
  `FEATURES.md` exists; a `Preconditions:` id that resolves to no task; a
  `Preconditions:` id naming a `[SKIP]` task; a precondition cycle; an
  `[ITERATED]` feature; a `[STALE]` task; a `FEATURES.md` slug absent from
  `PLAN.md`; a plan edge naming an unknown slug; a `[PENDING]` runbook whose
  `Steps:` shows every step done; a `[PLANNED]` feature whose every task has
  resolved and which has not been flipped.
- **"A feature's `Tasks:` id absent from `TASKS.md`" is not a finding**, and the
  file says so in a short note rather than by silent omission: under feature
  `task-archive`, `/task-clean` moves the body to `.claude/tasks/archive/<N>.md`
  and leaves the `Tasks:` line intact, so that absence is the normal state of a
  cleaned feature and means **archived, terminal**. The rule is cited from
  `${CLAUDE_HOME:-$HOME/.claude}/skills/task-engine/references/resolution.md`,
  never restated.
- No detection rule probes `.claude/tasks/archive/`, opens an archived file, or
  reports on its contents, and the file states that prohibition once, for the
  whole catalogue.
- The `[PLANNED]`-feature finding is defined so an archived id counts as
  resolved: it fires when every id on the feature's `Tasks:` line is `[DONE]`,
  `[SKIP]`, or absent from `TASKS.md`. Without that clause a cleaned feature
  would never be reported as ready to flip, which is the exact ambiguity
  `task-archive` exists to remove.
- Each remaining finding's detection rule names the `graph.md` edge it walks and
  reads only index lines. No rule opens a file under `.claude/tasks/`,
  `.claude/runbooks/` or `.claude/domain/`.
- The runbook `[PENDING]` finding is derived from `RUNBOOKS.md` alone —
  `Steps: <n>/<n>` together with `Status: [PENDING]` — and the file states that
  derivation, since it is the one finding whose index-only form is not obvious.
- Records that "a pending runbook step naming a task already `[DONE]` or
  `[SKIP]`" is **deliberately absent**, and why: detecting it would mean opening
  a runbook body, which the read-only register forbids, and `/runbook-run`
  surfaces the same problem when it prints the step before spawning it.
  `RUNBOOKS.md` carrying per-step targets is what would unblock a cheap
  index-only version. A reader must not conclude it was forgotten.
- Severity is **two levels, `ERROR` and `WARNING`**, and the file states the
  discriminator once rather than leaving it per finding: `ERROR` is a reference
  that cannot be resolved or a state that will misdirect a run — an unknown
  slug, an unknown or `[SKIP]` precondition id, a cycle, a plan edge naming a
  slug that does not exist. `WARNING` is a legal state that needs its owner's
  attention — an `[ITERATED]` feature, a `[STALE]` task, a slug missing from
  `PLAN.md`, a finished-but-`[PENDING]` runbook, a fully resolved `[PLANNED]`
  feature, a task with no `Feature:` line. Every finding carries exactly one.
- Each finding names exactly one fixing command, and every command named has a
  row in `routing.md`: `/task-add feature=<slug>` for an `[ITERATED]` feature,
  `/production-plan` for a slug missing from the plan, a plain `flip to [DONE]`
  for a fully resolved `[PLANNED]` feature, `/pipeline-patch` or
  `/pipeline-revise` for the rest. (Those two have no routing row until task
  187 lands; the fix column may name them regardless — the check in
  `check-routing.sh` reads rows, not fix columns.)
- Each finding carries a one-line output template so `/pipeline-check` and the
  revision surfaces render it identically, with the severity, the artifact and
  the offending identifier in a fixed position.
- States the two failure rules: a finding whose index is absent is dropped from
  the run rather than reported as an error, and a malformed block is a finding
  of its own — `ERROR`, with its own fix — rather than an abort.
- States that it detects **structural** inconsistency only. Whether a feature
  document still describes what its tasks build is `/architect amend`'s
  precision guard, and the catalogue says so rather than leaving the boundary to
  a reader's judgement.

### `commands/pipeline-check.md`
- Frontmatter is complete: `name: pipeline-check`, `version: 0.1.0`,
  `type: command`, `requires: skill:pipeline-engine`, and a `description:` that
  states the read-only register and the `feature=<slug>` form.
- The body cites all four reference files as
  `${CLAUDE_HOME:-$HOME/.claude}/skills/pipeline-engine/references/<file>.md`
  and never a `docs/` path — `docs/` is authoring-time-only and is not installed.
  It restates no probe, no edge and no finding; it states only its own
  deviations, the `task-engine` discipline verbatim.
- The read-only register is stated explicitly and in the same register
  `/production-status` uses: writes nothing, creates nothing, commits nothing,
  flips no status, opens no file under `.claude/tasks/` — **`.claude/tasks/archive/`
  named explicitly among them** — `.claude/runbooks/` or
  `.claude/domain/features/`, and runs no shell beyond the probe.
- Every absent index removes its findings rather than failing the run. The only
  stop is a project carrying none of the indexes at all, which is pointed at
  `/task-setup` and `/domain-setup` and stops there.
- A clean project prints exactly one line.
- Findings are grouped by artifact, in a fixed artifact order, each rendered
  from `lint.md`'s output template and each carrying its fix command verbatim.
  The run ends with one summary line counting `ERROR` and `WARNING` findings.
- `feature=<slug>` scopes the walk to that feature and to the tasks, plan edges
  and runbook steps that name it. An unknown slug lists the slugs that do exist
  rather than reporting an empty clean run.
- An unrecognised argument is reported in one line and the default report still
  runs — the command never refuses over its own arguments, matching
  `/production-status`.
- The command is invoked explicitly and by nothing else: the body carries no
  instruction for another feature to call it, and nothing in this task edits
  another feature to do so.
- The body matches the command's own `routing.md` row.
- `./bin/chosko-llm ls --available` lists `command:pipeline-check` at `0.1.0`
  with `skill:pipeline-engine` in the REQUIRES column, and
  `./bin/chosko-llm add command:pipeline-check` into a scratch `CLAUDE_HOME`
  installs `skill:pipeline-engine` first.

### `scripts/check-routing.sh`
- Starts with `set -euo pipefail`, sources `lib.sh` the way
  `check-changelog.sh` does, and adds no dependency beyond awk / sed / grep.
- Invariant 1: every row in `skills/pipeline-engine/references/routing.md` names
  a feature that exists in this repo — `commands/<name>.md` **or**
  `skills/<name>/SKILL.md`, either kind accepted, since a feature can migrate
  between them. A row naming a feature that exists as neither fails, naming the
  row and both paths it looked for.
- Invariant 2: every shipped feature declaring `requires: skill:pipeline-engine`
  has a row in the table. A consumer without a row fails, naming the feature.
  The check uses `lib.sh`'s existing `requires:` helpers rather than parsing
  frontmatter again.
- The script's parser contract is stated in a comment at the top — which line
  shape it reads as a row and what it ignores — the way `check-changelog.sh`
  states its `^## ` contract, so a later edit to the table's formatting does not
  silently break the check.
- A leading comment states what the script can and cannot prove: existence in
  both directions, never whether a row's Consumes / Produces / Owns entries are
  true, and never that a pipeline feature which does not read the engine has a
  row — that half stays a human's job.
- Silent on success, non-zero with a specific message on failure; it uses
  `lib.sh`'s `die`, matching `check-changelog.sh`'s register exactly.
- Repo-local and authoring-time only: not a feature, no frontmatter, invisible
  to every CLI verb, installed nowhere.
- Exits clean against the table and the command this task ships.

## Decisions
- **One task for the whole feature's shipped surface.** Planned as six tasks
  (175–180) and merged on 2026-09-11 (user decision). The four reference files
  are mutually constrained and the command is a thin reader of all four; six
  tasks meant six `VERSION` bumps, the skill at `0.4.0` before anything could
  invoke it, a shipped map table naming files that did not exist, and four
  agents each re-reading the same inputs. Task 126 (`task-engine`, seven files,
  932 insertions) is the precedent for a whole engine in one task. The
  documentation task (181) stays separate: it is `VERSION`-exempt, describes
  what actually shipped, and carries its own grant.
- **Editing `.claude/domain/features/pipeline-engine.md` is explicitly
  authorised for this task (user decision, 2026-09-09), for the 2
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document is
  normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here. Task 181 holds a second
  grant on the same document, on four disjoint points; do not apply those here.
- The probe list is fixed here rather than grown per consumer. A consumer that
  needs a fact the probe does not carry adds it to `probes.md`; it does not
  probe privately, or the verdict stops being one line.
- No archive probe anywhere — `probes.md`, `graph.md`, `lint.md` or the command
  — stated as a rule rather than left as an omission. `task-archive` makes
  `.claude/tasks/archive/` a folder no command traverses, and states that a
  hand-deleted body and an archived one are indistinguishable to every reader
  by design — the difference surfaces only when the user asks to read the
  task; a probe added "just to check" is exactly how that guarantee would be
  lost, and a rule that checked would be claiming a distinction the product
  has deliberately declined to make.
- The graph is index-only by construction, not by convention. Every edge that
  would need a body is either dropped or re-expressed over an index line — that
  is what keeps the lint's read cost bounded by the number of indexes rather
  than by the size of the backlog.
- The archived-and-terminal rule is cited from `resolution.md`, never written
  here, per `shared-phase-engine`'s one-authority-per-rule discipline. Task 196
  puts it there and is a precondition of this task, so the citation resolves.
  If `resolution.md` nonetheless lacks the rule when this task runs, stop and
  report it rather than writing a second copy here to bridge the gap — that
  copy is the one that would drift.
- The `Tasks:`-id finding is dropped at authoring time rather than shipped and
  retracted later. Shipping it would make `/pipeline-check` report every cleaned
  feature as drift on its first run against an archived backlog — the loudest
  possible false positive, on exactly the projects the lint is most useful for.
- Two severity levels, not three (user decision at planning time), and
  deliberately **not** `/task-review`'s `BLOCKING` / `IMPORTANT` / `ADVISORY`.
  Those were defined for judging code against acceptance criteria; a drift
  finding is either a broken reference or a state someone should look at, and a
  middle tier would only invite argument about which findings belong in it.
  `ERROR` / `WARNING` also stays clear of all three status vocabularies, so a
  grep for a status never returns a severity.
- The catalogue is closed, not extensible-by-default: adding a finding is an
  edit to `lint.md`, so `/pipeline-check` and both revision surfaces gain it at
  once and cannot disagree about whether it exists.
- Routing rows name a feature, never a kind, and `check-routing.sh` accepts
  either kind, for a concrete reason: feature `task-archive` migrates
  `/task-clean` from `commands/task-clean.md` to `skills/task-clean/SKILL.md`
  via `replaces:`. A table keyed on kind, or a check that assumed one kind,
  would go stale on a migration that broke nothing.
- `/task-clean`'s Owns entry is written from its shipped body at implementation
  time, not from today's memory of it. Task 196 (a precondition) removes its
  `FEATURES.md` `Tasks:` write on a prune, leaving one only under `--backfill`;
  whichever state the body is in when this task runs is what the row records.
- Two ownership tables now exist in the product — this one and `/task-add`'s
  pre-authorisation table — with different jobs: this one routes a change to an
  owner, that one gates an implementer's edit rights. They overlap on paths and
  must not disagree; the tie-break above is what keeps them from drifting apart,
  and `/rule-overlap` will see both.
- `/pipeline-check` is a command, not a skill: a thin read-only reporter with no
  conversation and no supporting files is exactly the register `/task-list` and
  `/production-status` occupy, and the design names it a command.
- The probe may shell out; nothing else in the command's run may. That is the
  one stated departure from `/production-status`, which runs no shell at all,
  and the body says so rather than leaving a reader to infer it.
- The archive folder is named in the command's read prohibition rather than
  left implied by `.claude/tasks/`. It is a subfolder of a path already
  forbidden, but naming it is what stops a later reader treating it as a
  separate store that the prohibition happened not to mention.
- No `--fix`, no `--quiet`, no exit-code contract on `/pipeline-check`. The lint
  reports and every fix is the named owner's; an exit code would invite a caller
  to gate on it, which is the auto-running the design rules out. The severity
  counts are for a human's eye, not a gate.
- The completeness half of `check-routing.sh` is scoped to features declaring
  `requires: skill:pipeline-engine` rather than to "every pipeline feature"
  (user decision at planning time). There is no mechanical definition of
  "pipeline feature", and the two candidates for one — an authored membership
  list, or a new frontmatter key — are respectively near-vacuous and new
  machinery CLAUDE.md tells us to avoid. Rows for non-consumers such as
  `/architect` and `/task-add` stay authored and unchecked, which is the
  unavoidable share of the table that is semantics.
- `scripts/` is shipped in the managed clone, so the script rides the same
  `VERSION` bump. The `.claude/skills/` exemption covers repo-local *skills*
  only, and `check-changelog.sh` set the precedent for a repo-local script
  under `scripts/`.
