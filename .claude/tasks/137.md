# Task 137 — Add the repo-local /rule-overlap audit skill

Target: claude

## Goal
Third step of the `repo-local-audits` feature
(`.claude/domain/features/repo-local-audits.md`). The same rules are restated
across the `task-*` suite — the problem `shared-phase-engine` exists to fix —
and there is no way to find the next instance, or to confirm after that refactor
that the extracted rules really did stop being restated. Add a repo-local
`/rule-overlap` skill built on one principle: **deterministic collection, model
judgment.** A mechanical pass gathers every normative statement exhaustively;
the model only decides which of them are the same rule wearing different words.

## Acceptance criteria
- `.claude/skills/rule-overlap/SKILL.md` exists. Frontmatter carries
  `name: rule-overlap`, `type: skill`, a one-line `description`, and **no
  `version:` field**, with the same one-line reason as `/context-budget`.
- Nothing is created under `skills/`. Verify: `./bin/chosko-llm ls --available`
  does not list `rule-overlap`.
- **Collect** — for each in-scope feature body, extract its headings and every
  normative statement: a line containing must, never, always, refuse, or a
  prohibition. Mechanical only — `grep` and `awk`, no model involvement in this
  step — and **exhaustive**. The body states why sampling is forbidden: a
  sampled collection produces confident conclusions about material it never saw.
- **Scope of collection** is markdown feature bodies: `commands/*.md`,
  `skills/**/*.md` (SKILL.md and supporting files alike), `claude-md/*.md`. The
  two vendored skills are excluded and the exclusion is stated with its reason.
  `hooks/*.sh` and `statusline/*.sh` are out of scope — they carry no normative
  prose — and the body says so rather than leaving it to inference.
- The scope is expressed as a glob over what exists at run time, never as a
  hardcoded list of feature names. Tasks 118 and 125–131 delete and add feature
  bodies; a name list would rot on the first of them.
- **Judge** — the model reads the full collected set and reports statements
  appearing in **three or more** features with materially the same meaning. The
  threshold and its reason are stated in the body: two features sharing a rule is
  often correct and coincidental; three is where a shared authority starts
  paying.
- **Report** — one entry per overlap group: the statement, the features carrying
  it, and whether they agree. Disagreement between copies is called out as the
  highest-value finding, because it means the rule has already drifted — the
  exact failure the engine refactor is meant to prevent.
- **Read-only, always.** Reports only. Never edits a body to dedupe, never opens
  a task, never proposes an extraction as an action, no `--commit`.
- No arguments in this task.
- **Root `VERSION` is NOT bumped**, per the exemption task 135 added.
  `VERSION` is deliberately absent from this task's `Files:` line.
- No dependency on the `shared-phase-engine` tasks (125–131) is declared, and
  the body says why: running this audit *before* that refactor is how its
  extraction list gets built; running it after is how the extraction is
  confirmed. Both are valid, in either order.
- No test suite by design: verify by running `/rule-overlap` in this repo
  against the `task-*` family — `commands/task-add.md`,
  `commands/task-clean.md`, `commands/task-list.md` and
  `skills/task-implement/SKILL.md`. The expected result depends on when the run
  happens, and the body must not assume either state:
  - **Before the engine refactor lands** (tasks 125–131), those files restate
    the commit-and-push protocol, the status vocabulary and the approval-gate
    rules between them. A run that surfaces no overlap across them means the
    collection step is under-collecting — that is the failure to look for, not
    evidence that the repo is clean.
  - **After it lands**, a clean or much-reduced result across the same files is
    the expected confirmation that the extracted rules really did stop being
    restated, and is not to be read as under-collection. Distinguish the two by
    checking whether the collection step still emits the normative lines at all:
    an under-collecting run emits few or no statements, a genuinely clean run
    emits them and finds them carried once each.

## Decisions
- **Inline `grep`/`awk` in the body, not a `.claude/scripts/` shell script.**
  The document's own leaning. A script is more faithful to "deterministic
  collection" but adds a file kind this repo has no precedent for outside
  `scripts/`. The body names the script as the escape hatch if inline proves
  unreliable, so the decision is revisitable without re-architecting.
- **Vendored skills excluded** (`skills/unity-mcp-skill/`,
  `skills/claude-council/`). They are re-synced from upstream, so a restatement
  found in one cannot be extracted without breaking the vendoring contract in
  `docs/authoring-guide.md` § Vendored skills — surfacing it would be noise the
  reader can never act on.
- **The verification is phrased for both sides of the engine refactor**
  (user decision, 2026-08-24). This audit's whole purpose spans that change, so
  a check that only makes sense before it would be stale the moment task 131
  lands. `commands/task-enrich.md` is deliberately absent from the verification
  set: task 118 deletes it with the dual-LLM lane.
- **Only the distillation idea is taken from ECC's `rules-distill`**, none of
  its machinery: its scripts need `jq`, which this repo's rules forbid.
  `rules-distill` itself was discarded as a shipped skill during the ECC review
  (2026-08-24 session log) and is not being re-proposed here — this is one idea
  from it, reimplemented repo-locally.
