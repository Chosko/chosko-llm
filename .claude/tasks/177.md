# Task 177 — Write the pipeline routing table

Target: claude

> Merged into task 175 on 2026-09-11; that body is the authority. This task is `[SKIP]` and awaits `/task-clean`.

## Goal
Add `skills/pipeline-engine/references/routing.md`: one row per pipeline command
or skill, stating what it consumes, what it produces, which artifact lines it
owns, its preconditions and its argument shape. The Owns column is what
`/pipeline-patch` and `pipeline-revise` key on to name the single owner of a
change; Consumes and Produces are what the impact walk orders its steps by. It
is a table, never prose — a routing line that no routing decision reads is cut.

## Acceptance criteria
- One row for every pipeline command or skill shipped today: `/domain-setup`,
  `/product-design`, `/product-roadmap`, `/architect`, `/production-plan`,
  `/task-add`, `/task-implement`, `/task-review`, `/task-iterate`, `/task-list`,
  `/task-clean`, `/production-status`, `/runbook-create`, `/runbook-run`,
  `/runbook-list`, `/runbook-describe`, `/runbook-clean`, `runbook-suggest`, and
  `/pipeline-check`.
- Five columns: Consumes, Produces, Owns, Preconditions, Argument shape.
- The Owns column is **by line, not by file**, wherever a file has more than one
  writer — `FEATURES.md` `Doc:` and `Source:` are `/architect`'s while `Tasks:`
  and `Status:` are `/task-add`'s; `TASKS.md`'s summary blocks are `/task-add`'s
  to create and `/task-implement`'s to flip. No two rows claim the same line.
- Every row's Owns entry is verified against the shipped body it describes, not
  against the domain layer, and a row that cannot be verified from a shipped
  body is not written.
- Where a path also appears in `/task-add`'s OWNERSHIP PRE-AUTHORISATION owner
  table, this table agrees with it. A disagreement is resolved by fixing this
  table, never `/task-add`'s — that table is the sole source of ownership for
  the pre-authorisation check and is not this feature's to change.
- Each row identifies its feature by name only. The kind — command or skill — is
  not a column, so a later kind migration changes no row.
- `/pipeline-check`'s own row is present, even though the command itself is
  written by task 179, so the table is complete the moment the command lands.
- The file states the table's contract in one line: it is the ownership
  authority the revision suite reads, and a consumer states only its deviations
  from a row.
- `skills/pipeline-engine/SKILL.md` takes a **minor** `version:` bump; its map
  table is not edited.
- Root `VERSION` takes a **patch** bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` exits zero.

## Decisions
- Rows for the three not-yet-shipped revision surfaces (`/pipeline-patch`,
  `pipeline-revise`, `pipeline-suggest`) are **not** written here. Task 180's
  check requires every row to name a feature that exists in the repo; a row for
  an unwritten feature would fail its own guard. Those features add their own
  rows when they land.
- Rows name a feature, never a kind, for a concrete reason: feature
  `task-archive` migrates `/task-clean` from `commands/task-clean.md` to
  `skills/task-clean/SKILL.md` via `replaces:`. A table keyed on kind would go
  stale on that migration; one keyed on name does not, and task 180's check
  already accepts either path.
- `/task-clean`'s Owns entry is written from its shipped body at implementation
  time, not from today's memory of it. `task-archive` removes its `FEATURES.md`
  `Tasks:` write on a prune, leaving one only under `--backfill`; whichever
  state the body is in when this task runs is what the row records.
- Two ownership tables now exist in the product — this one and `/task-add`'s
  pre-authorisation table — with different jobs: this one routes a change to an
  owner, that one gates an implementer's edit rights. They overlap on paths and
  must not disagree; the tie-break above is what keeps them from drifting apart,
  and `/rule-overlap` will see both.
- `.claude/domain/features/pipeline-engine.md` is read-only in this task.
