# Task 268 — `/task-review`'s report closes on For the record then Follow-ups

Target: claude

## Goal
Part of feature `unattended-parking`. `/task-review` is the last shipped
body whose closing section is *Needs you* then *For the record*, while both
run-closing skills now close on *For the record* then *Follow-ups* under one
heading and one reply-handle rule (`.claude/domain/features/unattended-parking.md`
§ The closing report). Give the reviewer's report the same two groups in the
same order — what the caller must decide, an `unverifiable` criterion and
what would settle it, under *Follow-ups*, numbered as the reply handle — and
align the three documentation passages that describe it.

## Acceptance criteria
- `skills/task-review/SKILL.md` § THE REPORT's closing section is two groups
  in this order: **For the record** (unchanged in content and shape) then
  **Follow-ups** — every item the old *Needs you* held, numbered `1.`, `2.`,
  …, each at whatever length it needs, the number the handle the caller
  replies with, starting at 1 in every report, a single item still numbered.
  An empty group prints its heading and `none`. The body says, in one
  sentence, that the heading and order are shared with the run-closing
  skills and that this read-only skill does not apply `/follow-ups`' rules —
  it reads a diff, not a session.
- No other passage of `skills/task-review/SKILL.md` names *Needs you*; the
  frontmatter `description:` and the header comment need no change unless
  they name the group.
- `docs/reference.md`'s `/task-review` paragraph reads *For the record* then
  *Follow-ups*, numbered so you can answer by number.
- `.claude/context/features.md`'s `/task-review` entry reads the same.
- `.claude/domain/features/task-peer-review.md` states the agreed design
  change — the report closes on *For the record* then *Follow-ups*, the same
  two groups `/task-implement` closes on — in every passage that stated the
  old order, and drops the sentence contrasting `/task-implement`'s
  *Follow-ups* with the reviewer's *Needs you*, since both now share it.
  Nothing else in the document changes.
- `task-review`'s frontmatter `version:` bumped (patch); root `VERSION`
  bumped (patch) with a matching `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` and `./scripts/check-home-paths.sh` pass.

## Decisions
- Heading and order only: `/task-review` reads a diff, not a session, and is
  read-only, so it does not apply `/follow-ups`' rules — that fold belongs to
  run-closing skills (`commands/follow-ups.md`).
- `/task-iterate` and `skills/task-implement/review-rounds.md` consume the
  findings, not the closing section; neither names either group, so neither
  changes.
- **Design change agreed (user decision, 2026-09-23):**
  `.claude/domain/features/task-peer-review.md` § the report's closing
  section: *Needs you* then *For the record* → *For the record* then
  *Follow-ups*, and its contrast with `/task-implement`'s list collapses.
  That document is normally `/architect`'s; this task updates it for exactly
  this and for nothing else. A further design decision met at implementation
  time is not covered: leave that passage untouched and name it under
  *Follow-ups* as a precise follow-up (`/architect amend
  feature=task-peer-review "…"`).
