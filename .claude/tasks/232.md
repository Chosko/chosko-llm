# Task 232 — Store a per-runbook step counter in the body header

Target: claude

## Goal
A runbook body's step ids are stable and never renumbered, but `/runbook-create
--append` derives the next one as max() over the existing step headings. Nothing
removes a step today, so the derivation holds. `/runbook-prune` (task 233) will,
and the moment it does the max drops and a later append hands a pruned step's id
to a new step — repointing every reference written down before the prune:
`Depends on:` lines, `Failed at: step <n>`, `Context:` bullets, commit messages.
Add a stored `Last step number:` header field, monotonic, that the append rule
reads instead.

## Acceptance criteria
- `runbook-schema.md` § The header documents `Last step number:` — the highest
  step id ever assigned in this runbook, only ever increases, never derived with
  max(). Its rationale cites `TASKS.md`'s `Last task number:` and the index's
  `Last runbook number:`, whose rule it is verbatim.
- `runbook-schema.md` § A step states that the next unused id comes from that
  counter, replacing "the highest existing step id".
- A body with no `Last step number:` line is backfilled in place, set to the
  highest step id present, by `/runbook-create --append` (before it assigns) and
  by `/runbook-prune` (before it removes anything) — the only two commands the
  counter is load-bearing for. `/runbook-run` and `step-amend.md` write bodies
  and never backfill: the header is `/runbook-create`'s line, and neither needs
  the value. Read-only commands never backfill. Stated beside the existing
  id-backfill rule, which is the same shape.
- `/runbook-create` writes the line on a new runbook (set to the last id it
  assigned) and, on `--append`, reads it, assigns from it, and advances it.
- `commands/runbook-create.md`'s "Numbering continues from the highest existing
  step id" (§ Append rules) is replaced by the counter rule.
- `commands/runbook-create.md` frontmatter `version:` bumped; root `VERSION`
  minor-bumped with a matching top `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` silent.

## Decisions
- **The counter lives in the body, not the index block.** The body is the source
  of truth for steps and stays runnable by hand; the index's id and its counter
  are the single stated exception to "the index is a summary", and a second
  non-derivable field there would widen it.
- **Backfill, not a migration.** A body written before this field is legal and
  is upgraded by the first of the two commands above that writes it — the rule
  the id-less index already uses. No sweep, no script, no `/pipeline-check`
  finding.
- **The backfill is scoped to two commands, not to every body writer.** A run
  writes markers and `Done:` lines constantly and never needs the value, and the
  header is `/runbook-create`'s by the ownership-by-line table; widening that
  table for a value the run does not read buys nothing.
