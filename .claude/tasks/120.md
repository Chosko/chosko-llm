# Task 120 — Update documentation for feature task-implement-launcher

Target: claude

## Goal

Task 119 changes what `/task-implement`'s batch parent reads and what it hands
each subagent, implementing the `task-implement-launcher` feature. Both
knowledge layers still describe the previous delegation contract — the parent
composing a per-task hand-off prompt from material it read itself — and the
feature document still describes two mechanisms that were not what shipped.
Bring the documentation in line with the shipped behaviour.

## Acceptance criteria

- `.claude/context/features.md`'s `task-implement` entry describes the launcher
  contract: the parent evaluates the delegation guard from the `TASKS.md`
  summary blocks it already reads, never opens a task body for a delegated
  task, hands each agent a fixed-size prompt carrying the task number and the
  run's resolved flags, and keeps only the four returned fields per agent.
- `.claude/domain/task-workflow.md`'s "Delegated runs" section says the same in
  its own register, and its rationale is updated: the parent's context no longer
  grows with batch size, and the delegated flow and the manual flow are now the
  same flow rather than two things that can drift apart. The
  sequential-never-parallel rule, the partial-delegation rule and the
  one-commit-per-task invariant are restated unchanged, because they are.
- `.claude/context/INDEX.md`'s `Last updated` anchor is current.
- `.claude/domain/features/task-implement-launcher.md` is reconciled with what
  shipped on exactly two points — editing it is authorised for this task, see
  Decisions: its "What the parent reads" table no longer says the three fields
  are greped out of the task body (they come from the `TASKS.md` summary block),
  and it no longer says `FEATURES.md` must be joined for staleness (`[STALE]` is
  a `TASKS.md` status). Its two corresponding "Open questions" bullets are
  resolved rather than left open. Nothing else in the document changes.
- Root `VERSION` takes a patch bump.
- `README.md` is not edited: it describes `/task-implement` only at the level of
  "build a task end-to-end, one commit each" and never describes delegation, so
  nothing in it goes stale.
- No shipped feature body under `commands/` or `skills/` is edited here — task
  119 owns those, and any needed change there is a bug in 119, not this task.

## Decisions

- **Editing `.claude/domain/features/task-implement-launcher.md` is explicitly
  authorised for this task (user decision, 2026-08-24), for the two
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document is
  normally `/architect`'s, and anything beyond those two points still belongs to
  `/architect`. The two corrections are factual reconciliations with shipped
  behaviour, not redesigns; if a correction turns out to need a design decision
  rather than a wording fix, stop and say so instead of deciding it here.
- **Patch bump, not minor.** Documentation-only; no shipped feature's behaviour
  changes in this task.
