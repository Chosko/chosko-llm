# Task 286 — Add the pipeline-dashboard skill and cite it from the orchestrators

Target: claude

## Goal
Add `skills/pipeline-dashboard/SKILL.md`, the protocol of feature `pipeline-dashboard` (`.claude/domain/features/pipeline-dashboard.md`) that the orchestrating session follows: activation, ownership, ordering, publish and reuse, refresh triggers with the Monitor watcher, the pending question, the chat line, the text snapshot on request, degradation. Cite it in one line from `runbook-run` and `task-implement`, bump versions, and publish the real dashboard of `music-producer-tycoon` from this session as the verification.

## Acceptance criteria
- `skills/pipeline-dashboard/SKILL.md` has frontmatter `name: pipeline-dashboard`, `version: 0.1.0`, `type: skill`, a `description` that triggers on its own whenever a pipeline run (`/runbook-run`, `/task-implement`, any multi-task run) starts or is in progress in a project with `.claude/TASKS.md` or `.claude/RUNBOOKS.md`, and whenever the user asks about progress ("come siamo messi", "a che punto siamo", "dashboard") — within the description contract of docs/authoring-guide.md; no `requires:`. The body opens with the `# /pipeline-dashboard` + `# Global skill: …` header block.
- The body states, citing its bundled files by paths relative to itself (`./scripts/generate.sh`, `./assets/index.html`):
  - only the main session publishes or writes state; a subagent never does;
  - regenerate only after every status marker of the event is written;
  - the state folder (from `generate.sh --print-state-dir`) holds `url`, `index.html` (copied from the asset when missing or older), `data.js`, `pending.json`; nothing is written in the working tree;
  - first publish with no stored `url`: Artifact `list`, reuse an artifact titled `Pipeline <project>` (read, then republish to it), else publish `index.html` with `files: {"data.js": …}` and icon `chart`; store the `url`; every later update: `read` the stored `url`, then republish to it; never a second artifact;
  - the five refresh triggers; the Monitor (deferred, via ToolSearch) running a 10-second snapshot of in-scope task statuses, one line per change, re-armed on expiry while the run is active with one line only after a gap;
  - the pending protocol: schema, Italian fields, write then republish, clear to `null` once answered then republish;
  - one Italian chat line per republish, the link only on the first publish or on request;
  - the text snapshot (`generate.sh --text`) printed in a code block only on a progress question; no split panes or side panels;
  - degradation: any failure is one warning line and the run continues.
- `skills/runbook-run/SKILL.md` and `skills/task-implement/SKILL.md` each gain one line, placed where the session's orchestration is described, saying the main session follows the `pipeline-dashboard` skill while it orchestrates, when that skill is available — naming it, restating none of its rules, no `requires:` change; their `version:` bumped minor.
- Root `VERSION` bumped minor with a matching top `CHANGELOG.md` section; `./scripts/check-changelog.sh`, `./scripts/check-home-paths.sh` and `./scripts/check-routing.sh` pass; `./bin/chosko-llm ls --available` lists `pipeline-dashboard` at 0.1.0.
- **Verification**, results in the closing report:
  - following the body in this session against the `music-producer-tycoon` clone, the dashboard is published and its URL stored in the state folder; the link is shown to the user;
  - a simulated second session (stored `url` only, no memory of the publish) reads it and republishes to the same URL;
  - a run with a fake `pending.json` republishes with the banner and modal, then the file is cleared to `null` and republished;
  - the state folder is outside every repository; `git status` of both repositories is clean of dashboard files.

## Decisions
- **Optional citation, no `requires:`** (user decision at `/architect`): a user without the skill sees no change.
- **The real publish happens in this cloud session** from the sparse clone of `music-producer-tycoon`; the stored `url` lives in this container's user scope, and Q1's title lookup is what lets the user's Windows machine find the same artifact later.
- **Settled here**: the asset is copied into the state folder on first use and refreshed when the skill's copy is newer.
