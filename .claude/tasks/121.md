# Task 121 — Add the /task-review skill

Target: claude

## Goal

Implements the read half of the `task-peer-review` feature. The review step of
the implement → review → fix loop is performed by hand today: open a PR, open a
fresh session to review it, come back. It works, but the fresh-context step
depends on the human remembering why it must be fresh. `/task-review` is that
step as a shipped skill — it audits a diff **against the acceptance criteria of
the task that produced it**, which is the thing Claude Code's built-in
`/code-review` structurally cannot do and the only reason this skill exists
beside it. Automating a reviewer naively makes things worse, so the two gates
borrowed from ECC's `code-reviewer` are load-bearing and go in the body in
spirit verbatim: zero findings is a valid review, and a finding must cite a
line and name a concrete failure mode or it is dropped.

## Acceptance criteria

- A new skill exists at `skills/task-review/SKILL.md` with full frontmatter —
  `name: task-review`, `version: 0.1.0`, `type: skill`, and a single-paragraph
  `description` naming the three input forms, the confidence gate, and that a
  review with no findings is a valid result.
- Three input forms are resolved from the argument: absent → **local** mode,
  `git diff HEAD`; a branch name → **branch** mode,
  `git diff <base>...<branch>`; a PR number or URL → **pr** mode,
  `gh pr diff <N>`. Branch mode defaults `<base>` to the repository's default
  branch and accepts an explicit `base=<ref>` override.
- PR input is sanitised before it can reach a shell: accept a bare integer, or
  the trailing number of a
  `https://github.com/<owner>/<repo>/pull/<N>` URL; reject anything else and
  stop. The raw argument is never interpolated into a command. This rule is
  stated in the body, not merely implied.
- `gh` is required for pr mode only. Its absence on PR input produces a clear
  error naming `gh` and stops — never a silent fallback to local or branch
  mode. Local and branch modes never invoke `gh`.
- The task the diff belongs to is resolved in this order: an explicit
  `task=<n>`, the branch name, the PR title, then the most recently modified
  `.claude/tasks/*.md`. Its body is read and its acceptance criteria extracted.
  If no task resolves, the skill stops and asks for `task=<n>` rather than
  degrading into a generic code review.
- The review gates are in the body and are stated as gates, not advice:
  - report only findings held at **≥80% confidence**;
  - a **Pre-Report Gate** of four questions answered before any finding is
    written — can I cite the exact line; can I name the concrete failure mode
    (input, state, bad outcome); have I read the callers, imports and tests; is
    the severity defensible — where any "no" or "unsure" downgrades or drops
    the finding;
  - a **BLOCKING finding requires proof**: the snippet, the failure scenario,
    and why existing guards do not already catch it. Missing any of the three,
    demote;
  - **zero findings is a valid review**, said explicitly, because a reviewer
    under implicit pressure to produce output will produce it.
- Severity has exactly three tiers: `BLOCKING` (bugs, data loss, security, or
  an unmet acceptance criterion), `IMPORTANT` (missing coverage, real quality
  problems), `ADVISORY` (suggestions; reported once, never re-reviewed). An
  unmet acceptance criterion is always BLOCKING.
- Each finding carries a stable id of the form `R<round>-<n>` (e.g. `R1-3`),
  its severity, `file:line`, the claim in one sentence, the failure scenario,
  and a suggested fix. The report additionally carries a per-criterion verdict
  — met, not met, or unverifiable — and a one-line overall verdict.
- Output destination branches on how the skill was invoked:
  - spawned by `/task-implement --review` — structured output returned to the
    caller, nothing written to disk;
  - invoked manually — ask once whether to report in chat only (the default) or
    also write `.claude/reviews/<task>-R<round>.md`.
- When the caller supplies a previous round's context — the hunks the last
  iterate changed, plus the rejection ledger — the skill reviews only those
  hunks, and a finding rejected in an earlier round may not be re-raised, only
  escalated with evidence that round did not have.
- The read-only contract is stated in the body and honoured: the skill makes no
  edit to any source, test, task or status file and runs no mutating command;
  the only file it may ever write is the `.claude/reviews/` report the user
  explicitly opted into. It never opens a PR.
- The body defers to Claude Code's built-in `/code-review` where the two
  overlap and says so, rather than reimplementing generic code review, and
  states the differentiator (this checks the diff against the task's acceptance
  criteria).
- No reviewer fan-out: one reviewer, one pass. The skill spawns no dimension
  subagents.
- `skills/task-review/remote-diffs.md` holds branch and PR mode — base
  resolution and `base=<ref>`, the PR-number sanitisation rule, the `gh`
  absence error, and reading a PR's review comments — and `SKILL.md` reads it
  only when the argument is non-empty. A local-mode run never loads it.
- Root `VERSION` takes a minor bump, relative to whatever task 118 leaves in
  place (expected `1.1.0` → `1.2.0` if 118 and 119 land first).
- Nothing under `commands/`, `skills/task-implement/`, `.claude/context/` or
  `.claude/domain/` is edited by this task: task 123 owns the
  `/task-implement` integration and task 124 owns the documentation.

## Decisions

- **`remote-diffs.md` is the split the design calls for.** The feature document
  says review is worth one supporting file. Local mode is the common path
  (`/task-implement --review` always uses it), and branch/PR resolution is the
  branch that costs tokens to carry — so that is what moves out, matching this
  repo's established "read on demand, not up front" pattern.
- **An unresolvable task stops the run instead of degrading to a generic
  review.** The task's acceptance criteria are the whole reason this skill
  exists beside `/code-review`; a run without them would silently ship the
  weaker product under the stronger name.
- **Resolving the document's read-only tension.** The feature document states
  both "writes nothing to the working tree… read-only, always" and an opt-in
  `.claude/reviews/` file. The reading adopted here: the skill mutates nothing
  it is reviewing and runs no mutating command, and the report file is the one
  exception, written only on explicit opt-in in manual mode. Task 124 records
  this in the feature document.
- **The finding schema is deliberately duplicated into `/task-iterate` (task
  122) rather than shared.** Install copies each skill folder independently, so
  a `../task-review/...` reference would not resolve on an installed machine,
  and the `requires:` frontmatter field that would make a cross-feature
  reference safe belongs to the unimplemented `shared-phase-engine` feature.
  De-duplicating these two bodies is that feature's job, not this task's.
- **`--rounds` stays off `/task-review`.** Per the design's open question: a
  manual review produces one report and the user decides. The loop belongs to
  `/task-implement`.
- **Precondition 118.** After the dual-LLM deletion the `Target:` set is
  `claude` / `claude+human` / `human`; this body must not mention
  `Target: local`, `/task-enrich`, or an enriched body schema.
