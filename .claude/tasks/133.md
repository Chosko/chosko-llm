# Task 133 — Add the /session-resume command

Target: claude

## Goal
Ship `commands/session-resume.md`, the read half of the `session-continuity`
feature: resolve one file out of `.claude/sessions/`, brief the current session
from it, and then stop. Its value is entirely in the stopping — a resume
command that starts working is the failure mode that makes handoff tooling
untrustworthy, so this one never edits, never runs a command, and never begins
the work it just described. It also carries the instruction that closes the
pruning loop: the session it resumes is told to delete the file once the work
is finished.

## Acceptance criteria
- `commands/session-resume.md` exists with complete frontmatter: `name:
  session-resume`, `version: 0.1.0`, `type: command`, one-line `description`.
- Argument resolution has exactly three forms:
  | Argument | Behaviour |
  |---|---|
  | *(none)* | the newest candidate file in `.claude/sessions/` |
  | `YYYY-MM-DD` | the newest candidate from that date |
  | a path | read that file directly |
  There is no task-number selector.
- **Only files carrying a `Work:` line are candidates.** `.claude/sessions/` may
  hold companion documents that are not handoffs — this repo already contains
  one, `.claude/sessions/2026-08-24-1430-landing-prompts.md`, which has no
  `Work:` line and would otherwise be selected as "the newest file". A
  non-candidate is skipped silently, not reported as an error. A path given
  explicitly is read as given, with no candidacy check.
- **Ties are broken deterministically.** The two files in this repo share the
  identical `2026-08-24-1430` prefix, so "newest" is ambiguous on the prefix
  alone. Sort on the full filename and name the file that was picked, so the
  user can correct it with an explicit path.
- A missing `.claude/sessions/` directory, or no matching candidate, is
  reported plainly and the command stops. It never invents a briefing.
- On a **pointer-form** file, the command reads the artifact named by
  `Resume from:` and briefs from that; if the path no longer resolves, it says
  so and briefs from what the pointer file itself carries.
- The briefing is fixed in shape: what was being built, what must not be
  retried, and the exact next step — the three things the next session would
  otherwise repeat or lose.
- **The briefing ends by naming the file and handing over the deletion.** In so
  many words: *you resumed from `<path>`; delete that file when the `Work:` it
  describes is finished — deletion is part of finishing.* The resumed session
  removes the file when the work completes, at its final commit or when the
  user confirms done. `/session-resume` itself deletes nothing, and this
  sentence is the only mechanism by which it participates in pruning.
- After the briefing the command **stops and waits.** It starts no work, edits
  no file, and runs no shell command. The body says so explicitly.
- A file older than 14 days is flagged as stale **before** the briefing, not
  after. For a file that is never resumed, this flag is the only pruning signal
  that will ever fire.
- A file referencing paths that no longer exist names each missing path, rather
  than briefing as though they were there.
- Read-only throughout: writes nothing, deletes nothing, and reads nothing
  under `.claude/tasks/`, `.claude/FEATURES.md` or `.claude/PLAN.md` unless the
  `Work:` line points there.
- Root `VERSION` takes a minor bump (new feature).

## Decisions
- **Preconditioned on 132** — not because the file cannot be written first, but
  because the briefing must match the section names and `Work:` grammar that
  actually shipped in `/session-save`, not just the ones in the design. Landing
  the writer first removes the chance of the two drifting on day one.
- **The task-number selector is dropped** (user decision, 2026-08-24). The
  feature document offered `a task number → newest file whose Work: line names
  that task`. `/task-implement` runs are the least likely sessions to be paused
  — they are shorter than product-design and architect sessions — so a
  selector keyed to a task number is too specific for the actual usage. The
  `Work:` line keeps `task <n>` as a value, because it is what links the
  handoff to `.claude/tasks/<n>.md`; only the selector goes.
- **Candidacy by `Work:` line** is an addition to the feature document, which
  assumes every file in the store is a handoff. This repo already falsifies
  that. The `Work:` line is the cheapest reliable discriminator and is
  mandatory in both file forms.
- **Following the pointer** is likewise not spelled out in the document, but is
  the only reading consistent with the pointer form's own sentence ("It holds
  the state; this one only says where it is").
- **Pruning resolved** (user decision, 2026-08-24). A session file is deleted
  automatically once it has been resumed and the work it describes is finished.
  This task owns the first half of that mechanism — the handover sentence in
  the briefing — deliberately phrased as an instruction to the resumed session
  rather than an action, so `/session-resume` stays strictly read-only. The
  second half (a `/session-save` in a resumed session deleting the file it
  resumed from, as superseded) is task 132's. A file that was never resumed is
  never auto-deleted, and there is no `--prune` flag.
- **Stale is 14 days**, taken verbatim from the document, and is a flag, never
  a refusal.
