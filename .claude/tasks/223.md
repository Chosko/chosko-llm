# Task 223 — Auto-answer `/task-implement`'s dirty-tree prompt under `--inline` when only runbook bookkeeping is dirty

Target: claude

## Goal
Under `--inline`, a `/task-implement` step runs in the orchestrating session, so
it meets that session's own bookkeeping at its pre-flight dirty-tree check:
`.claude/RUNBOOKS.md` at `[RUNNING]` and the runbook body's `[~]` marker, both
written one moment earlier by this very run and both forbidden from being
committed. The run stalls on a prompt whose answer it already knows. When those
two files are the only dirty ones, the execution phase should answer `proceed`
itself and carry on.

## Acceptance criteria
- Under `--inline`, when a step's command reaches the dirty-tree prompt from
  `task-engine/references/tree.md` and the dirty set is **exactly** the runbook
  body and `.claude/RUNBOOKS.md`, the execution phase answers `1` / `proceed`
  without putting the prompt to the user, and says in one line that it did.
- The answer is `[1] proceed` specifically, never `[2] include`: folding the
  markers into the task's commit would commit the in-flight state the run's
  commit rules forbid.
- If anything else is dirty, the prompt is put to the user unchanged — the same
  fall-through that protects a genuinely forgotten commit.
- The condition is written to mirror the existing Stop-hook reply in `SKILL.md`,
  which already turns on "the runbook and the index you yourself just wrote", so
  the two read as one rule applied twice.
- `skills/task-engine/references/tree.md` is **not** modified: the caller answers
  its own prompt, and `/task-implement` learns nothing about runbooks.
- Nothing about the inline mode's bookkeeping changes — selection, markers,
  `Done:` lines, the index, fact propagation and commit cadence are untouched.
- Root `VERSION` and `CHANGELOG.md` bumped per CLAUDE.md § Versioning (patch);
  `./scripts/check-changelog.sh` exits clean.

## Decisions
- **The rule lives in `references/inline-contract.md`,** with at most a pointer
  from `SKILL.md`. It is a property of executing a step inline, not of the task
  engine, and putting it in `tree.md` would make every `/task-implement` caller
  carry knowledge of runbooks.
- **`proceed`, never `include`.** The two bookkeeping files must stay
  uncommitted until the step's own commit writes them under the run's rules.
- **Default (spawned) mode is unaffected.** A subagent starts in its own context
  and meets the same dirty tree, but that path is out of scope here; this task
  fixes the inline stall the user hit.
