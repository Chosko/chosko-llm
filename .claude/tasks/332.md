# Task 332 — Add Parallelism: to the runbook schema and the worktree rules to the subagent contract

Target: claude

## Goal
Lay the data and contract layer of feature `parallel-runbooks` in
`/runbook-run`'s reference files, before any orchestrator reads it. The
schema gains the `Parallelism:` header line and the two rules that change
under a parallelism above one — `Depends on:` as the only ordering
constraint, `[~]` committable with the resume signal moved to a local
worktree. The subagent contract gains a fourth placeholder, the step's
worktree path, and the two rules it carries, so a step agent in a worktree
works only there and leaves pull and push to the orchestrator.

## Acceptance criteria
- `runbook-schema.md` § *The header* gains a `Parallelism:` row beside
  `Execution policy:`: optional; an integer of 2 or more, or `max`; absent
  means 1; authored by `/runbook-create` only when the user asks and never
  by default; never rewritten by a run, which overrides it per run with
  `--parallel`; any other value an argument error at run time; mutually
  exclusive with `Sequencing:`, and the row says why in one clause (the
  line records an ordering constraint the graph does not carry).
- § *A step*'s `Depends on:` bullet states the current rule: it records the
  real constraint; under a parallelism above one it is the only ordering
  constraint and list position is priority among steps selectable at the
  same moment; under 1 steps run in list order. The sentence that it never
  causes anything to run in parallel is gone.
- § *The five step markers* states that `[~]` is never committed by a
  sequential run and may be committed by a run whose parallelism is above
  one, where the resume signal is `[RUNNING]` in the index plus a
  `wt/runbook-<id>-step-<n>` worktree on this machine
  (`../../task-engine/references/worktree.md`); a `[~]` with no worktree
  behind it is a step an interrupted run left behind.
- `subagent-contract.md`'s OPERATING RULES gains a `<WORKTREE>` placeholder
  — the absolute directory the step's work happens in — listed with the
  other three and filled per step, and two rules in fixed text: every path
  the agent touches is under `<WORKTREE>`, the repository root for the
  step; and the remote is the orchestrator's — an invoked skill's
  pull-at-start, re-sync and push are skipped as under `--no-push`, its
  commits made as usual, said once in the report, and before `DONE` the
  branch is integrated onto the base as `worktree.md` says. On a sequential
  run the placeholder is the base tree's path, so both rules hold there too
  and the block stays one text. § *Why each rule is in there* explains
  both.
- `skills/runbook-run/SKILL.md`'s `version:` is bumped (the reference files
  ride with it); its body is otherwise unchanged by this task.
- `./scripts/check-home-paths.sh` passes; root `VERSION` is bumped (minor)
  with a matching `CHANGELOG.md` section; `./scripts/check-changelog.sh`
  passes.

## Decisions
- Schema and contract land first, in their own task: `/runbook-run`,
  `/runbook-create`, `/runbook-describe` and `/pipeline-check` all read
  them, and each later task can then cite a line that exists.
- The contract keeps one text for sequential and parallel runs: the
  placeholder reads as the base tree's path on a sequential run, so the two
  rules are true there too and the contract stays a single verbatim block,
  which is the property that makes it a contract.
