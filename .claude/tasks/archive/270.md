## Goal
When the user answers a numbered Follow-ups list — "flip all eligible
features to [DONE]", "ask me now about the decision", "fix it in place",
"I'll handle it myself, remove it" — the handling today is "ordinary
conversation", and the user has to restate the same execution policy every
time. Ship it once, as a new auto-triggering skill `follow-ups-resolve`, read
whenever the user replies to a Follow-ups list, whatever produced it
(`/follow-ups`, `/runbook-run`'s or `/task-implement`'s closing report, or
any list of that shape). The skill keeps one working list and runs it:

1. **Resolve.** The user's feedback rewrites the list — items merged where
   they share an action, items the user takes on removed, questions the user
   asked to be asked put now. The rewritten list is re-presented until the
   user approves it. Nothing executes before approval.
2. **Execute.** An approved list runs. The main agent orchestrates and
   delegates each item to a subagent, independent items in parallel; it may do
   small work itself (a one-line fix in place).
3. **Gates.** Every delegated prompt tells the subagent to auto-confirm an
   approval gate that asks nothing but approval ("Approve and write?") and to
   surface as usual any gate carrying a genuine question. The orchestrator
   never answers a gate already raised to it — auto-mode policy may refuse
   that.
4. **New follow-ups.** One that arises during execution goes to the user for
   approval, then joins the list.
5. **Tasks land in a runbook.** Every task a follow-up creates brings a
   companion item proposing the runbook and position it belongs at; that item
   is part of the list like any other.

## Acceptance criteria
- `skills/follow-ups-resolve/SKILL.md` exists with full frontmatter (`name:
  follow-ups-resolve`, `version: 0.1.0`, `type: skill`, a `description`
  following the short what+when contract whose trigger is a user reply to a
  numbered Follow-ups list) and a body stating rules 1–5 above, each once.
- The body defines the **working list**: its numbering is the reply handle;
  its output shape is the `Follow-ups` heading and numbered items, split into
  an **Approved** section and an **Awaiting approval** section once any item
  is approved (approved first).
- The gate rule states: the user's approval of an item counts as the approval
  its gate asks for only while the gate's draft stays inside that item; a
  design divergence or open question goes to the user.
- `commands/follow-ups.md`: when a working list exists in the conversation,
  its output is that list in the two-section shape; § THE NUMBERING IS THE
  HANDLE points to `follow-ups-resolve` for acting on a reply instead of

## Decisions
- **A skill, not a section of `/follow-ups` (user decision, 2026-09-30):**
  the command is read-only by contract, and only a skill auto-loads on a
  reply.
- **Gate auto-confirm scope (user decision, 2026-09-30):** list approval
  stands in for a gate's approval only within the approved item.
- **The runbook-placement item applies whenever the project has runbooks**,
  not only during a run — a task created outside a runbook drifts out of the
  implementation pipeline just the same (`/follow-ups` § WHAT DOES NOT
  already names that risk).
- Mid-run behaviour is task 271's and is not written here.
