# Task 206 — Answer the cloud Stop hook's block with a fixed literal reply instead of re-deriving it every step

Archived: 2026-09-14
Status: [DONE]
Files: skills/runbook-run/SKILL.md, docs/reference.md, .claude/context/features.md, .claude/context/INDEX.md, VERSION, CHANGELOG.md
Preconditions: none

Target: claude

## Goal
Every Claude Code cloud sandbox registers a Stop hook that runs
`~/.claude/stop-hook-git-check.sh`, which exits 2 on any dirty tree. That block
lands on `/runbook-run` constantly, because a run deliberately leaves two
markers uncommitted for the whole duration of a step — the step heading at `[~]`
in `.claude/runbooks/<name>.md`, and that runbook's `Status: [RUNNING]` in
`.claude/RUNBOOKS.md`. Those two together are the skill's resume signal, and
committing them would publish a second concurrent run to the remote, so the
block cannot be cleared from inside the run.

The hook's own recursion guard —
`stop_hook_active == "true" → exit 0` at the top of the script — means each
block costs **exactly one forced model turn**, not a loop. That turn is the
entire cost, and it is produced by the model, so it is reachable by
instruction. Today the orchestrator spends it re-deriving and re-explaining why
those two files must stay uncommitted: a few hundred output tokens plus a
`git status`, at every step start and at every question relayed to the user.

Make that turn nearly free. `/runbook-run`'s body gains one rule: when the Stop
hook blocks and the only dirty files are the runbook and the index the
orchestrator itself just wrote, reply with a fixed literal and end the turn.

## Acceptance criteria

**The rule**
- `skills/runbook-run/SKILL.md` gains a `**The Stop-hook reply.**` section,
  placed after § COMMIT CADENCE — the section that already states `[~]` is never
  committed, which is the premise the rule rests on.
- It states the mechanism, so a reader knows why no fix is attempted: the block
  cannot be cleared from here, and it costs one forced turn per fire — at each
  step start and at every question relayed to the user.
- The trigger is **the orchestrator's own knowledge, not an inspection**: the
  condition is that the only uncommitted changes are the runbook and the index
  it itself just wrote, one step ago. No `git status`, no diff read.
- The prescribed reply is the literal `stop hook refused`, and the turn ends
  there. **No tool call** — that is the expensive half, not the prose.
- The fall-through is explicit: if anything else is dirty, this is not that
  case and it is handled normally. This is what preserves the real check
  against a genuinely forgotten commit.
- § DO NOT gains one line: re-deriving or re-explaining the Stop-hook block on
  an in-flight step, pointing at the new section.
- Nothing else in the body changes. COMMIT CADENCE's staging rule, the `[~]`
  never-committed rule and ONE RUN PER RUNBOOK are untouched.

**Documented**

## Decisions
- **Shipped as a rule in `/runbook-run`'s body, NOT as a `hook` feature.**
  *This reverses this task's original decision, and the reason is worth
  keeping:* the first design was `hook:remote-stop-exemption`, a `SessionStart`
  hook that patched `stop-hook-git-check.sh` in place with a narrow, directional
  exemption for exactly the two markers. It was written and passed `bash -n`,
  and it was abandoned unverified. A script whose job is to rewrite a session's
  Stop-hook guard reads as weakening a guardrail no matter how narrow its
  exemption, and a cloud session — the *only* place it can be verified, since
  the gate is positive-only and the target exists nowhere else — refused to
  execute it, refused to install it, and refused to commit it. A feature that
  cannot be built or tested in the environment it exists for is not shippable.
  The replacement touches no guard at all.
- **The earlier rejection of an instruction-based fix is narrowed, not
  dropped.** That rejection said the harness runs the script after the model
  stops, so instructions cannot clear an exit-2 block. That remains true, and
  this rule does not try to clear the block — the block still fires and the
  forced turn still happens. It shapes the *content* of that turn, which is
  model-produced and therefore instruction-reachable. Different target.
- **The rule lives in `runbook-run`'s body, not in a global `claude-md`**
  (user decision). `Stop` fires for the main session — the orchestrator — and
  the orchestrator is the one holding this skill in context; a subagent's stop
  is `SubagentStop`, a different event. So the instruction is loaded exactly
  when it can fire and costs zero resident tokens in every session that is not
  a runbook run. A `claude-md` artifact would pay rent forever for a problem
  with one narrow scope.
- **The condition is "the two files I just wrote", not a git inspection.** The
  orchestrator set the `[~]` marker itself in step 4 and the index `Status:`
  right beside it, so it needs no `git status` to know what is dirty. This is
  what makes the reply cheap — the avoided tool call costs more than the prose
  — and it is also what keeps it safe: conditioning on the orchestrator's own
  writes means anything *else* dirty falls through to normal handling, so the
  genuine "you forgot to commit" case still gets thought about.
- **A literal reply rather than an empty turn.** The model must emit something;
  `stop hook refused` (user's wording) is three tokens and is greppable in a
  transcript.
- **Accepted limits, recorded so they are not mistaken for bugs.** The saving is
  the output plus the avoided tool calls, not the whole turn: the forced turn
  still re-reads the (cached) context either way. And the hook's own message is
  imperative — *"Please commit and push these changes"* — so an instruction to
  ignore it will be followed well, not perfectly; occasional drift back to
  explaining is expected, not a defect.
- **Rejected, not to be re-litigated:** patching `stop-hook-git-check.sh` from a
  hook (above); editing `~/.claude/launcher-settings.json` (recreated per
  sandbox, and settings may be read once at startup); a gitignored `[~]`
  sidecar for `/runbook-run` (changes the skill in every project and splits
  runbook state across two files); replacing `stop-hook-git-check.sh` wholesale
  (its unsigned-commit detection carries hard-won SSH-signing, `%G?` and
  shallow-clone detail with issue references); and registering a second `Stop`
  hook in `.claude/settings.json` (hooks do not override each other — if any
  exits 2 the turn is still blocked).
- **Out of scope:** committing the markers and making ONE RUN PER RUNBOOK
  identity-based with a `Running on: <host>/<session>` stamp. That would remove
  the problem rather than mitigate it, but it reworks the resume signal, the
  commit cadence and `references/runbook-schema.md` — a separate, larger change.
  Also out of scope: `README.md`, which is the tour and not the place for a
  behavioural rule inside an existing skill.
