# Task 215 — Route staled tasks to `/task-add feature=<slug>` reconciliation in `/pipeline-revise`'s amend branch

## Goal
Reported 2026-09-14 from a `job-hunter-cli` session. In `/pipeline-revise`'s
amend branch, a structural change anchored on a feature runs `/architect amend`
(step 2) and then one task amend per touched task (step 3). When step 2 is
answered not editorial it stales those tasks, and step 3 then rewrites the same
bodies through `task-engine/references/amend.md` — an arm that never clears
`[STALE]`. The only clearer, `/task-add feature=<slug>` reconciliation, rewrites
stale bodies in place anyway (`stale.md` § Clearing it). So the plan does the
work twice, behind twice the gates, and still ends `[ITERATED]`/`[STALE]` with
reconciliation as a follow-up the user must carry; and it has no step that
drafts a task for scope the arm judged added. Fix the branch so reconciliation
replaces the per-task amends for staled tasks, and tidy two adjacent gaps the
same run exposed.

## Acceptance criteria
- `amend.md` § Owner sequence renders step 3 in two forms at the gate, modeled
  on `insert.md` § "When step 1 leaves the feature [ITERATED]":
  (a) per-task amends through `task-engine/references/amend.md` — the form when
  step 2 stales nothing and leaves the feature's status unchanged;
  (b) one owner step, `/task-add feature=<slug>` (reconciliation) — the form
  when step 2 stales any task or moves the feature to `[ITERATED]` for added
  scope. Step 2's outcome selects the form at actuation; the user saw both at
  the gate.
- Under form (b), no per-task step-3 amend runs for a task step 2 staled.
  A per-task amend still runs, before the reconciliation step, for a task step 2
  did not stale whose own summary fields must change (e.g. a `Preconditions:`
  edge on its own line). The file says which runs first and why.
- The "Why upstream first" paragraph no longer says a staled task is still
  amended in step 3; it says reconciliation rewrites staled bodies, clears
  the tag, and drafts tasks for added scope.
- Change-text facts that are not in the feature document (implementation
  notes such as which files to touch, cross-task decisions) are listed at the
  revise gate, forwarded as the reconciliation step's free-form annotation
  text, and named as items to check at `/task-add`'s own gate.
- § Tier, § Outcomes and § Never agree with the new form. Outcomes: under (b)
  the feature returns to `[PLANNED]` and staled tasks go to `[MISSING]` (or
  `[SKIP]` + replacement), each `/task-add`'s own write. Never: `/task-add
  feature=<slug>` reconciliation is allowed as step 3's form (b); a `/task-add`
  run is still never used to change a single existing task outside that form.
- Where `amend.md` or the gate states what staling does, it cites
  `task-engine/references/stale.md` § Implementing a stale task: a `[STALE]`
  task is implementable on the user's explicit say-so (a single-task run warns
  and asks; batch selectors skip it). No wording implies a stale task cannot
  be implemented.
- `SKILL.md` step 10 emits no `Reconcile with /task-add feature=<slug>.`
  follow-up for a feature whose reconciliation ran as a step. The follow-up
  still appears when the sequence stopped before that step.
- `SKILL.md` step 2/3: a change that also names artifacts under a different
  anchor (e.g. a task of another feature) is scoped to the resolved anchor;
  the rest is reported in one line as a separate `/pipeline-revise` run,
  mirroring the existing two-kinds rule.
- `SKILL.md` step 8's moot-step rule and COMMITTING table need no new row
  (`/task-add` already has one) — confirmed, changed only if wording
  contradicts form (b).
- `pipeline-revise` frontmatter `version:` bumped (minor, from 0.2.1), root
  `VERSION` bumped (minor), matching top `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` and `./scripts/check-routing.sh` both silent.

## Decisions
- Fix A + D chosen over B (letting the task arm clear `[STALE]`) and C (gate
  warning only). B breaks `stale.md`'s single-clearer rule; C still leaves the
  user running reconciliation; A reuses a precedent the insert branch and
  `SKILL.md` step 8 already allow ("the one alternative a branch file has the
  gate show beside a step"). (User decision, 2026-09-14.)
- Conversation-only facts ride `/task-add`'s annotation text plus a checklist
  at its gate, not a new input channel — `/task-add` feature mode already
  accepts free-form text that "narrows or annotates the scope", so no owner
  gains an argument.
- The editorial-question pass-through from the same report is task 216, not
  here: it relaxes an invariant in a second skill (`architect`) and can ship
  or revert on its own.
