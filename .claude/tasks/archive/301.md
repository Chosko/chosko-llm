# Task 301 — Add `spec=<path>` to `/task-review` and `/task-iterate`

Archived: 2026-10-07
Status: [DONE]
Files: skills/task-review/SKILL.md, skills/task-iterate/SKILL.md, skills/pipeline-engine/references/routing.md, VERSION, CHANGELOG.md
Preconditions: 282, 293
Feature: quick-implement

Target: claude

## Goal
Part of feature `quick-implement`. A `/quick-implement --review` run has no
task body for the review pair to audit against. Add `spec=<path>` to
`/task-review` and `/task-iterate`: the acceptance criteria and scope come from
the spec file's sections instead of `.claude/tasks/<n>.md`.

## Acceptance criteria
- Both skills accept `spec=<path>`; it ranks with `task=<n>` at the top of
  task resolution, the two are mutually exclusive (an argument error naming
  both), and a spec run never falls back to the branch name, the PR title or
  the most recently modified task body.
- A `spec=` path that does not exist stops the run with one line naming it.
- Under `spec=`, the criteria come from the spec's `## Acceptance criteria`,
  scope from `## Goal` / `## Decisions` / `## Hints`, exactly as from a task
  body; `Feature:`-based lookups that need a summary block are skipped, and a
  manual `/task-review` report file is named from the spec's stem
  (`.claude/reviews/<spec-stem>-R<round>.md`).
- Usage lines, header comments and the `routing.md` rows for `/task-review`
  and `/task-iterate` (Consumes, Preconditions, Argument shape) state it.
- Both `version:` minor-bumped; root `VERSION` minor-bumped with a
  `CHANGELOG.md` section; `check-changelog.sh`, `check-home-paths.sh`,
  `check-routing.sh` pass.

## Decisions
- The review file for a spec run is named by the spec's stem: there is no
  task id, and the stem is unique per run.
- Lands after 282 (interaction policy in `/task-iterate`) and 293
  (`project-policy:` declarations on both skills' frontmatter).
