# Task 106 — Add the /product-roadmap skill and the roadmap document schema

Target: claude

## Goal
Ship `skills/product-roadmap/SKILL.md`, the skill that writes
`.claude/domain/product-roadmap.md` in a target project: an ordered list of
milestones, each with a goal, exit criteria, rationale, and the scope slices
that say which share of a high-level feature it takes on. This is the
product-level half of the pipeline's missing WHEN layer, from feature
`product-roadmap` — ordering today exists only as `Preconditions:` on
individual tasks, far too low a level to express a release. The skill covers
both the first run and every re-run: it reads any existing roadmap as its own
resume state, proposes changes against it, and warns (never refuses) when the
roadmap runs ahead of `product-design.md` or when an edited slice's section
already has architected features.

## Acceptance criteria
- `skills/product-roadmap/SKILL.md` exists with complete frontmatter:
  `name: product-roadmap`, `version: 0.1.0`, `type: skill`, one-line
  `description`. No `replaces:` — this is new, not a kind migration.
- Argument parsing handles `--commit` and `--no-push` exactly as
  `skills/architect/SKILL.md` does; nothing is committed without `--commit`,
  and `--commit --no-push` commits locally without the sync/push cycle.
- A PHASE 0 gate refuses when `.claude/domain/` or `.claude/domain/INDEX.md`
  is missing, points at `/domain-setup`, and creates nothing.
- The read pass takes in `.claude/domain/INDEX.md`, `product-design.md` when
  present (optional — the skill is usable from a bare description), any
  existing `.claude/domain/product-roadmap.md`, and `.claude/FEATURES.md`.
- The milestone/slice schema is written **inline in `SKILL.md`**, not in a
  supporting file. The skill folder ships `SKILL.md` only.
- The document schema is specified: ordered milestone blocks keyed by a
  stable kebab-case slug (e.g. `m1-mvp`), each carrying `Goal:`,
  `Exit criteria:`, `Rationale:`, and `Covers:`; then a `Not now` section
  where each deferred item carries the trigger that would pull it back in,
  and an `Open sequencing questions` section.
- No `Status:` line anywhere in the document — milestone state belongs to a
  later feature (`production-plan`), and the schema must not anticipate it.
- `Covers:` entries name `product-design.md` sections, never `FEATURES.md`
  slugs, and every entry carries a prose scope statement whose payload is its
  exclusions. Slice identity is the `(milestone, section)` pair; no fourth
  identifier vocabulary is introduced.
- `SKILL.md` states that `Covers:` is a decomposition instruction for
  `/architect`, not a delivery claim, and that partial coverage of a section
  across milestones is the normal case — nothing validates coverage
  completeness.
- Milestone order is list position; slugs are never renamed or renumbered,
  and inserting a milestone between two others requires no renumbering.
- Exactly one write phase behind one approval gate, writing
  `.claude/domain/product-roadmap.md` and registering it as a row in
  `.claude/domain/INDEX.md`. Nothing else is ever written — in particular not
  `FEATURES.md`, `PLAN.md`, `TASKS.md`, or `product-design.md`.
- A re-run reads the existing document, proposes changes against it, and
  writes behind the same single gate. No separate marker/state file.
- Failure contract implemented as warnings, not refusals: a `Covers:` entry
  naming a section absent from `product-design.md` warns and proceeds; and
  editing a slice whose section already has features in `FEATURES.md` warns,
  points at `/architect`, and proceeds on the user's say-so. `FEATURES.md` is
  read-only — the skill never writes `Status:` there.
- `--commit` with nothing written makes no commit and says so.
- Root `VERSION` bumped minor (new skill).
- `./bin/chosko-llm ls --available` lists `product-roadmap` at `0.1.0`.

## Decisions
- **Schema inline in `SKILL.md`, not a supporting file.** The folder ships one
  file. `/architect`'s `feature-doc-template.md` precedent exists, but that
  template covers a seven-section document read only in PHASE 3; the roadmap
  is one document whose schema every run needs, so there is no cheap path a
  split would protect.
- **One task, not split.** The first-run write path and the re-run/warning
  path share the same read pass, the same schema, and the same approval gate;
  splitting them would ship a skill that cannot be re-run.
- **Skill, not command**, per the feature document: the work is a multi-round
  conversation, matching `/product-design` and `/architect`.
- **Document at `.claude/domain/product-roadmap.md`**, alongside
  `product-design.md` rather than in the backlog, because it records intent
  and rationale rather than state.
