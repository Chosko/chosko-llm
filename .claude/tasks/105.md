# Task 105 — Make `add` and `update` accept multiple feature names in one invocation

Target: claude

## Goal
`chosko-llm add <feature>` and `chosko-llm update <feature>` only take one
feature spec per call today. Let both accept a space-separated list of specs
in a single invocation (`chosko-llm add foo skill:bar claude-md:baz`), looping
resolution/copy over each name instead of forcing one process per feature.

## Acceptance criteria
- `chosko-llm add <f1> <f2> ...` installs each named feature; single-name
  invocation behaves exactly as before (byte-identical output/exit code for
  the all-success case).
- `chosko-llm update <f1> <f2> ...` updates (or installs, per existing
  install-if-missing semantics) each named feature; single-name invocation
  unchanged.
- Best-effort execution: a failure on one name (already installed for `add`,
  no such feature, statusline + `--local`) logs an error via `log_error` and
  processing continues with the remaining names. Script exits 1 at the end
  if any name failed, 0 only if every name succeeded.
- `--all` combined with explicit feature names dies with a clear usage
  error — `--all` already means "every feature," combining is ambiguous.
- `--local` / `--global` still parsed once via `resolve_scope` for the whole
  invocation (unchanged), applying to every name in the list.
- `apply_replaces` still runs per successfully-installed/updated name.
- `-h` / `--help` usage text on both commands documents the multi-name form.
- `docs/cli-help.txt` and `README.md` show a multi-name example for both
  `add` and `update`.

## Decisions
- Best-effort continue-on-error (confirmed with user): matches the existing
  `--all` pattern of skip-and-log rather than aborting the whole batch on
  the first bad name — one typo in a 5-name list shouldn't block the other 4.
- `--all` + explicit names is a hard error, not "ignore the names" or
  "ignore --all" — avoids silently doing something other than what was typed.
