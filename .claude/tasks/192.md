# Task 192 — Add the `/pipeline-patch` command

Target: claude

## Goal
`/pipeline-patch` is the cheap half of feature `pipeline-revision`: the
reviser's single-owner branch shipped as a separate, thinner unit. It probes,
walks the graph from the anchor reading only the indexes, counts the owners the
change would touch, and either executes that one owner's amend arm and runs the
scoped lint, or refuses in one line naming `/pipeline-revise` and the signal
that triggered it. This task writes `commands/pipeline-patch.md` and its
routing row.

## Acceptance criteria
- `commands/pipeline-patch.md` exists with `name: pipeline-patch`,
  `version: 0.1.0`, `type: command`, a description naming the single-owner rule
  and the refuse, and `requires: skill:pipeline-engine, skill:architect,
  skill:task-engine, skill:runbook-run`.
- Argument shape: `/pipeline-patch <anchor> "<change>" [--commit] [--no-push]`.
  The anchor is required here, unlike on the reviser; its forms are
  `feature=<slug>`, `task=<N>` and `runbook=<name|id> step=<n>`.
- Probing cites `pipeline-engine`'s `probes.md` by path and reuses a verdict
  line already in the conversation per that file's rule.
- The graph walk reads ONLY the indexes — `.claude/FEATURES.md`,
  `.claude/TASKS.md`, `.claude/PLAN.md`, `.claude/RUNBOOKS.md`. Never a task
  body, never a feature document, never a runbook body. This appears as an
  explicit DO NOT, and it is the line separating this command from the reviser.
- The proceed condition is a count plus a checklist, never a judgement: exactly
  one owner among feature document, task and runbook step, AND none of the five
  structural signals present.
- The five signals are listed verbatim and closed: more than one owner; a
  dependency edge changing; scope added that no task covers; a deletion that
  crosses artifacts; a reorder of existing entries.
- Proceed path: load that owner's amend arm by path, execute it including its
  own gate, then run `/pipeline-check` scoped to the anchor, then report.
- Refuse path: one line naming `/pipeline-revise` and the signal that triggered
  it, then stop. No escalation, no second question, nothing written, no partial
  work.
- Failure contract: an anchor resolving to nothing stops by listing what
  exists.
- `--commit` / `--no-push` are parsed and forwarded to the arm; the command
  makes no commit of its own.
- The command writes no line any owner owns and does not appear in the
  who-writes-what table.
- `skills/pipeline-engine/references/routing.md` gains a `/pipeline-patch` row
  with owner-of `none`, so `scripts/check-routing.sh` stays silent once this
  ships.
- Root `VERSION` bumped (minor), `CHANGELOG.md` top section matches,
  `./scripts/check-changelog.sh` silent.

## Decisions
- **The command takes `[--commit] [--no-push]` and forwards them.** The feature
  document's interface line lists no flags, but the arms it executes take
  exactly this pair and default to committing nothing; a patcher that could not
  express the arm's own default would be the only writer in the suite unable
  to. Recorded as reconciliation point 2 for the feature document in task 193.
- **It ships after the reviser.** Its refuse line names `/pipeline-revise`, and
  shipped content never names an unshipped command — hence `Preconditions:`
  carries 187.
- **It does not depend on the four branch files.** The refuse names the skill,
  not a branch; blocking the cheap surface on all four branches would delay it
  for nothing.
- **The routing row lands with the command**, for the same
  `check-routing.sh` reason as task 187.
- **No escalation.** A patch that discovers it is structural stops rather than
  silently becoming a revise; the user chose the cheap tool and gets to choose
  again.
