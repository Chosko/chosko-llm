# Task 57 — Add the /product-design skill — resumable high-level product and business-model design

Target: claude

## Goal
Add a `/product-design` skill that brainstorms and designs a product from the ground up
with the user, producing high-level design documentation: high-level features designed
around the user experience, plus an optional business model. Its output is `/architect`'s
input. The process spans multiple sessions, so its state is a versioned document rather
than conversation history.

## Acceptance criteria
- `skills/product-design/SKILL.md` with complete frontmatter (`name: product-design`,
  `version: 0.1.0`, `type: skill`) carrying the phase spine.
- Three supporting files, each read ONLY when its branch fires, with SKILL.md naming both
  the file and its exact trigger:
  - `document-templates.md` — section-by-section stub content for `design-process.md`,
    `product-design.md`, `business-model.md`. Read in PHASE 1 and the write-back phases.
  - `business-model.md` — the business-strategy question bank (revenue model, cost
    structure, segments, pricing, go-to-market, unit economics, risks). Read only when the
    user opts into business modelling.
  - `resuming.md` — the resume protocol. Read only when PHASE 0 finds an existing
    `design-process.md`.
- PHASE 0 — GATE + RESUME. Verifies `.claude/domain/` and `.claude/domain/INDEX.md` exist;
  if not, stops and points at `/domain-setup`, in the style of `/task-add`'s setup gate.
  Then probes for `design-process.md`: if present, reads the recorded stage, summarizes
  where the last session stopped, and asks whether to resume there or start fresh. No
  `resume` argument — the document is the state.
- PHASE 1 — ORIENT + STUB. Detects greenfield vs. brownfield by reading the repo (source
  tree, `.claude/context/` layer if present, existing domain docs). Writes
  `design-process.md` describing the method and phases, and stubs `product-design.md` and
  — only if business modelling was requested — `business-model.md`. Registers every created
  doc in `.claude/domain/INDEX.md`.
- PHASE 2 — INTERVIEW. Conversational Q&A covering user experience, the big design
  decisions, and (when opted in) the business model. Claude contributes proactively —
  confirmations, suggestions, warnings, alternatives — rather than only asking. On
  brownfield the framing is "here's what I see you've built — is this still the intent?".
  The user decides when to move on; the skill must NOT advance on its own.
- PHASE 3 — WRITE-BACK. Fills `product-design.md` and `business-model.md`. Style is
  documentational: WHAT and, to a degree, HOW — not WHY. Updates the stage marker.
- PHASE 4 — HIGH-LEVEL FEATURES. A second conversational round identifying the product's
  high-level features, each described at medium-high detail from the user-experience angle,
  explicitly staying out of technical and implementation territory. The user confirms when
  the set is complete.
- PHASE 5 — FEATURE WRITE-BACK. Records the feature set in `product-design.md` and updates
  the stage marker. Does NOT write `.claude/FEATURES.md` entries or feature docs — those
  are `/architect`'s output.
- Every phase transition rewrites the stage marker in `design-process.md` BEFORE the phase
  ends, so an interrupted session always resumes from a truthful stage.
- Nothing committed by default, closing with an explicit note; `--commit` stages exactly
  the documents written in one commit; non-git VCS honours the `## VCS` mapping.
- A `DO NOT` section forbids: technical or implementation-level detail (`/architect`'s
  job), creating tasks or touching `.claude/TASKS.md`, writing `.claude/FEATURES.md` or
  feature docs, advancing a phase without the user's go-ahead, committing without
  `--commit`.
- `.claude/context/features.md` and `README.md` updated. Root `VERSION` bumped (minor).

## Decisions
- Skill rather than command, confirmed by the user: the phase spine stays small and the
  templates / question bank / resume protocol load only when their branch fires — the
  `skills/task-implement/` pattern.
- Resume auto-detected from `design-process.md`, no argument. Confirmed by the user: weeks
  pass between sessions and nobody remembers a flag; the state document is the natural
  anchor.
- Brownfield supported and detected in PHASE 1, not a separate mode. Confirmed by the user
  — the primary near-term use is on projects that already have code.
- `--commit` opt-in instead of the original draft's "propose to commit" phase. Confirmed by
  the user: matches every other authoring command, and an interactive prompt at the end of
  each phase of a multi-session process would be noise.
- Business modelling is opt-in and `business-model.md` is not created unless requested, so
  the skill stays usable for internal tools and side projects.
