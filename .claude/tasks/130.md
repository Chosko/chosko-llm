# Task 130 — Migrate /task-implement onto the task-engine

Target: claude

## Goal

The last step of the `shared-phase-engine` migration order, and deliberately
last of everything: `skills/task-implement/SKILL.md` is the target of three
other changes (task 118's dual-LLM deletion, task 119's launcher, task 123's
`--review` loop), and rebasing a large restructure onto a file that moved twice
is the failure this ordering exists to avoid. Replace the skill's restated rules
with references to `skills/task-engine/references/`, reconcile the extracted
`commit.md` and `tree.md` against what tasks 119 and 123 actually shipped, and
change nothing a user can observe. Design target: 708 lines down to under 350.

## Acceptance criteria

- `skills/task-implement/SKILL.md`'s frontmatter carries
  `requires: skill:task-engine`.
- The skill cites all six reference files: `resolution.md` for
  `LOCATING THE BACKLOG` and the `all` / `next` / explicit-list selectors,
  `status.md` for the implementable-status list and the terminal-status flip in
  Step 6, `targets.md` for the `Target:` values and the delegation guard,
  `stale.md` for the `STALE TASKS` section, `tree.md` for the dirty-tree
  protocol, and `commit.md` for Step 7 and the `--no-commit` / `--no-push`
  gating.
- Everything unique to `/task-implement` stays: `ARGUMENT PARSING` with every
  flag, the `SUPPORTING FILES` read-on-demand table, `RESOLVING THE TEST
  RUNNER` and the testing-policy marker, `USING THE TASK BODY`,
  `DOCUMENTATION-ONLY TASKS`, the seven-step `PER-TASK WORKFLOW`,
  `BETWEEN TASKS`, `FEATURE COMPLETION`, `FAILURE HANDLING`, and the `DO NOT`
  list.
- **Written against the post-118, post-119, post-123 shape.** No `Target:
  local`, no `/task-enrich`, no `chosko-llm task-impl` and no enriched-body
  schema (118); `delegated-runs.md` carrying the fixed-size launcher hand-off
  prompt and the four-field return contract (119); `review-rounds.md` and the
  `--review` / `--rounds N` loop present and unchanged in behaviour (123).
- **`commit.md` reconciliation.** Task 123 establishes that a task produces
  exactly one commit under `--review`, and that `/task-iterate` must not commit
  inside a run. That rule is stated **once** after this migration: either in
  `commit.md`, if it generalises, or in `skills/task-implement/SKILL.md`, if it
  is genuinely specific to this skill — not in both. Whichever is chosen, the
  other side says where it lives.
- **`tree.md` reconciliation.** `skills/task-implement/dirty-tree.md` is the
  source `tree.md` was extracted from. After this task the protocol exists once:
  `dirty-tree.md` either becomes a reference to `tree.md` plus this skill's own
  DIRTY_FOLD / DIRTY_FOLD_UNTRACKED specifics, or is deleted outright with its
  `SUPPORTING FILES` row. It does not survive as a second copy.
- Any supporting file left with nothing of its own after the migration is
  deleted, and its `SUPPORTING FILES` row goes with it. Any that survives has
  its row's read-condition left correct.
- `delegated-runs.md`'s hand-off prompt keeps its fixed-size property and its
  open-ended "the run's resolved flags" list — it is **not** converted into a
  closed enumeration, per task 119's decision and task 123's reliance on it.
- **`/task-review` and `/task-iterate` are not migrated and are not touched** —
  see Decisions. The `--review` availability gate that task 123 puts in the body
  stays a runtime check and is **not** converted into a `requires:` declaration.
- **Observable behaviour is unchanged**: same usage header and examples, same
  flags including `--review` / `--rounds N` / `--agents` / `--no-agents` / `-y`,
  same prompts, same per-task commit, same delegation contract, same feature-
  completion proposal.
- Verification is a real run: `/task-implement <n> --no-commit` on a task in a
  clone before and after, confirming the same step sequence, the same prompts
  and the same resulting tree.
- The body is under 350 lines, with the same caveat as tasks 127-129.
- `skills/task-implement/SKILL.md` takes a minor frontmatter `version:` bump,
  relative to what task 123 leaves in place (expected `1.2.0` → `1.3.0`); root
  `VERSION` takes a patch bump, relative to what task 129 leaves in place.
- Nothing under `.claude/context/` or `.claude/domain/` is edited here — task
  131 owns both knowledge layers.

## Decisions

- **Last, by design.** Three other tasks edit this file. Landing the
  restructure first would force 119 and 123 to rebase onto a body whose
  structure had just changed, in the largest file in the repo.
- **`/task-review` and `/task-iterate` stay out of scope.** Tasks 121 and 122
  both name this feature as the one that will collapse their duplication, so the
  question is live — but what they duplicate is a **finding schema** and a
  diff-input resolution (local / branch / PR, `gh` handling, PR-number
  sanitisation), which is a different shared surface from the six phase rules
  this engine owns. Putting it in `task-engine` would mean inventing a seventh
  reference file the design does not specify, and the feature document's scope
  section is explicit that the pattern is proved on the four existing consumers
  first. A follow-up feature can extract it once the two skills exist and their
  shared surface has settled.
- **The `--review` availability gate is not converted to `requires:`.**
  `requires:` is unconditional and resolved at install time; `--review` is
  opt-in and off by default. Declaring `requires: skill:task-review,
  skill:task-iterate` would force every `/task-implement` user to install two
  skills most of them never invoke, and would change install behaviour — which
  this feature is not allowed to do. The runtime gate task 123 ships is the
  correct mechanism for an optional dependency, and the body should say so, so a
  later editor does not "finish the job".
- **One statement of the one-commit-per-task rule, wherever it lands.** Task 123
  flags this rule as the one a future editor is most likely to "fix" into
  symmetry. Leaving a copy in both `commit.md` and `SKILL.md` would reintroduce
  exactly the drift this feature exists to remove.
- **The supporting-file set is reconciled, not just added to.** The engine and
  `skills/task-implement/*.md` are both read-on-demand reference layers; leaving
  both holding the dirty-tree protocol would mean the migration made the
  duplication worse, not better.
