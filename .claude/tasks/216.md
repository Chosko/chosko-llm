# Task 216 — Carry `/pipeline-revise`'s editorial answer into the `/architect amend` step as a confirmation

Target: claude

## Goal
Under `/pipeline-revise`, the same change gets the editorial question twice back
to back — at the revise gate, then again at the `/architect amend` step's own
gate — because both files forbid pre-answering it (reported 2026-09-14 from
`job-hunter-cli`). Let the answer given at the revise gate carry into the
architect step: that step's gate still renders in full, but shows the carried
answer as a confirmation instead of re-asking the question verbatim. Standalone
`/architect amend` and `/pipeline-patch` keep asking it fresh.

## Acceptance criteria
- `skills/architect/amend.md` § 4 The gate: when the arm is executed by
  `/pipeline-revise` with the editorial answer already given at its gate, the
  question is rendered as a confirmation of that answer (e.g. "You answered
  *not editorial* at the revise gate — edit the document, mark <ids>
  `[STALE]`, `Status:` becomes <outcome>. Confirm?"), with switching to the
  other answer and Stop still available.
- The gate is never skipped and the step is never auto-approved: change,
  touched set and outcome still render, an explicit reply is still required,
  and silence, an unclear reply or EOF is still Stop.
- Every other consumer is unchanged: standalone `/architect amend` and
  `/pipeline-patch` ask the full editorial question as today. § Never and the
  "never inferred, classified or pre-answered" wording are narrowed to name
  the one exception precisely, not deleted.
- `skills/pipeline-revise/SKILL.md` step 7 / step 8 / DO NOT: the answer
  carried into owner steps is the one the user gave at this gate; the skill
  still never infers or skips its own question, and step 8 says the architect
  step receives the answer.
- Every branch file step that executes `architect/amend.md` — `amend.md`
  step 2, `insert.md` step 1, `delete.md` step 1 — reads consistently with the
  pass-through (edited only where `SKILL.md` step 8 does not already cover it;
  confirm each).
- `.claude/domain/features/pipeline-revision.md` is reconciled with what
  shipped on exactly these 2 points — editing it is authorised for this task,
  see Decisions:
  1. § Architecture → "Tiers, one gate": "The editorial question is always
     asked, never inferred" gains the pass-through to the arm it drives.
  2. § Interfaces and contracts → hard contracts: "the editorial question is
     always asked" states it is asked at the revise gate and confirmed (not
     re-asked) at the `/architect amend` step.
  Nothing else in the document changes.
- `architect` frontmatter `version:` bumped (minor, from 0.9.0),
  `pipeline-revise` frontmatter `version:` bumped (patch on top of task 215's),
  root `VERSION` bumped (minor), matching top `CHANGELOG.md` section;
  `./scripts/check-changelog.sh` and `./scripts/check-routing.sh` silent.

## Decisions
- Confirmation, not suppression: the user still sees and explicitly answers
  the architect gate. The two "never pre-answered" rules exist so the stale
  decision is never taken silently; a shown, confirmable answer keeps that
  guarantee while removing the verbatim repeat. (User decision, 2026-09-14.)
- Scoped to the `/pipeline-revise` consumer only — `/pipeline-patch` has no
  gate of its own before the arm, so there is no earlier answer to carry.
- Split from task 215 and waits on it: it changes an invariant in a second
  skill with its own version, and can be reverted without undoing the
  duplicate-pass fix.
- **Editing `.claude/domain/features/pipeline-revision.md` is explicitly
  authorised for this task (user decision, 2026-09-14), for the 2
  reconciliations listed above and for nothing else. Do not ask for permission
  at implementation time — the permission is already granted.** That document
  is normally `/architect`'s, and anything beyond those points still belongs to
  `/architect`. These are factual reconciliations with shipped behaviour, not
  redesigns; if one turns out to need a design decision rather than a wording
  fix, stop and say so instead of deciding it here.
