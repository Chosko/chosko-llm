# Task 254 — Render `/task-add`'s approval plan as a digest: heading, target, goal, decisions

Target: claude

## Goal

`/task-add`'s PHASE 3 prints the whole draft summary block and the whole
draft body at the approval gate — `Files:`, `Preconditions:`, the index and
body file paths, the counter-update line, every acceptance criterion and
every Hint. That is implementer material the user cannot usefully check
before the task is written, and it buries the parts that actually decide the
answer. Make PHASE 3 render a digest instead: per task, the
`## <N>. <Title>` heading, `Target:`, `## Goal`, `## Decisions` when
present, and `## Manual interventions` in full when the target is
`claude+human` or `human`. Everything else is authored exactly as it is
today and written by PHASE 4 — only the chat render shrinks, never what
lands in the files.

## Acceptance criteria

- PHASE 3's single-task render emits the digest and nothing else: the
  `## <N>. <Title>` heading, `Target:`, `## Goal`, `## Decisions` when the
  draft has one, and `## Manual interventions` in full when `Target:` is
  `claude+human` or `human`. No summary block, no `Files:`, no
  `Preconditions:` field, no acceptance criteria, no Hints, no
  index-file/body-file path lines and no counter-update line.
- PHASE 3's split render emits one digest per part in write order, plus a
  single `Order:` line naming the new IDs in that order. Each part's digest
  follows the same rule as the single-task one.
- The `--short` render follows the same rule; its digest is simply shorter,
  since a `--short` body carries no acceptance criteria and no Hints in the
  first place.
- A `--before <N>` / `--after <N>` run still renders its one `Placement:`
  line. That line and `Order:` are the only wiring shown at the gate.
- PHASE 4 is unchanged: it writes the full summary block — `Status:`,
  `Target:`, `Files:`, `Preconditions:`, `Feature:` — and the full body per
  the body schema, acceptance criteria and Hints included. The digest
  changes what is *displayed*, never what is authored or written.
- PHASE 4's report still names the task ID(s), both paths written and the
  counter advance, so the file detail the gate no longer shows is reported
  once the write has happened.
- The RECONCILIATION render, the feature-source header, the DOCUMENTATION
  TASK draft, the OWNERSHIP PRE-AUTHORISATION question, THE ORPHAN QUESTION
  and the closing **"Approve and write?"** are untouched.
- The body schemas — PER-TASK BODY FILE FORMAT and its `--short` variant —
  are untouched. They describe the file, not the render.
- `docs/reference.md` § `/task-add` says the approval plan is a digest and
  that the full body goes to the file.
- `.claude/context/features.md`'s `commands/task-add.md` entry records the
  digest render.
- Root `VERSION` bumped (patch — a behaviour change to a shipped feature,
  not a new one), `commands/task-add.md`'s own `version:` frontmatter
  bumped, and a matching `CHANGELOG.md` section added on top.
- `./scripts/check-changelog.sh` and `./scripts/check-home-paths.sh` both
  run silent.

## Decisions

- **Acceptance criteria and Hints leave the render entirely**, rather than
  being compressed to a count (user decision). The gate is for approving
  intent; the count would be noise of a smaller size, and the body file is
  where the detail belongs.
- **`## Manual interventions` renders in full** although it is not one of
  the four parts named in the request (user decision). A task that needs the
  user at the keyboard is the most user-facing thing it can carry, and
  `Target: claude+human` alone does not say which steps they are signing up
  for.
- **A split keeps one `Order:` line; a placement flag keeps its existing
  `Placement:` line** (user decision). Ordering is approval-relevant in a
  way `Files:` and `Preconditions:` as fields are not — the user is
  approving that the parts land in that sequence.
- Reconciliation, the ownership question and the orphan question are left
  alone deliberately: they are classifications and gates, not drafts, and
  the request is about the draft render.
- Per the editing discipline in `CLAUDE.md`, state the digest rule once in
  PHASE 3 and do not add a DO NOT bullet that merely negates it.
