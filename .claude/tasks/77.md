# Task 77 — Make /architect adopt technical-direction.md as the established stack

Target: claude

## Goal
Task 76 makes `/product-design` produce
`.claude/domain/technical-direction.md`, but the document only earns its
keep if stage 2 obeys it. Teach `/architect` to read it as a primary input
and treat it exactly as it treats an existing stack: adopt it, reference it
in each feature document rather than re-arguing it, and skip PHASE 2a's
tech-stack selection entirely when it exists. The bare-prompt path — a
project that never ran `/product-design` — must behave exactly as it does
today.

## Acceptance criteria
- `skills/architect/SKILL.md` PHASE 0 reads
  `.claude/domain/technical-direction.md` when present, in the input list
  alongside `product-design.md`.
- The "detect whether a stack exists" step treats a present
  `technical-direction.md` as a stack that exists, so PHASE 2a is skipped
  and `./tech-stack-selection.md` is never read on that path.
- PHASE 2b designs within the recorded direction and says in one line that
  it is doing so, naming the document.
- A genuine mismatch between the feature and the recorded direction is
  surfaced once as a flagged concern and then designed around — same rule
  that already governs an existing codebase stack. `/architect` never
  silently overrides the direction and never edits
  `technical-direction.md`; the remedy it points at is re-running
  `/product-design`.
- Feature documents reference the direction instead of restating it (the
  existing "Built on <stack> per the product design" convention, extended
  to name `technical-direction.md`).
- `skills/architect/tech-stack-selection.md` states up front that a present
  `technical-direction.md` means this file does not apply, and its
  "Recording the choice" section routes a bare-prompt stack decision as it
  does today (first feature document) while noting `technical-direction.md`
  is the better home once one exists.
- `technical-direction.md` is added to `/architect`'s DO NOT list as a
  document it never writes, keeping the one-writer-per-artifact rule intact.
- `.claude/domain/product-workflow.md` records the consumption relationship
  in the pipeline table's stage-2 "Consumes" column and in "Who writes
  what" (`/architect` reads it, `/product-design` owns it).
- `.claude/context/features.md` and `README.md` reflect the new input.
- `skills/architect/SKILL.md` frontmatter `version:` bumps 0.1.0 → 0.2.0,
  and root `VERSION` bumps to the next minor (0.25.0 if task 76 landed
  first at 0.24.0 — read the file, don't assume).

## Decisions
- **`tech-stack-selection.md` is kept, not deleted.** It remains the
  fallback for the bare-prompt path and for projects that never ran
  `/product-design`; removing it would break the documented "architect from
  a description with no design documents" entry point.
- **The direction is treated as an existing stack, not as a new concept.**
  `/architect` already has a well-tested rule for "a stack exists, adopt
  it"; routing the new document through that rule keeps one behaviour
  instead of two.
- **`/architect` never writes back to `technical-direction.md`,** even
  though it does write back to `product-design.md`. The direction is a
  whole-product decision and a feature-level run is the wrong place to
  amend it.
