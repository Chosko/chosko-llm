# Task 166 — Add `/runbook-describe`

Target: claude

## Goal
`/runbook-list` answers "what runbooks exist and how far did they get" from the
index alone. Nothing answers "what is actually in this one" without opening the
file by hand. Add a sixth shipped artifact, `commands/runbook-describe.md`,
which takes one runbook by ID or name and prints it in depth: its header, its
status, and every step enumerated with its marker, its dependencies, whether it
has run, and whether it needs a human. Unlike the listing it is explicitly
permitted to read one body in full — that is the trade it exists to make.

## Acceptance criteria
- `/runbook-describe <id|name>` prints, for exactly one runbook: the header
  fields (`Created:`, `Source:`, `Model:`, `Sequencing:`, `Companion:`), the
  index `Status:` and `Steps:`, the `Failed at:` line when present, and then
  every step in order.
- Each step line carries its number, its marker (`[ ]` / `[~]` / `[x]` / `[!]`),
  its title, its `Depends on:`, and — where a run has written one — its `Done:`
  line, rendered rather than summarised away.
- `runbook-schema.md` gains an optional per-step `Needs:` line with exactly
  three values, `agent` (the default when the line is absent), `agent+human`
  and `human` — deliberately the same vocabulary as the task suite's `Target:`
  so the two stores read alike.
- `/runbook-create` authors `Needs:` — a question in the from-scratch
  interview, harvested from context in conversation mode — and shows it at the
  confirmation gate alongside the step titles and dependencies. A step whose
  value is not `agent` is called out there, since it is the thing that decides
  whether a run can be left unattended.
- `/runbook-describe` prints `Needs:` as authoritative when the step carries it.
  For a step without one it may read the prompt block and print an inferred
  note, which must be visibly labelled as inferred and must never be rendered
  in the same form as an authored value.
- It opens exactly one body — the one it was asked about — plus that runbook's
  index block. It never walks `.claude/runbooks/`.
- It writes nothing, runs no shell command including `git`, and corrects no
  status, count or marker however wrong it looks. Reporting an inconsistency in
  prose is fine; editing it is not.
- An unknown ID or name reports the available runbooks and stops. A missing or
  empty `.claude/RUNBOOKS.md` is not an error — one line naming
  `/runbook-create`.
- Frontmatter is complete and correct: `name: runbook-describe`,
  `version: 0.1.0`, `type: command`, a `description:` carrying the read-one-body
  trade and the ID-or-name argument, and `requires: skill:runbook-run` (it cites
  that skill's `runbook-schema.md`).
- The body references only `${CLAUDE_HOME:-$HOME/.claude}` paths, never
  `~/.claude` and never anything under `docs/`.
- Root `VERSION` takes a minor bump with a matching `CHANGELOG.md` section;
  `runbook-run` and `runbook-create` get their frontmatter `version:` bumped
  for the schema and authoring changes.
- `./bin/chosko-llm ls --available` lists `runbook-describe` at 0.1.0.

## Decisions
- **`Needs:` is authored, with inference only as a labelled fallback** (user
  decision, 2026-09-02). An authored field is what `/runbook-create` can capture
  while the author still knows; inference exists so hand-written and
  pre-existing runbooks show something, and is marked as a guess because that is
  what it is.
- **A separate command, not a `--verbose` on `/runbook-list`.** The listing's
  defining contract is that it never opens a body; adding a flag that does would
  destroy the property the whole command is built around.
- **It may read one body but never many.** The cost stays bounded by the size of
  one runbook, which is what makes "allowed to read in full" safe.
- **README's runbook section is updated by task 168, not here**, so the
  documentation pass lands as one coherent unit. This is deliberate — do not
  edit README in this task.
