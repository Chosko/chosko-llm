# Task 302 — Add the `/quick-implement` skill and its routing row

Target: claude

## Goal
Part of feature `quick-implement`. Add `/quick-implement`: a `/task-add`-style
spec conversation with a drift check, one gate, then `/task-implement`'s
sequence read from `task-engine`, ending in one commit that carries the change
and its spec file under `.claude/specs/`, and a closing report naming the
documentation that now lags and the follow-up that fixes it. No backlog entry.

## Acceptance criteria
- `skills/quick-implement/SKILL.md` at `version: 0.1.0` with full frontmatter,
  `requires: skill:task-engine, skill:interaction-engine` (plus
  `command:follow-ups` if the closing report applies its rules), and the usage
  `/quick-implement "<change>" [feature=<slug>] [--review [--rounds N]]`.
- The run, in order: dirty-tree check (`tree.md`); spec conversation
  (goal, acceptance criteria, decisions, hints; `feature=<slug>` reads that
  feature document as context); drift check; one gate whose class and summary
  follow `interaction-engine`; a spec judged too big for one commit stops at
  the gate with a `/task-add` pointer and writes nothing; spec written;
  testing-policy resolution and tests-first sequence
  (`testing-policy.md`, `tests-first.md`); `--review` / `--rounds` run the
  review loop with `spec=<path>`; one commit (change + spec) and push per
  `commit.md`; closing report per `closing-report.md`, its follow-ups being
  `/architect amend` for a diverging point and `/pipeline-revise --catch-up
  <spec>` for the rest.
- `skills/quick-implement/drift-check.md`: search the domain layer, context
  layer, `CLAUDE.md` and README for the spec's identifiers, files and terms,
  read only the hit sections, classify each hit with `design-change.md`
  (*settles* / *diverges*); divergences are listed at the gate and never block.
- `skills/quick-implement/spec.md`: the spec file
  `.claude/specs/<YYYY-MM-DD>-<slug>.md` — the task body schema plus a
  `## Drift` section — and its lifecycle (written after gate approval, staged
  in the implementation commit, deleted only by `/pipeline-revise --catch-up`).
- No `--no-commit` / `--no-push`; no write to `TASKS.md` or `FEATURES.md`; a
  failed commit leaves change and spec staged and stops.
- `routing.md` gains the `/quick-implement` row (consumes the conversation,
  the drift-check sections and `CLAUDE.md`'s testing policy; produces code,
  tests and the spec file; owns the spec file; amend `—`).
- `task-engine`'s reader list names `/quick-implement`.
- Root `VERSION` minor-bumped with a `CHANGELOG.md` section;
  `check-changelog.sh`, `check-home-paths.sh`, `check-routing.sh` pass;
  `./bin/chosko-llm ls --available` lists `quick-implement 0.1.0`.

## Decisions
- Settled here, against `.claude/domain/features/quick-implement.md` § The
  run (no conflict): the dirty-tree check runs at the start of the run, before
  the spec conversation, so the spec the run writes is never itself the dirty
  file the check reports; the spec's `<slug>` is derived from its title, and a
  same-day collision takes a `-2` suffix.
- Behaviour under orchestrate-mode (spec phase in a subagent, implementation
  split into areas) is not built here; it lands with feature
  `orchestrate-mode`, which is still `[NEW]`.
- Unattended behaviour comes from `interaction-engine` as cited: a class 1
  gate passes on its own; a class 2 gate cannot park (there is no task to park)
  and stops with the question last.
