# Task 239 — Cite reference files relative to the citing body, so they resolve under `--local`

Target: claude

## Goal
37 shipped bodies cite their reference files by the absolute runtime path
`${CLAUDE_HOME:-$HOME/.claude}/skills/<name>/references/<file>.md` — 136
citations in all. That path never resolves for a `--local` install.
`scripts/lib.sh:103` repoints `CLAUDE_HOME="$PWD/.claude"` only while
`chosko-llm add --local` is running; at run time the executing agent expands
the variable itself and always lands on the global home. A project that
installed the `task-*`, `runbook-*` or `pipeline-*` suites locally therefore
has every one of those citations pointing at a different copy or at nothing,
and it fails silently — the reading is skipped, or the wrong copy is read,
with nothing saying why.

Replace them with paths relative to the citing body (see Decisions), rewrite
the authoring-guide rule that currently mandates the broken form, and add a
guard so it cannot come back.

## Decisions
- **The convention: cite by path relative to the citing file, never an absolute
  home path** (settled with the user, 2026-09-19). Three forms:
  - within one skill — `./<file>.md` (already the idiom: `./delegated-runs.md`,
    `./review-rounds.md`);
  - skill → another skill's reference — `../<other>/references/<file>.md`;
  - command → a skill's reference — `../skills/<other>/references/<file>.md`.
- **Why it is scope-proof.** `--local` repoints `CLAUDE_HOME` for the whole
  install, and `cmd-add` installs `requires:` dependencies into that same home.
  Citing body and cited file are therefore always siblings under one root,
  whichever root it is, so a relative path is correct by construction in both
  scopes — no probing, no fallback, no second path to keep in step.
- **Why relative rather than naming the feature.** Naming is right for a
  *command* you want consulted (`/follow-ups`, VERSION 1.56.3) because commands
  are addressable by name. A reference file inside a skill is not, and precise
  citation is the point of these references. Relative also extends the `./`
  idiom already in use rather than introducing a second convention.
- **The `CLAUDE_HOME` override is not being abandoned** — it still governs where
  `install.sh` and every `scripts/cmd-*.sh` write. What changes is that shipped
  *bodies* stop re-deriving it at run time, which they were never able to do
  correctly. Say this explicitly where the three install-path notes currently
  imply the opposite.
- **The guard has no automated runner, by design.** No CI, no pre-commit hook;
  `check-changelog.sh` and `check-routing.sh` are run by hand, prompted by
  CLAUDE.md and by each task's acceptance criteria. Follow that pattern rather
  than introducing CI — matching the repo's no-lockfile / no-state-file stance.
- **Editing `.claude/domain/features/shared-phase-engine.md`,
  `runbook-suite.md` and `pipeline-engine.md` is explicitly authorised for this
  task (user decision, 2026-09-19), for the 5 reconciliations listed above and
  for nothing else. Do not ask for permission at implementation time — the
  permission is already granted.** Those documents are normally `/architect`'s,
  and anything beyond those points still belongs to `/architect`. These are
  factual reconciliations with shipped behaviour, not redesigns; if one turns
  out to need a design decision rather than a wording fix, stop and say so
  instead of deciding it here.
- **Verify that `../` resolves for a reference file read by another feature.**
  The `./` form is proven in use; `../` is the same mechanism one level up, but
  confirm it on a real read early rather than after 136 rewrites.
