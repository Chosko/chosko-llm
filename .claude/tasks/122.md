# Task 122 — Add the /task-iterate skill

Target: claude

## Goal

Implements the write half of the `task-peer-review` feature. `/task-iterate`
takes findings it did not produce, triages every one of them explicitly, applies
what survives, and records why the rest did not. That triage is the step
currently done silently in someone's head; forcing a written verdict per finding
is the point of the skill, because it makes "fix what's worth fixing" auditable
and produces the rejection ledger the next review round depends on. An iterator
that fixes everything it is told converges on whatever the reviewer said last,
so triage is mandatory rather than advisory.

## Acceptance criteria

- A new skill exists at `skills/task-iterate/SKILL.md` with full frontmatter —
  `name: task-iterate`, `version: 0.1.0`, `type: skill`, and a single-paragraph
  `description` naming the three input forms, mandatory triage, and the
  caller-dependent commit behaviour.
- It accepts the same three input forms as `/task-review`, resolved the same
  way, with the same PR-number sanitisation rule (bare integer, or the trailing
  number of a GitHub pull URL; anything else rejected; never interpolated into
  a command) and the same clear `gh`-absent error on PR input.
- Findings come from exactly one of: the review subagent's structured output
  passed in by the caller, a `.claude/reviews/<task>-R<n>.md` file, or — in PR
  mode — the PR's review comments read via `gh`. The body states plainly that
  the skill **never invents a finding** and never adds one of its own; it only
  triages what it was given.
- **Triage is mandatory and explicit.** Every finding is assigned exactly one
  of `fix`, `defer`, or `reject`. `defer` requires a follow-up task number or a
  note that one should be authored; `reject` requires a one-line reason. The
  full verdict table is written out before any edit is made.
- The `fix` findings are then applied; affected tests are re-run where the
  project has a suite (skipped where it does not, or where CLAUDE.md declares a
  skip-tests policy); and in PR mode the skill replies on each thread it acted
  on and resolves those it addressed, leaving rejected threads open for the
  human.
- **Committing differs by caller, and the body states the reason, not just the
  rule:**
  - **Standalone** — `/task-iterate` commits and pushes its changes following
    `docs/authoring-guide.md`'s commit-and-push protocol, accepting
    `--no-commit` and `--no-push` like every other auto-committing feature.
  - **Inside `/task-implement --review`** — it commits nothing and pushes
    nothing. It leaves the corrected tree for that run's existing Step 7, so
    the task still produces **exactly one commit**. Letting it commit here
    would give a task an implementation commit plus a separate fix commit for
    work no human reviewed separately, breaking the one-commit-per-task
    contract `/task-implement` already holds. This is a deliberate departure
    from the symmetric design and the body says why.
- The in-run mode is **asserted by the caller, never inferred**: the body
  treats "you are running inside a `/task-implement --review` round; do not
  commit or push" as an instruction it must be given, and applies the
  standalone rules whenever that assertion is absent. It never guesses from a
  dirty tree or from the presence of findings.
- **Sticky rejections.** The skill returns its rejection ledger — finding id
  plus the one-line reason — as part of its output, so the next round's
  reviewer receives it as binding context. In PR mode the rejection replies on
  the threads serve as the same ledger.
- The skill returns a triage summary the caller can act on: per finding id, the
  verdict and (for `fix`) what changed, plus whether any `BLOCKING` findings
  remain unresolved. `/task-implement`'s loop reads that last field to decide
  whether another round is warranted.
- The skill never opens a pull request, in any mode.
- Root `VERSION` takes a minor bump, relative to what task 121 leaves in place
  (expected `1.2.0` → `1.3.0`).
- Nothing under `skills/task-implement/`, `.claude/context/` or
  `.claude/domain/` is edited by this task: task 123 owns the
  `/task-implement` integration and task 124 owns the documentation.

## Decisions

- **The finding schema and the input-form resolution are restated in this
  skill, not referenced from `skills/task-review/`.** Install copies each skill
  folder independently, so a cross-folder path would not resolve on an
  installed machine, and the `requires:` field that would make such a reference
  safe belongs to the unimplemented `shared-phase-engine` feature. The
  duplication is deliberate and temporary; collapsing it is that feature's job.
- **No supporting file.** The feature document calls for a split-out reference
  on review only. This body's PR-mode branch is short enough to stay inline; a
  second file would be structure without a reader.
- **The commit asymmetry is the load-bearing rule of this task** and is spelled
  out in the body with its reason, because a future editor who sees only the
  rule will "fix" the asymmetry and silently break the one-commit-per-task
  contract.
- **Caller mode is asserted, not inferred**, for the same reason: an inference
  that gets it wrong commits inside a `/task-implement` run, which is exactly
  the failure the rule exists to prevent.
- **Precondition 121** — the finding ids, severity tiers and report shape this
  skill consumes are defined there. **Precondition 118** — the body must not
  mention `Target: local`, `/task-enrich` or the enriched body schema.
