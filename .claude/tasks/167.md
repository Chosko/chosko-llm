# Task 167 — Relay a subagent's spawns through the orchestrator when nesting is unavailable

Target: claude

## Goal
In cloud sessions a subagent cannot spawn a subagent, so a step whose prompt
invokes something that wants a child agent — `/task-implement --review
--rounds 2` is the case that surfaced this — cannot run. `runbook-run`'s depth
budget currently states the limit as a warning and stops there. Give the suite a
way through it: the step's subagent writes the child's prompt to a file and asks
for it to be spawned; the orchestrator spawns the child itself, at its own
level, and relays completion back to the caller without ever reading either
file.

## Acceptance criteria
- `subagent-contract.md`'s pasted OPERATING RULES block gains a rule: when the
  step's work needs a subagent and one cannot be spawned, do **not** do the
  child's work inline and do **not** silently degrade. Write the child's
  complete prompt to a file, then end the turn with the literal line
  `SPAWN REQUEST` followed by the prompt path, the result path, and the model.
- The block stays fixed text with only its existing placeholders substituted —
  the contract must remain identical across every spawn.
- `SKILL.md` gains a **fourth result case** beside the three it has: on
  `SPAWN REQUEST`, spawn one child subagent whose prompt tells it to read the
  request file, do the work, and write its report to the result file; wait for
  it; then send the **same** caller subagent a completion notice naming the
  result path, and let it resume.
- **The orchestrator opens neither file.** It forwards paths, it does not read
  content — the token-saving property this exists for, and the same discipline
  as "the orchestrator compresses, it does not answer".
- The body states plainly *why* this works: the child is spawned by the
  orchestrator, so it sits at the same nesting level as the caller rather than
  one below it.
- The sequencing contract is preserved and the exception is named explicitly:
  the caller is suspended for the whole time the child runs, exactly as it is
  during a `QUESTIONS FOR USER` relay, so only one agent is doing work at any
  moment. "One subagent at a time" gains this narrow, stated exception and
  nothing wider.
- A child's own `QUESTIONS FOR USER` is relayed to the user exactly as a
  caller's is, and the answer is returned to the child.
- A `SPAWN REQUEST` from a child is handled identically, so fan-out stays flat
  rather than nesting. A per-step cap of 8 relay rounds halts the step as a
  failure — marker `[!]`, `Done:` line, index `[FAILED]` with `Failed at:` —
  rather than looping unboundedly.
- Relay files live under the OS temp directory (`$TMPDIR`), never inside the
  repository tree, named per runbook, step and round. The orchestrator's staging
  rule is unchanged: exactly the runbook and the index, by explicit path.
- `--relay-spawns` forces the mode for a whole run when the environment is known
  to be flat; without it, the subagent's own self-detection is the only trigger
  and behaviour where nesting works is unchanged.
- The DEPTH BUDGET section is rewritten: the depth-4 warning is superseded for
  work routed through the relay, and it says what happens when work is not.
- `/runbook-create` gains a tenth prompt-quality rule: a step that would need a
  nested spawn is preferably authored as two steps (implement, then review),
  each spawned by the orchestrator; the relay is the fallback for skills that
  spawn internally without the author knowing.
- Root `VERSION` takes a minor bump with a matching `CHANGELOG.md` section;
  `runbook-run` and `runbook-create` get their frontmatter `version:` bumped.

## Decisions
- **Detection belongs to the subagent, not the orchestrator** (user decision,
  2026-09-02). Only the subagent can observe whether it actually has the tool;
  an orchestrator-side probe measures the orchestrator's environment and costs a
  spawn per run. The orchestrator manages the relay — it does not detect.
- **Relay files under `$TMPDIR`, never in the repo** (user decision), so no
  scratch file can ever be committed and no `.gitignore` entry is needed. This
  also keeps the repo's no-state-files rule intact: the files are transient
  message-passing, not state.
- **The orchestrator never reads the request or the result.** Reading them would
  reintroduce the token cost the relay exists to avoid, and would edge the
  orchestrator toward reviewing work it delegated — which its contract forbids.
- **The relay is added alongside the authoring rule, not instead of it.**
  Splitting the step is free and structurally better where the author can see
  the nesting coming; the relay covers the case where they cannot.
- **A failed relay is a step failure, not a silent degrade.** An agent that
  quietly does the reviewer's work in the implementer's context produces a
  `Done:` line that lies, which is the one outcome this suite is built to
  prevent.
