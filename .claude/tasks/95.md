# Task 95 — Add the claude-council decision gate to /product-design PHASE 6

Target: claude

## Goal
Extend the council gate built in task 94 to `/product-design`'s PHASE 6, where
the product's technical foundations — stack, topology, data, hosting, protocols
— are decided once for the whole product. This is the highest-leverage decision
in the pipeline: `technical-direction.md` becomes a standing constraint that
`/architect` adopts rather than re-argues, so an unexamined choice here
propagates into every feature document downstream. The gate fires on the
greenfield branch only; brownfield has nothing to decide.

## Acceptance criteria
- `skills/product-design/council-gate.md` exists and is a faithful copy of
  `skills/architect/council-gate.md`, differing only where the two skills
  genuinely differ: the fold-back target (`product-design.md`'s design decisions
  rather than a feature document's Open questions) and the absence of a
  PHASE 3 write barrier.
- Both copies carry a short header noting they are kept in step and naming the
  sibling path, so a future editor of one knows to touch the other.
- `SKILL.md`'s SUPPORTING FILES table gains a `./council-gate.md` row scoped to
  the PHASE 6 greenfield branch.
- The gate is offered in PHASE 6's **greenfield** branch only. The brownfield
  confirm-and-record branch is untouched — verify by reading it and leaving it
  byte-identical.
- `technical-direction.md`'s "recommend one — never leave the user with an
  unranked list" points at the gate.
- Detection, triage, no-mode invocation, and silent-when-absent behave exactly
  as in task 94.
- The DO NOT list gains an explicit line keeping council artifacts out of
  `WRITTEN` and out of any `--commit` staging. It gains **no** file-writing
  carve-out — `/product-design` has no "write nothing before PHASE N"
  prohibition to carve out, unlike `/architect`.
- PHASE 7's final report states whether the council was convened, the question,
  the run SHA, the verdict, and where the artifacts landed.
- The `design-process.md` stage marker is unchanged — council consultation
  happens within PHASE 6 and is not a phase transition.
- Frontmatter `version:` bumped 0.4.0 → 0.5.0.

## Decisions
- Greenfield only. PHASE 6's brownfield branch is confirm-and-record over an
  existing stack; there is no trade-off to pressure-test, and offering one there
  would re-litigate what the codebase already settled.
- The protocol file is duplicated, not shared. `cmd-add` copies
  `skills/<name>/` recursively and the repo has no cross-skill shared-file
  mechanism, so a single shared file could not be installed. Duplication with an
  in-step obligation is the only option the install model allows; task 96
  records that obligation in the authoring guide.
- Depends on task 94 so the protocol is authored once and copied, rather than
  written twice and reconciled afterwards.
- No stage-marker change. The marker tracks phase transitions; a mid-phase
  consultation isn't one, and recording it would make a resumed run look like it
  stopped somewhere it didn't.
- No file-writing carve-out here, departing from the original brief. Verified
  against `SKILL.md`'s DO NOT list: `/product-design` stubs documents in PHASE 1
  and writes in PHASE 3/5/7, so it has no blanket write prohibition. Its
  existing "stage only the explicit `WRITTEN` paths, never a catch-all" already
  covers the artifact concern; only an explicit reminder is added.
