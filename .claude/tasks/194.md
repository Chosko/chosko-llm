# Task 194 — Add the `pipeline-suggest` skill

Target: claude

## Goal
Feature `pipeline-suggest` is the cheapest tier of the revision suite and the
only one the harness selects rather than the user: an auto-triggering skill
that reads a free-form request on a project with a pipeline, says in one line
which pipeline command fits it, and stops. This task ships the whole feature —
the skill folder, the trigger description that is its only selection
mechanism, the two-probe gate, the shape table, the silence rules and the
fixed output shape — plus its row in the pipeline routing table. Its register
and its length are `skills/runbook-suggest/SKILL.md`'s, which is the shipped
precedent for a skill nobody invokes.

## Acceptance criteria
- `skills/pipeline-suggest/SKILL.md` exists with `name: pipeline-suggest`,
  `version: 0.1.0`, `type: skill`, and
  `requires: skill:pipeline-engine, skill:pipeline-revise,
  command:pipeline-patch` (see Decisions).
- The `description:` is the whole trigger — there is no hook and no event
  registration anywhere in this feature — and carries both halves the way
  `runbook-suggest`'s does. Fires on: a free-form request to build, change,
  fix, remove or sequence work, on a project that has a feature index or a
  backlog, when the request does not already name a slash command. Not for,
  and the list is deliberately longer than the "for": a question; a request
  that names a command; "just do it" or "directly"; work already under way in
  a `/task-implement` run; an enumeration inside an explanation; a follow-up
  list, which `runbook-suggest` owns.
- The gate is exactly two probes — does `.claude/FEATURES.md` exist, does
  `.claude/TASKS.md` exist. Both absent: say nothing and end, silently. A
  probe that errors is treated as absent. No third probe, and no read of the
  engine's `probes.md` — this skill deliberately does not use the shared probe
  set, because it needs to know only whether a pipeline exists, not its shape.
- The body carries the shape table, ten rows at most, from request shape to
  command: a new capability or feature-sized addition → `/architect`; a bug, a
  small change or a chore → `/task-add`; a small change to something already
  planned → `/pipeline-patch`; a large change, an insertion at a point in the
  sequence, a deletion or a reorder of planned work → `/pipeline-revise`;
  "what should I build next" → `/production-status`; "is the backlog
  consistent" → `/pipeline-check`; an ordered list of follow-ups →
  `runbook-suggest` already fires; a design-level decision →
  `/product-design`; a milestone or release question → `/product-roadmap` or
  `/production-plan`.
- A request that matches no row produces no output. A request that matches two
  rows names both in one line.
- The output is at most two lines: one naming the command and the phrase in
  the request that matched, and optionally one saying the parent can proceed
  directly instead. Nothing about the request's substance is restated, and no
  failure path produces a third line.
- Stated as DO NOTs: never invoke what it suggests; never ask a question or
  gate anything; never write; never open a file beyond the two existence
  probes — no reference file, not `routing.md`, and not the contents of the
  two files it probes for.
- The body is under about forty-five lines and states that a suppression list
  is deliberately absent because it would be a state file: a repeated request
  earns a repeated line, bounded by the silence rules rather than by memory.
  It also states, as `runbook-suggest` does, that fire rate is tuned by
  narrowing the description after observing real sessions, never by a flag.
- The body notes in one line that its table is not the engine's routing table:
  the two differ in job and content — request shape → command here,
  consumes / produces / owns there — so `/rule-overlap` reads the pair as an
  intended difference rather than drift.
- `skills/pipeline-engine/references/routing.md` gains a `pipeline-suggest`
  row — Consumes, Produces `none`, Owns `none`, Preconditions, and an
  argument shape recording that it takes none and is selected by description
  — so `scripts/check-routing.sh`'s completeness invariant stays silent, since
  this skill declares `requires: skill:pipeline-engine`.
- Root `VERSION` is bumped (minor) and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` is silent.
  `skills/pipeline-engine/SKILL.md`'s `version:` is bumped too if its
  `description:` enumerates what `routing.md` carries.

## Decisions
- **`requires:` names the two revision surfaces as well as the engine**
  (user decision at planning time). `requires:` is flat and non-transitive, so
  requiring the engine alone would leave `/pipeline-patch` and
  `pipeline-revise` uninstalled while four of the table's rows point at them.
  The other commands the table names — `/architect`, `/task-add`,
  `/production-status`, `/product-design`, `/product-roadmap`,
  `/production-plan`, `runbook-suggest` — are deliberately not required: they
  are the project pipeline's own, a project carrying `FEATURES.md` or
  `TASKS.md` is already using them, and requiring the whole pipeline in order
  to install a two-line pointer would make the cheapest tier the heaviest
  install.
- **It requires the engine although it reads no reference file.** The
  dependency is for installation, not for reading: the zero-reference-read
  contract stands. The consequence is deliberate and is the reason the row
  above is mandatory — `scripts/check-routing.sh`'s second invariant keys on
  `requires: skill:pipeline-engine`, so declaring it buys a routing row.
- **The routing row lands with the skill**, for the reason task 187 gives and
  task 175 anticipated when it left this row out: a shipped consumer
  with no row makes the repo fail its own check, so deferring the row to a
  later consolidating task would leave a broken interval.
- **One task for the whole feature.** The feature ships exactly one file,
  under forty-five lines, with no separable interface and no independently
  deliverable slice; the routing row is one line in a file this feature does
  not own. `/task-add`'s inverted split calculus for feature mode has nothing
  to cut along here, and the small-feature exception is what applies.
- **`.claude/domain/features/pipeline-suggest.md` is read-only in this task**
  (user decision at planning time). `/architect` owns it; the reconciliation
  grant lives in task 195 and nowhere else.
