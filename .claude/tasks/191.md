# Task 191 — Write the `pipeline-revise` reorder branch

Target: claude

## Goal
`/pipeline-patch` refuses "a reorder of existing entries" to
`/pipeline-revise` by name, so the reviser needs a branch to receive it. This
task writes `skills/pipeline-revise/reorder.md` — deliberately the shortest of
the four files, because a reorder is a skip-and-insert and the file's job is to
say exactly that, fix the tier and draw the classifier boundary, not to restate
`./delete.md` and `./insert.md`.

## Acceptance criteria
- `skills/pipeline-revise/reorder.md` exists and is complete on its own: a
  consumer that has read `./SKILL.md` and this file can execute the branch end
  to end, following the two cited files for the mechanics.
- Reordering a task is stated as: `[SKIP]` the entry in place, with a reason
  naming the reorder, then insert a replacement at the new position — per
  `./delete.md` and `./insert.md`, cited by path. Ids are never renumbered and
  the file cites `task-engine`'s resolution rule for why.
- Reordering a runbook step is the same shape: strike, then positional insert.
- The classifier boundary is stated: a change to `Preconditions:` that does not
  move an entry is an *amend*, not a reorder, and routes to `./amend.md`. This
  is what keeps `./SKILL.md`'s classification unambiguous.
- The tier is fixed, not judged: every reorder is *structural*, because it
  changes an order or an edge by definition.
- The file restates no rule that `./delete.md` or `./insert.md` owns; it
  composes them and adds only its own boundary, tier and reason wording.
- The branch writes nothing itself.
- `./SKILL.md`'s SUPPORTING FILES table gains its `./reorder.md` row.
- Root `VERSION` bumped, `CHANGELOG.md` top section matches,
  `./scripts/check-changelog.sh` silent.

## Decisions
- **The branch ships with the feature rather than as a later increment.** The
  feature document leaves this open, but `/pipeline-patch`'s fixed refuse
  checklist names a reorder and points at `/pipeline-revise`; shipping that
  refuse path into a surface with no branch for it would be a documented dead
  end. The file is small precisely because it composes.
- **A reorder is skip-and-insert, never a renumber or a move.** Task ids are
  stable by `resolution.md`, and runbook steps are never renumbered by
  `runbook-run`'s schema; a move would break both.
- **Preconditions-only changes are excluded by name.** Without that sentence
  the classifier has two plausible branches for the same request, which is the
  one failure a four-way classification can actually produce.
