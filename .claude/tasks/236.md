# Task 236 — Add `/follow-ups` — list what this conversation left unhandled

Target: claude

## Goal
Ship a new global command `commands/follow-ups.md` that reads the current
conversation and reports what it would lose if it ended now: actions
proposed but never executed, outcomes never recorded on disk, information
or decisions taken in conversation and written down nowhere. It answers
with exactly `No follow-ups left`, or with a numbered list. An empty list
is a guarantee: the conversation can be quit without information or
operation loss. The command is deliberately short — it is a reading and a
list, not a pipeline stage.

## Acceptance criteria
- `commands/follow-ups.md` exists with full frontmatter — `name: follow-ups`,
  `version: 0.1.0`, `type: command`, `description:` — and `name` matches the
  filename.
- It takes no arguments and is read-only: it opens no project file, writes
  nothing, commits nothing, and never invokes another command.
- Its output is exactly one of: the single line `No follow-ups left`, or a
  numbered list, one follow-up per item.
- Each item is written as a slash command plus a short "to …" explanation
  wherever a command fits the follow-up — e.g.
  `/task-add feature=<slug> to reconcile tasks X and Y that went stale after
  the amendment`. Free-form items are legal, but the command form is
  preferred whenever one is suitable.
- The body states the exclusion rule with both sides: work already tracked
  on disk is not a follow-up (`/runbook-run X to continue the
  implementation` is not one — the runbook already tracks it), while a task
  created in this conversation but not yet appended to the running runbook
  is one, because it can otherwise slip out of the implementation pipeline.
- The body states that the numbering is the handle: the user may reply by
  number ("execute 1 and 2 now", "insert 3 as the next step in this
  runbook"), and that acting on a number is ordinary conversation, not
  something this command implements.
- `skills/pipeline-engine/references/routing.md` gains a `follow-ups` row —
  consumes the conversation only, produces nothing, owns nothing, no
  preconditions, no arguments, no amend entry — matching the shape the
  `runbook-suggest` and `pipeline-suggest` rows already use.
- `./scripts/check-routing.sh` passes.
- Root `VERSION` takes a minor bump and `CHANGELOG.md` gains a matching top
  section; `./scripts/check-changelog.sh` passes.

## Decisions
- **A command, not a skill.** The user invokes it by name, so it is a
  `commands/*.md` file. It is the inverse of `runbook-suggest`, which fires
  from its description and is never invoked — and the two are complementary:
  a `/follow-ups` list of three or more ordered items is exactly what
  `runbook-suggest` already watches for, and no wiring between them is added.
- **It gets a routing row even though it requires no engine.** The table is
  the pipeline's ownership authority, and `runbook-suggest` and
  `pipeline-suggest` both carry rows without declaring
  `requires: skill:pipeline-engine`. `check-routing.sh` does not demand the
  row; consistency does.
- **Short by instruction.** The user asked for a short body. Resist the
  repo's house habit of a long normative body: the whole command is a
  reading rule, an exclusion rule, an output shape and a stop.
