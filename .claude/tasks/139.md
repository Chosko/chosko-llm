# Task 139 — Replace /task-add's ownership notice with a pre-authorisation gate

Target: claude

## Goal

When `/task-add` drafts a documentation task whose Hints name a document owned
by another pipeline command, it announces the ownership and then leaves the file
in the task ("say so if you'd rather it stayed out"). The implementer meets the
one-writer-per-artifact rule at implementation time holding no authority to
proceed, so it either stops to ask — a stall in a delegated or unattended run —
or edits an owned document without asking. On 2026-08-24 the user worked around
this by hand-wording a scoped pre-authorisation grant into five task bodies
(120, 124, 131, 134, 138). Make that the command's own flow: at the PHASE 3 gate
`/task-add` enumerates the specific reconciliations each owned document needs and
asks the user to grant pre-authorisation for exactly those points or to drop the
file, then writes the grant — or the removal — into the task body. The notice
becomes a question with two recorded outcomes, and no task is ever written naming
an owned document without one of them.

## Acceptance criteria

- `commands/task-add.md` no longer contains the "Ownership notice." paragraph or
  its `> Note: … Say so if you'd rather it stayed out.` block quote. They are
  replaced by an OWNERSHIP PRE-AUTHORISATION section covering the five points
  below.
- **Placement and scope.** The new section is a top-level section of the body,
  not a sub-part of `DOCUMENTATION TASK`, and it applies to **every task the run
  drafts** — the documentation task, a single free-form task, each part of a
  split, and any existing body rewritten during reconciliation. The
  `DOCUMENTATION TASK` section keeps only a one-line pointer to it, and the
  documentation task remains the worked example inside it.
- **Detection.** The section carries the command's own owner list — the sole
  source of ownership, extended from the four documents named today to:

  | Path | Owner |
  | --- | --- |
  | `.claude/domain/features/*.md` | `/architect` |
  | `.claude/domain/product-design.md`, `technical-direction.md`, `business-model.md` | `/product-design` |
  | `.claude/domain/product-roadmap.md` | `/product-roadmap` |
  | `.claude/PLAN.md` | `/production-plan` |

  It states that `.claude/FEATURES.md` and `.claude/TASKS.md` are excluded:
  they are split by line rather than by file, and `/task-add` is one of their
  writers. The check runs against both the drafted `## Hints` and the summary
  block's `Files:` line.
- **Enumeration.** For each detected file the command lists the specific
  reconciliations the task needs to make to it — the concrete points at which the
  implementation diverges from, or settles, what the document says — numbered, in
  the register tasks 120/124/131 use. A file for which no concrete point can be
  named is not a Hint at all and is dropped without a question.
- **The question.** At PHASE 3, inside the existing single approval gate and not
  as a second gate, the command asks one question per detected file (grouped into
  one question when several files are involved, across all drafted tasks in one
  pass), offering exactly two answers: grant pre-authorisation for exactly the
  enumerated points, or drop the file and leave the document to its owner command
  for a later run. The rendered form is given as a worked example in the body.
- **Grant outcome.** On a grant, the drafted body's `## Acceptance criteria`
  carries the enumerated points with the `— editing it is authorised for this
  task, see Decisions` marker and a closing `Nothing else in the document
  changes.`, and `## Decisions` carries a bullet in this shape:

  > **Editing `<path>` is explicitly authorised for this task (user decision,
  > `<YYYY-MM-DD>`), for the `<N>` reconciliations listed above and for nothing
  > else. Do not ask for permission at implementation time — the permission is
  > already granted.** That document is normally `<owner>`'s, and anything beyond
  > those points still belongs to `<owner>`. These are factual reconciliations
  > with shipped behaviour, not redesigns; if one turns out to need a design
  > decision rather than a wording fix, stop and say so instead of deciding it
  > here.

  The date is the date of the `/task-add` run.
- **Decline outcome.** On a decline, the path is removed from the drafted
  `## Hints` and from the summary block's `Files:` line, and `## Decisions`
  records that the document is deliberately left to its owner, naming the points
  that remain unreconciled so a later run of the owner command knows what is
  outstanding.
- **Hard rules.** The command states, and its `DO NOT` list enforces, that a
  grant is never written without an explicit user answer, that PHASE 3's
  "Approve and write?" alone does not answer the ownership question (an approval
  given without answering it is re-asked, not assumed), and that PHASE 4 must not
  write a task in which a detected file is neither granted nor removed — if it
  would, the run stops and reports.
- The `DO NOT` bullet currently reading "Add an `/architect`-owned or
  `/product-design`-owned document to the documentation task's Hints without
  naming it and its owner at the PHASE 3 gate…" is rewritten to forbid writing
  any drafted task that names an owned document without a recorded grant or
  removal, and to say that silence is not a grant. The bullet is rewritten, never
  dropped.
- The PHASE 3 cross-reference "See DOCUMENTATION TASK below for its content and
  the ownership notice that accompanies it" names the pre-authorisation question
  instead of the notice.
- **A grant does not make `/task-add` a writer.** The command still never edits an
  owned document itself; the grant authorises the *implementer of the task it
  drafts*. The body says so explicitly, and the existing `DO NOT` bullet "Edit
  `.claude/domain/features/<slug>.md`, or any other domain document. They are
  read-only here" survives unchanged.
- `.claude/domain/product-workflow.md`'s "Documentation task" section (the
  paragraph beginning "Documents owned by another command in pipeline") describes
  the gate rather than the notice: detection from `/task-add`'s own owner list,
  the enumerated reconciliations, the one-question-per-file gate applying to every
  drafted task rather than the documentation task alone, and the two recorded
  outcomes. Its closing sentence — that ownership still means one writer per
  artifact for the pipeline commands and `/task-add` itself never edits these
  files — is kept, extended to say a grant is a one-off, dated, point-scoped
  exception carried in a task body and exercised by that task's implementer, so
  the "Who writes what" table below it still has exactly one writer per artifact.
- `.claude/domain/task-workflow.md`'s "Feature-derived tasks" section extends its
  `Feature document itself read-only to /task-add.` statement with the gate: the
  document may still be named in a drafted task's Hints, but only with a dated,
  point-scoped grant the user gave at the PHASE 3 gate, or not at all — and the
  grant binds the implementer, never `/task-add`.
- `.claude/context/features.md`'s `commands/task-add.md` entry replaces its
  "`/architect`-owned and `/product-design`-owned documents MAY appear in that
  task's Hints, but never silently — file and owner named at PHASE 3 gate, user
  can strike it" sentences with the gate in the same compressed register: owner
  detection from the command's own four-row list, enumerated reconciliations, one
  question per file at PHASE 3 for every drafted task, grant written into
  Decisions with date and scope or file dropped from `Files:`/Hints, never
  silent, never left un-adjudicated.
- `.claude/context/INDEX.md`'s `Last updated` anchor is current.
- `commands/task-add.md` takes a minor frontmatter `version:` bump relative to
  what task 129 leaves in place (expected `2.1.0` → `2.2.0`), and its frontmatter
  `description` mentions the pre-authorisation gate. Root `VERSION` takes a minor
  bump relative to whatever is in place then (task 118 sets it to `1.0.0`).
- `README.md` and `docs/authoring-guide.md` are not edited: neither describes the
  documentation task or the ownership notice at all (verified by grep), so
  nothing in them goes stale.
- No other `task-*` feature body and nothing under `skills/task-engine/` is
  edited: the ownership prose is `/task-add`'s alone and task 129 keeps it in
  `commands/task-add.md` rather than moving it into the engine references.

## Decisions

- **A question, not an automatic grant.** The five hand-worded grants were user
  decisions each time; making the grant automatic would move an authority
  decision from the user to the command, which is the failure the ownership rule
  exists to prevent. The command may propose the scope; only the user may grant
  it.
- **Asked inside the PHASE 3 gate, not as a second gate.** Feature mode's
  standing invariant is one approval covering reconciliation and new drafts
  together. The ownership question is rendered with the plan and answered in the
  same exchange; what changes is that an approval which leaves the question
  unanswered is incomplete and is re-asked.
- **The gate covers every task the run drafts, not only the documentation task.**
  The failure it prevents — an implementer holding an owned document with no
  authority — is identical for a free-form task, a split part, or a body rewritten
  during reconciliation. Restricting it to the doc task would leave that hole
  behaving exactly as it does today, which is the bug.
- **The command's own owner list stays the sole source; no runtime read of
  `.claude/domain/product-workflow.md`.** That document's "Who writes what" table
  is this repo's own domain doc, not a shipped artifact and not something
  `/domain-setup` emits, so a target project generally does not have it.
  `/task-add` already works everywhere off the inline list it carries today
  (`commands/task-add.md` lines ~680–683); this task extends that list with
  `product-roadmap.md` → `/product-roadmap` and `.claude/PLAN.md` →
  `/production-plan` rather than introducing a conditional dependency on a file
  that usually will not be there.
- **The grant authorises the implementer, not `/task-add`.** `/task-add` remains a
  non-writer of every owned document; the one-writer-per-artifact table is
  unchanged. This is stated in both the command and the domain layer because it is
  the point a future editor is most likely to "simplify" away.
- **Precondition 129, not 118 alone.** Task 118 and task 129 both rewrite
  `commands/task-add.md`; 129 is the later and larger of the two (it restructures
  the whole body onto the task-engine and is itself written against the post-118
  shape). Landing behind 129 means this task is written once against the final
  shape instead of being rebased twice. 129's own preconditions (125, 126, 128)
  carry the rest of the chain. Task 129's acceptance criteria keep
  `DOCUMENTATION TASK` and its ownership prose in `commands/task-add.md` rather
  than moving them into `skills/task-engine/references/`, so this task's target
  file is unaffected by that migration; task 124 does not touch `/task-add` at
  all.
- **Not preconditioned on 131, despite both editing
  `.claude/context/features.md`.** Task 131 adds `requires:`/engine notes to the
  same `task-add` entry, but in different sentences from the ownership prose this
  task rewrites; whichever lands second merges by hand without a conflict of
  meaning. Forcing an order would delay this behind six other tasks for no
  correctness gain.
- **Minor bumps on both versions.** The command grows a new user-visible prompt
  and two new task-body outcomes — added behaviour, not a fix and not a break.
